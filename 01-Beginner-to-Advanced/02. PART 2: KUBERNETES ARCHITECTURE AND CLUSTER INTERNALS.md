# 2. Start With the Big Picture

A Kubernetes cluster has two broad sides:

```text
Kubernetes Cluster
│
├── Control Plane
│
└── Worker Nodes
```

The control plane manages the cluster.

Worker nodes run application workloads.

A more useful diagram is:

```text
Kubernetes Cluster
│
├── Control Plane
│   ├── kube-apiserver
│   ├── etcd
│   ├── kube-scheduler
│   ├── kube-controller-manager
│   └── cloud-controller-manager [when applicable]
│
└── Worker Nodes
    │
    ├── Node A
    │   ├── kubelet
    │   ├── Container Runtime
    │   ├── Networking Components
    │   └── Pods
    │
    ├── Node B
    │   ├── kubelet
    │   ├── Container Runtime
    │   ├── Networking Components
    │   └── Pods
    │
    └── Node C
        ├── kubelet
        ├── Container Runtime
        ├── Networking Components
        └── Pods
```

This is the first architecture you need to remember.

---

# 3. What Is a Kubernetes Cluster?

A Kubernetes cluster is a collection of machines and software components working together to run and manage containerized workloads.

At the highest level:

```text
Kubernetes Cluster
=
Control Plane
+
Worker Nodes
```

The cluster provides a system where you can declare:

```text
What workloads should exist?

How many should exist?

What resources do they need?

How should they be exposed?

How should they be configured?

Where may they run?
```

The cluster then works continuously toward the requested state.

---

# 4. Control Plane vs Worker Nodes

Think of the responsibilities this way:

```text
Control Plane
↓
Makes and coordinates cluster-level decisions

Worker Nodes
↓
Provide the environment where application workloads actually run
```

This is simplified but useful.

The control plane does not normally mean:

```text
"The place where all application containers run."
```

In production architectures, application workloads are normally placed on worker nodes.

---

# 5. A Company Analogy

Imagine a delivery company.

The control plane behaves roughly like:

```text
Operations Headquarters
```

It decides and tracks:

```text
What work exists?

Who should perform it?

What is the desired state?

Which workers are available?

What changed?

What must be corrected?
```

Worker nodes behave roughly like:

```text
Operational Teams
```

They perform the actual work.

Do not take the analogy too literally, but it helps separate:

```text
Decision / Coordination
```

from:

```text
Execution.
```

Core control-plane components include:

```text

                CONTROL PLANE
```

# 7. The API-Centered Architecture

One of the most important Kubernetes architectural principles is:

```text
Components interact through the Kubernetes API.
```

Think:

```text
kubectl
    \
Controller
      \
Scheduler ----> API Server ----> etcd
      /
kubelet
    /
Other Clients
```

Do not imagine every Kubernetes component randomly changing etcd directly.

The API server is the central front end for the Kubernetes control plane.

```text
kube-apiserver
```

Think:


Examples of clients include:

```text

Scheduler
```

# 9. The API Server Is the Front Door

Imagine you run:

```bash
kubectl get pods
```

`kubectl` does not normally:

```text
SSH into every worker node
```

and ask what containers exist.

Instead:

```text
kubectl
↓
Kubernetes API
↓
kube-apiserver
```

The API server processes the request.

This is why understanding the API is more important than memorizing `kubectl`.

# 10. kubectl Is an API Client

A beginner may think:

```text
kubectl = Kubernetes
```

It is not.

`kubectl` is a command-line client for interacting with Kubernetes.

The architecture is:

```text
Human
↓

↓
HTTP Request
↓
Kubernetes API Server
↓
Cluster
```

Other software can communicate with the API without using `kubectl`.

# 14. Kubernetes API Objects

Kubernetes manages resources represented as API objects.

Examples include:

```text
Pod

Node

Namespace

Service

ConfigMap

Secret

Deployment

ReplicaSet

Job
```

When you create a Kubernetes manifest, you are usually describing an API object.

For example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: example
spec:
  containers:
    - name: web
      image: nginx
```

Do not worry about creating this yet.

Look at:

```text
apiVersion
kind
metadata
spec
```

These fields tell Kubernetes what object you are describing and what you want.

# 15. Object Desired State

For many Kubernetes resources:

```text
spec
```

describes desired state.

Conceptually:

```text
spec
↓
What I Want
```

Kubernetes may also expose:

```text
status
```

which represents observed/current state information.

Conceptually:

```text
status
↓
What Kubernetes Observes
```

This connects directly to Part 1.

# 16. Desired vs Observed State

Think:

```text
spec
↓
Desired State

↓
Observed State
```

Controllers use this information to work toward convergence.

For example:

```text
Desired Replicas = 3
Observed Available Replicas = 2
```

The system has work to do.

Suppose Kubernetes needs to evolve an API.

It cannot simply change every field overnight without affecting:

```text
Users

Automation

Controllers

Operators

CI/CD pipelines

Manifests
```

API versioning allows Kubernetes APIs to evolve more deliberately.

This becomes especially important during Kubernetes upgrades.

# 23. API Request Pipeline

Now we reach one of the most important flows in Kubernetes.

A simplified modifying request travels through stages such as:

```text
Client
↓
API Server
↓
Authentication
↓
Authorization
↓
Admission
↓
Validation / API Processing
↓
Persistence
↓
etcd
```

The exact API-server internals contain additional processing and ordering detail.

For beginner architecture, remember:

```text
Who are you?
↓
May you do this?
↓
Should this request be admitted?
↓
Is the resulting object acceptable?
↓
Persist state
```

---

# 24. Authentication

Authentication answers:

```text
Who are you?
```

A request reaches the API server.

Kubernetes needs an identity.

That identity might represent:

```text
Human User

ServiceAccount

kubelet

Controller

External automation
```

Authentication attempts to establish that identity.

---

# 25. Authentication Is Not Authorization

This distinction is extremely important.

Authentication:

```text
Who are you?
```

Authorization:

```text
What are you allowed to do?
```

For example:

```text
Authentication
↓
You are Anne.

Authorization
↓
Anne may list Pods in Namespace A,
but may not delete Nodes.
```

These are separate decisions.

---

# 26. Kubernetes User Categories

At a high level, Kubernetes works with identities such as:

```text
Normal users

ServiceAccounts
```

Normal human user identities are generally managed outside Kubernetes itself.

ServiceAccounts are Kubernetes-managed identities commonly used by workloads and automation.

You will study them deeply in the security part of this series.

---

# 27. Authentication Failure

Suppose your credentials are invalid.

The request may fail before Kubernetes even asks:

```text
Are you allowed to create this Pod?
```

Because Kubernetes could not establish who you are.

Troubleshooting question:

```text
Authentication problem?
```

is different from:

```text
Authorization problem?
```

---

# 28. Authorization

After identity is established, Kubernetes evaluates whether the request is allowed.

Authorization asks:

```text
Can this identity perform this action
on this resource
in this context?
```

For example:

```text
User: developer-a

Verb: create

Resource: pods

Namespace: development
```

Kubernetes authorization decides whether that action is permitted.

---

# 29. Authorization Example

Suppose:

```text
User = alice

Request = delete Pod

Namespace = production
```

Authentication succeeds.

Kubernetes knows:

```text
You are alice.
```

But authorization may say:

```text
alice cannot delete Pods in production.
```

The request is rejected.

---

# 30. RBAC Preview

A common Kubernetes authorization mechanism is:

```text
RBAC
```

which means:

```text
Role-Based Access Control
```

Later you will learn objects such as:

```text
Role

ClusterRole

RoleBinding

ClusterRoleBinding
```

For Part 2, remember only:

```text
Authentication
↓
Identity

Authorization
↓
Permission
```

---

# 31. Admission

Suppose:

```text
Authentication = Passed

Authorization = Passed
```

That does not necessarily mean the object will be accepted.

The request can still pass through:

```text
Admission Control
```

Admission controllers intercept applicable API requests after authentication and authorization and before the resource is persisted.

---

# 32. What Admission Can Do

Admission can:

```text
Modify requests

Validate requests

Reject requests

Apply policy
```

There are:

```text
Mutating admission mechanisms

Validating admission mechanisms
```

A mutating mechanism can modify an incoming object.

A validating mechanism can approve or reject it without changing it.

---

# 33. Admission Example

Suppose someone requests:

```text
Create Pod
```

The user is authenticated.

The user is authorized.

But organizational policy says:

```text
Privileged containers are not allowed.
```

An admission policy may reject a Pod that violates the policy.

Therefore:

```text
Authenticated
≠
Authorized
≠
Admitted
```

Each answers a different question.

---

# 34. Mutating Admission Example

Suppose a policy automatically adds or changes approved configuration on an object.

Conceptually:

```text
Incoming Object
↓
Mutating Admission
↓
Modified Object
↓
Validation
```

The exact behavior depends on configured admission mechanisms.

---

# 35. Validating Admission Example

Conceptually:

```text
Incoming Object
↓
Validation Policy
↓
Does It Meet Policy?
├── Yes → Continue
└── No → Reject
```

Admission is one reason a manifest can look syntactically correct yet still be rejected by a cluster.

---

# 36. Admission Is Not Used for Ordinary Reads in the Same Way

An important detail:

Admission controllers primarily intercept requests that create, modify, delete, or connect to resources.

Ordinary:

```text
get

list

watch
```

requests bypass admission control.

This distinction matters when troubleshooting API behavior.

---

# 37. Validation

The API server also validates API objects.

Examples of problems include:

```text
Unknown fields

Wrong types

Missing required information

Invalid values

Malformed object structure
```

For example, if a field expects:

```text
integer
```

but receives an unacceptable value, the API server can reject the object.

---

# 38. Authentication vs Authorization vs Admission vs Validation

Memorize this model:

```text
Authentication
↓
Who are you?

Authorization
↓
May you do this?

Admission
↓
Should this request be accepted or modified
according to configured admission logic?

Validation
↓
Is the resulting API object valid?
```

This will become extremely useful in production troubleshooting.

---

# 39. Persistence

If a state-changing request passes the required API processing, Kubernetes persists the relevant cluster state.

The backing store used by standard Kubernetes is:

```text
etcd
```

Conceptually:

```text
Accepted API Object
↓
API Server
↓
Serialized State
↓
etcd
```

---

# 40. etcd

etcd is a distributed key-value store.

Kubernetes uses etcd as its backing store for cluster data.

Think:

```text
Kubernetes API State
↓
etcd
```

This makes etcd one of the most critical components in a self-managed Kubernetes control plane.

---

# 41. What Is a Key-Value Store?

A key-value store organizes data conceptually as:

```text
Key → Value
```

For example:

```text
some-key
↓
some-value
```

The real Kubernetes storage representation is more sophisticated than a beginner key/value example, but the important point is that etcd stores Kubernetes' persisted API state.

---

# 42. What Does etcd Store?

Kubernetes persists API object state through the API server into etcd.

That includes state representing resources such as:

```text
Pods

Deployments

Services

ConfigMaps

Secrets

Namespaces

Nodes

RBAC objects
```

and other API resources.

This is why etcd is critical.

---

# 43. What etcd Does Not Mean

Do not think:

```text
etcd contains the running application process.
```

It does not.

Suppose a Pod runs Nginx.

etcd contains Kubernetes state describing the Pod.

The actual container process runs on a worker node.

Think:

```text
etcd
↓
Cluster State

Worker Node
↓
Running Workload
```

---

# 44. Why etcd Matters

Imagine losing every record of what Kubernetes believes should exist.

You could lose critical cluster state describing:

```text
Workloads

Configuration

Access controls

Services

Secrets

Cluster resources
```

This is why etcd availability, security, and backup are serious production concerns.

---

# 45. etcd and the API Server

The normal Kubernetes architecture is:

```text
Client
↓
API Server
↓
etcd
```

not:

```text
Client
↓
etcd
```

and not:

```text
kubectl
↓
etcd
```

The API server provides Kubernetes API semantics, validation, access control, version conversion, admission, and other critical behavior.

---

# 46. Why Direct etcd Modification Is Dangerous

Directly changing Kubernetes data in etcd bypasses important API-server behavior.

You may bypass:

```text
Authentication / authorization architecture

Admission logic

API validation

API semantics

Version handling

Normal Kubernetes workflows
```

You can create state that Kubernetes components do not expect.

Production rule:

```text
Use the Kubernetes API to manage Kubernetes resources.
```

Do not treat etcd like an ordinary application database where engineers manually edit records.

---

# 47. etcd Is Distributed

Production etcd commonly runs as a cluster of members rather than one isolated process.

Conceptually:

```text
etcd Cluster
│
├── Member 1
├── Member 2
└── Member 3
```

or:

```text
Member 1
Member 2
Member 3
Member 4
Member 5
```

The purpose is to provide consistency and fault tolerance.

---

# 48. Consensus

Distributed etcd members must agree on changes.

etcd uses the Raft consensus algorithm.

You do not need to master Raft here.

Understand the production implication:

```text
A write should not simply be independently accepted
by arbitrary members with no agreement.
```

The cluster uses consensus to maintain consistent state.

---

# 49. Quorum

A distributed consensus cluster needs a majority of members available to make progress.

This majority is commonly called:

```text
quorum.
```

For a three-member cluster:

```text
Majority = 2
```

For a five-member cluster:

```text
Majority = 3
```

---

# 50. Three-Member Example

Imagine:

```text
etcd-1
etcd-2
etcd-3
```

Quorum requires:

```text
2 members.
```

One member can fail and the remaining two can still form a majority.

If two members fail:

```text
Only 1 remains.
```

No majority exists.

The etcd cluster cannot safely continue normal consensus-based writes.

---

# 51. Five-Member Example

Imagine:

```text
etcd-1
etcd-2
etcd-3
etcd-4
etcd-5
```

Quorum:

```text
3.
```

The cluster can tolerate two member failures and still retain a majority.

---

# 52. Why Odd Numbers Are Common

Compare:

```text
3 members
↓
Quorum 2
↓
Can tolerate 1 failure
```

and:

```text
4 members
↓
Quorum 3
↓
Can tolerate 1 failure
```

The fourth member does not increase the number of failures tolerated in this simple comparison.

Therefore etcd clusters are commonly designed with odd member counts.

Production design still requires careful architecture rather than blindly adding members.

---

# 53. etcd Leader Concept

etcd is leader-based.

At a simplified level:

```text
etcd Members
↓
Leader
+
Followers
```

The leader coordinates consensus operations.

If leadership is lost, the cluster attempts leader election.

Network and disk performance are important because instability can interfere with heartbeats and consensus.

---

# 54. etcd Availability and Kubernetes

Suppose running Pods already exist on worker nodes.

Then etcd becomes unavailable.

It does not necessarily mean every existing application process instantly disappears.

Some already-running workloads may continue running.

But the control plane cannot normally make progress on new persistent state changes without a functioning backing store.

For example, new scheduling and cluster-state changes can be affected.

This distinction is important:

```text
Control Plane Failure
≠
Immediate Death of Every Existing Container
```

But control-plane failure is still a serious production incident.

---

# 55. etcd Performance Matters

etcd depends heavily on:

```text
Reliable networking

Low-latency disk I/O

Adequate CPU

Adequate memory
```

Resource starvation can destabilize etcd.

That can destabilize Kubernetes control-plane operations.

Therefore production etcd should not be treated as:

```text
"just another tiny database process."
```

---

# 56. etcd Backup

Because etcd contains critical Kubernetes state, production clusters need a backup and recovery strategy.

A common mechanism is:

```text
etcd snapshot
```

Conceptually:

```text
Live etcd
↓
Snapshot
↓
Protected Backup Storage
↓
Recovery Capability
```

---

# 57. Backup Is Not Complete Until Restore Is Tested

A file existing somewhere is not enough.

A mature backup strategy asks:

```text
Can we restore it?

Is the snapshot valid?

Is it encrypted/protected?

Who can access it?

How old is it?

Where is it stored?

What is the recovery procedure?

Has the procedure been tested?
```

A backup that cannot be restored is not a useful recovery strategy.

---

# 58. etcd Snapshots Are Sensitive

An etcd snapshot can contain highly sensitive Kubernetes state.

That may include:

```text
Secrets

Configuration

Identity-related resources

Cluster topology

Application information
```

Therefore snapshots must be protected.

Do not upload them casually to:

```text
Public Git repositories

Unsecured shared folders

Public object storage
```

---

# 59. etcd Security

Production etcd security may include:

```text
TLS

Client certificate authentication

Peer certificate authentication

Network restrictions

Restricted access

Protected backups
```

A strong principle is:

```text
Only components that genuinely need etcd access should have it.
```

For standard Kubernetes operation, the API server is the primary etcd client.

---

# 60. Scheduler

Now imagine a Pod object has been accepted.

The Pod exists in Kubernetes state.

But it has not yet been assigned to a node.

Conceptually:

```text
Pod Created
↓
No Node Assigned
↓
Pending Scheduling
```

The component responsible for normal Pod placement is:

```text
kube-scheduler
```

---

# 61. What kube-scheduler Does

The scheduler watches for Pods that need node assignment.

Its job is:

```text
Unscheduled Pod
↓
Evaluate Nodes
↓
Choose Suitable Node
↓
Record Binding Decision
```

The scheduler does not normally start the container itself.

That distinction matters.

---

# 62. Scheduler vs kubelet

Scheduler:

```text
Where should this Pod run?
```

kubelet:

```text
This Pod has been assigned to my node.
I need to make sure its containers run.
```

Think:

```text
Scheduler
↓
Placement Decision

kubelet
↓
Node-Level Execution/Reconciliation
```

---

# 63. Pending Pod

A newly created Pod may initially be:

```text
Pending
```

One possible reason is:

```text
It has not yet been scheduled.
```

But `Pending` does not mean only one possible problem.

Later you will learn to inspect:

```text
Pod status

Conditions

Events

Scheduling messages
```

rather than guessing.

---

# 64. Candidate Nodes

Suppose the cluster has:

```text
Node A
Node B
Node C
Node D
```

The scheduler evaluates possible nodes.

Not every node is necessarily suitable.

Some may lack:

```text
CPU

Memory

Required labels

Required topology

Required storage compatibility
```

or may violate scheduling constraints.

---

# 65. Scheduler Filtering

The first major scheduling phase is filtering.

Conceptually:

```text
All Nodes
↓
Filtering
↓
Feasible Nodes
```

Example:

```text
Node A → Enough CPU → Pass
Node B → Not enough memory → Reject
Node C → Constraint mismatch → Reject
Node D → Suitable → Pass
```

Remaining:

```text
Node A
Node D
```

These are feasible candidates.

---

# 66. Scheduler Scoring

If several nodes remain feasible, the scheduler scores them.

Conceptually:

```text
Feasible Nodes
↓
Scoring
↓
Rank Nodes
↓
Select Suitable Placement
```

Example:

```text
Node A → Score 72
Node D → Score 91
```

The scheduler may select:

```text
Node D
```

based on configured scheduling logic.

# 67. Filtering vs Scoring

Remember:

```text

↓
Can this Pod run here?
```

Then:

```text
Scoring
↓
Among feasible nodes,
which placement is preferred?
```

These are different stages.

# 68. Resource Requirements

One scheduling factor is workload resource requirements.

Suppose a Pod requests:

```text
CPU = 2

Memory = 4 GiB
```

Node A has insufficient allocatable resources.

Node B has sufficient resources.

The scheduler can exclude Node A during filtering.

Important:

```text
Scheduling primarily considers declared requests
rather than simply asking which node appears quiet right now.
```

You will study requests and limits later.

# 69. Scheduling Constraints

Scheduling can also consider constraints such as:

```text

Pod anti-affinity

Topology spread

Policies
```

You do not need to understand each one yet.

For now:

```text
Scheduler
≠

```

It performs policy-aware placement.

# 70. No Feasible Node

```text

```

Conceptually:

```text

↓

↓

↓

```

# 71. Binding


```text

↓

↓
Binding
↓
API Server
↓
Pod Assigned to Node B
```

Now Node B's kubelet can act on the assignment.

# 72. The Scheduler Does Not SSH Into Nodes

This is a common misunderstanding.

The scheduler does not normally:

```text
SSH Node B
↓
docker run ...
```

Instead:

```text

↓

↓
Records Assignment
```

Then:

```text

↓
Observes Assigned Pod
↓
Acts
```

This API-driven architecture is central to Kubernetes.

# 73. kube-controller-manager

The next major control-plane component is:

```text
kube-controller-manager
```

It runs multiple controller processes.

Conceptually:

```text
kube-controller-manager
│
├── Node Controller
├── Job Controller
├── EndpointSlice Controller
├── ServiceAccount Controller
└── Other Controllers
```

Logically, controllers have different responsibilities.

Many are packaged into the controller-manager process.

---

# 74. What Is a Controller?

A controller is a control loop.

A control loop continuously:

```text
Observes State
↓
Compares With Desired State
↓
Acts When Necessary
↓
Observes Again
```

This is reconciliation.

---

# 75. Thermostat Analogy

Suppose:

```text
Desired Temperature = 22°C
```

Actual:

```text
18°C
```

A thermostat detects the difference.

It activates heating.

Later:

```text
Actual = 22°C
```

The controller no longer needs the same corrective action.

Kubernetes controllers use the same broad control-loop idea for cluster state.

---

# 76. Kubernetes Controller Model

```text
Desired State
↓
Controller Watches State
↓
Current State
↓
Compare
↓
Difference?
├── No
│   ↓
│   Continue Watching
│
└── Yes
    ↓
    Take / Request Action
    ↓
    Observe Again
```

Controllers do not simply execute once and disappear.

They continuously reconcile.

---

# 77. Example: Replica Management


```text

```

A relevant controller observes the mismatch.

Conceptually:

```text
Desired = 3

↓
Controller
↓

↓
Desired = 3
Actual Moves Toward 3
```

The new Pod may then require scheduling.

# 86. cloud-controller-manager Responsibilities

# 88. Worker Nodes

# 89. Worker Node Architecture

```text

├── kubelet
├── Container Runtime
├── Networking Components
```

# 90. kubelet

The kubelet is the primary Kubernetes node agent.

It runs on each node.

Its core responsibility is to ensure that containers described by Pod specifications assigned to that node are running and healthy according to the Pod specification.

Think:

```text

↓

↓
kubelet on Node A
↓
Ensure Pod Containers Run
```

```text

```

```text

```

Suppose Node A is assigned:

```text

```

The kubelet sees that Pod should exist on its node.

It coordinates with:

```text

Storage-related components
```

to establish the runtime environment.

Conceptually:

```text

↓

↓

↓

```

# 93. PodSpec

```text

```

---

# 94. kubelet Reconciliation

kubelet also behaves as a reconciler.

It repeatedly works to make node-level runtime state match the Pod specifications assigned to the node.

Think:

```text

↓

↓

↓
```

# 95. kubelet and Non-Kubernetes Containers

An important architectural detail:

kubelet is responsible for Pods supplied to it through Kubernetes-supported mechanisms.

It is not a generic manager for every arbitrary process or container someone manually starts on the machine.

If you manually start an unrelated process outside Kubernetes, do not expect Kubernetes automatically to adopt and manage it.

# 110. End-to-End Pod Creation

Now trace the process carefully.

Assume later you run:

```bash
kubectl apply -f pod.yaml
```

What happens?

---

# 111. Step 1: kubectl Reads Configuration

`kubectl` needs to know:

```text
Which cluster?

Which API server?

Which credentials?

Which context?
```

This information commonly comes from:

```text
kubeconfig.
```

Conceptually:

```text
kubectl
↓
kubeconfig
↓
Cluster Endpoint + Identity Information
```

---

# 112. Step 2: kubectl Builds an API Request

`kubectl` reads your manifest and sends an HTTP request to the Kubernetes API server.

Conceptually:

```text
pod.yaml
↓
kubectl
↓
HTTP API Request
↓
kube-apiserver
```

---

# 113. Step 3: TLS Connection

Production Kubernetes API communication normally uses TLS.

The client needs to establish trusted secure communication with the API endpoint.

Potential failure:

```text
x509 certificate error
```

may indicate a trust, hostname, certificate, or kubeconfig problem rather than a Pod problem.

This is why troubleshooting starts from the correct layer.

---

# 114. Step 4: Authentication

The API server asks:

```text
Who is making this request?
```

Authentication establishes identity.

Failure here means the request does not progress normally into authorization as an authenticated identity.

---

# 115. Step 5: Authorization

Kubernetes asks:

```text
Is this identity allowed to create this resource?
```

For example:

```text
User
↓
create
↓
pods
↓
namespace development
```

If denied:

```text
403 Forbidden
```

is a common API response.

---

# 116. Step 6: Admission

If authorized, applicable admission logic processes the modifying request.

Possible outcomes:

```text
Accept

Modify then continue

Reject
```

Examples can include:

```text
Resource quota enforcement

Pod security policy enforcement mechanisms

Custom validating policy

Custom mutating policy
```

---

# 117. Step 7: API Validation

The resulting object must conform to the Kubernetes API expectations.

If not:

```text
Request Rejected
```

Possible reasons include:

```text
Invalid field

Invalid value

Incorrect type

Missing required structure
```

---

# 118. Step 8: State Is Persisted

If accepted, the API server persists the object state through the Kubernetes storage layer, normally etcd.

Now Kubernetes knows:

```text
This Pod should exist.
```

But this does not mean the container is already running.

That distinction is critical.

---

# 119. Step 9: Pod Initially Has No Node

The Pod may exist as an API object without a node assignment.

Conceptually:

```text
Pod Object Exists
↓
spec.nodeName not yet assigned
↓
Needs Scheduling
```

The scheduler observes this state.

---

# 120. Step 10: Scheduler Notices the Pod

`kube-scheduler` watches for Pods that need placement.

It sees:

```text
New Unscheduled Pod
```

and begins scheduling.

---

# 121. Step 11: Filtering

The scheduler considers candidate nodes.

Example:

```text
Node A
Node B
Node C
```

After filtering:

```text
Node A → Pass
Node B → Fail: insufficient resource
Node C → Pass
```

Feasible:

```text
Node A
Node C
```

---

# 122. Step 12: Scoring

The scheduler scores feasible nodes.

Example:

```text
Node A → 63

Node C → 87
```

Node C wins under the active scoring rules.

---

# 123. Step 13: Binding

The scheduler records:

```text
This Pod belongs on Node C.
```

through the API.

Now:

```text
Pod
↓
Node C
```

is the desired placement.

---

# 124. Step 14: kubelet Notices

The kubelet on Node C observes:

```text
There is a Pod assigned to my node.
```

The kubelet now works to make the Pod real on that node.

---

# 125. Step 15: Runtime Preparation

kubelet communicates with the configured container runtime through CRI.

Conceptually:

```text
kubelet
↓
CRI
↓
containerd / CRI-O
```

The runtime environment for the Pod is prepared.

---

# 126. Step 16: Image Handling

If the required image is not locally available, the runtime may need to pull it from a registry according to the Pod's image pull policy and credentials.

Conceptually:

```text
Container Registry
↓
Image
↓
Node
↓
Container Runtime
```

Possible failure:

```text
ImagePullBackOff
```

is therefore a node/runtime/image-access problem, not a scheduler problem after placement has already occurred.

---

# 127. Step 17: Networking

The Pod needs its network environment.

The cluster's networking implementation participates in setting up connectivity.

Conceptually:

```text
Pod
↓
Network Namespace / Runtime Networking
↓
Cluster Networking
```

Exact implementation depends on the cluster.

---

# 128. Step 18: Storage

If the Pod needs volumes, relevant storage mechanisms must prepare and mount them.

Conceptually:

```text
Pod
↓
Volume Requirement
↓
Storage Components
↓
Mounted Storage
```

A storage failure can prevent a Pod from starting even though scheduling succeeded.

---

# 129. Step 19: Containers Start

The runtime starts the required containers.

Now:

```text
Container Process
```

actually exists on the worker node.

Only at this stage are we close to what a beginner casually means by:

```text
"Kubernetes started my application."
```

A large amount happened before that.

---

# 130. Step 20: Status Is Reported

The kubelet reports Pod and container status through the Kubernetes API.

Conceptually:

```text
Container Runtime State
↓
kubelet
↓
API Server
↓
Cluster Observed State
```

Then:

```bash
kubectl get pods
```

can retrieve the state exposed through the API.

# 134. What Happens When a Container Crashes?

Suppose:

```text
Pod
└── Container
    ↓
    Crash
```

The node's kubelet/runtime behavior and Pod restart policy determine container restart behavior.

If the entire Pod disappears while a higher-level controller expects replicas, the controller may create a replacement Pod.

These are different levels of recovery.

---

# 135. Container Restart vs Pod Replacement

Remember:

```text
Container Failure
↓
May Be Restarted Within Existing Pod
```

versus:

```text
Pod Lost
↓
Higher-Level Controller May Create Replacement Pod
```

Do not treat:

```text
restart container
```

and:

```text
create replacement Pod
```

as identical.

---

# 136. What Happens When a Node Fails?

Suppose:

```text
Node B
X
```

The control plane detects node-health changes over time.

Relevant controllers and workload policies determine how the cluster responds.

For controller-managed workloads, replacement Pods may eventually be created and scheduled elsewhere when appropriate.

But:

```text
Node failure
```

does not mean:

```text
Every Pod instantly teleports to another node.
```

Detection, status changes, tolerations, eviction behavior, scheduling, storage, and workload configuration all matter.

---

# 137. What Happens When the Scheduler Fails?

Suppose existing Pods are already running.

Then:

```text
kube-scheduler
X
```

Existing assigned Pods do not necessarily stop.

But new unscheduled Pods cannot receive normal placement from that scheduler until scheduling functionality is restored or another configured scheduler handles them.

This teaches an important principle:

```text
Different component failures affect different stages.
```

---

# 138. What Happens When kubelet Fails?

Suppose kubelet stops on Node A.

Containers already running through the runtime might not instantly vanish.

But Kubernetes loses normal node-agent reconciliation and status reporting from that kubelet.

The control plane may eventually mark the node unhealthy according to node-health mechanisms.

Again:

```text
Component Failure
≠
Immediate Destruction of Everything
```

You need to understand component responsibility.

---

# 139. What Happens When the Runtime Fails?

If containerd or another runtime fails:

```text
kubelet
↓
CRI
↓
Runtime X
```

kubelet cannot normally create/manage containers through that runtime until runtime functionality returns.

Troubleshooting must therefore inspect:

```text
kubelet

CRI endpoint

runtime service

runtime logs
```

rather than immediately blaming the API server.

---

# 140. What Happens When the API Server Fails?

The API server is the front door to the control plane.

If unavailable:

```text
kubectl
↓
API Server X
```

API requests fail.

Other Kubernetes components that depend on API communication are also affected.

Existing containers on nodes may continue running temporarily because the processes already exist.

But cluster management and reconciliation become severely impaired.

---

# 141. What Happens When etcd Fails?

If etcd loses the ability to serve the required cluster state operations:

```text
API Server
↓
etcd X
```

the control plane cannot normally persist or retrieve state as required for normal operation.

Existing workloads may continue running.

But the cluster loses critical control-plane functionality.

etcd is therefore a high-priority production dependency.

---

# 142. Production High Availability

A learning cluster might contain:

```text
1 Control Plane Node
1 Worker Node
```

A production cluster commonly needs greater fault tolerance.

Conceptually:

```text
             Load-Balanced API Endpoint
                      |
          ┌───────────┼───────────┐
          |           |           |
          v           v           v
     Control 1    Control 2    Control 3
          \           |           /
           \          |          /
                etcd Cluster

          Worker A
          Worker B
          Worker C
          Worker D
```

Exact architectures vary.

---

# 143. API Server Horizontal Scaling

`kube-apiserver` is designed to support multiple instances.

Conceptually:

```text
Clients
↓
Load-Balanced API Endpoint
├── API Server 1
├── API Server 2
└── API Server 3
```

This helps avoid one API-server process becoming the only access point.

---

# 144. Controller and Scheduler High Availability

Production clusters may run multiple instances of components such as:

```text
kube-scheduler

kube-controller-manager
```

with leader-election mechanisms ensuring the appropriate active leadership for control loops.

Do not assume:

```text
3 scheduler processes
=
every Pod scheduled three times.
```

High availability requires coordination.

# 145. Managed Kubernetes Difference

In a service such as a managed cloud Kubernetes platform, you may not have operating-system access to the control-plane machines.

You still interact with:

```text
Kubernetes API
```

but the provider manages much of:

```text
API server infrastructure

etcd infrastructure

Control-plane lifecycle
```

depending on the service.

This does not make the architecture irrelevant.

Understanding it is essential when interpreting failures and service responsibilities.

# 200. Production Security Perspective

The API server is one of the most security-sensitive endpoints in the platform.

Why?

Because it can control:

```text
Workloads

Secrets

Configuration

RBAC

Networking resources

Storage resources

Cluster resources
```

Therefore production clusters need strong controls around:

```text
API exposure

Authentication

Authorization

TLS

Auditability

Admission policy

Administrative credentials
```

---

# 201. Protect etcd

etcd access is extremely sensitive.

A party with broad etcd access can potentially access critical cluster state.

Production principles:

```text
Restrict network access

Use TLS

Use appropriate client authentication

Protect certificates

Protect snapshots

Encrypt backup storage

Limit operational access

Monitor health
```

Do not expose etcd casually to general networks.

---

# 202. Protect kubelet

kubelet is also security-sensitive.

It operates node workloads.

Kubelet communication requires appropriate authentication and authorization controls.

Do not treat the kubelet API as an ordinary public application endpoint.

---

# 203. Control Plane Network Design

A production cluster should deliberately design network exposure.

Conceptually:

```text
Administrators / Automation
↓
Controlled API Endpoint
↓
Control Plane

Worker Nodes
↓
Required Control-Plane Communication

General Internet
X
Direct etcd Access
```

Exact network architecture varies by environment.

# 206. Knowledge Check: etcd

### 19. What is etcd?

A consistent distributed key-value store used as Kubernetes' backing store.

### 20. Does etcd run application containers?

No.

### 21. Why is etcd critical?

It stores persistent Kubernetes cluster state.

### 22. What is quorum?

The majority of members required for the distributed consensus cluster to make progress safely.

### 23. What is quorum for three members?

```text
2
```

### 24. What is quorum for five members?

```text
3
```

### 25. Why are odd member counts common?

They provide useful failure tolerance without adding a member that does not increase tolerated failures at that size.

### 26. Why are backups required?

To support recovery of critical Kubernetes state after serious control-plane/data loss.

### 27. Why are etcd snapshots sensitive?

They contain critical Kubernetes state and can include sensitive information.

### 28. Should engineers normally modify Kubernetes state directly in etcd?

No.

---

# 207. Knowledge Check: Scheduler

### 29. What kind of Pod does the scheduler look for?

A Pod that needs node assignment.

### 30. What is filtering?

Eliminating nodes that cannot satisfy scheduling requirements.

### 31. What is scoring?

Ranking feasible nodes to choose a preferred placement.

### 32. What happens if no node is feasible?

The Pod remains unscheduled until placement becomes possible or the underlying issue changes.

### 33. Does the scheduler start the container?

No.

### 34. What happens after scheduling?

The Pod's node assignment is recorded, and the kubelet on the selected node can act on it.

---

# 208. Knowledge Check: Controllers

### 35. What is a controller?

A control loop that observes state and works to move current state toward desired state.

### 36. What is reconciliation?

The process of comparing desired and observed state and taking corrective action.

### 37. Does one controller manage everything in Kubernetes?

No.

Kubernetes uses many specialized controllers.

### 38. Give examples of controllers.

```text
Node controller

Job controller

EndpointSlice controller

ServiceAccount controller
```

### 39. Why are controllers continuous?

Because cluster state changes continuously.

---

# 209. Knowledge Check: Worker Nodes

### 40. What does kubelet do?

It ensures that containers described by Pods assigned to its node are running as required.

### 41. Does kubelet choose which node a Pod should use?

Normally no. That is the scheduler's responsibility.

### 42. What is CRI?

```text
Container Runtime Interface
```

### 43. What does CRI connect?

```text
kubelet
↓
Container runtime
```

### 44. Name two CRI-compatible runtime implementations.

```text
containerd

CRI-O
```

### 45. What does kube-proxy do?

In architectures that use it, kube-proxy maintains node network rules implementing part of Kubernetes Service behavior.

### 46. Is kube-proxy universally required?

No. Some networking implementations provide equivalent Service packet-forwarding behavior.

# 223. Final Mental Model

The control plane does not personally run every container.

It maintains and coordinates desired cluster state.

```text
Control Plane
↓
"What should exist?"
```

The scheduler answers:

```text
"Where should this Pod run?"
```

The kubelet answers:

```text
"What should be running on my node?"
```

The container runtime answers:

```text
"How do I execute this container?"
```

etcd answers:

```text
"What persistent Kubernetes API state has been recorded?"
```

The API server provides the controlled communication point tying these systems together.

Controllers continually ask:

```text
"Does observed state match desired state?"
```

And Kubernetes continually works toward:

```text
Desired State
≈
Observed State
```

That is the architecture underneath the commands.
