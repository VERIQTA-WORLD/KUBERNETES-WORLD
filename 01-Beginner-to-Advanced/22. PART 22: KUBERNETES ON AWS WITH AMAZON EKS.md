# PART 22: KUBERNETES ON AWS WITH AMAZON EKS

## From a Local Kubernetes Lab to a Managed Production Cloud Platform

---

# 1. Goal

The goal of this part is to move from local Kubernetes environments into a managed cloud Kubernetes environment using Amazon Elastic Kubernetes Service, Amazon EKS.

Until now, much of our learning has focused on Kubernetes itself:

```text
Pods
Deployments
Services
Ingress
Storage
Scheduling
Security
Scaling
Observability
Troubleshooting
Helm
```

Now we add another layer:

```text
AWS
```

This changes the operational picture.

A production EKS environment combines:

```text
AWS Infrastructure
+
Amazon EKS
+
Kubernetes
+
Application Workloads
```

By the end of this part, you should understand how these layers connect and where responsibility for each layer belongs.

---

# 7. EKS Control Plane

AWS manages the EKS Kubernetes control plane.

The control plane includes Kubernetes components such as:

```text
kube-apiserver

etcd

scheduler

controller components
```

The learner does not normally log into an EC2 instance running the EKS API server.

AWS operates the underlying control-plane infrastructure.

---

# 8. EKS Control Plane Availability

Amazon EKS provides a highly available control plane.

AWS distributes EKS control-plane infrastructure across multiple Availability Zones.

This is fundamentally different from a beginner local cluster where the entire control plane may exist inside:

```text
one VM

one Docker container

one laptop
```

# 29. Fargate Profiles

Conceptually:


# 30. Fargate Is Not "EC2 Without Seeing EC2"

# 34. What Is a VPC?

VPC means:

```text
Virtual Private Cloud
```

It is an isolated virtual network in AWS.

Example:

```text

```

Inside the VPC you create network resources such as:

```text

route tables

security groups

gateways

network interfaces
```

---

# 35. VPC Example

```text
VPC
10.0.0.0/16
│
├── Public Subnet AZ-A
│   10.0.1.0/24
│
├── Public Subnet AZ-B
│   10.0.2.0/24
│
├── Private Subnet AZ-A
│   10.0.11.0/24
│
└── Private Subnet AZ-B
    10.0.12.0/24
```

# 36. Subnets

Example:

```text

10.0.20.0/24
```

# 47. What Is an ENI?

ENI means:

```text

```

# 48. Why Pod IP Capacity Matters

Pod density can be affected by:

```text
instance type

network-interface limits

available IP addresses

CNI configuration

subnet size
```

This introduces a cloud-specific scheduling problem:

```text
CPU available
+
Memory available
+
No Pod IP capacity
=
Pod placement/networking problems
```

---

# 49. Subnet IP Exhaustion

Suppose:

```text
Private subnet
↓
very small CIDR
↓
many Nodes
↓
many Pods
↓
available addresses exhausted
```

New Pods may fail to obtain required network resources.

This is why VPC CIDR planning is a Kubernetes capacity concern.

# 53. IAM Is Not Kubernetes RBAC

This distinction is essential.

```text

```

```text

```

EKS connects these worlds, but they are not identical.

# 54. Two Authorization Worlds

```text

```



# 77. IRSA Concept

You may also encounter:

```text

```

commonly called:

```text

```

IRSA uses the cluster's OIDC identity-provider integration to allow Kubernetes ServiceAccounts to assume IAM roles.

You should understand both:

```text

```

because production clusters and third-party documentation may use either model.

# 78. Pod Identity vs IRSA

Conceptually:

```text

↓

```

while:

```text

↓
```

Both solve the broader problem:


# 85. EBS and Availability Zones

EBS volumes are associated with an Availability Zone.

This matters enormously.

Example:

```text
EBS Volume
↓
AZ-A
```

A Pod needing that volume cannot simply attach it to an incompatible node in:

```text
AZ-B
```

as though the volume were global.

Storage topology and scheduling are connected.

---

# 86. Why `WaitForFirstConsumer` Matters

StorageClasses commonly use topology-aware provisioning patterns such as:

```text
volumeBindingMode: WaitForFirstConsumer
```

Conceptually:

```text
Pod scheduling requirements
+
available node topology
↓
choose placement
↓
provision compatible storage
```

This can avoid creating storage in the wrong zone before the scheduler knows where the Pod should run.


Conceptually:

```text
AWS-managed serverless compute
for supported Kubernetes Pods.
```

# 247. Practical Assessment 5

What does the VPC CNI do?

It integrates Kubernetes Pod networking with AWS VPC networking and manages networking/IP allocation required for Pods.

---

# 248. Practical Assessment 6

Why can subnet sizing affect Kubernetes?

Because Pods using the VPC networking model consume address capacity.

Therefore:

```text
subnet IP exhaustion
```

can become:

```text
Kubernetes scaling failure.
```

---

# 249. Practical Assessment 7

What is the difference between IAM and RBAC?

```text
IAM
=
AWS authorization
```

```text
RBAC
=
Kubernetes authorization
```

EKS integrates identity flows across these systems, but they remain distinct authorization layers.

---

# 250. Practical Assessment 8

What is EKS Pod Identity?

A mechanism for associating an IAM role with a Kubernetes ServiceAccount so supported Pods can obtain temporary AWS credentials without static access keys.

---

# 251. Practical Assessment 9

Should Pods use the node IAM role for every AWS permission?

No.

Prefer workload-level IAM where appropriate so different applications can receive different least-privilege permissions.

---

# 252. Practical Assessment 10

```text
Kubernetes storage
↓
Amazon EBS
```

---

# 253. Practical Assessment 11

Why does EBS topology matter?

Because EBS volumes are associated with Availability Zones.

Pod placement and storage location must therefore be compatible.

---

# 254. Practical Assessment 12

What is EFS useful for?

Shared file storage use cases where multiple workloads require appropriate filesystem semantics.

It is not automatically a replacement for EBS.

# 278. The Most Important Lesson

EKS does not remove infrastructure.

It changes who operates different pieces of infrastructure.

EKS does not remove Kubernetes.

It provides a managed environment in which Kubernetes operates.

EKS does not remove security.

It introduces additional AWS identity, networking, storage, and infrastructure security layers.

EKS does not remove troubleshooting.

It expands the troubleshooting path from:

```text
Kubernetes
```

to:

```text
AWS
+
Kubernetes
+
Application
```

A production EKS engineer must understand all three.
