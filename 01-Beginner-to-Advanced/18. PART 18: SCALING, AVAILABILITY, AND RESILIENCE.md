# PART 18: SCALING, AVAILABILITY, AND RESILIENCE

## Operating Kubernetes Workloads Through Changing Demand and Infrastructure Failure

---

# 1. Goal

The goal of this part is to understand how Kubernetes applications continue operating when:

```text
traffic increases

traffic decreases

Pods fail

containers crash

nodes disappear

nodes require maintenance

deployments are updated

capacity becomes constrained

infrastructure is disrupted
```

By the end, you should understand how Kubernetes combines:

```text
replicas

Horizontal Pod Autoscaling

resource metrics

resource requests

node autoscaling

scheduling

failure domains

PodDisruptionBudgets

graceful termination

rolling updates

capacity planning
```

to create resilient applications.

The central production idea is:

```text
Demand changes
↓
Workload capacity changes
↓
Pods increase or decrease
↓
Scheduler places Pods
↓
Cluster capacity must exist
↓
Node autoscaling may add capacity
↓
Replicas remain distributed
↓
Failures occur
↓
Controllers reconcile
↓
Healthy capacity is restored
```

---

# 2. Scaling Is Not the Same as Availability

These concepts are related but different.

Scaling asks:

```text
Can the system increase or decrease capacity
as demand changes?
```

Availability asks:

```text
Can users continue receiving service
when components fail or change?
```

Resilience asks:

```text
Can the system absorb failures,
recover, and return to a healthy state?
```

A workload can scale without being highly available.

Example:

```text
1 Pod
↓
HPA
↓
10 Pods
```

But if all 10 Pods run on:

```text
one node
```

then one node failure can still remove the entire application.

Scaling alone does not guarantee resilience.

# 4. Three Major Scaling Dimensions

Kubernetes environments commonly scale at three different levels.

## Horizontal workload scaling

```text
more Pods
or
fewer Pods
```

Example:

```text
3 replicas
↓
8 replicas
```

## Vertical workload scaling

```text
more or fewer CPU/memory resources
per Pod
```

Example:

```text
CPU request:
250m
↓
500m
```

## Node scaling

```text
more Nodes
or
fewer Nodes
```

Example:

```text
3 worker nodes
↓
6 worker nodes
```

These solve different capacity problems.

# 5. Horizontal vs Vertical Scaling

Horizontal:

```text

Pod

↓

Pod
Pod
Pod
Pod
Pod
Pod
```

Vertical:

```text

CPU: 250m

```

Horizontal scaling increases:

```text

```

```text

```

# 6. Why Horizontal Scaling Is Common in Kubernetes

Many cloud-native applications are designed as:

```text
multiple interchangeable replicas.
```

Example:

```text
Service
↓
web-1
web-2
web-3
```

Requests can be distributed across replicas.

If demand rises:

```text
Service
↓
web-1
web-2
web-3
web-4
web-5
web-6
```

This makes horizontal scaling natural.

# 7. Horizontal Scaling Requires Application Design

Adding replicas does not automatically make an application scalable.

Problems can include:

```text
local session state

local files

single-writer assumptions

database bottlenecks

shared locks

external API limits

queue contention

connection limits
```

A stateless HTTP service usually scales horizontally more easily than a stateful database.

Manual scaling requires a human or external automation to notice:

```text

```

```text

```

# 12. Horizontal Pod Autoscaler

The Horizontal Pod Autoscaler is commonly abbreviated:

```text
HPA
```

Its purpose is:

```text
automatically adjust workload replica count
based on observed metrics.
```

Architecture:

```text
Metrics
↓
HPA Controller
↓
Desired Replica Calculation
↓
Deployment / StatefulSet
↓
ReplicaSet where applicable
↓
Pods
```

---

# 13. HPA Does Not Directly Create Pods

This is important.

HPA normally changes:

```text
the replica count of its target workload.
```

For a Deployment:

```text
HPA
↓
Deployment replicas
↓
ReplicaSet
↓
Pods
```

HPA is not itself a Pod factory.

---

# 14. HPA Control Loop

Conceptually:

```text
Observe metrics
↓
Compare current metric with target
↓
Calculate desired replicas
↓
Apply scaling behavior
↓
Update target workload
↓
Controllers create/delete Pods
↓
Observe again
```

This repeats continuously as a control loop.

# 15. HPA Is Periodic

HPA does not react infinitely fast.

The controller periodically evaluates metrics.

Therefore:

```text
traffic spike
```

does not mean:

```text
new Pods appear instantaneously.
```

There is always some delay involving:

```text
metric collection

autoscaler evaluation

Pod creation

scheduling

image startup

application startup

readiness
```

This matters during sudden traffic spikes.

# 21. CPU-Based Scaling

CPU is one of the most common introductory HPA metrics.

Suppose containers request:

```yaml
resources:
  requests:
    cpu: "100m"
```

and HPA target is:

```text
50% CPU utilization.
```

The target is based on utilization relative to the requested CPU.

---

# 22. CPU Request Matters

Suppose:

```text
CPU request = 100m
```

and observed average CPU usage is approximately:

```text
80m
```

Then utilization is roughly:

```text
80 / 100
=
80%
```

If the HPA target is:

```text
50%
```

the workload may need more replicas.

---

# 23. Simplified HPA Formula

A useful mental model is:

```text
desired replicas
≈
current replicas
×
current metric
÷
desired metric
```

Example:

```text
current replicas = 4

current CPU utilization = 80%

target CPU utilization = 40%
```

Simplified:

```text
4 × 80 / 40
=
8
```

So the autoscaler may target approximately:

```text
8 replicas.
```

The real algorithm contains additional handling for missing metrics, readiness, tolerances, and scaling behavior.

# 24. CPU HPA Manifest

Example:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
  namespace: scaling-lab

spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web

  minReplicas: 2
  maxReplicas: 10

  metrics:
    - type: Resource
      resource:
        name: cpu

        target:
          type: Utilization
          averageUtilization: 50
```

# 26. `minReplicas`

Example:

```yaml
minReplicas: 2
```

means the autoscaler should not normally scale below:

```text
2 replicas.
```

This can provide a basic availability floor.

But:

```text
minReplicas: 2
```

does not guarantee the two replicas are on different nodes.

Scheduling controls still matter.

---

# 27. `maxReplicas`

Example:

```yaml
maxReplicas: 10
```

protects against unlimited horizontal growth.

Without appropriate limits, unexpected metrics or traffic can create:

```text
excessive Pods

resource pressure

downstream overload

unexpected cloud cost
```

Autoscaling must have boundaries.

# 30. LAB 2: Create Scalable Application

Create:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: scaling-lab

spec:
  replicas: 2

  selector:
    matchLabels:
      app: web

  strategy:
    type: RollingUpdate

    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1

  template:
    metadata:
      labels:
        app: web

    spec:
      terminationGracePeriodSeconds: 30

      containers:
        - name: web
          image: registry.k8s.io/hpa-example:latest

          ports:
            - name: http
              containerPort: 80

          resources:
            requests:
              cpu: "100m"
              memory: "64Mi"

            limits:
              cpu: "500m"
              memory: "128Mi"

          readinessProbe:
            httpGet:
              path: /
              port: http

            initialDelaySeconds: 2
            periodSeconds: 5

          livenessProbe:
            httpGet:
              path: /
              port: http

            initialDelaySeconds: 5
            periodSeconds: 10
```

For a real production workload, prefer a deliberately versioned and controlled image reference rather than a mutable `latest` tag. The tag here is only for the official HPA demonstration image used in this disposable lab.

# 42. Why Scale-Down Is Deliberately Slower

Rapid scale-down can create:

```text
flapping

capacity oscillation

traffic instability
```

Example:

```text
load rises
↓
scale up
↓
load per Pod falls
↓
immediate scale down
↓
load per Pod rises
↓
scale up again
```

This oscillation is undesirable.

HPA includes behavior designed to reduce it.

---

# 43. Stabilization

HPA scaling behavior can include:

```text
stabilization windows
```

which consider previous scaling recommendations before reducing or increasing replica counts.

Scale-down is commonly more conservative than scale-up.

That helps prevent:

```text
rapid oscillation.
```

---

# 44. HPA Behavior Example

Example:

```yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300

  scaleUp:
    stabilizationWindowSeconds: 0
```

Conceptually:

```text
scale up quickly
↓
respond to demand

scale down cautiously
↓
avoid removing capacity too quickly
```

---

# 45. Scaling Policies

HPA behavior can also limit:

```text
how rapidly replicas change.
```

Example concept:

```yaml
behavior:
  scaleUp:
    policies:
      - type: Percent
        value: 100
        periodSeconds: 60
```

```text

```

```text

```

# 59. VPA Is Separate From HPA


# 60. HPA and VPA Interaction

Be careful when both systems control overlapping resource dimensions.

Example:

```text
HPA scales based on CPU utilization
```

while:

```text
VPA continuously changes CPU requests.
```

Because CPU utilization percentages depend on requests, the two systems can influence each other.

Design combined autoscaling intentionally.

# 63. Node Autoscaling

Horizontal workload autoscaling changes:

```text
number of Pods.
```

Node autoscaling changes:

```text
cluster compute capacity.
```

Architecture:

```text
Demand increases
↓
HPA creates more desired replicas
↓
Pods created
↓
some Pods cannot schedule
↓
Node autoscaler detects capacity requirement
↓
new Node provisioned
↓
Node joins cluster
↓
scheduler places Pending Pods
```

---

# 64. Cluster Autoscaler Concepts

Cluster Autoscaler is one implementation of Kubernetes node autoscaling.

Conceptually it can:

```text
increase configured node-group capacity
```

when Pods cannot be scheduled because of insufficient suitable capacity.

It can also help remove unnecessary Nodes under appropriate conditions.

---

# 65. Node Autoscaler Inputs

Node autoscaling depends heavily on:

```text
Pod resource requests

scheduling constraints

node configuration

available infrastructure capacity
```

Example:

```text
Pod requests 4 CPU
```

but existing Nodes have only:

```text
1 CPU available.
```

The Pod remains:

```text
Pending.
```

A compatible node autoscaler may provision additional capacity.

---

# 66. Why Requests Matter Again

Node autoscalers reason about scheduling requirements.

Therefore:

```text
resource requests
```

are crucial.

If requests are much too low:

```text
scheduler/autoscaler may believe capacity is sufficient
```

even while real usage creates pressure.

If requests are much too high:

```text
unnecessary Nodes may be provisioned
```

or consolidation may be prevented.

---

# 67. Node Autoscaling Is Not CPU-Based in the Same Way as HPA

A common misconception:

```text
Node CPU reaches 80%
↓
Cluster Autoscaler automatically adds Node
```

That is not the core scheduling model.

Node autoscaling commonly responds to:

```text
Pods that cannot be scheduled
because suitable Node capacity is unavailable
```

and performs consolidation when capacity is no longer needed.

# 68. Complete Autoscaling Chain

A powerful production pattern is:

```text
Traffic rises
↓
Pod CPU rises
↓
HPA increases replicas
↓
new Pods created
↓
cluster has insufficient schedulable capacity
↓
Pods become Pending
↓
node autoscaler provisions Nodes
↓
Nodes become Ready
↓
scheduler places Pending Pods
↓
Pods become Ready
↓
Service gains endpoints
```

This is workload autoscaling combined with node autoscaling.

---

# 69. Scale-Down Chain

When demand falls:

```text
traffic decreases
↓
HPA reduces replicas
↓
fewer Pods needed
↓
some Nodes become underutilized
↓
node autoscaler evaluates consolidation
↓
eligible Pods are disrupted/rescheduled
↓
unneeded Node removed
```

This is why:

```text
PodDisruptionBudgets

scheduling constraints

resource requests
```

matter during node consolidation.

---

# 70. Modern Node Autoscaling Concept

Kubernetes documentation describes node autoscaling broadly rather than treating one implementation as the only model.

Current implementations can include:

```text
Cluster Autoscaler

Karpenter integrations
```

depending on cloud/platform.

The core concept remains:

```text
provision and consolidate Nodes
according to workload scheduling requirements
and infrastructure constraints.
```

---

# 71. Cluster Autoscaler vs Dynamic Node Provisioning

Traditional node-group-based autoscaling often chooses among:

```text
preconfigured node groups.
```

More dynamic node provisioning systems can choose infrastructure based on:

```text
workload requirements

zones

architecture

capacity type

cost constraints
```

depending on implementation.

Part 22 will revisit this in AWS/EKS context.

---

# 72. High Availability

High availability means designing the system so that failure of an individual component does not unnecessarily make the entire service unavailable.

At workload level:

```text
1 replica
```

is usually a single point of failure.

---

# 73. Single Replica Failure

Architecture:

```text
Service
↓
Pod A
```

If:

```text
Pod A fails
```

then:

```text
zero healthy replicas
```

until replacement becomes Ready.

Kubernetes can recover the Pod.

But:

```text
recovery
≠
continuous availability.
```

---

# 74. Multiple Replicas

Better:

```text
Service
↓
Pod A
Pod B
Pod C
```

If:

```text
Pod B fails
```

then:

```text
Pod A + Pod C
```

may continue serving traffic.

Meanwhile:

```text
controller creates replacement Pod.
```

This reduces disruption.

---

# 75. Self-Healing vs High Availability

Self-healing:

```text
failed replica
↓
replacement created
```

High availability:

```text
other healthy replicas
continue serving
while replacement occurs.
```

These are not the same.

---

# 76. Replica Distribution

Multiple replicas are useful only if failure does not remove all of them together.

Bad:

```text
Node A
├── web-1
├── web-2
└── web-3
```

Node A fails:

```text
all replicas lost.
```

Better:

```text
Node A → web-1

Node B → web-2

Node C → web-3
```

Now one node failure removes only part of capacity.

---

# 77. Pod Anti-Affinity

As learned in Part 15, Pod anti-affinity can encourage or require replicas not to share the same topology domain.

Concept:

```text
Do not place matching replicas together.
```

Example topology:

```text
kubernetes.io/hostname
```

This can spread replicas across Nodes.

---

# 78. Required Anti-Affinity Trade-Off

Strict rule:

```text
one replica per node
```

may improve failure isolation.

But if there are:

```text
3 nodes
```

and you request:

```text
4 replicas
```

one Pod may remain:

```text
Pending.
```

Availability constraints can become scheduling constraints.

---

# 79. Preferred Anti-Affinity

Preferred rules tell the scheduler:

```text
try to spread these replicas,
but schedule them together if necessary.
```

This improves schedulability but provides weaker placement guarantees.

Choose according to reliability requirements.

---

# 80. Topology Spread Constraints

Topology spread constraints provide another mechanism for distributing Pods across topology domains.

Examples:

```text
nodes

zones

other labeled infrastructure domains
```

Architecture:

```text
Zone A
├── Pod 1
└── Pod 4

Zone B
├── Pod 2
└── Pod 5

Zone C
├── Pod 3
└── Pod 6
```

This reduces correlated failure risk.

---

# 81. Failure Domain

A failure domain is:

```text
a set of infrastructure
that can fail together.
```

Examples:

```text
node

rack

availability zone

data center

region
```

The exact domains depend on infrastructure.

---

# 82. Node Failure Domain

If all replicas run on one Node:

```text
Node failure
=
application failure.
```

Spread across Nodes:

```text
one Node failure
=
partial capacity loss.
```

---

# 83. Zone Failure Domain

Suppose:

```text
Zone A
├── Pod 1
├── Pod 2
└── Pod 3
```

Even though Pods run on different Nodes, a zone failure can remove all three.

Better:

```text
Zone A → Pod 1
Zone B → Pod 2
Zone C → Pod 3
```

where infrastructure and application requirements support multi-zone operation.

---

# 84. High Availability Requires Capacity in Remaining Domains

Suppose normal load requires:

```text
6 Pods.
```

Architecture:

```text
Zone A → 2
Zone B → 2
Zone C → 2
```

If one zone disappears:

```text
4 Pods remain.
```

Can four Pods handle normal traffic?

If not:

```text
the application is distributed
but not adequately provisioned for zone failure.
```

Failure-domain planning requires capacity planning.

---

# 85. Resilience Question

Do not ask only:

```text
Are replicas spread?
```

Ask:

```text
If one failure domain disappears,
can remaining capacity handle demand?
```

That is a much stronger production question.

---

# 86. Failure Types

Kubernetes workloads encounter two broad categories of disruption:

```text
involuntary disruptions

voluntary disruptions
```

Understanding the difference is essential for PodDisruptionBudgets.

---

# 87. Involuntary Disruptions

Examples:

```text
hardware failure

node crash

kernel failure

network partition

power failure

VM disappears

zone outage
```

These happen unexpectedly.

Kubernetes cannot ask a PodDisruptionBudget for permission before physical hardware suddenly dies.

---

# 88. Voluntary Disruptions

Examples can include:

```text
node drain

cluster maintenance

some node autoscaler consolidation

administrative eviction

certain upgrade operations
```

These are initiated intentionally.

Kubernetes eviction mechanisms can consider PodDisruptionBudgets during supported voluntary disruptions.

---

# 89. PodDisruptionBudget

A PodDisruptionBudget is abbreviated:

```text
PDB.
```

It limits how many selected Pods may be voluntarily disrupted at the same time.

It does not create replicas.

It does not make unhealthy Pods healthy.

It does not stop every type of failure.

---

# 90. PDB Example

Suppose:

```text
replicas = 3
```

and:

```yaml
minAvailable: 2
```

During an eviction-controlled voluntary disruption:

```text
at least 2 selected Pods
should remain available.
```

Conceptually:

```text
3 available
↓
evict 1
↓
2 available
↓
further eviction may be blocked
until availability recovers
```

---

# 91. PDB Manifest

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web
  namespace: scaling-lab

spec:
  minAvailable: 2

  selector:
    matchLabels:
      app: web
```

---

# 92. `minAvailable`

Example:

```yaml
minAvailable: 2
```

means voluntary eviction should only proceed when at least:

```text
2 Pods
```

will remain available according to PDB semantics.

---

# 93. `maxUnavailable`

Alternative:

```yaml
maxUnavailable: 1
```

means:

```text
at most one selected Pod
may be unavailable
under the disruption budget.
```

Use either:

```text
minAvailable
```

or:

```text
maxUnavailable
```

for a PDB, not both.

---

# 94. Percentage PDB

You can use percentages.

Example:

```yaml
minAvailable: 75%
```

or:

```yaml
maxUnavailable: 25%
```

Understand rounding behavior before using percentages for small replica counts.

For small workloads, one Pod can represent a large percentage of total capacity.

---

# 95. PDB Does Not Protect Against Node Crash

Critical rule:

```text
PDB
≠
force field around Pods.
```

If a physical node disappears unexpectedly:

```text
Pods disappear regardless of PDB.
```

PDBs primarily influence supported voluntary eviction operations.

---

# 96. PDB Does Not Stop Direct Pod Deletion

A direct:

```bash
kubectl delete pod <POD>
```

does not behave like a policy-respecting eviction request.

Do not assume PDB protects workloads from every administrative action.

---

# 97. PDB and Deployment Rolling Updates

Another important distinction:

Deployment rolling-update availability is primarily controlled by:

```text
maxUnavailable

maxSurge
```

in the Deployment strategy.

PDBs are mainly about:

```text
voluntary disruptions through eviction mechanisms.
```

Do not use a PDB as a replacement for proper rollout configuration.

---

# 98. PDB Can Block Maintenance

Suppose:

```text
3 replicas

minAvailable: 3
```

Then no selected healthy Pod can normally be voluntarily evicted without violating the budget.

A node drain may stall.

This may be intentional.

Or it may be an overly strict configuration.

---

# 99. PDB Design Question

Ask:

```text
How many replicas can disappear
during planned maintenance
while the application still meets availability requirements?
```

That should guide the budget.

Not:

```text
What YAML looks safest?
```

---

# 100. Unhealthy Pods and PDBs

Modern PDBs include:

```text
unhealthyPodEvictionPolicy
```

to control how running but unhealthy Pods are treated during eviction.

This matters because a broken Pod can otherwise complicate node drain and maintenance.

Use this setting deliberately after understanding application behavior and Kubernetes version support.

# 103. Graceful Termination

Availability is not only about replica count.

When Kubernetes removes a Pod, the application should shut down safely.

Conceptual sequence:

```text
Pod termination requested
↓
Pod begins terminating
↓
endpoint traffic handling changes
↓
preStop hook if configured
↓
SIGTERM sent to container process
↓
application stops accepting new work
↓
in-flight work finishes
↓
process exits
↓
grace period expires if necessary
↓
remaining processes forcibly terminated
```

Exact timing and ordering contain important implementation details, but this is the operational mental model.

---

# 104. `terminationGracePeriodSeconds`

Example:

```yaml
spec:
  terminationGracePeriodSeconds: 30
```

This gives containers a grace period to shut down before forceful termination when applicable.

Default Pod grace period is commonly:

```text
30 seconds.
```

Choose a value appropriate for the application.

---

# 105. Application Must Handle SIGTERM

A grace period is useless if the application ignores graceful shutdown requirements.

Application behavior should include:

```text
receive SIGTERM
↓
stop accepting new work
↓
finish or safely abandon in-flight work
↓
flush required state
↓
close connections
↓
exit
```

---

# 106. Graceful HTTP Shutdown

A web application might:

```text
become unready
↓
stop receiving new traffic
↓
finish active requests
↓
close listeners
↓
exit
```

The exact implementation depends on the application framework.

Kubernetes cannot invent graceful application behavior for you.

---

# 107. `preStop`

A lifecycle hook can run before container termination.

Example:

```yaml
lifecycle:
  preStop:
    exec:
      command:
        - /bin/sh
        - -c
        - sleep 5
```

This is useful in some designs.

But:

```text
sleep 5
```

is not automatically a production-grade shutdown strategy.

Understand why the delay exists.

---

# 108. Termination Grace Period Includes Lifecycle Handling

The termination process has a finite grace period.

Do not design:

```text
preStop = 30 seconds
+
application shutdown = 30 seconds
```

while assuming a 30-second Pod grace period gives 60 seconds.

Design the shutdown budget intentionally.

---

# 109. Graceful Shutdown and Readiness

Readiness is critical during shutdown.

You want traffic routing to stop before the application becomes unable to serve requests.

This is one reason application lifecycle and readiness design must work together.

---

# 110. Connection Draining

External load balancers, ingress systems, proxies, Services, and applications may each have their own update or draining behavior.

Production shutdown design may need to account for:

```text
Kubernetes endpoint changes

proxy propagation

load balancer health checks

keep-alive connections

long-running requests

WebSockets

streaming connections
```

Graceful termination is an end-to-end problem.

---

# 111. Rolling Updates

Deployment rolling updates replace old replicas gradually.

Architecture:

```text
Old ReplicaSet
↓
old Pods

New Deployment template
↓
New ReplicaSet
↓
new Pods

Old ↓
New ↑
```

The goal is to introduce a new version while maintaining service availability.

---

# 112. `maxUnavailable`

Example:

```yaml
strategy:
  type: RollingUpdate

  rollingUpdate:
    maxUnavailable: 1
```

This limits how many desired Pods can be unavailable during the Deployment rollout.

---

# 113. `maxSurge`

Example:

```yaml
maxSurge: 1
```

allows Kubernetes to create an extra Pod above the desired replica count during rollout.

Example:

```text
desired replicas = 4

maxSurge = 1
```

During rollout, Kubernetes can temporarily create additional capacity.

---

# 114. Availability-Oriented Rolling Update

Example:

```yaml
strategy:
  type: RollingUpdate

  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

Conceptually:

```text
create one new Pod
↓
wait until it becomes available
↓
remove an old Pod
↓
repeat
```

This can reduce rollout unavailability.

But it requires spare cluster capacity for the surge Pod.

---

# 115. Zero Unavailable Requires Capacity

Suppose every Node is completely full.

Deployment:

```text
replicas: 10

maxUnavailable: 0

maxSurge: 1
```

Kubernetes wants:

```text
one extra Pod
```

before removing an old one.

But there is:

```text
no capacity.
```

The rollout may stall.

Availability settings and capacity planning are connected.

---

# 116. Readiness Protects Rolling Updates

Suppose a new Pod starts but the application is broken.

Without meaningful readiness:

```text
container starts
↓
considered usable too early
↓
old Pod removed
↓
users hit broken application
```

With good readiness:

```text
new Pod starts
↓
readiness fails
↓
new Pod not available for traffic
↓
rollout cannot safely progress as quickly
↓
old healthy capacity remains
```

This is why Part 16 matters.

---

# 117. Rolling Update Is Not Automatically Safe

A rollout can still fail because of:

```text
bad image

bad configuration

broken readiness

insufficient capacity

scheduling constraints

Secret errors

PVC issues

dependency failure

application incompatibility
```

Always observe rollout status.

# 119. Capacity

Capacity means:

```text

the system can provide.
```

Kubernetes capacity exists at multiple levels:

```text
container

Pod

Node

cluster

application

dependency

cloud infrastructure
```

---

# 120. Node Capacity vs Allocatable

A Node may have physical/virtual capacity such as:

```text
8 CPU
32Gi memory
```

but Kubernetes may expose less as:

```text
Allocatable
```

because resources are reserved for:

```text
operating system

Kubernetes components

eviction thresholds

other system needs
```

The scheduler reasons about allocatable resources and Pod requests.

---

# 121. Inspect Node Capacity

```bash

```

Look for:

```text
Capacity

Allocatable

Allocated resources
```

This helps explain scheduling behavior.

---

# 122. Cluster Capacity Is Not Application Capacity

Suppose cluster has:

```text
100 CPU
```

but your database supports only:

```text
500 connections.
```

Scaling web Pods from:

```text
10
```

to:

```text
100
```

may overload the database.

Therefore:

```text
Kubernetes capacity
≠
end-to-end system capacity.
```

---

# 123. Downstream Bottlenecks

Autoscaling can shift the bottleneck.

Example:

```text
Traffic ↑
↓
HPA adds API Pods
↓
API concurrency ↑
↓
database connections ↑
↓
database overloads
```

The autoscaler successfully scales the API while making the complete system less stable.

---

# 124. Scaling Requires Dependency Awareness

Before enabling aggressive autoscaling ask:

```text
Can database handle additional connections?

Can cache handle additional clients?

Can message broker handle additional consumers?

Can external API handle additional requests?

Can storage handle additional throughput?

Can load balancer handle additional targets?
```

Scaling one tier changes pressure on other tiers.

---

# 125. Capacity Planning

Capacity planning asks:

```text
How much demand must we support?

How much capacity does one replica provide?

How many replicas are required normally?

How many during peak?

How many after a node failure?

How many after a zone failure?

How quickly can capacity increase?

What are downstream limits?
```

Autoscaling does not eliminate capacity planning.

---

# 126. Headroom

Headroom means:

```text
unused capacity deliberately retained
to absorb demand or failure.
```

Example:

```text
normal demand = 60 units

available capacity = 100 units
```

Headroom:

```text
40 units
```

This can absorb:

```text
traffic spikes

Pod failures

node failures

rollouts

autoscaling delay
```

---

# 127. Running at 100% Capacity Is Fragile

If every Node is fully allocated:

```text
no room for surge Pods

no room for rescheduled Pods

no room for temporary spikes

node failure causes scheduling pressure
```

High utilization can reduce cost but also reduce resilience.

Production engineering balances:

```text
cost
vs
headroom
vs
recovery speed.
```

---

# 128. Overprovisioning Concepts

Overprovisioning means deliberately maintaining spare cluster capacity.

Conceptually:

```text
Actual required capacity:
70%

Provisioned:
100%
```

The spare capacity can absorb sudden workload growth or failures.

---

# 129. Why Overprovision

Node provisioning can take time.

A new cloud VM may require:

```text
instance provisioning

boot

kubelet startup

cluster registration

network initialization

DaemonSet startup

image pulls
```

If workload demand increases faster than Nodes can appear:

```text
Pending Pods
```

may accumulate.

Spare capacity reduces this delay.

---

# 130. Overprovisioning Trade-Off

More spare capacity means:

```text
faster resilience
```

but also:

```text
higher infrastructure cost.
```

Less spare capacity means:

```text
lower idle cost
```

but potentially:

```text
slower recovery

slower scale-up

greater disruption risk.
```

This is a business and reliability trade-off.

---

# 131. Placeholder Overprovisioning Concept

Some environments intentionally run low-priority placeholder workloads that reserve resources.

When real workloads need capacity:

```text
higher-priority real workload arrives
↓
placeholder can be preempted
↓
real workload schedules immediately
↓
node autoscaler observes resulting capacity need
↓
new infrastructure can be provisioned
```

This is an advanced strategy.

Do not introduce it without understanding:

```text
PriorityClasses

preemption

node autoscaler behavior

cost implications.
```

# 206. Production Workload Example

Deployment:

```yaml

  name: api
  namespace: production

  selector:

      app: api

  strategy:
    type: RollingUpdate

              app: api

          whenUnsatisfiable: ScheduleAnyway

            matchLabels:

              cpu: "250m"
              memory: "256Mi"

              port: 8080

              path: /live
              port: 8080
```


even when the application cannot serve real requests.

Kubernetes thinks:

```text
Ready
```

while users receive failures.

A readiness probe must represent real traffic-serving capability.

---

# 220. Reliability Anti-Pattern: Immediate Hard Shutdown

Application receives SIGTERM and instantly exits while requests are still active.

Result:

```text
connection resets

failed requests

partial work
```

Implement graceful shutdown.

---

# 221. Reliability Anti-Pattern: No Headroom

Cluster:

```text
100% requested capacity
```

Then:

```text
Node failure
```

causes replacement Pods to remain Pending.

Or:

```text
rolling update
```

cannot schedule surge Pods.

Plan spare capacity or rapid node provisioning.

---

# 222. Reliability Anti-Pattern: Scale Everything on CPU

CPU is not always the limiting factor.

A worker may be blocked by:

```text
queue backlog

I/O

database

network

external service

locks
```

Choose metrics that represent the actual workload.

---

# 223. Reliability Anti-Pattern: Autoscaling a Broken Dependency

Database fails.

Application requests hang.

CPU rises.

HPA adds Pods.

Each new Pod opens more database connections.

Result:

```text
failure amplification.
```

Autoscaling needs dependency-aware limits and operational monitoring.

---

# 224. Reliability Anti-Pattern: Unlimited Growth

Autoscaling is not:

```text
more is always better.
```

Unbounded scaling can create:

```text
cost explosions

dependency overload

rate-limit violations

cluster exhaustion
```

Use intentional maximums.
