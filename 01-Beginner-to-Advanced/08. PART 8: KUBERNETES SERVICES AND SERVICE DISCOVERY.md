## Stable Networking for Dynamic Pods

---

# 1. Goal


# 2. The Networking Problem

Suppose your Deployment maintains three Pods:

```text
Deployment: web
replicas: 3
```

Current state:

```text
Pod A
10.244.1.10

Pod B
10.244.2.14

Pod C
10.244.3.21
```

A client application could theoretically connect directly to:

```text
10.244.1.10:8080
```

But then Pod A disappears.

The Deployment replaces it.

Replacement:

```text
Pod D
10.244.2.37
```

The client still knows:

```text
10.244.1.10
```

That address no longer represents the desired application backend.

---

# 3. Why Pod IPs Are Not Stable Application Interfaces

Pods are designed to be replaceable workload instances.

A Pod can disappear because of:

```text
Deployment rollout

ReplicaSet reconciliation

Node failure

Eviction

Scaling

Manual deletion

Scheduling changes

Application recovery
```

The replacement Pod is a:

```text
new Kubernetes object
```

and can receive:

```text
a new IP address.
```

Therefore:

```text
Pod IP
≠
Stable application identity
```

---

# 4. Pod IPs Are Still Important

Do not misunderstand the previous statement.

Pod IPs are real network identities inside the cluster network.

Pods communicate using networking provided by the cluster.

The problem is not:

```text
Pod IPs are useless.
```

The problem is:

```text
Clients should normally not depend on individual,
replaceable Pod IPs as the stable interface
for a replicated application.
```

---

# 5. Application Identity vs Pod Identity

Suppose the application is:

```text
payments-api
```

Today:

```text
payments-api Pod A
10.244.1.11

payments-api Pod B
10.244.2.19

payments-api Pod C
10.244.3.27
```

Tomorrow:

```text
payments-api Pod D
10.244.1.42

payments-api Pod E
10.244.2.51

payments-api Pod F
10.244.3.63
```

The Pods changed.

But the logical application is still:

```text
payments-api
```

Kubernetes needs a stable abstraction representing:

```text
the application
```

rather than:

```text
one temporary application instance.
```

That abstraction is the:

```text
Service
```

---

# 6. What Is a Kubernetes Service?

A Kubernetes Service is an API object that provides a stable network abstraction for a logical group of backend endpoints.

For the common selector-based case:

```text
Service
↓
Selector
↓
Matching Pods
```

The Service provides a stable way for clients to reach those backends even as individual Pods change.

---

# 7. Basic Service Mental Model

Without Service:

```text
Client
↓
Pod IP
```

Problem:

```text
Pod disappears
↓
IP changes
↓
Client breaks
```

With Service:

```text
Client
↓
Service
↓
Pod A
Pod B
Pod C
```

Pod B disappears.

New Pod D appears.

Now:

```text
Client
↓
Same Service
↓
Pod A
Pod C
Pod D
```

The client-facing Service identity remains stable.

# 8. Service Architecture

A simplified architecture is:

```text
Client
↓
Service DNS Name
↓
Service ClusterIP
↓
Service Proxy / Dataplane
↓
Backend Endpoint
↓
Pod
```

The API-level backend information is commonly represented using:

```text
EndpointSlices
```

So another useful mental model is:

```text
Service
↓
Selector
↓
EndpointSlices
↓
Pod IPs
```

---

# 9. Important Distinction

A Service does not:

```text
contain the application
```

and it does not:

```text
create Pods.
```

The Deployment creates/manages application workload state.

The Service provides network access to appropriate backends.

Think:

```text
Deployment
↓
manages
↓
Pods
```

while:

```text
Service
↓
selects / routes toward
↓
Pods
```

These are separate Kubernetes resources.

```text

Pods

↑
```

Or from the request perspective:

```text

↓
Service
↓

```

From the workload-management perspective:

```text

↓
ReplicaSet
↓
Pods
```

The Pods connect the two models.

# 22. `port` vs `targetPort`

Memorize:

```text
port
=
port exposed by the Service
```

```text
targetPort
=
backend port to which Service traffic is directed
```

Example:

```yaml
ports:
  - port: 80
    targetPort: 8080
```

means:

```text
Client
↓
Service:80
↓
Pod:8080
```

---

# 23. They Do Not Need to Match

This is valid:

```yaml
port: 80
targetPort: 8080
```

This is also valid:

```yaml
port: 443
targetPort: 8443
```

The Service-facing port and application-facing port can differ.

---

# 24. targetPort Can Be Named

Suppose your Pod declares:

```yaml
ports:
  - name: http
    containerPort: 8080
```

The Service can use:

```yaml
ports:
  - port: 80
    targetPort: http
```

This means:

```text
Service port 80
↓
Pod port named "http"
```

---

# 25. Why Named targetPorts Are Useful

Suppose the application changes:

```text
8080
↓
9090
```

but the Pod port remains named:

```text
http
```

The Service can continue targeting:

```yaml
targetPort: http
```

This can make application port transitions cleaner.

# 29. Service Type

A Service can have different exposure behavior.

The core Service types you need to know are:

```text
ClusterIP

NodePort

LoadBalancer

ExternalName
```

Each solves a different networking problem.

---

# 30. Service Type Hierarchy

A useful mental model is:

```text
ClusterIP
↓
Internal cluster Service
```

```text
NodePort
↓
ClusterIP behavior
+
Node-level port exposure
```

```text
LoadBalancer
↓
External load-balancer integration
+
Service networking underneath
```

```text
ExternalName
↓
DNS alias to an external DNS name
```

ExternalName behaves differently from the other three.

---

# 31. ClusterIP

`ClusterIP` is the default Service type.

Example:

```yaml
spec:
  type: ClusterIP
```

If `type` is omitted, the default is:

```text
ClusterIP
```

---

# 32. What ClusterIP Provides

A ClusterIP Service normally receives a virtual IP from the cluster's Service IP range.

Example:

```text
10.96.20.50
```

Clients inside the cluster can use the Service through:

```text
Service DNS name
```

or:

```text
ClusterIP
```

DNS is usually preferred for application configuration.

---

# 33. ClusterIP Mental Model

```text
Client Pod
↓
web:80
↓
DNS resolves Service
↓
ClusterIP
↓
Service dataplane
↓
Backend Pod
```

---

# 34. ClusterIP Is Usually Internal

A ClusterIP is normally intended for access within the cluster.

Your laptop outside the cluster generally cannot simply:

```text
curl 10.96.20.50
```

because Service IPs are commonly not routable from outside the cluster.

---

# 35. Stable Does Not Mean Permanent Forever

A Service's ClusterIP provides stable addressing for the lifetime/configuration of that Service.

Do not interpret this as:

```text
This exact IP is globally permanent forever.
```

If the Service is deleted and recreated, addressing can change.

For applications, prefer:

```text
Service DNS names
```

over hardcoding Service IPs.

---

# 36. Why DNS Is Better Than Hardcoded ClusterIP

Bad:

```text
PAYMENTS_API=10.96.20.50
```

Better:

```text
PAYMENTS_API=http://payments-api
```

or cross-namespace:

```text
PAYMENTS_API=http://payments-api.production
```

DNS gives logical application identity.

---

# 37. Endpoint Concept

A Service needs actual destinations.

Those destinations are represented as endpoints.

Conceptually:

```text
Service: web
↓
Endpoints:
10.244.1.20:8080
10.244.2.31:8080
10.244.3.42:8080
```

Modern Kubernetes represents Service backend information primarily using:

```text
EndpointSlice
```

objects.

---

# 38. EndpointSlice

EndpointSlices provide a scalable representation of network endpoints associated with a Service.

Conceptually:

```text
Service
↓
EndpointSlice
├── Pod A IP
├── Pod B IP
└── Pod C IP
```

For larger Services, multiple EndpointSlices can exist.

---

# 39. Why EndpointSlice Exists

Imagine a Service with:

```text
10 Pods
```

Now imagine:

```text
10,000 Pods
```

A single giant endpoint object becomes inefficient to update and distribute.

EndpointSlices divide endpoint information into manageable groups.

This improves scalability.

---

# 40. Legacy Endpoints Object

You may encounter:

```bash
kubectl get endpoints
```

or:

```bash
kubectl get ep
```

Historically, Kubernetes used the Endpoints API heavily for Service backend information.

Modern Kubernetes uses:

```text
EndpointSlice
```

as the scalable API.

For learning and troubleshooting, understand both names, but prioritize EndpointSlices.

EndpointSlices can contain information such as:


For ordinary Service troubleshooting, focus first on:

```text

```

# 44. Service Selector to EndpointSlice Flow

For selector-based Services:

```text
Service created
↓
Service selector evaluated
↓
Matching Pods discovered
↓
EndpointSlice controller manages EndpointSlices
↓
Backend Pod addresses represented
↓
Service dataplane uses backend information
```

This relationship is central to Kubernetes networking.

```text

10.244.2.20
```

```text

```


```text

```

The client still uses:

```text

```

# 46. Service Is Not a Traditional Process Listening on ClusterIP

A common beginner mental model is:

```text
There must be a Service process
running at the ClusterIP.
```

That is misleading.

The Service IP is generally:

```text
virtual networking state
```

implemented by the cluster's Service dataplane.

There is not necessarily an ordinary user-space server process bound to that ClusterIP like an application would bind a normal host socket.

---

# 47. Service Dataplane

Traditionally Kubernetes commonly uses:

```text
kube-proxy
```

on nodes to implement Service traffic forwarding.

Depending on the cluster/network implementation, Service networking may instead be implemented by another dataplane.

Examples can involve:

```text
iptables

nftables

IPVS in existing deployments

eBPF-based implementations
```

Do not assume every cluster uses the exact same packet-processing mechanism.


# 54. Namespace-Qualified Service Name

A client in another namespace can use:

```text
web.service-lab
```

This identifies:

```text
Service = web
Namespace = service-lab
```

---

# 55. Fully Qualified Service DNS Name

The conventional cluster DNS form is:

```text
<service>.<namespace>.svc.<cluster-domain>
```

A common default cluster domain is:

```text
cluster.local
```

Therefore:

```text
web.service-lab.svc.cluster.local
```

is a typical Service FQDN.

Do not hardcode `cluster.local` as an absolute universal requirement because cluster administrators can configure another cluster domain.

---

# 56. DNS Name Hierarchy

Example:

```text
web.service-lab.svc.cluster.local
```

Break it down:

```text
web
↓
Service name
```

```text
service-lab
↓
Namespace
```

```text
svc
↓
Kubernetes Service DNS hierarchy
```

```text
cluster.local
↓
Cluster DNS domain in a common configuration
```

---

# 57. Same-Namespace Resolution

Client:

```text
Namespace:
service-lab
```

Service:

```text
web
```

Client can usually use:

```text
web
```

because the Pod's DNS search configuration expands the short name.

---

# 58. Cross-Namespace Resolution

Client:

```text
Namespace:
frontend
```

Service:

```text
web

Namespace:
service-lab
```

Using only:

```text
web
```

normally searches for `web` in the client's own namespace.

Use:

```text
web.service-lab
```

or the FQDN.

---

# 59. Why Namespace Matters

Suppose:

```text
development
└── database

production
└── database
```

A Pod in:

```text
development
```

using:

```text
database
```

normally resolves the Service in:

```text
development
```

A Pod needing production's Service would need to qualify the namespace:

```text
database.production
```

Namespace-aware DNS prevents every Service name from needing to be globally unique across the cluster.

---

# 60. Pod DNS Search Domains

Inside a Linux Pod, inspect:

```bash
cat /etc/resolv.conf
```

You may see search entries conceptually resembling:

```text
service-lab.svc.cluster.local
svc.cluster.local
cluster.local
```

This allows short names such as:

```text
web
```

to be expanded during DNS resolution.

Exact resolver configuration can vary by cluster.

---

# 61. DNS Policy

The common default Pod DNS policy is:

```text
ClusterFirst
```

This means cluster-related DNS names are resolved through the cluster DNS configuration, while non-cluster queries can be forwarded upstream according to cluster DNS configuration.

You will not need to customize DNS policy for most beginner workloads.

```text

↓

```

# 64. Headless Service Preview

A Service can be configured:

```yaml

```

This creates a:

```text

```

For headless Services, DNS behavior differs and can return backend addresses rather than a normal Service ClusterIP.

This is especially useful in some stateful/discovery scenarios.

You will encounter it again with StatefulSets.

```yaml
      targetPort: 8080
```

If you omit `nodePort`, Kubernetes normally allocates one from the configured NodePort range.

---

# 74. Default NodePort Range

The commonly configured default NodePort range is:

```text
30000-32767
```

Cluster administrators can configure a different range.

Do not assume this range is immutable across every Kubernetes environment.

---

# 75. NodePort Fields

Suppose:

```yaml
ports:
  - port: 80
    targetPort: 8080
    nodePort: 30080
```

Then:

```text
port = 80

targetPort = 8080

nodePort = 30080
```

---

# 76. NodePort Traffic Mental Model

```text
External / reachable client
↓
NodeIP:30080
↓
NodePort Service
↓
Service backend selection
↓
PodIP:8080
↓
Application
```

---

# 77. NodePort Still Has a ClusterIP

A NodePort Service also normally has ClusterIP behavior.

You can access it internally through:

```text
Service ClusterIP:port
```

and through eligible node addresses using:

```text
NodeIP:nodePort
```

---

# 78. NodePort Does Not Mean Pod Port

A classic mistake:

```text
nodePort: 30080
```

does not mean:

```text
The container listens on 30080.
```

The application might still listen on:

```text
8080
```

Flow:

```text
Node:30080
↓
Service:80
↓
Pod:8080
```

---

# 79. Manually Choosing nodePort

You can request:

```yaml
nodePort: 30080
```

if that value is allowed and available.

But in many situations it is easier and safer to let Kubernetes allocate the NodePort unless you specifically require a fixed value.

---

# 80. NodePort Production Considerations

NodePort is useful for:

```text
learning

testing

certain infrastructure architectures

integration with external load balancers
```

But directly exposing many applications through manually managed NodePorts can become operationally awkward.

You must consider:

```text
firewalls

node reachability

port management

security

load balancing

node lifecycle
```

---

# 81. Local Cluster NodePort Warning

In environments such as:

```text
kind

minikube

k3d

Docker Desktop
```

the Kubernetes nodes may themselves run inside:

```text
containers

VMs

special networking layers
```

Therefore:

```text
NodeIP:NodePort
```

may not be directly reachable from your host in the same way as a traditional bare-metal cluster.

The exact access method depends on your local cluster implementation.

Do not mistake a local networking limitation for a Kubernetes Service failure.

# 82. LoadBalancer

A Service of type:

```text

```

requests external load-balancer integration from the environment.

Example:

```yaml
apiVersion: v1

  name: web-lb
  namespace: service-lab

spec:
  type: LoadBalancer

  selector:
    app: web

      port: 80
```

# 83. LoadBalancer Mental Model

In a supporting cloud environment:

```text
Internet / External Client
↓
Cloud Load Balancer
↓
Kubernetes Service
↓
Backend Pods
```

The exact implementation varies by provider and cluster architecture.

---

# 84. LoadBalancer Provisioning

Creating:

```yaml
type: LoadBalancer
```

does not mean the Kubernetes API server itself magically becomes an Internet load balancer.

Instead, integration with infrastructure components such as:

```text
cloud-controller functionality

provider-specific controllers

load-balancer controllers
```

can provision/configure external infrastructure.

Later, in a supported environment:

# 86. `<pending>` Is Not Automatically a Failure

On a local cluster with no load-balancer integration:


```text

```

---

# 87. LoadBalancer and NodePort Relationship

Traditionally, Kubernetes implementations often implement LoadBalancer Services on top of NodePort behavior.

Conceptually:

```text
External Load Balancer
↓
NodePort / Service implementation
↓
Backend Pods
```

Modern provider implementations can differ, and supported environments can configure load-balanced Services without allocating NodePorts.

Do not assume every LoadBalancer implementation has exactly the same packet path.

---

# 88. LoadBalancer Is Not Ingress

Do not confuse:

```text
Service type LoadBalancer
```

with:

```text
Ingress
```

or:

```text
Gateway API
```

A LoadBalancer Service exposes a Service using external load-balancer infrastructure.

Ingress and Gateway provide higher-level traffic-routing concepts, especially for HTTP/HTTPS and shared routing.

You will study those later.

---

# 89. ExternalName

`ExternalName` is fundamentally different.

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-database
  namespace: service-lab

spec:
  type: ExternalName
  externalName: database.example.com
```

---

# 90. ExternalName Behavior

Instead of selecting Pods, Kubernetes DNS provides an alias-style DNS response.

Conceptually:

```text
Client
↓
external-database
↓
Kubernetes DNS
↓
database.example.com
```

There is no normal selector-based Pod backend relationship.

---

# 91. ExternalName Does Not Proxy Traffic

This is critical.

ExternalName does not mean:

```text
Kubernetes receives traffic
↓
proxies it to external server
```

Instead:

```text
DNS aliasing
```

is involved.

The client ultimately connects to the resolved external destination.

---

# 92. ExternalName Has No Selector

Typical ExternalName:

```yaml
spec:
  type: ExternalName
  externalName: database.example.com
```

There is no:

```yaml
selector:
```

because the Service is not selecting Kubernetes Pods.

---

# 93. ExternalName Caution

Protocols that depend on hostname identity can behave unexpectedly when accessed through an alias.

Examples include:

```text
HTTP Host headers

TLS server-name verification
```

because the client-visible Service name can differ from the external server's expected hostname.

Understand the protocol before using ExternalName.


# 95. Service Without Selector

A Service does not always require:

```yaml
selector:
```

You can create a Service without a selector and manage backend EndpointSlices separately.

This can be useful for integrating Kubernetes Service discovery with destinations not represented by normal selected Pods.

---

# 96. Why Selectorless Services Matter

Imagine:

```text
Kubernetes application
↓
needs legacy database
↓
database runs outside Kubernetes
```

You may want a Kubernetes Service identity representing that backend.

Advanced configurations can use:

```text
Service without selector
+
manually/custom-managed EndpointSlice
```

This is different from ExternalName.

---

# 97. Selector-Based vs Selectorless

Selector-based:

```text
Service
↓
selector
↓
Pods
↓
EndpointSlices managed automatically
```

Selectorless:

```text
Service
↓
No Pod selector
↓
Endpoints supplied through other mechanisms
```

For this part, your labs will primarily use selector-based Services.

---

# 98. Ready Pods and Service Backends

For ordinary selector-based Service behavior, Pod readiness matters.

A Pod that is not Ready is normally not treated as a ready backend for ordinary Service traffic.

Conceptually:

```text
Pod Running
+
Ready=True
↓
eligible ready backend
```

whereas:

```text
Pod Running
+
Ready=False
↓
normally not a ready Service backend
```

This is why readiness probes become extremely important.

---

# 99. Readiness Connects Deployment and Service Behavior

Deployment:

```text
Uses readiness/availability
to determine rollout progress
```

Service:

```text
Uses endpoint readiness information
to avoid ordinary traffic to unready backends
```

Therefore:

```text
readinessProbe
```

affects both:

```text
deployment safety
```

and:

```text
traffic safety.
```

```yaml
  - name: http

```

```yaml
  - name: http
    port: 80
    targetPort: http

  - name: metrics
```

# 183. Multi-Port Mental Model

```text
Service
├── http:80
│   ↓
│   Pod:http
│
└── metrics:9090
    ↓

```

---

# 184. Service Does Not Check Application Semantics

A Service can have:

```text
correct selector

correct EndpointSlice

correct port
```

while the application returns:

```text
HTTP 500
```

Kubernetes Service networking cannot determine whether the business logic is correct.

Networking success and application correctness are different layers.

---

# 185. Load Distribution

When a Service has multiple eligible endpoints:

```text
Pod A

Pod B

Pod C
```

the Service dataplane can distribute connections/traffic among backends according to the implementation.

Do not assume:

```text
strict round-robin request-by-request behavior
```

across every Kubernetes implementation and protocol.

---

# 186. Connection-Level Reality

For TCP, once a connection is established to a backend, multiple application requests can travel over that same connection.

Therefore observing:

```text
many requests hitting the same Pod
```

does not automatically mean Service load balancing is broken.

Application connection reuse matters.

---

# 187. Session Affinity

Services support:

```text
sessionAffinity
```

The default is:

```text
None
```

A Service can use:

```text
ClientIP
```

session affinity in supported scenarios.

Example:

```yaml
spec:
  sessionAffinity: ClientIP
```

This can influence backend selection for a client.

Use it only when application requirements justify it.

---

# 188. Why Stateless Applications Are Easier

If every backend is interchangeable:

```text
Request
↓
Pod A
```

or:

```text
Request
↓
Pod B
```

should produce equivalent application behavior.

That makes Service-based load distribution much simpler.

Applications that keep critical session state only in local Pod memory can create problems when traffic reaches another replica.

---

# 189. Better State Pattern

Instead of:

```text
User session
↓
stored only inside Pod A
```

prefer architectures where necessary shared state lives in appropriate external systems such as:

```text
database

cache

distributed state service
```

when application requirements permit.

Then replicas remain more interchangeable.

---

# 190. Service and Rolling Deployment

Part 7:

```text
Old Pods
↓
New Pods
```

Part 8 adds:

```text
Service
↓
ready backend endpoints
```

During a well-designed rollout:

```text
Old ready Pods
+
New ready Pods
```

can temporarily coexist behind the same Service.

---

# 191. Rollout Traffic Flow

Conceptually:

```text
Service
↓
EndpointSlice
├── v1 Pod
├── v1 Pod
└── v2 Pod
```

As rollout progresses:

```text
Service
↓
EndpointSlice
├── v1 Pod
├── v2 Pod
└── v2 Pod
```

Eventually:

```text
Service
↓
EndpointSlice
├── v2 Pod
├── v2 Pod
└── v2 Pod
```

The Service name did not change.

---

# 192. This Is Why Readiness Is Critical

New version starts.

But imagine it requires:

```text
30 seconds
```

before it can safely serve traffic.

If Kubernetes considers it Ready too early:

```text
Service
↓
sends traffic
↓
application not actually ready
↓
users see failures
```

Correct readiness configuration protects the Service backend set.

---

# 193. Pod Termination and Service Traffic

During Pod termination, Kubernetes components work to update endpoint readiness/termination state and remove the Pod from normal Service traffic.

Application graceful shutdown still matters.

There can be propagation timing across:

```text
API

EndpointSlices

Service dataplane

external load balancers

application connections
```

Production applications should tolerate distributed-system timing.

---

# 194. Service Discovery Is Dynamic

Do not think:

```text
DNS returns a Pod
```

for normal ClusterIP Services.

Think:

```text
DNS identifies stable Service
↓
Service networking dynamically maps traffic
↓
current backend endpoints
```

That distinction is essential.

# 210. Common Mistake: Service Selector Matches Deployment, Not Pods

Remember:

```text
Service selector
```

must match:

```text
Pod labels
```

not merely labels on the Deployment object's own metadata.

Example:

```yaml
metadata:
  labels:
    team: platform
```

on the Deployment does not automatically mean Pods have:

```text
team=platform
```

The relevant Pod labels are under:

```yaml
spec:
  template:
    metadata:
      labels:
```

---

# 211. Common Mistake: Wrong Namespace

Service:

```text
production/api
```

Pods:

```text
development/api
```

A Service selector does not select Pods from another namespace.

Service and selector-based backend Pods must be in the appropriate same namespace relationship.

# 212. Common Mistake: Wrong targetPort

Service:

```yaml

```

Application:

```text
listens on 3000
```

Result:

```text

but connection fails.
```

# 213. Common Mistake: Assuming containerPort Opens a Port

Manifest:

```yaml
containerPort: 8080
```

Application actually listens:

```text
3000
```

Kubernetes does not rewrite the application to listen on 8080 simply because the manifest declares `containerPort: 8080`.

Your process must actually listen on the expected port.

# 214. Common Mistake: Testing ClusterIP From Laptop

User runs:

```bash
curl http://10.96.x.x
```

from a normal laptop shell outside the cluster.

It fails.

They conclude:

```text
Service broken.
```

Not necessarily.

ClusterIP is usually only routable within cluster networking.

Test from a Pod first.

# 215. Common Mistake: Expecting LoadBalancer Locally

User creates:

```yaml

```

on a simple local cluster.

Sees:

```text

```

Concludes:

```text

```

No.

# 216. Common Mistake: Confusing NodePort With port

Given:

```yaml
port: 80
targetPort: 8080
nodePort: 30080
```

Client inside cluster may use:

```text
Service:80
```

External reachable node path may use:

```text
NodeIP:30080
```

Backend receives traffic at:

```text
Pod:8080
```

Three distinct values.

# 217. Common Mistake: Hardcoding Pod IP

Bad configuration:

```text
BACKEND_URL=http://10.244.2.17:8080
```

After rollout:

```text
Pod disappears
```

Application breaks.

Use:

```text
Service DNS
```

where appropriate.

---

# 218. Common Mistake: Hardcoding ClusterIP

Better than Pod IP in terms of stability, but still unnecessary in most application configurations.

Prefer:

```text
payments-api
```

instead of:

```text
10.96.55.20
```

DNS gives human-readable logical identity and avoids unnecessary coupling to a Service IP.

# 219. Common Mistake: Restarting CoreDNS First

Service unavailable.

Engineer immediately:

```text
restarts CoreDNS
```

But actual problem:

```text
Service selector typo.
```

Use evidence.

First determine whether:

```text

```

is actually failing.

# 220. Common Mistake: Restarting Pods When Service Has No Endpoints

Pods are healthy.

Service selector wrong.

Restarting Pods:

```text
does not repair the selector.
```

Fix desired configuration.

# 221. Common Mistake: Deleting and Recreating Service Without Understanding

This can:

```text
change Service IP

cause unnecessary disruption

hide the original evidence
```

Inspect first.

Understand root cause.

Then make the smallest correct change.

# 222. Common Mistake: Exposing Everything

Not every application needs:

```text
NodePort
```

or:

```text
LoadBalancer
```

Internal applications should generally remain internal unless external access is actually required.

Apply:

```text
least exposure
```

just as you apply:

```text

```

# 223. Service Security Model

Ask:

```text
Who needs to access this application?

From where?

On which port?

Using which protocol?

Should it be internal only?

Should it be externally reachable?

Is encryption required?

```

Service exposure is part of security architecture.

# 224. ClusterIP Does Not Automatically Mean Secure

A ClusterIP is normally internal to the cluster.

That does not mean:

```text
every Pod should be allowed to access it.
```

Without network isolation, many cluster workloads may be able to communicate freely.

Later you will use:

```text
NetworkPolicy
```

to restrict traffic.

---

# 225. LoadBalancer Does Not Automatically Mean Secure

A public load balancer can expose an application to the Internet.

You still need to consider:

```text
TLS

authentication

authorization

firewalls/security groups

WAF

rate limiting

application security

network policy

logging

monitoring
```

Exposure is not security.

# 226. Service DNS Does Not Provide Authorization

If:

```text
frontend
```

can resolve:

```text
payments-api
```

that only means:

```text
it can discover the name/address.
```

DNS resolution does not mean:

```text
the caller is authorized to perform payment operations.
```

Application authentication and authorization remain separate concerns.

# 230. Service Names Become Architecture

Once applications depend on:


Service names become part of application configuration and operational contracts.

Changing Service names casually can break consumers.

Treat stable service naming as an architectural decision.

# 231. DNS Naming Best Practices

Prefer names that describe:

```text
logical application capability
```

Examples:

```text
payments-api

orders-api

inventory

redis

user-service
```

Avoid names based on temporary deployment details such as:

```text
payments-v7-pod-group-final
```

unless version-specific routing is intentionally part of the architecture.

# 232. Service and Versioning

During a normal rolling Deployment update:

```text
Service
```

usually remains unchanged.

Backend versions transition behind it.

```text
Service: payments-api
↓
v1 Pods
```

becomes:

```text
Service: payments-api
↓
v1 + v2 Pods
```

then:

```text
Service: payments-api
↓
v2 Pods
```

Stable service identity enables application evolution.

# 233. Blue/Green Preview

```text

Deployment Green
```

A Service selector can be changed to point from:

```text

```

to:

```text

```

This can switch traffic between groups.

That is an advanced deployment pattern.

The important lesson here is:

```text
Service selectors influence traffic destination.
```

Changing them can have immediate production consequences.

Do not assume Service alone provides every traffic-management capability.

# 271. DNS Caching Matters

For normal ClusterIP Services, the Service IP is relatively stable, which reduces the effect of backend churn on DNS clients.

For headless Services and external DNS patterns, DNS caching becomes more operationally visible.

# 292. Knowledge Check: Pod Networking

### 1. Why should clients normally not depend directly on Pod IPs?

Because Pods are replaceable and replacement Pods can receive different IP addresses.

### 2. Does a replacement Pod have the same identity as the deleted Pod?

No.

### 3. Are Pod IPs useless?

No.

They are important network identities, but they are not normally the stable application interface for replicated workloads.

---

# 293. Knowledge Check: Services

### 4. What is a Service?

A stable Kubernetes network abstraction for reaching a logical set of backend endpoints.

### 5. Does a Service create Pods?

No.

### 6. What usually connects a selector-based Service to Pods?

Labels and selectors.

### 7. What represents backend endpoint information in modern Kubernetes?

EndpointSlices.

---

# 294. Knowledge Check: Selectors

### 8. Service selector:

```text
app=web
```

Pod label:

```text
app=api
```

Will it match?

No.

### 9. Can healthy Pods exist while a Service has no selected backends?

Yes.

### 10. What should you inspect?

```text
Service selector

Pod labels

EndpointSlices

Pod readiness
```

---

# 295. Knowledge Check: Ports

### 11. What is `port`?

The port exposed by the Service.

### 12. What is `targetPort`?

The backend port to which Service traffic is directed.

### 13. What is `nodePort`?

The node-level port allocated/requested for a NodePort-style exposure.

### 14. Must `port` equal `targetPort`?

No.

### 15. Can targetPort use a named Pod port?

Yes.

---

# 296. Knowledge Check: ClusterIP

### 16. What is the default Service type?

ClusterIP.

### 17. Is ClusterIP normally designed for direct Internet access?

No.

### 18. Should applications normally hardcode ClusterIP?

Prefer Service DNS names.

### 19. Can ClusterIP change if the Service is deleted and recreated?

Yes.

---

# 297. Knowledge Check: NodePort

### 20. What does NodePort provide?

Service access through a port on eligible node addresses.

### 21. Does NodePort still have ClusterIP behavior?

Normally yes.

### 22. What is the commonly configured default NodePort range?

```text
30000-32767
```

### 23. Can the range be changed?

Yes.

### 24. Does NodePort equal the application container port?

Not necessarily.

---

# 298. Knowledge Check: LoadBalancer

### 25. What does `type: LoadBalancer` request?

External load-balancer integration from the supporting environment.

### 26. Does Kubernetes itself guarantee every environment can provision one?

No.

### 27. What can `<pending>` mean on a local cluster?

No external load-balancer implementation is available.

### 28. Can LoadBalancer resources cost money in cloud environments?

Yes.

---

# 299. Knowledge Check: ExternalName

### 29. Does ExternalName select Pods?

No.

### 30. Does it proxy traffic?

No.

### 31. What does it primarily provide?

DNS aliasing to another DNS name.

### 32. What protocols may require care?

Protocols sensitive to hostname identity, such as HTTP and TLS.

# 300. Knowledge Check: DNS

### 33. What commonly provides cluster DNS?

CoreDNS.

### 34. Same namespace Service name?

```text
web
```

### 35. Namespace-qualified?

```text
web.service-lab
```

### 36. Typical FQDN?

```text
web.service-lab.svc.cluster.local
```

assuming `cluster.local` is the configured cluster domain.

### 37. Does normal Service DNS usually resolve directly to every Pod IP?

No.

For a normal ClusterIP Service, it resolves to the Service ClusterIP.

---

# 301. Knowledge Check: EndpointSlices

### 38. Why do EndpointSlices exist?

To represent Service backend endpoints in a scalable way.

### 39. Can one Service have multiple EndpointSlices?

Yes.

### 40. What happens when Pods are replaced?

Endpoint information changes to reflect current eligible backends.

### 41. Does the client need to learn every new Pod IP?

No.

The client continues using the Service identity.
