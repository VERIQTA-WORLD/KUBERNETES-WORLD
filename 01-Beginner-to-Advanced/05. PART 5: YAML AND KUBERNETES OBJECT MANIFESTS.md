# PART 5: YAML AND KUBERNETES OBJECT MANIFESTS

## Learn to Read and Write Kubernetes Manifests Correctly

---

# 1. Goal

In Part 4, you learned how `kubectl` communicates with the Kubernetes API.

You learned:

```text
kubectl
↓
kubeconfig
↓
API Server
↓
Kubernetes API
↓
Objects
```

Now we move to one of the most important Kubernetes skills:

```text
Writing the objects yourself.
```

The goal of this part is not merely:

```text
Learn YAML syntax.
```

The real goal is:

```text
Understand Kubernetes object structure
↓
Express desired state correctly
↓
Validate manifests
↓
Submit them to the Kubernetes API
↓
Inspect what Kubernetes stored
↓
Compare desired configuration with live state
↓

```

By the end, you should be comfortable opening an unfamiliar Kubernetes manifest and explaining what it asks Kubernetes to do.

---

# 2. Why YAML Matters in Kubernetes

Kubernetes is API-driven.

You can interact with the API imperatively:

```bash
kubectl run web --image=nginx:alpine
```

But production Kubernetes relies heavily on declarative configuration.

Instead of saying:

```text
Create this Pod now.
```

you describe:

```text
This is the state I want.
```

For example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
    - name: nginx
      image: nginx:alpine
```

Then:

```bash
kubectl apply -f pod.yaml
```

Kubernetes processes that desired configuration.

---

# 4. YAML Is Not Kubernetes

This distinction is fundamental.

YAML is a general-purpose data serialization format.

Kubernetes uses YAML because it is convenient for humans to write structured configuration.

But:

```text
YAML
≠
Kubernetes
```

A file can be perfectly valid YAML and completely invalid Kubernetes configuration.

For example:

```yaml
favoriteFood: rice
temperature: hot
country: Nigeria
```

This can be valid YAML.

It is not a valid Kubernetes object manifest.

Therefore you must understand two things separately:

```text
YAML Syntax
+
Kubernetes API Schema
```

---

# 5. YAML vs Kubernetes Validation

Consider:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  imaginaryField: hello
```

The YAML parser may understand this perfectly.

But Kubernetes may reject it because:

```text
imaginaryField
```

is not a valid field in that part of the Pod schema.

Therefore:

```text
Valid YAML
↓
Does NOT automatically mean
↓
Valid Kubernetes manifest
```

---

# 6. YAML Basics

YAML commonly represents:

```text
Mappings
Lists
Scalars
Nested structures
```

Kubernetes manifests combine all of them.

---

# 7. Key-Value Pairs

The simplest YAML structure is:

```yaml
name: web
```

Think:

```text
key
:
value
```

Here:

```text
key   = name
value = web
```

Another example:

```yaml
replicas: 3
```

Here:

```text
key   = replicas
value = 3
```

---

# 8. Strings

Examples:

```yaml
name: web
environment: production
message: "hello world"
```

Strings can often be written without quotes.

Quotes are useful when values could be ambiguous or contain characters that make interpretation less obvious.

For clarity, do not randomly quote everything and do not randomly remove quotes from everything.

Understand the value you intend to represent.

---

# 9. Numbers

Example:

```yaml
replicas: 3
```

This is conceptually a numeric value.

Compare:

```yaml
replicas: "3"
```

The second value is a string.

Whether Kubernetes accepts either depends on the schema of the field.

Kubernetes API schemas have types.

Do not assume:

```text
3
```

and:

```text
"3"
```

are interchangeable.

---

# 10. Booleans

Examples:

```yaml
enabled: true
debug: false
```

Again, compare:

```yaml
enabled: "true"
```

The latter is a string.

Type matters.

---

# 11. YAML Mappings

A mapping contains key-value relationships.

Example:

```yaml
metadata:
  name: web
  namespace: production
```

Conceptually:

```text
metadata
│
├── name: web
└── namespace: production
```

Indentation expresses nesting.

---

# 12. YAML Lists

Lists use:

```text
-
```

Example:

```yaml
containers:
  - name: web
    image: nginx:alpine
```

Conceptually:

```text
containers
↓
List
↓
Item 1
├── name
└── image
```

---

# 13. Multiple List Items

Example:

```yaml
containers:
  - name: application
    image: example/application:1.0

  - name: helper
    image: example/helper:1.0
```

Now:

```text
containers
│
├── Container 1
│   ├── name: application
│   └── image: ...
│
└── Container 2
    ├── name: helper
    └── image: ...
```

This becomes important when you study multi-container Pods.

---

# 14. Nested Structures

Kubernetes manifests are deeply nested.

Example:

```yaml
spec:
  containers:
    - name: web
      image: nginx:alpine
      ports:
        - containerPort: 80
```

Read from left to right conceptually:

```text
spec
↓
containers
↓
first container
↓
ports
↓
first port
↓
containerPort
```

---

# 15. Indentation Matters

YAML uses indentation to represent hierarchy.

Correct:

```yaml
metadata:
  name: web
```

Incorrect structure:

```yaml
metadata:
name: web
```

The second example no longer expresses `name` as a child of `metadata`.

---

# 16. Use Spaces, Not Tabs

For YAML indentation, use spaces.

A common convention is:

```text
2 spaces per indentation level
```

Example:

```yaml
spec:
  containers:
    - name: web
      image: nginx:alpine
```

Consistency matters more than trying to make indentation visually decorative.

---

# 17. Comments

YAML comments begin with:

```text
#
```

Example:

```yaml
# Web application Pod
apiVersion: v1
kind: Pod
```

Comments are useful for humans.

Do not use comments to compensate for confusing configuration.

Prefer clear structure and names first.

---

# 18. The Standard Kubernetes Object Structure

Most Kubernetes object manifests have the following top-level structure:

```yaml
apiVersion:
kind:
metadata:
spec:
```

A live object commonly also contains:

```yaml
status:
```

Think:

```text
apiVersion
↓
Which API?

kind
↓
What object?

metadata
↓
Which object?

spec
↓
What do I want?

status
↓
What does Kubernetes observe?
```

This mental model should become automatic.

---

# 19. A Complete Beginner Example

Create:

```text
pod.yaml
```

with:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: manifest-lab
  labels:
    app: web
    environment: lab
spec:
  containers:
    - name: nginx
      image: nginx:alpine
      ports:
        - containerPort: 80
```

Do not apply it yet.

First understand every line.

---

# 20. apiVersion

```yaml
apiVersion: v1
```

This tells Kubernetes:

```text
Use this API group/version for this object.
```

For a Pod:

```text
v1
```

refers to the core API group version.

---

# 21. kind

```yaml
kind: Pod
```

This tells Kubernetes:

```text
The object I am describing is a Pod.
```

`kind` determines which resource schema Kubernetes uses to interpret the rest of the object.

---

# 22. metadata

```yaml
metadata:
  name: web
  namespace: manifest-lab
```

Metadata identifies and describes the object.

Common metadata fields include:

```text
name
namespace
labels
annotations
```

Live objects contain additional server-managed metadata.

---

# 23. spec

```yaml
spec:
```

The specification expresses the desired state for resources that define a spec.

For this Pod:

```yaml
spec:
  containers:
    - name: nginx
      image: nginx:alpine
```

you are saying:

```text
I want this Pod to contain a container
↓
named nginx
↓
using nginx:alpine
```

---

# 24. status

A live Pod may contain:

```yaml
status:
  phase: Running
```

You normally do not write this in your source manifest.

Why?

Because:

```text
spec
↓
Desired state
↓
Usually authored by user/client

status
↓
Observed state
↓
Maintained by Kubernetes components
```

---

# 25. Desired State vs Observed State

Think:

```text
spec
=
What should exist
```

```text
status
=
What Kubernetes currently sees
```

For example:

```text
Desired:
Container should run nginx:alpine

Observed:
Container is running successfully
```

or:

```text
Desired:
Container should run nginx:alpine

Observed:
Image cannot be pulled
```

Desired and observed state can temporarily differ.

---

# 26. Why Users Normally Do Not Author status

Suppose you write:

```yaml
status:
  phase: Running
```

That does not magically make a broken Pod run.

The Pod's actual state is determined by what happens in the cluster.

You cannot solve:

```text
Container failed
```

by declaring:

```text
status: Running
```

Kubernetes components own status reporting for normal resources.

---

# 27. metadata.name

Example:

```yaml
metadata:
  name: payments-api
```

The name identifies the object within its scope.

For namespaced resources, uniqueness applies within the namespace for that resource type.

Therefore:

```text
Pod/payments-api in dev
```

and:

```text
Pod/payments-api in production
```

can both exist.

---

# 28. Kubernetes Resource Names

Object names are not arbitrary free-form text.

Different Kubernetes resources can have naming constraints.

A common pattern for many resources follows DNS-style naming rules.

Safe naming habits include:

```text
lowercase letters

numbers

hyphens
```

Example:

```text
payments-api
```

Avoid inventing names such as:

```text
Payments API!!!
```

Always check the naming requirements of the resource you are creating.

---

# 29. Good Names

Examples:

```text
payments-api

checkout-worker

inventory-service

web-frontend
```

Good names communicate purpose.

Poor:

```text
pod1

test2

thing

new-app-final-final
```

Production object names should help operators understand what they are looking at.

---

# 30. metadata.namespace

Example:

```yaml
metadata:
  namespace: production
```

This places a namespaced object in:

```text
production
```

If a manifest explicitly contains a namespace, that namespace becomes part of the desired object identity.

---

# 31. Namespace in File vs Command

Manifest:

```yaml
metadata:
  namespace: manifest-lab
```

Command:

```bash
kubectl apply -f pod.yaml
```

The file already specifies the namespace.

You can also work with manifests that omit the namespace and provide namespace context separately.

For beginner labs, explicit namespaces often make object scope easier to understand.

---

# 32. Cluster-Scoped Resources

Not every resource accepts:

```yaml
metadata:
  namespace:
```

For example:

```text
Node
Namespace
PersistentVolume
ClusterRole
ClusterRoleBinding
```

are cluster-scoped resource types.

Do not blindly add namespace to every manifest.

Discover:

```bash
kubectl api-resources
```

and inspect:

```text
NAMESPACED
```

---

# 33. Labels

Labels are key/value metadata designed for identification and selection.

Example:

```yaml
metadata:
  labels:
    app: payments
    environment: production
    tier: backend
```

Think:

```text
Object
│
├── app=payments
├── environment=production
└── tier=backend
```

---

# 34. Why Labels Matter

Labels can be used by:

```text
kubectl selectors

Services

Workload controllers

Policies

Operational tooling

Monitoring

Automation
```

Labels are part of Kubernetes architecture, not merely descriptive decoration.

---

# 35. Good Label Design

Useful labels describe stable operational characteristics.

Examples:

```yaml
labels:
  app.kubernetes.io/name: payments-api
  app.kubernetes.io/component: backend
  app.kubernetes.io/part-of: payments-platform
```

Kubernetes documents a set of recommended common labels.

You do not need every recommended label in every beginner exercise, but production teams should establish consistent conventions.

---

# 36. Labels Should Not Store Large Arbitrary Data

Labels are intended for identifying and selecting objects.

Do not use labels for:

```text
long descriptions

large JSON documents

large configuration blobs

sensitive information
```

Use the correct Kubernetes mechanism for the data.

---

# 37. Label Selectors

A selector describes which labeled objects should match.

Example:

```text
app=web
```

You used selectors in Part 4:

```bash
kubectl get pods -l app=web
```

But selectors also appear inside Kubernetes objects.

---

# 38. Selector Mental Model

Imagine Pods:

```text
Pod A
app=web

Pod B
app=web

Pod C
app=worker
```

Selector:

```text
app=web
```

matches:

```text
Pod A
Pod B
```

not:

```text
Pod C
```

---

# 39. Selectors in Workload Objects

A Deployment uses a selector to identify the Pods that belong to it.

Simplified example:

```yaml
spec:
  selector:
    matchLabels:
      app: web
```

Its Pod template might contain:

```yaml
template:
  metadata:
    labels:
      app: web
```

These values must align correctly.

---

# 40. Selector Relationship

Think:

```text
Deployment Selector
app=web
↓
Matches
↓
Pod Template Labels
app=web
```

If they do not align, the manifest can be invalid or the relationship will not behave as intended, depending on the resource and mismatch.

This is why labels and selectors must be designed together.

---

# 41. Annotations

Annotations are metadata intended for non-identifying information.

Example:

```yaml
metadata:
  annotations:
    example.com/owner: "platform-team"
    example.com/runbook: "internal-runbook-reference"
```

Annotations are not normally used for selecting objects.

---

# 42. Labels vs Annotations

Think:

```text
Labels
↓
Identify and select
```

```text
Annotations
↓
Attach additional metadata
```

Labels:

```yaml
labels:
  app: payments
  environment: production
```

Annotations:

```yaml
annotations:
  example.com/change-ticket: "CHG-12345"
```

---

# 43. Annotation Use Cases

Annotations may contain information such as:

```text
tool metadata

build information

release metadata

change references

external system references

controller-specific settings
```

The exact usage depends on the platform and tooling.

---

# 44. Do Not Put Secrets in Annotations

Do not write:

```yaml
annotations:
  password: super-secret-password
```

Annotations are not secret storage.

Likewise, labels are not secret storage.

Sensitive data requires appropriate secret-management architecture.

Examples:

```yaml

```


```yaml
apiVersion: networking.k8s.io/v1
```

For:

think:

```text
v1
```

Run:

```bash

```

Find:

```text
pods

```

Inspect their:

```text
APIVERSION
```

```bash

```

---

# 50. Why API Versions Matter

A manifest written years ago may use an API version no longer served by a newer cluster.

For example:

```text
Old Manifest
↓
Deprecated API
↓
API Removed
↓
New Cluster
↓
Manifest Rejected
```

This is a real Kubernetes upgrade concern.

---

# 51. Do Not Blindly Copy Old Manifests

When copying Kubernetes configuration from:

```text
old blog posts

old repositories

old tutorials

old Stack Overflow answers
```

verify:

```text
apiVersion

kind

field structure

current Kubernetes support
```

A syntactically beautiful manifest can still target an obsolete API.

---

# 52. kind and API Version Work Together

This pair:

```yaml
apiVersion: v1
kind: Pod
```

tells Kubernetes which schema you intend.

A Deployment uses:

```yaml
apiVersion: apps/v1
kind: Deployment
```

A Job uses:

```yaml
apiVersion: batch/v1
kind: Job
```

Do not choose `apiVersion` and `kind` independently.

# 58. Read the Manifest Like an Engineer

Before running anything, answer:

```text

Which object kind?

What is the object's name?
```

# 59. Validate With kubectl

Run:

```bash
kubectl apply \
  --dry-run=client \
  -f pod.yaml
```

Then:

```bash
kubectl apply \
  --dry-run=server \
  -f pod.yaml
```

This introduces an important distinction.

---

# 60. Client vs Server Dry Run

Client dry run:

```text
kubectl
↓
Client-side processing
↓
No persisted API change
```

Server dry run:

```text
kubectl
↓
API Server
↓
Server-side processing
↓
Admission / validation as applicable
↓
No persisted object change
```

Server dry run generally provides stronger cluster-aware validation.

---

# 61. Why Client Dry Run Is Not Enough

A client-side dry run cannot prove:

```text
Your identity is authorized

The namespace exists

Admission policies accept the object

The cluster serves the requested API

All server-side rules will accept it
```

Therefore production validation should not rely solely on:

```bash
--dry-run=client
```

```bash

```

# 63. Compare Source and Live Object

Source:

```bash
cat pod.yaml
```

Live:

```bash
kubectl get pod web \
  -n manifest-lab \
  -o yaml
```

The live object is much larger.

Why?

Because Kubernetes adds information.

# 64. Server-Managed Information

The live object may include fields such as:

```text
uid

resourceVersion

creationTimestamp

managedFields

status

Pod IP

node assignment

conditions

container status
```

These are not all fields you should manually copy into your source manifest.

---

# 65. Source Manifest vs Live Object

Think:

```text
Source Manifest
↓
Desired Configuration
```

```text
Live Object
↓
Desired Configuration
+
Defaults
+
Server-Managed Metadata
+
Observed State
```

They serve different purposes.

---

# 66. Do Not Copy status Into Git

Suppose the live object contains:

```yaml

  phase: Running
```

Do not copy it into:

```text
pod.yaml
```

as if it were desired configuration.

Status belongs to observed state.

---

# 69. Do Not Ignore Parser Errors

The error may mention concepts such as:

```text
mapping

expected key

YAML

line number
```

Your first job is not:

```text
Search for a Kubernetes networking problem.
```

The request never reached that layer.

The document itself could not be parsed correctly.

---

# 70. Failure Layer

Think:

```text
File
↓
YAML Parsing
X
```

The failure happened before:

```text
Kubernetes API validation
```

This distinction makes troubleshooting faster.

---

# 71. Repair the YAML

Restore:

```yaml
metadata:
  name: web
  namespace: manifest-lab
```

Then:

```bash
kubectl apply \
  --dry-run=client \
  -f broken-yaml.yaml
```

Now the YAML parsing problem should be gone.

# 72. LAB 5: Valid YAML, Invalid Kubernetes Field

Modify a disposable copy:

```yaml
apiVersion: v1

  containers:
```


Read the validation response.

---

# 73. Failure Layer

This time:

```text
YAML Parser
↓
Success
↓
Kubernetes Object Processing
↓
Schema / Validation
X
```

Different failure.

Therefore:

```text
Valid YAML
≠
Valid Kubernetes
```

# 74. Use kubectl explain to Repair Fields

Run:

```bash
kubectl explain pod.spec
```

Search for:

```text
imaginaryField
```

It does not belong there.

Remove it.

Then rerun:

```bash
kubectl apply \
  --dry-run=server \
  -f invalid-field.yaml
```

This is the correct workflow:

```text
Error
↓
Inspect Schema
↓
```

```text
├── deployment.yaml
├── service.yaml
├── configmap.yaml
```

# 235. Knowledge Check

### 1. Is YAML Kubernetes?

No.

YAML is a serialization format used to represent Kubernetes object configuration.

### 2. What four top-level fields commonly appear in a Kubernetes source manifest?

```text
apiVersion

kind

metadata

spec
```

### 3. What additional major field commonly appears on live objects?

```text
status
```

### 4. What does spec represent?

Desired state/configuration.

### 5. What does status represent?

Observed state reported by Kubernetes.

---

# 236. Knowledge Check: Metadata

### 6. What does metadata.name do?

Identifies the object within its scope.

### 7. What does metadata.namespace do?

Specifies the namespace for a namespaced object.

### 8. What are labels for?

Identification, grouping and selection.

### 9. What are annotations for?

Additional non-identifying metadata.

### 10. Should secrets be stored in labels or annotations?

No.

---

# 237. Knowledge Check: API

### 11. What does apiVersion identify?

The API group/version used for the object.

### 12. What does kind identify?

The Kubernetes resource type.

### 13. How do you discover resource API versions?

```bash
kubectl api-resources
```

and related API discovery commands.

### 14. How do you inspect fields?

```bash
kubectl explain
```

### 15. Is Kubernetes release version the same thing as object apiVersion?

No.

---

# 238. Knowledge Check: YAML

### 16. What creates hierarchy in YAML?

Indentation.

### 17. What does `-` commonly indicate?

A list item.

### 18. Is `"3"` necessarily the same type as `3`?

No.

### 19. Can valid YAML be invalid Kubernetes configuration?

Yes.

### 20. What separates YAML documents in a multi-document file?

```yaml
---
```

---

# 239. Knowledge Check: Selectors

### 21. What is a selector?

A rule for matching objects using supported selection criteria such as labels.

### 22. What must a Deployment selector match?

The labels on its Pod template.

### 23. Must a Deployment selector include every Pod label?

No.

### 24. Can an existing `apps/v1` Deployment selector be casually changed?

No. The selector is immutable after creation.

### 25. Why are selector mistakes serious?

Selectors establish ownership/relationship between resources.

---

# 240. Knowledge Check: Declarative Workflow

### 26. What does `kubectl apply` do conceptually?

Submits declarative configuration so Kubernetes can create/update the object according to apply semantics.

### 27. What does client dry run prove?

Only client-side processing appropriate to that operation. It is not complete cluster validation.

### 28. Why use server dry run?

To exercise API-server-side processing without persisting the requested change.

### 29. Why use kubectl diff?

To inspect proposed differences before applying.

### 30. Does successful apply prove the application works?

No.

---

# 241. Knowledge Check: Live Objects

### 31. Why is live YAML larger than source YAML?

Kubernetes adds/defaults/manages metadata, status and other fields.

### 32. Should you copy `uid` into source manifests?

Normally no.

### 33. Should you copy `resourceVersion` into normal source manifests?

Normally no.

### 34. Should you author Pod status to make it Running?

No.

### 35. What is the source manifest primarily expressing?

Desired configuration.
