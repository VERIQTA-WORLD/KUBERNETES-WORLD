# PART 10: INGRESS, GATEWAY CONCEPTS, AND EXTERNAL TRAFFIC

## From Internet Request to Load Balancer to Ingress or Gateway to Service to Pod

---

# 1. Goal

The goal of this part is to understand how users and systems outside a Kubernetes cluster reach applications running inside the cluster.

By the end of this part, you should understand:

* the external traffic problem
* why ClusterIP alone is not enough
* reverse proxies
* load balancers
* Ingress
* Ingress resources
* Ingress controllers
* IngressClass
* host-based routing
* path-based routing
* TLS concepts
* TLS termination
* DNS
* Gateway API
* GatewayClass
* Gateway
* HTTPRoute
* why Gateway API exists
* the relationship between Gateway API and Ingress
* how an external request moves through Kubernetes
* how to troubleshoot external traffic layer by layer

The core request path is:

```text
User
↓
DNS
↓
External Load Balancer / Reachable Entry Point
↓
Ingress Controller or Gateway Implementation
↓
Routing Rule
↓
Service
↓
EndpointSlice
↓
Pod
↓
Application
```

The most important objective is not merely learning how to write an Ingress manifest.

It is learning how to answer:

```text
"The website is unreachable."

Where exactly is the request failing?
```

# 3. The External Traffic Problem

Imagine an application running as three Pods:

```text
frontend Pod A
10.244.1.10

frontend Pod B
10.244.2.15

frontend Pod C
10.244.3.20
```

A ClusterIP Service provides:

```text
frontend
10.96.50.20
```

Inside the cluster:

```text
curl http://frontend
```

works.

But a customer sitting at home cannot normally browse to:

```text
10.96.50.20
```

because a ClusterIP is intended for cluster-internal access.

We therefore need a controlled external entry point.

---

# 4. External Exposure Is a Different Problem

Internal traffic:

```text
Pod
↓
Service
↓
Pod
```

External traffic:

```text
Internet User
↓
Public DNS
↓
Public / Reachable Network Address
↓
Load Balancer / Proxy
↓
Kubernetes Routing
↓
Service
↓
Pod
```

The external path contains more infrastructure.

Therefore it contains more possible failure points.

---

# 5. Ways Kubernetes Applications Can Be Exposed

Common approaches include:

```text
NodePort

LoadBalancer Service

Ingress

Gateway API
```

These are not interchangeable abstractions.

Each solves a different part of external connectivity.

---

# 6. NodePort Recap

A NodePort Service exposes a Service through a port on cluster nodes.

Conceptually:

```text
External Client
↓
NodeIP:NodePort
↓
Service
↓
Pod
```

Example:

```text
192.168.10.21:32080
```

could forward to:

```text
frontend Service
↓
frontend Pods
```

---

# 7. Why NodePort Is Usually Not the Final Web Architecture

Imagine 50 applications.

You do not want users remembering:

```text
example.com:30123

example.com:31567

example.com:32701
```

Web applications normally need:

```text
https://shop.example.com

https://api.example.com

https://example.com/admin
```

This requires HTTP-aware routing.

---

# 8. LoadBalancer Service Recap

A Service of type:

```yaml
type: LoadBalancer
```

asks an environment capable of providing external load balancers to expose that Service.

Conceptually:

```text
Internet
↓
External Load Balancer
↓
Kubernetes Service
↓
Pods
```

---

# 9. LoadBalancer Limitation

Suppose you have:

```text
frontend Service

API Service

admin Service

payments Service
```

You could potentially create:

```text
4 LoadBalancer Services
```

which might create:

```text
4 external load balancers
```

depending on the environment.

But HTTP applications can often share an entry point.

For example:

```text
shop.example.com
↓
frontend

api.example.com
↓
API

admin.example.com
↓
admin
```

or:

```text
example.com/shop
↓
frontend

example.com/api
↓
API
```

That is where HTTP-aware routing becomes valuable.

---

# 10. Layer 4 vs Layer 7 Concepts

Before Ingress, understand the difference.

A traditional network load balancer may make decisions using information such as:

```text
IP address

TCP port

UDP port
```

This is commonly associated with Layer 4 concepts.

HTTP-aware routing can inspect:

```text
hostname

URL path

HTTP headers

HTTP methods
```

This is commonly associated with Layer 7 concepts.

---

# 11. Layer 4 Example

Traffic:

```text
203.0.113.20:443
```

may be forwarded to backend systems.

The routing decision can occur without understanding:

```text
/shop

/api

Host: api.example.com
```

---

# 12. Layer 7 Example

Request:

```http
GET /api/orders HTTP/1.1
Host: shop.example.com
```

An HTTP-aware proxy can inspect:

```text
Host:
shop.example.com
```

and:

```text
Path:
/api/orders
```

and route accordingly.

---

# 13. Reverse Proxy

A reverse proxy accepts requests on behalf of backend applications.

Conceptually:

```text
Client
↓
Reverse Proxy
↓
Backend Application
```

The client communicates with:

```text
proxy.example.com
```

rather than directly with:

```text
backend Pod IP.
```

---

# 14. Why It Is Called a Reverse Proxy

A forward proxy commonly represents:

```text
clients
```

when those clients access external destinations.

A reverse proxy represents:

```text
servers/backends
```

to clients.

Conceptually:

```text
Users
↓
Reverse Proxy
↓
Many Backends
```

---

# 15. Reverse Proxy Responsibilities

Depending on implementation, a reverse proxy can perform:

```text
host routing

path routing

TLS termination

load balancing

redirects

header manipulation

authentication integration

traffic splitting

observability
```

Not every implementation supports every feature in exactly the same way.

---

# 16. Load Balancer vs Reverse Proxy

These terms overlap.

A load balancer primarily distributes traffic among backend destinations.

A reverse proxy receives client requests and forwards them to backend applications.

A reverse proxy can also perform load balancing.

Therefore a component can be:

```text
reverse proxy
+
load balancer
```

at the same time.

---

# 17. The Kubernetes Ingress Concept

Ingress is a Kubernetes API object for managing external HTTP and HTTPS access to Services using routing rules.

Typical capabilities include:

```text
host-based routing

path-based routing

TLS configuration

name-based virtual hosting
```

Ingress does not itself process traffic.

This distinction is critical.

---

# 18. The Most Important Ingress Distinction

Memorize:

```text
Ingress Resource
≠
Ingress Controller
```

Again:

```text
Ingress Resource
≠
Ingress Controller
```

Creating an Ingress object alone does not automatically create a functioning traffic-processing system.

---

# 19. Ingress Resource

An Ingress resource is:

```text
configuration / desired routing state
```

Example:

```text
Host:
shop.example.com

Path:
/api

Backend:
api-service:80
```

It tells an implementing controller:

```text
"When traffic matching this rule arrives,
route it to this backend."
```

---

# 20. Ingress Controller

An Ingress controller is software that:

```text
watches Ingress-related Kubernetes objects

interprets routing configuration

configures traffic-handling infrastructure

processes or enables processing of incoming traffic
```

depending on the implementation.

---

# 21. Ingress Architecture

Conceptually:

```text
Ingress Resource
↓
Kubernetes API
↓
Ingress Controller watches configuration
↓
Controller configures proxy / load balancer
↓
Traffic enters
↓
Routing rules evaluated
↓
Service selected
↓
Backend Pod
```

---

# 22. What Happens Without an Ingress Controller?

Suppose you create:

```yaml
kind: Ingress
```

but no compatible Ingress controller exists.

The Kubernetes API may accept the object.

You can run:

```bash
kubectl get ingress
```

and see it.

But:

```text
traffic routing may not happen.
```

The resource describes desired routing configuration.

Something still needs to implement it.

---

# 23. Why This Confuses Beginners

They run:

```bash
kubectl apply -f ingress.yaml
```

and receive:

```text
ingress.networking.k8s.io/web created
```

Then they expect:

```text
https://example.com
```

to work.

But:

```text
Object created
```

does not mean:

```text
External routing fully operational.
```

---

# 24. The Same Kubernetes Pattern Appears Again

Remember:

```text
Deployment
↓
Deployment Controller
```

Similarly:

```text
Ingress
↓
Ingress Controller
```

The API object represents desired state.

A controller reacts to it.

---

# 25. Current Ingress API

A modern Ingress uses:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
```

Do not blindly copy old tutorials using obsolete API versions.

---

# 26. Important Current Kubernetes Direction

Ingress remains a stable Kubernetes API.

However:

```text
the Ingress API is frozen.
```

It is not being expanded with new features.

Kubernetes recommends Gateway API for newer routing capabilities.

This does not mean:

```text
Ingress suddenly stops working.
```

It means:

```text
Ingress remains supported
but future API evolution is focused on Gateway API.
```

# 27. IngressClass

Different Ingress controllers can exist in one cluster.

Kubernetes therefore provides:

```text
IngressClass
```

to identify which controller should implement an Ingress.

---

# 28. Inspect Ingress Classes

Run:

```bash
kubectl get ingressclass
```

Example:

```text
NAME      CONTROLLER
nginx     example.io/ingress-controller
```

The actual values depend on your implementation.

---

# 29. `ingressClassName`

An Ingress can specify:

```yaml
spec:
  ingressClassName: nginx
```

This references an:

```text
IngressClass
```

named:

```text
nginx
```

---

# 30. Why Explicit Classes Matter

Imagine a cluster containing:

```text
internal ingress controller

external ingress controller
```

You need to communicate:

```text
Which controller should handle this Ingress?
```

IngressClass helps provide that association.

---

# 31. Do Not Rely on Old Ingress-Class Annotations

Older configurations commonly used:

```yaml
metadata:
  annotations:
    kubernetes.io/ingress.class: nginx
```

Modern Ingress resources should normally use:

```yaml
spec:
  ingressClassName: nginx
```

when selecting an IngressClass.

The older annotation is deprecated.

# 32. Basic Ingress Manifest

Example:

```yaml
apiVersion: networking.k8s.io/v1

  name: web-ingress
  namespace: ingress-lab

  ingressClassName: nginx
  rules:

                port:
                  number: 80
```

# 35. Ingress Class

```yaml
ingressClassName: nginx
```

means:

```text
This Ingress should be handled by
the controller associated with
the nginx IngressClass.
```

The actual class name is implementation-specific.

Never assume your cluster uses:

```text
nginx
```

without checking.

# 36. Host Rule

```yaml
host: app.example.test
```

means:

```text
Match requests whose HTTP Host
matches app.example.test
```

---

# 37. HTTP Paths

```yaml
http:
  paths:
```

defines HTTP path-based routing rules for that host.

---

# 38. Path

```yaml
path: /
```

specifies the request path to match.

---

# 39. pathType

Ingress v1 requires a:

```text
pathType
```

for each path.

Common values include:

```text
Exact

Prefix

ImplementationSpecific
```

---

# 40. Exact

Example:

```yaml
path: /shop
pathType: Exact
```

matches the exact path according to Kubernetes Ingress path semantics.

Conceptually:

```text
/shop
```

matches.

But:

```text
/shop/item
```

does not match the same Exact rule.

---

# 41. Prefix

Example:

```yaml
path: /shop
pathType: Prefix
```

can match paths such as:

```text
/shop

/shop/

/shop/item

/shop/orders/123
```

according to element-wise path-prefix semantics.

---

# 42. ImplementationSpecific

```yaml
pathType: ImplementationSpecific
```

delegates path interpretation to the IngressClass implementation.

Behavior can therefore vary.

Use it only when you understand the controller-specific semantics you require.

---

# 43. Backend

This section:

```yaml
backend:
  service:
    name: web-service
    port:
      number: 80
```

means:

```text
Send matching requests
to Service web-service
on Service port 80.
```

---

# 44. Ingress Normally Routes to a Service

The normal architecture is:

```text
Ingress
↓
Service
↓
EndpointSlice
↓
Pods
```

not:

```text
Ingress
↓
hard-coded Pod IP
```

Services preserve backend stability as Pods change.

---

# 45. Host-Based Routing

Suppose you have:

```text
shop.example.com
api.example.com
admin.example.com
```

One external entry point can route each hostname differently.

---

# 46. Host-Based Architecture

```text
                  ┌─ shop-service
shop.example.com ─┤
                  │
External Entry ───┼─ api-service
                  │
api.example.com ──┤
                  │
admin.example.com └─ admin-service
```

More clearly:

```text
shop.example.com
↓
shop-service

api.example.com
↓
api-service

admin.example.com
↓
admin-service
```

---

```yaml
      http:
        paths:
          - path: /
            pathType: Prefix

                name: api-service

                  number: 80
```

# 48. HTTP Host Header

When you request:

```text
http://shop.example.com/products
```

the HTTP request contains a Host header conceptually similar to:

```http
Host: shop.example.com
```

The reverse proxy can use this value to select a routing rule.

---

# 49. DNS and Host Routing Are Related but Different

DNS answers:

```text
Where should I send the connection?
```

Ingress routing answers:

```text
Which backend should handle this HTTP request?
```

Do not confuse them.

---

# 50. Example

DNS:

```text
shop.example.com
↓
203.0.113.20
```

and:

```text
api.example.com
↓
203.0.113.20
```

Both names can resolve to the same entry point.

The proxy then uses the hostname to route:

```text
shop.example.com
↓
shop-service

api.example.com
↓
api-service
```

---

# 51. Path-Based Routing

You can also route using paths.

Example:

```text
example.com/
↓
frontend-service

example.com/api
↓
api-service

example.com/admin
↓
admin-service
```

---

# 52. Path-Based Manifest

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: platform-ingress
  namespace: ingress-lab
spec:
  ingressClassName: nginx
  rules:
    - host: platform.example.test
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80

          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80
```

---

# 53. Routing Decision

Request:

```text
platform.example.test/api/orders
```

matches:

```text
/api
```

and routes toward:

```text
api-service
```

Request:

```text
platform.example.test/
```

routes toward:

```text
frontend-service
```

---

# 54. Path Routing Does Not Automatically Rewrite Paths

This is important.

Suppose:

```text
Client requests:
/api/orders
```

Routing to:

```text
api-service
```

does not universally mean the backend receives:

```text
/orders
```

instead.

Path rewriting is typically implementation-specific and may require controller-specific configuration.

Never assume routing automatically means rewriting.

---

# 55. Default Backend Concept

An Ingress implementation can provide default handling for requests that do not match routing rules.

For example:

```text
unknown hostname
↓
default backend
```

or:

```text
unknown path
↓
default response
```

Exact behavior depends on the implementation and configuration.

---

# 56. Why You May See 404 From an Ingress Controller

A request can successfully reach the controller but fail to match any configured rule.

That can produce:

```text
404
```

This is very different from:

```text
connection timeout.
```

A 404 can prove that several lower network layers are already functioning.

---

# 57. HTTP Status Codes Are Troubleshooting Evidence

Examples:

```text
DNS failure
```

means the client may never reach the cluster.

```text
Connection refused
```

suggests something different.

```text
404
```

may indicate no matching route.

```text
502
```

may indicate an upstream/backend problem.

```text
503
```

may indicate unavailable backends.

Exact responses depend on the controller.

Treat status codes as evidence, not universal proof.

# 64. TLS Concepts

HTTP traffic can be encrypted using:

```text
TLS
```

giving:

```text
HTTPS.
```

Example:

```text
http://shop.example.com
```

is unencrypted HTTP.

```text
https://shop.example.com
```

uses HTTP over TLS.

---

# 65. What TLS Provides

TLS is designed to provide properties such as:

```text
encryption

integrity

server authentication
```

and optionally client authentication in configurations such as mutual TLS.

---

# 66. TLS Certificate

A server certificate helps prove that a server is authorized for a hostname.

Example:

```text
shop.example.com
```

Certificate identity should be valid for:

```text
shop.example.com
```

according to certificate validation rules.

---

# 67. TLS Private Key

The corresponding private key is highly sensitive.

Never:

```text
commit private keys to Git

paste them into public repositories

put them into documentation examples using real credentials

share production certificate keys
```

Treat them as secrets.

---

# 68. TLS Termination

TLS termination means:

```text
encrypted client connection
↓
TLS endpoint decrypts traffic
↓
traffic is processed / forwarded
```

Example:

```text
Browser
↓
HTTPS
↓
Ingress Controller
↓
HTTP
↓
Service
↓
Pod
```

if the controller terminates TLS and backend traffic is unencrypted.

---

# 69. TLS Termination Location Matters

TLS might terminate at:

```text
cloud load balancer

Ingress controller

Gateway implementation

application itself
```

Architecture determines:

```text
where encryption ends
```

and whether traffic is re-encrypted downstream.

---

# 70. TLS Termination vs TLS Passthrough

Termination:

```text
Client
↓
TLS
↓
Proxy decrypts
↓
backend connection
```

Passthrough concept:

```text
Client
↓
encrypted TLS
↓
intermediary forwards encrypted traffic
↓
backend terminates TLS
```

Support and configuration are implementation-specific.

---

# 71. TLS Re-encryption Concept

Another architecture:

```text
Client
↓
TLS
↓
Proxy terminates TLS
↓
new TLS connection
↓
Backend
```

This provides encryption on both network segments.

Again, support varies.

---

A typical Ingress can contain:

```yaml

        - shop.example.com

```

The referenced Secret commonly contains:

```text

```

# 73. Kubernetes TLS Secret Type

A TLS Secret commonly uses:

```yaml
type: kubernetes.io/tls
```

with keys:

```text
tls.crt

tls.key
```

Secrets are covered deeply later.

For now, understand that Ingress TLS configuration can reference a Secret containing certificate material.

---

# 74. Never Commit Real TLS Private Keys

A manifest such as:

```yaml
data:
  tls.key: ...
```

containing a real production private key should not be stored casually in source control.

Production secret management requires deliberate controls.

# 77. SNI Concept

SNI stands for:

```text
Server Name Indication
```

It allows a TLS client to indicate the hostname it is trying to reach during the TLS handshake.

This makes it possible to host multiple TLS names behind shared infrastructure.

---

# 78. Why SNI Matters

One external IP can potentially serve:

```text
shop.example.com

api.example.com

admin.example.com
```

with different certificates or routing behavior.

SNI helps the TLS endpoint know which hostname the client requested.

---

# 79. Host Routing vs SNI

Simplified:

```text
SNI
↓
TLS-layer hostname information
```

```text
HTTP Host header
↓
HTTP-layer hostname information
```

They operate at different stages.

Do not treat them as identical.

# 131. Why Gateway API Exists

Ingress became extremely useful, but its model is intentionally limited.

Advanced capabilities often required implementation-specific annotations.

Examples might include:

```text
traffic weighting

header matching

advanced routing

cross-team ownership

infrastructure policy

protocol-specific routing
```

Different controllers developed different annotation ecosystems.

This reduced portability and made advanced configuration harder to standardize.

---

# 132. Gateway API

Gateway API provides a more expressive, extensible, role-oriented model for service networking.

Rather than placing everything into one Ingress object, responsibilities can be represented using separate resources.

Core concepts include:

```text
GatewayClass

Gateway

HTTPRoute
```

and additional route types.

---

# 133. Gateway API Is an Extension API

Gateway API resources are not the same kind of built-in API as core resources such as:

```text
Pod

Service
```

Gateway API is installed through extension APIs, commonly CustomResourceDefinitions, together with an implementation that supports them.

Therefore:

```text
kubectl apply Gateway
```

requires the appropriate Gateway API resources and implementation to exist.

---

```text

↓
Gateway
↓
HTTPRoute
↓
Service
↓
EndpointSlice
↓

```

This separation is deliberate.

# 143. HTTPRoute

HTTPRoute defines:

```text

```

It answers:


---

# 144. HTTPRoute Example

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop
  namespace: applications
spec:
  parentRefs:
    - name: public-web
      namespace: gateway-system
  hostnames:
    - shop.example.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api
      backendRefs:
        - name: shop-api
          port: 80
```

Cross-namespace attachment and backend references are subject to Gateway API rules and permissions.

Do not assume every cross-namespace reference is automatically permitted.

```text

```

```text

```

The platform team does not need to let every application team directly control the shared load balancer configuration.

# 250. Knowledge Check

### What is Ingress?

A Kubernetes API object that describes HTTP/HTTPS external routing to Services.

### Does Ingress itself process packets?

No.

### What implements Ingress behavior?

An Ingress controller.

---

# 251. Knowledge Check

### Ingress Resource equals Ingress Controller?

No.

Memorize:

```text
Ingress Resource
≠
Ingress Controller
```

The resource is desired routing configuration.

The controller implements that desired state.

---

# 252. Knowledge Check

### What is IngressClass?

A resource used to identify a class of Ingress implementation/controller configuration.

### Why is it useful?

Because a cluster can have different Ingress implementations or classes.

---

# 253. Knowledge Check

### What are the three common Ingress path types?

```text
Exact

Prefix

ImplementationSpecific
```

### Which one delegates semantics to the implementation?

```text
ImplementationSpecific.
```

# 254. Knowledge Check

### What is host-based routing?

Selecting a backend based on hostname.

Example:

```text
api.example.com
↓
api-service
```

### What is path-based routing?

Selecting a backend based on URL path.

Example:

```text
example.com/api
↓
api-service
```

---

# 255. Knowledge Check

### Does path routing automatically mean path rewriting?

No.

Routing and rewriting are separate concepts.

---

# 256. Knowledge Check

### What is TLS termination?

The point where an encrypted TLS connection is decrypted by the TLS endpoint.

### Can TLS terminate at different infrastructure layers?

Yes.

Examples:

```text
cloud load balancer

Ingress controller

Gateway implementation

application
```

---

# 257. Knowledge Check

### What does DNS do?

Maps names to reachable addresses.

### Does DNS decide which Kubernetes Service receives `/api`?

Normally no.

HTTP routing handles that decision.

---

# 258. Knowledge Check

### What is Gateway API?

A family of Kubernetes extension APIs for expressive, extensible, role-oriented service networking and traffic routing.

### Is Gateway API simply a renamed Ingress?

No.

Its resource model is different.

---

# 259. Knowledge Check

### What is GatewayClass?

The class of Gateway infrastructure and the controller responsible for managing it.

### What is Gateway?

An instance/configuration of traffic-handling infrastructure.

### What is HTTPRoute?

HTTP routing configuration attached to a Gateway.

Gateway API.

# 282. What Comes Next

External traffic is now reaching applications.

But applications need configuration.

A database endpoint may differ between:

```text
development

staging

production.
```

Applications also need sensitive values such as:

```text
database passwords

API credentials

tokens

certificates
```

Hard-coding those values into container images is a poor operational model.

Kubernetes therefore provides configuration abstractions.

That leads to:

```text
PART 11
↓
ConfigMaps, Secrets, and Application Configuration
```

where the architecture becomes:

```text
Application Pod
├── ConfigMap
│   └── non-sensitive configuration
│
└── Secret
    └── sensitive configuration
```

and we will learn the critical security lesson:

```text
Base64
≠
Encryption
```
