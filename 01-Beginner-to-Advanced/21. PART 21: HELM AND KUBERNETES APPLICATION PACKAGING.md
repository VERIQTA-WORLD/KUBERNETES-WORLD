# PART 21: HELM AND KUBERNETES APPLICATION PACKAGING

## From Repeated YAML to Reusable, Versioned Kubernetes Application Packages

---

# 1. Goal

The goal of this part is to learn how to manage reusable and configurable Kubernetes application packages with Helm.

By the end, you should understand how to move from:

```text
many duplicated Kubernetes YAML files
```

to:

```text
Reusable Chart
+
Environment Values
+
Versioned Release
+
Controlled Upgrade
+
Rollback
```

You will build a real Helm chart, parameterize Kubernetes resources, render and validate templates, install releases, upgrade them, deliberately introduce a failure, investigate the failure, roll back, and uninstall the application.

---

# 2. The Problem Helm Solves

By now, a production application may require:

```text
Namespace
Deployment
Service
ConfigMap
Secret references
ServiceAccount
RBAC
NetworkPolicy
Ingress/Gateway
HPA
PDB
PersistentVolumeClaim
```

Managing these as raw manifests is possible.

But repetition quickly appears.

Imagine:

```text
development/
deployment.yaml
service.yaml
configmap.yaml

staging/
deployment.yaml
service.yaml
configmap.yaml

production/
deployment.yaml
service.yaml
configmap.yaml
```

Much of the YAML may be identical.

Only values such as these change:

```text
replicas

image tag

CPU request

memory request

Service type

hostname

feature flags
```

Copying entire manifests for every environment creates configuration drift and maintenance problems.

Helm provides another approach.

---

# 3. What Is Helm?

Helm is a package manager for Kubernetes.

Its package format is called a:

```text
Chart
```

A chart contains:

```text
Kubernetes manifest templates
+
default configuration
+
chart metadata
+
optional dependencies
```

Helm renders those templates into Kubernetes manifests.

Conceptually:

```text
Chart
+
Values
↓
Helm Template Engine
↓
Rendered Kubernetes YAML
↓
Kubernetes API
↓
Resources
```

---

# 4. Helm Does Not Replace Kubernetes

Helm does not replace:

```text
Deployments

Services

ConfigMaps

RBAC

NetworkPolicies

Kubernetes API

kubectl
```

Helm generates and manages Kubernetes resources.

Think:

```text
Kubernetes
=
application orchestration platform

Helm
=
Kubernetes application packaging and release-management tool
```

---

# 5. Helm Does Not Replace Terraform

A common production boundary is:

```text
Terraform
↓
Infrastructure
↓
VPC
Subnets
IAM
EKS
Node infrastructure
Cloud resources
```

Then:

```text
Helm / Kubernetes manifests
↓
Application layer
↓
Deployments
Services
ConfigMaps
Policies
Application resources
```

The exact ownership boundary depends on the organization.

---

# 6. Helm Does Not Replace GitOps

Helm can package an application.

GitOps systems can deploy and reconcile Helm-based applications.

For example:

```text
Git
↓
Helm Chart
↓
Values
↓
GitOps Controller
↓
Helm Rendering
↓
Kubernetes
```

Helm and GitOps are complementary technologies.

Part 23 will explore this further.

# 8. Important Helm Vocabulary

You must distinguish:

```text
Chart
Release
Repository
Values
Template
Dependency
Revision
```

These are different concepts.

---

# 9. Chart

A:

```text
Chart
```

is the application package.

Example:

```text
veriqta-web/
```

The chart describes how the Kubernetes application should be created.

---

# 10. Release

A:

```text
Release
```

is an installed instance of a chart.

For example, the same chart:

```text
veriqta-web
```

could be installed as:

```text
veriqta-dev

veriqta-staging

veriqta-production
```

Each is a separate release.

---

# 11. Chart vs Release

Think:

```text
Chart
=
blueprint/package
```

```text
Release
=
installed instance of that package
```

This distinction is fundamental.

---

# 12. Repository

A Helm repository is a location from which charts can be discovered and retrieved.

Conceptually:

```text
Chart Repository
├── chart-a
├── chart-b
└── chart-c
```

Traditional HTTP chart repositories remain common.

Modern Helm also supports distributing charts through OCI-compatible registries.

---

# 13. Values

Values provide configuration to templates.

Examples:

```yaml
replicaCount: 3

image:
  repository: nginx
  tag: "1.27"

service:
  type: ClusterIP
  port: 80
```

Templates reference these values.

---

# 14. Templates

Templates are Kubernetes manifests containing Helm template expressions.

Example:

```yaml
spec:
  replicas: {{ .Values.replicaCount }}
```

If:

```yaml
replicaCount: 3
```

Helm renders:

```yaml
spec:
  replicas: 3
```

---

# 15. Why Templates Matter

Without templates:

```text
deployment-dev.yaml
deployment-staging.yaml
deployment-production.yaml
```

With Helm:

```text
templates/deployment.yaml
+
values-dev.yaml
values-staging.yaml
values-production.yaml
```

This can reduce duplication.

It does not automatically eliminate configuration complexity.

Poorly designed charts can become more difficult to understand than plain YAML.

---

# 16. Helm Chart Structure

The simplified structure from our curriculum is:

```text
my-chart/
├── Chart.yaml
├── values.yaml
├── templates/
└── charts/
```

A practical chart may become:

```text
veriqta-web/
├── Chart.yaml
├── values.yaml
├── values.schema.json
├── .helmignore
├── charts/
└── templates/
    ├── _helpers.tpl
    ├── deployment.yaml
    ├── service.yaml
    ├── serviceaccount.yaml
    ├── configmap.yaml
    ├── ingress.yaml
    ├── hpa.yaml
    ├── pdb.yaml
    └── NOTES.txt
```

Not every chart needs every file.

# 17. `Chart.yaml`

`Chart.yaml` contains chart metadata.

Example:

```yaml
apiVersion: v2
name: veriqta-web
description: VERIQTA training web application
type: application
version: 0.1.0
appVersion: "1.0.0"
```

---

# 18. `apiVersion`

For modern application charts:

```yaml
apiVersion: v2
```

This refers to the Helm chart API version.

It is not the same as:

```yaml
apiVersion: apps/v1
```

inside a Kubernetes Deployment.

---

# 19. `name`

Example:

```yaml
name: veriqta-web
```

This is the chart name.

It is not necessarily the release name.

---

# 20. `version`

Example:

```yaml
version: 0.1.0
```

This is the:

```text
chart version.
```

It versions the package.

---

# 21. `appVersion`

Example:

```yaml
appVersion: "1.0.0"
```

This describes the application version.

Important:

```text
Chart version
!=
Application version
```

For example:

```yaml
version: 2.4.0
appVersion: "8.7.1"
```

can be perfectly valid.

---

# 22. Why Separate Versions?

A chart can change without the application changing.

For example:

```text
application remains v3.2.0

but

resource limits change
```

You might therefore release:

```text
Chart 1.4.0
App 3.2.0
```

and later:

```text
Chart 1.4.1
App 3.2.0
```

---

# 23. `type`

Typical application chart:

```yaml
type: application
```

Helm also supports library charts.

Library charts provide reusable chart primitives rather than directly installable application resources.

This file contains default configuration.

Example:

```yaml

  repository: nginx
  tag: "1.27"
  pullPolicy: IfNotPresent

  type: ClusterIP
  port: 80
  targetPort: 80

    memory: 128Mi
  limits:
    memory: 256Mi
```

# 25. `templates/`

The:

```text
templates/
```

directory contains files processed by Helm's template engine.

Example:

```text
templates/
├── deployment.yaml
├── service.yaml
└── _helpers.tpl
```

After rendering, the result should be valid Kubernetes manifests.

---

# 26. `charts/`

The:

```text
charts/
```

directory can contain chart dependencies.

For example:

```text
veriqta-web/
└── charts/
    └── dependency-chart/
```

Dependencies can also be declared in:

```text
Chart.yaml
```

and managed using Helm dependency commands.

---

# 27. `.helmignore`

A chart can contain:

```text
.helmignore
```

which tells Helm which files should be excluded when packaging the chart.

Conceptually similar to:

```text
.gitignore
```

but specifically for Helm chart packaging.

# 44. Create Helpers

Create:

```text
templates/_helpers.tpl
```

with:

```gotemplate
{{- define "veriqta-web.name" -}}
{{ .Chart.Name }}
{{- end }}

{{- define "veriqta-web.fullname" -}}
{{ printf "%s-%s" .Release.Name .Chart.Name | trunc 63 | trimSuffix "-" }}
{{- end }}

{{- define "veriqta-web.labels" -}}
app.kubernetes.io/name: {{ include "veriqta-web.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
helm.sh/chart: {{ printf "%s-%s" .Chart.Name .Chart.Version | replace "+" "_" }}
{{- end }}
```

---

# 45. What Is `_helpers.tpl`?

Files beginning with:

```text
_
```

inside `templates/` are commonly used for reusable template definitions.

`_helpers.tpl` often contains:

```text
names

labels

selectors

common annotations
```

It does not itself need to render a Kubernetes resource.

---

# 46. Named Templates

This:

```gotemplate
{{- define "veriqta-web.name" -}}
...
{{- end }}
```

creates a named template.

Use it with:

```gotemplate
{{ include "veriqta-web.name" . }}
```

---

# 47. Why Prefix Helper Names?

Named templates are global within the rendering context.

Therefore:

```text
labels
```

is a poor helper name.

Prefer:

```text
veriqta-web.labels
```

This reduces naming collisions with dependencies and other templates.

---

# 48. Template Whitespace

You will frequently see:

```gotemplate
{{-
```

and:

```gotemplate
-}}
```

The hyphen trims whitespace around template actions.

Whitespace handling matters because malformed indentation can create invalid YAML.

Do not randomly add whitespace trimming until you understand the rendered result.

# 49. Build Deployment Template

Create:

```text
templates/deployment.yaml
```

with:

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: {{ include "veriqta-web.fullname" . }}
  labels:
    {{- include "veriqta-web.labels" . | nindent 4 }}

spec:
  replicas: {{ .Values.replicaCount }}

  selector:
    matchLabels:
      app.kubernetes.io/name: {{ include "veriqta-web.name" . }}
      app.kubernetes.io/instance: {{ .Release.Name }}

  template:
    metadata:
      labels:
        app.kubernetes.io/name: {{ include "veriqta-web.name" . }}
        app.kubernetes.io/instance: {{ .Release.Name }}

    spec:
      containers:
        - name: {{ .Chart.Name }}

          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"

          imagePullPolicy: {{ .Values.image.pullPolicy }}

          ports:
            - name: http
              containerPort: {{ .Values.service.targetPort }}
              protocol: TCP

          resources:
            {{- toYaml .Values.resources | nindent 12 }}
```

---

# 50. Understand `include`

This:

```gotemplate
{{ include "veriqta-web.fullname" . }}
```

calls the named helper.

The:

```text
.
```

passes the current template context.

Without the correct context, the helper may not have access to objects such as:

```text
.Release

.Chart

.Values
```

---

# 51. Understand `toYaml`

This:

```gotemplate
toYaml .Values.resources
```

converts the value structure into YAML.

Given:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
```

it can produce YAML equivalent to:

```yaml
requests:
  cpu: 100m
  memory: 128Mi
```

---

# 52. Understand `nindent`

This:

```gotemplate
nindent 12
```

adds a newline and indents the generated text by the requested number of spaces.

It is extremely useful when inserting YAML structures into templates.

Incorrect indentation is one of the most common beginner Helm problems.

# 55. Values Precedence

Helm can receive values from several sources.

Conceptually:

```text
chart defaults
↓
user-supplied values files
↓
command-line overrides
```

More specific supplied overrides can replace chart defaults.

Always understand which values are actually being used.

# 56. Override With a Values File

Create:

```text
values-production.yaml
```

outside the chart:

```yaml
replicaCount: 4

image:
  tag: "1.27"

service:
  type: ClusterIP

resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    memory: 512Mi
```

Render using:

```bash
helm template veriqta-production \
  ./veriqta-web \
  -f values-production.yaml
```

---

# 57. Override With `--set`

Example:

```bash
helm template veriqta-test \
  ./veriqta-web \
  --set replicaCount=5
```

This overrides:

```yaml
replicaCount: 2
```

with:

```yaml
replicaCount: 5
```

---

# 58. When to Use `--set`

Useful for:

```text
small one-off overrides

automation

testing

simple CI variables
```

For large structured configuration, values files are generally easier to review.

Avoid enormous unreadable commands containing dozens of `--set` expressions.

# 59. Quote Strings Carefully

Example:

```yaml
image:
  tag: "1.27"
```

Quoting prevents YAML from interpreting values unexpectedly.

Templates often use:

```gotemplate
{{ .Values.image.tag | quote }}
```

when rendering strings.

# 60. Helm Functions

Helm templates support many functions.

Common examples include:

```text
quote

upper

lower

default

required

printf

include

toYaml

nindent

indent

replace

trunc

trimSuffix
```

---

# 61. Pipelines

Instead of:

```gotemplate
{{ quote .Values.image.tag }}
```

you can write:

```gotemplate
{{ .Values.image.tag | quote }}
```

The output of one operation becomes input to the next.

Example:

```gotemplate
{{ .Chart.Name | upper | quote }}
```

Conceptually:

```text
Chart name
↓
uppercase
↓
quoted
```

---

# 62. `default`

Example:

```gotemplate
{{ .Values.replicaCount | default 1 }}
```

If the supplied value is considered empty, Helm can use:

```text
1
```

Be careful.

If a stable default already belongs in:

```text
values.yaml
```

put it there rather than scattering duplicate defaults throughout templates.

---

# 63. `required`

Some configuration should not have a silent fallback.

Example:

```gotemplate
{{ required "image.repository must be configured" .Values.image.repository }}
```

If the value is absent or empty, rendering fails with the supplied message.

This is useful for critical configuration.

---

# 64. `printf`

Example:

```gotemplate
{{ printf "%s-%s" .Release.Name .Chart.Name }}
```

If:

```text
Release.Name = production
Chart.Name = veriqta-web
```

result:

```text
production-veriqta-web
```

# 68. `with`

Helm supports:

```gotemplate
{{ with ... }}
```

for changing scope.

Example:

```gotemplate
{{- with .Values.podAnnotations }}
annotations:
  {{- toYaml . | nindent 8 }}
{{- end }}
```

Inside the block:

```text
.
```

refers to:

```text
.Values.podAnnotations
```

not the original root object.

---

# 69. Scope Matters

A common Helm bug occurs because:

```text
.
```

changes inside:

```text
with

range
```

blocks.

You can preserve root scope using:

```text
$
```

Example:

```gotemplate
{{ $.Release.Name }}
```

The `$` normally represents the root context.

---

# 70. Loops

Helm uses:

```gotemplate
range
```

for iteration.

Suppose:

```yaml
environment:
  - name: APP_MODE
    value: production
  - name: LOG_LEVEL
    value: info
```

Template:

```gotemplate
env:
{{- range .Values.environment }}
  - name: {{ .name }}
    value: {{ .value | quote }}
{{- end }}
```

---

# 71. Rendered Loop

The result becomes:

```yaml
env:
  - name: APP_MODE
    value: "production"
  - name: LOG_LEVEL
    value: "info"
```

This allows collections of configuration to be represented cleanly.

---

# 72. Loop Over a Map

Suppose:

```yaml
podLabels:
  team: platform
  tier: frontend
```

You can use:

```gotemplate
{{- range $key, $value := .Values.podLabels }}
{{ $key }}: {{ $value | quote }}
{{- end }}
```

---

# 73. Avoid Over-Templating

Just because something can be parameterized does not mean it should be.

Bad charts expose hundreds of knobs without a clear contract.

A good chart makes meaningful configuration configurable while keeping safe defaults.

Think:

```text
flexibility
+
understandability
+
safe defaults
```

---

# 74. Helpers

Helpers reduce repeated template logic.

Good helper candidates include:

```text
resource names

standard labels

selector labels

ServiceAccount names

chart identifiers
```

Do not use helpers to hide important architecture unnecessarily.

---

# 75. Label Helper

Example:

```gotemplate
{{- define "veriqta-web.selectorLabels" -}}
app.kubernetes.io/name: {{ include "veriqta-web.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end }}
```

Then Deployment selector:

```yaml
selector:
  matchLabels:
    {{- include "veriqta-web.selectorLabels" . | nindent 4 }}
```

Pod labels:

```yaml
labels:
  {{- include "veriqta-web.selectorLabels" . | nindent 8 }}
```

Service selector:

```yaml
selector:
  {{- include "veriqta-web.selectorLabels" . | nindent 4 }}
```

This reduces accidental selector drift.

---

# 76. Why Selector Consistency Matters

Remember Part 20.

If:

```text
Deployment labels
!=
Service selector
```

the Service may have no application endpoints.

Helpers can reduce repeated label definitions and therefore reduce mismatch risk.

# 106. `--wait`

Example:

```bash
helm upgrade veriqta-web \
  ./veriqta-web \
  -n helm-lab \
  --wait
```

Helm waits for relevant resources to reach expected readiness conditions, subject to timeout behavior.

# 107. `--timeout`

```bash

  ./veriqta-web \
```

Understand realistic startup and rollout times.

# 108. `--atomic`

# 160. Chart Validation Schema

```text

```

```json

```
