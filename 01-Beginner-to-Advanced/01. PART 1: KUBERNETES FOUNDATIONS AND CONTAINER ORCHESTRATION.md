# PART 1: KUBERNETES FOUNDATIONS AND CONTAINER ORCHESTRATION

## From Servers and Containers to Production Orchestration

---

# 1. Goal

Before learning Kubernetes commands, manifests, Pods, Deployments, Services, or clusters, you need to understand the problem Kubernetes was created to solve.

By the end of this part, you should be able to explain:

* how applications were deployed before containers
* the difference between physical servers, virtual machines, and containers
* what container images are
* what container runtimes do
* where Docker fits
* why running containers is easier than operating containers at scale
* why manual container management becomes difficult
* what container orchestration means
* what desired state means
* what declarative management means
* why scheduling exists
* why self-healing exists
* why service discovery and load balancing exist
* what Kubernetes is
* what Kubernetes is not
* why Kubernetes was created
* how Kubernetes relates to Docker and containerd
* when Kubernetes makes sense
* when Kubernetes may be unnecessary
* how Kubernetes relates to DevOps, SRE, and platform engineering

The central question for this chapter is:

> If containers already run applications, why do we need Kubernetes?

Everything in this part builds toward answering that question.

# 2. Start With the Application

Imagine that you have built a web application.

It could be:

```text
Online Store

Banking API

Social Media Application

Internal Company Portal

Streaming Platform

Payment Service

Booking Platform
```

At the simplest level:

```text
User
↓
Application
```

But software cannot run by itself.

For example:

```text
Application
↓
Operating System
↓
CPU
↓
Memory
↓
Storage
↓
Network
↓
Physical Hardware
```

Therefore, the first problem organizations had to solve was:

```text
Where do we run applications?
```

---

# 3. Traditional Application Deployment

Before virtualization and containers became widespread, organizations commonly deployed applications directly onto physical servers.

Imagine an organization buys a server.

The server contains:

```text
CPU
Memory
Disk
Network Interface
Operating System
```

The organization installs an application directly onto it.

```text
Physical Server
│
├── Operating System
│
├── Application
│
└── Application Dependencies
```

This works.

But it creates several problems as infrastructure grows.

---

# 4. Physical Servers

A physical server is an actual computer designed to provide computing resources.

It contains hardware such as:

```text
CPU
RAM
Storage
Network Interfaces
```

The operating system runs directly on that hardware.

For example:

```text
Physical Server
↓
Linux
↓
Web Application
```

This is sometimes called:

```text
Bare-Metal Deployment
```

because the operating system runs directly on the hardware.

---

# 5. Example Physical Deployment

Imagine a company owns three applications:

```text
Website

Payment API

Reporting System
```

One simple architecture might be:

```text
Server 1
└── Website

Server 2
└── Payment API

Server 3
└── Reporting System
```

This provides isolation.

However, it may waste resources.

Suppose Server 1 has:

```text
16 CPU cores
64 GB RAM
```

but the website normally uses:

```text
2 CPU cores
8 GB RAM
```

A large amount of capacity may remain unused.

---

# 6. The Resource Utilization Problem

Organizations discovered that physical servers could be significantly underutilized.

Imagine:

```text
Physical Server

CPU Capacity:     16 cores
Application Use:   2 cores

Memory Capacity:  64 GB
Application Use:   8 GB
```

Much of the server remains unused.

Installing many unrelated applications directly onto the same operating system can improve utilization, but introduces other problems.

---

# 7. Multiple Applications on One Server

Suppose we install:

```text
Physical Server
│
├── Linux
├── Application A
├── Application B
└── Application C
```

Now applications share:

```text
CPU

Memory

Filesystem

Operating-system libraries

Network interfaces

System configuration
```

This creates potential conflicts.

---

# 8. Dependency Conflicts

Imagine:

```text
Application A requires Python version X.

Application B requires an incompatible Python version Y.
```

Or:

```text
Application A requires Library 1.5.

Application B requires Library 2.0.
```

Both applications live on the same operating system.

Changing dependencies for one application may affect another.

This is commonly called a dependency conflict.

---

# 9. Resource Contention

Imagine Application A suddenly consumes most available memory.

Application B may suffer.

Conceptually:

```text
Application A
        \
         \
          → Shared Server Resources
         /
Application B
```

Applications can interfere with one another when isolation is weak.

---

# 10. The "Works on My Machine" Problem

Another major problem was environmental inconsistency.

A developer might have:

```text
Developer Laptop

Python 3.x
Library A
Library B
Configuration X
```

Production might have:

```text
Production Server

Different Python
Different Library A
Missing Library B
Configuration Y
```

The application works locally.

Then it fails in production.

The problem is not necessarily the application code.

The environments differ.

---

# 11. Virtual Machines

Virtualization helped solve many of these problems.

Instead of dedicating an entire physical server to one operating system, a virtualization layer allows multiple virtual machines to share physical hardware.

Conceptually:

```text
Physical Server
↓
Hypervisor
├── VM 1
│   ├── Guest OS
│   └── Application A
│
├── VM 2
│   ├── Guest OS
│   └── Application B
│
└── VM 3
    ├── Guest OS
    └── Application C
```

---

# 12. What Is a Virtual Machine?

A virtual machine behaves like an independent computer.

It usually has allocated:

```text
Virtual CPU

Virtual Memory

Virtual Disk

Virtual Network Interface
```

and runs its own operating system.

For example:

```text
VM
│
├── Ubuntu
├── Python
├── Libraries
└── Application
```

Another VM on the same physical server might run:

```text
VM
│
├── Windows
├── .NET
└── Application
```

---

# 13. Why Virtual Machines Were Important

Virtual machines improved:

```text
Isolation

Hardware utilization

Environment separation

Provisioning flexibility

Workload portability
```

Instead of:

```text
One Physical Server
↓
One Application
```

organizations could use:

```text
One Physical Server
↓
Many Virtual Machines
↓
Many Applications
```

---

# 14. But Virtual Machines Have Overhead

Each VM typically includes its own guest operating system.

Conceptually:

```text
VM 1
├── Guest OS
└── Application

VM 2
├── Guest OS
└── Application

VM 3
├── Guest OS
└── Application
```

Those operating systems consume:

```text
CPU

Memory

Disk

Boot time

Patch-management effort
```

For many workloads, organizations wanted something lighter.

This helped drive container adoption.

---

# 15. Containers

A container packages an application together with the runtime dependencies it needs while using operating-system isolation mechanisms rather than packaging an entire independent guest operating system for every application.

Conceptually:

```text
Host
│
├── Container Runtime
│
├── Container A
│   └── Application A + Dependencies
│
├── Container B
│   └── Application B + Dependencies
│
└── Container C
    └── Application C + Dependencies
```

Containers provide process isolation while sharing the host kernel.

---

# 16. VM vs Container Mental Model

Virtual machine:

```text
Physical Server
↓
Hypervisor
↓
Virtual Machine
↓
Guest Operating System
↓
Application
```

Container:

```text
Physical / Virtual Server
↓
Host Operating System
↓
Container Runtime
↓
Container
↓
Application
```

This is simplified, but it gives you the correct beginner mental model.

---

# 17. Containers Are Not Tiny Virtual Machines

This distinction matters.

A container is not simply:

```text
Small VM
```

Virtual machines virtualize hardware and normally include independent guest operating systems.

Containers rely on operating-system-level isolation and share the host kernel.

The technologies solve overlapping but different problems.

---

# 18. Why Containers Became Popular

Containers provide useful properties for application delivery:

```text
Packaging

Isolation

Portability

Repeatability

Fast startup

Higher deployment density

Consistent environments
```

Instead of saying:

```text
Install Python.

Install these packages.

Install these libraries.

Copy these files.

Set these environment variables.

Run this command.
```

you can package much of the runtime requirement into an image.

---

# 19. Container Image

A container image is a packaged, ready-to-run representation of an application and the filesystem/runtime content needed to run it.

Conceptually:

```text
Container Image
│
├── Application Code
├── Runtime
├── Libraries
├── Dependencies
└── Default Configuration / Metadata
```

An image is not the running process itself.

It is the packaged artifact used to create containers.

---

# 20. Image vs Container

Think:

```text
Image
↓
Start
↓
Container
```

The image is the packaged artifact.

The container is a running instance created from that image.

A useful analogy is:

```text
Class
↓
Object
```

or:

```text
Blueprint
↓
Building
```

The analogy is imperfect, but useful for remembering the distinction.

---

# 21. One Image, Multiple Containers

Suppose you build:

```text
shop-api:1.0
```

You can start:

```text
Container 1
Container 2
Container 3
Container 4
```

from the same image.

Conceptually:

```text
shop-api:1.0
      |
      +----> Container A
      |
      +----> Container B
      |
      +----> Container C
```

This becomes important when scaling applications.

---

# 22. Container Immutability Mental Model

A strong container deployment model treats running containers as replaceable.

Instead of:

```text
Login to running container
↓
Manually edit application
↓
Hope configuration remains correct
```

prefer:

```text
Change Source
↓
Build New Image
↓
Deploy New Container
↓
Replace Old Container
```

For example:

```text
shop-api:1.0
↓
Code Change
↓
shop-api:1.1
↓
New Containers
```

This supports repeatability.

# 24. Container Runtime

Something must actually execute containers.

That component is the container runtime.

Conceptually:

```text
Container Image
↓
Container Runtime
↓
Running Container
```

In Kubernetes environments, common CRI-compatible runtime choices include:

```text

CRI-O
```

Kubernetes communicates with suitable runtimes through its Container Runtime Interface, or CRI.

# 25. What Does a Container Runtime Do?

At a beginner level, think of the runtime as responsible for operations around container execution and lifecycle.

Conceptually:

```text
Receive Request
↓
Obtain Image
↓
Prepare Container
↓
Start Container
↓
Monitor Container
↓
Stop Container
↓
Remove Container
```

# 26. Docker's Role

Docker dramatically simplified the developer experience around containers.

It provides tools and workflows for activities such as:

```text
Building images

Running containers

Inspecting containers

Viewing logs

Networking containers

Managing volumes

Publishing images
```

For example, developers commonly learn commands such as:

```bash
docker build
docker run
docker ps
docker logs
docker exec
docker stop
```

Docker remains highly relevant to container development.

---

# 27. Docker Is Not Kubernetes

This distinction must be clear from the beginning.

Docker and Kubernetes solve different layers of the problem.

Simplified:

```text
Docker
↓
Build and work with containers

Kubernetes
↓
Manage containerized workloads across infrastructure
```

That simplification is not the whole technical story, but it is a useful starting point.

---

# 28. Docker Engine and containerd

Do not assume:

```text
Docker = containerd = Kubernetes
```

They are different.

Docker Engine uses containerd as part of its container stack.

Kubernetes can use CRI-compatible runtimes such as containerd directly through the Kubernetes runtime interface.

Conceptually:

```text
Docker Workflow

Developer
↓
Docker
↓
containerd
↓
Lower-Level Container Runtime Components
↓
Container
```

A simplified Kubernetes path might be:

```text
Kubernetes
↓
kubelet
↓
CRI
↓
containerd
↓
Container
```

We will study the exact node architecture later.

---

# 29. Important Modern Kubernetes Detail

Older Kubernetes versions included a component called:

```text
dockershim
```

that allowed kubelet to work directly with Docker Engine through Kubernetes' integration layer.

That built-in integration was removed from Kubernetes beginning with version 1.24.

This does **not** mean:

```text
Docker images stopped working with Kubernetes.
```

Images built using Docker can still be used with Kubernetes when they conform to the relevant container image standards.

Do not confuse:

```text
Using Docker to build an image
```

with:

```text
Using Docker Engine as the Kubernetes node runtime.
```

These are different questions.

# 31. Container Lifecycle

A simplified container lifecycle looks like:

```text
Image Available
↓
Container Created
↓
Container Started
↓
Application Running
↓
Container Stops
↓
Container Removed
```

A container can stop because:


Imagine three servers:

```text
Server A

Server B

Server C
```

```text

├── Container 1

Server B
├── Container 3

├── Container 5
```

# 35. What Happens When Server B Fails?

Now:

```text
Server B
X
```

Containers 3 and 4 disappear.

Someone must determine:

```text

Where should replacements run?

Does another server have enough CPU?

Does it have enough memory?

Which configuration should be applied?

```

Doing this manually at scale is dangerous and slow.

# 36. Scaling Problem

Suppose traffic increases.

You currently have:

```text
3 application containers
```

but need:

```text
10 application containers.
```

Without orchestration, an operator might need to:

```text

↓
Check capacity
↓
Pull image
↓
Create containers
↓
Configure networking
↓
Configure application settings
↓
Register them with traffic routing
↓

```

Then traffic drops.

Now perhaps you need only:

```text
4 containers.
```

This becomes an ongoing scheduling and lifecycle problem.

# 37. Availability Problem

Suppose your application requires:

```text
5 healthy replicas.
```

One crashes.

Now:

```text
Desired = 5

Actual = 4
```

Without automation, someone must notice and react.

With an orchestration system, we want:

```text
Desired = 5
Actual = 4
↓
Difference Detected
↓
Create Replacement
↓
Actual = 5
```

This idea is central to Kubernetes.

# 38. Deployment Problem

You currently run:

```text

```

across 100 containers.

You need:

```text

```

A poor manual process might be:

```text

↓
Replace everything
↓
Start everything
```

A safer system should support controlled replacement.

```text

↓

```

# 39. Failed Deployment Problem

What if:

```text
application:2.0
```

does not start correctly?

You need to know:

```text
Which instances are old?

Which are new?

Which are healthy?

Should deployment continue?

Should it stop?

```

# 40. Service Discovery Problem

Containers are replaceable.

Their addresses can change.

Imagine:

```text
Frontend
↓
Backend
```

Today the backend container might have one address.

Tomorrow it may be replaced.

The frontend should not require humans to rewrite configuration every time a backend instance changes.

You need:

```text
Stable Service Identity
↓
Dynamic Backend Instances
```

This is service discovery.

---

# 41. Load-Balancing Problem

Suppose:

```text
Frontend
↓
Backend A
Backend B
Backend C
```

Requests should be distributed among available backends.

If Backend B fails:

```text
Backend A
Backend B X
Backend C
```

traffic should not continue blindly toward the failed instance.

You need mechanisms that connect stable service access to changing workload instances.

# 43. Storage Problem

Containers are designed to be replaceable.

But some data must survive.

Imagine:

```text
Container
↓
Writes Important Data
↓
Container Deleted
```

If the data exists only inside the container's writable layer, losing the container may mean losing that data.

Production systems need ways to provide storage independently of short-lived workload instances.

Conceptually:

```text
Application Workload
↓
Persistent Storage
```

instead of:

```text
Container Lifetime
=
Data Lifetime
```

# 48. What Is Container Orchestration?

Container orchestration is the automated coordination and management of containerized workloads across computing infrastructure.

At a high level, an orchestration platform helps answer:

```text
What should run?

How many should run?

Where should they run?

How should they communicate?

What happens when they fail?

How should they be updated?

How should resources be allocated?
```

---

# 49. Important Kubernetes Nuance About "Orchestration"

People commonly call Kubernetes:

```text
a container orchestrator.
```

That terminology is useful and widely understood.

However, the Kubernetes project itself makes an important conceptual distinction.

Traditional orchestration can imply:

```text
Do A
↓
Then B
↓
Then C
```

Kubernetes is more fundamentally built around independent control loops continuously reconciling actual state toward desired state.

Therefore the deeper Kubernetes mental model is not simply:

```text
Execute this sequence.
```

It is:

```text
Maintain this desired state.
```

That distinction becomes extremely important later.

---

# 50. Desired State

Suppose you say:

```text
I want 3 copies of my application running.
```

That is desired state.

For example:

```text
Desired Replicas = 3
```

Kubernetes observes:

```text
Current Replicas = 2
```

There is a difference.

The system works to reconcile it.

```text
Desired = 3
Actual = 2
↓
Create 1
↓
Actual = 3
```

---

# 51. Desired State Is Not a One-Time Command

A traditional imperative approach might say:

```text
Start container A.

Start container B.

Start container C.
```

A declarative approach says:

```text
I want three instances of this workload.
```

The system decides how to work toward that state.

This is a profound difference.

---

# 52. Declarative Management

Declarative management describes:

```text
What state should exist?
```

rather than requiring you to specify every low-level procedural step.

Conceptually:

```text
Desired State
↓
System
↓
Reconciliation
↓
Actual State Approaches Desired State
```

---

# 53. Imperative vs Declarative

Imperative:

```text
Start server A.

Start container X.

Start container Y.

If Y fails, start Y again.
```

Declarative:

```text
There should be two healthy replicas of this application.
```

Kubernetes is strongly built around the second model.

---

# 54. Reconciliation

Reconciliation means repeatedly comparing:

```text
Desired State
```

with:

```text
Observed State
```

and taking actions to reduce the difference.

Mental model:

```text
Desired State
↓
Observe
↓
Compare
↓
Difference?
├── No → Continue Observing
└── Yes
    ↓
    Act
    ↓
    Observe Again
```

This is not a one-time process.

It is continuous.

---

# 55. Declarative Model

The core model for this series is:

```text
Desired State
↓
Kubernetes API
↓
Controllers
↓
Observe Current State
↓
Compare
↓
Reconcile
↓
Desired State
```

You should remember this diagram.

It explains a huge amount of Kubernetes behavior.

---

# 56. Scheduling

Suppose you have:

```text
Node A
Node B
Node C
```

and need to run a new workload.

Where should it go?

Possible questions include:

```text

Which has memory?

Does the workload require a particular node?

Does it need specific hardware?

Should replicas be separated?

Are some nodes reserved?

Are there scheduling constraints?
```

The act of deciding where a workload should run is scheduling.

---

# 58. Scaling

```text

```

```text
10 replicas

```


# 59. Self-Healing

Suppose:

```text
Desired Replicas = 3
```

and one workload instance disappears.

Now:

```text
Actual Replicas = 2
```

A controller can detect the mismatch and work to restore the desired state.

```text
3 Desired
↓
1 Fails
↓
2 Running
↓
Controller Detects Difference
↓
Replacement Created
↓
3 Running
```

# 156. Knowledge Check

Answer these before moving forward.

### 1. What problem did physical-server deployment create?

Possible issues include poor resource utilization, weak workload isolation when sharing servers, slow provisioning, and dependency conflicts.

### 2. What does virtualization add?

It allows multiple isolated virtual machines with independent guest operating systems to share physical hardware.

### 3. What is a container image?

A packaged application artifact containing the application and runtime dependencies required to run it.

### 4. What is a container?

A running instance created from a container image.

### 5. What does a container runtime do?

It provides the runtime machinery required to execute and manage containers.

### 6. Name two Kubernetes-compatible container runtimes.

```text
containerd
CRI-O
```

### 7. Is Kubernetes a container runtime?

No.

### 8. Is Docker the same as Kubernetes?

No.

### 9. Can Docker-built images still run in modern Kubernetes environments?

Yes, assuming they conform to the relevant container image standards.

### 10. Why was dockershim important historically?

It provided Kubernetes' built-in compatibility layer for Docker Engine before that in-tree integration was removed.

---

# 157. Knowledge Check: Orchestration

### 11. Why are individual containers insufficient for large production environments?

Because organizations also need scheduling, scaling, recovery, service discovery, networking, storage, configuration, secrets, updates, and resource management.

### 12. What is desired state?

A declaration of what state the system should maintain.

### 13. What is actual state?

The state currently observed by the system.

### 14. What is reconciliation?

The continuous process of comparing actual state with desired state and taking actions to reduce differences.

### 15. What is scheduling?

Selecting an appropriate node on which a workload should run.

### 16. What is self-healing?

Automated action that works to restore desired workload state after certain failures.

### 17. Does self-healing fix bad code?

No.

### 18. Why is service discovery necessary?

Because workload instances can be replaced and their addresses can change.

### 19. What is a rolling update?

Gradually replacing old workload instances with new ones.

### 20. Why does resource management matter?

Because infrastructure has finite CPU, memory, and other resources.

---

# 158. Knowledge Check: Kubernetes

### 21. What is Kubernetes?

An open-source platform for managing containerized workloads and services using declarative configuration and automation.

### 22. Is Kubernetes a programming language?

No.

### 23. Is Kubernetes a container image?

No.

### 24. Is Kubernetes a complete CI/CD system?

No.

### 25. Is Kubernetes automatically a complete developer platform?

No.

### 26. Where did Kubernetes originate?

Google open sourced Kubernetes in 2014, drawing on extensive experience operating production workloads and internal cluster-management systems.

### 27. What is Borg?

A Google internal cluster-management system whose operational experience helped influence ideas behind Kubernetes.

### 28. What is CNCF?

The Cloud Native Computing Foundation, which supports Kubernetes and many other cloud-native projects.

### 29. What is managed Kubernetes?

A service model where a provider operates significant portions of the Kubernetes cluster foundation/control plane while customers retain important workload and platform responsibilities.

### 30. What is self-managed Kubernetes?

A model where the organization takes responsibility for more of the cluster lifecycle and infrastructure.
