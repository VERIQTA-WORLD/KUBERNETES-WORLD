# PART 16: HEALTH CHECKS, PROBES, AND APPLICATION RELIABILITY

## Teaching Kubernetes the Difference Between Starting, Ready, Alive, and Unhealthy

---

```text
an application that is alive

an application that is stuck

an application that should be restarted
```

```text

↓

↓

↓

Yes

```

```text
Deployment
↓

↓

↓

↓

        │                             │

        │                             │

        │                             │

```

# 2. The Application Health Problem

Kubernetes can know:

```text
container process exists
```

without knowing:

```text
application works correctly.
```

Imagine an HTTP server process is still running.

But internally:

```text
thread pool deadlocked

application initialization incomplete

cache still warming

database connection unavailable

configuration not loaded

worker queue stuck

application cannot answer requests
```

From the operating system's perspective:

```text
process exists.
```

From the user's perspective:

```text
application is broken.
```

Kubernetes needs additional signals.

Those signals are:

```text
probes.
```

---

# 3. What Is a Probe?

A Kubernetes probe is a diagnostic performed by the kubelet against a container.

The kubelet can use the result to determine whether:

```text
the application has started

the application is ready

the application is alive
```

Probe mechanisms include:

```text
HTTP

TCP

exec

gRPC
```

This part concentrates primarily on:

```text
HTTP

TCP

exec
```

while introducing gRPC health checking as an additional supported mechanism.

---

# 4. The Three Main Probe Purposes

Kubernetes provides three main probe purposes:

```text
startupProbe

readinessProbe

livenessProbe
```

Do not treat them as three names for the same thing.

They answer different questions.

---

# 5. The Most Important Table in This Part

| Probe     | Question                                         | Failure Effect                                                           |
| --------- | ------------------------------------------------ | ------------------------------------------------------------------------ |
| Startup   | Has the application finished starting?           | Container is eventually restarted if startup continues failing           |
| Readiness | Should this Pod receive traffic now?             | Pod becomes NotReady and is removed from normal matching Service traffic |
| Liveness  | Is the application alive enough to keep running? | Container is restarted after configured failure threshold                |

Memorize the intent, not merely the YAML syntax.

---

# 6. The Simplest Mental Model

```text
Startup
=
Can I begin checking normal health?
```

```text
Readiness
=
Should users send requests here?
```

```text
Liveness
=
Should Kubernetes restart me?
```

---

# 7. Running Does Not Mean Ready

A Pod can be:

```text
Running
```

while:

```text
Ready = False
```

Example:

```text
NAME     READY   STATUS    RESTARTS
web      0/1     Running   0
```

This means:

```text
the container is running
```

but:

```text
the container is not currently considered ready.
```

That distinction is fundamental.

---

# 8. Why This Matters

Without readiness checks:

```text
Container Starts
↓
Application still initializing
↓
Service sends traffic
↓
Requests fail
```

With readiness:

```text
Container Starts
↓
Not Ready
↓
No normal Service traffic
↓
Application initializes
↓
Readiness succeeds
↓
Ready
↓
Traffic begins
```

---

# 9. Liveness Probe

A liveness probe asks:

```text
Is this container's application still healthy enough
that keeping this container running makes sense?
```

If the liveness probe fails enough consecutive times:

```text
kubelet
↓
terminates container
↓
container restart policy applies
↓
container may restart
```

---

# 10. What Liveness Is Designed to Detect

A classic example is:

```text
deadlock.
```

The application process may still exist.

But:

```text
application cannot make progress.
```

Restarting the container may recover service.

---

# 11. Liveness Is Not a Traffic Switch

A common beginner mistake is thinking:

```text
liveness failure
=
remove Pod from Service.
```

That is primarily the job of:

```text
readiness.
```

Liveness failure is much more aggressive:

```text
restart the container.
```

---

# 12. Liveness Can Be Dangerous

A badly designed liveness probe can turn:

```text
temporary slowdown
```

into:

```text
mass restart event.
```

Example:

```text
traffic spike
↓
responses become slower
↓
liveness probes time out
↓
containers restart
↓
remaining replicas receive more traffic
↓
they become overloaded
↓
their liveness probes fail
↓
more containers restart
↓
capacity collapses
```

This is a cascading failure.

---

# 13. Liveness Rule

Only use liveness to test conditions where:

```text
restarting the container
is an appropriate recovery action.
```

Ask:

```text
If this check fails,
will restarting the process actually help?
```

If the answer is:

```text
No
```

that condition probably does not belong in liveness.

---

# 14. Readiness Probe

A readiness probe asks:

```text
Can this container currently serve its intended workload?
```

If readiness fails:

```text
container continues running
```

but:

```text
Pod is considered not ready.
```

For matching Services, that affects endpoint readiness and normal traffic routing.

---

# 15. Readiness Does Not Restart the Container

This is essential.

```text
Readiness failure
↓
Not Ready
↓
Traffic removed
```

not:

```text
Readiness failure
↓
Restart container
```

---

# 16. Readiness Can Fail Temporarily

Suppose an application becomes overloaded.

It might be better to:

```text
temporarily stop receiving new requests
```

rather than:

```text
restart the entire process.
```

Readiness can model temporary inability to serve.

---

# 17. Readiness Runs Throughout Container Life

Readiness is not merely a startup check.

It continues during the container lifecycle.

A Pod can transition:

```text
Not Ready
↓
Ready
↓
Not Ready
↓
Ready
```

without necessarily restarting.

---

# 18. Startup Probe

A startup probe asks:

```text
Has the application successfully started?
```

It protects slow-starting applications from premature liveness or readiness evaluation.

---

# 19. Startup Probe Behavior

When a startup probe exists:

```text
Container Starts
↓
Startup Probe Runs
↓
Startup Probe Failing
↓
Liveness and Readiness are not executed yet
↓
Startup eventually succeeds
↓
Startup Probe stops
↓
Liveness and Readiness begin normal operation
```

This creates a clean startup phase.

---

# 20. Why Startup Probes Matter

Imagine an application normally needs:

```text
90 seconds
```

to initialize.

Liveness configuration:

```text
probe every 10 seconds

restart after 3 failures
```

Without startup protection:

```text
application starts
↓
not ready in 30 seconds
↓
liveness fails
↓
container restarted
↓
application starts again
↓
not ready
↓
restarted again
```

The application may never finish starting.

---

# 21. Startup Probe Solves This

Example:

```yaml
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  periodSeconds: 5
  failureThreshold: 30
```

This gives approximately:

```text
30 × 5 seconds
=
150 seconds
```

of startup failure tolerance, aside from other timing factors.

Once startup succeeds:

```text
normal liveness/readiness checking begins.
```

---

# 22. Startup Probe Is Not Permanent

Unlike readiness and liveness:

```text
startup probe stops after success.
```

It protects initialization.

It is not intended to continuously evaluate application health after successful startup.

---

# 23. Probe Results

Probe executions can produce:

```text
Success

Failure

Unknown
```

Conceptually:

```text
Success
→ check passed
```

```text
Failure
→ check failed
```

```text
Unknown
→ diagnostic itself could not be completed normally
```

Kubernetes reacts according to the probe type and configured thresholds.

---

# 24. Probe Mechanisms

A probe must define a mechanism.

Common mechanisms:

```text
httpGet

tcpSocket

exec

grpc
```

Each tests application health differently.

---

# 25. HTTP Probe

An HTTP probe sends an HTTP request to the container through the Pod network.

Example:

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
```

The kubelet sends a request to:

```text
Pod IP
↓
Port 8080
↓
/ready
```

---

# 26. HTTP Success

For standard HTTP probes, status codes:

```text
200 through 399
```

are considered successful.

Other HTTP response status codes indicate failure.

---

# 27. Good HTTP Health Endpoints

Common patterns:

```text
/health

/healthz

/live

/ready

/startup
```

The names are application design choices.

Kubernetes does not require those exact paths.

---

# 28. Better Endpoint Separation

A mature application might expose:

```text
/health/live

/health/ready

/health/startup
```

Each endpoint answers a different question.

This is often safer than making one endpoint perform every possible dependency check.

---

# 29. HTTP Liveness Example

```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3
```

Meaning:

```text
every 10 seconds
↓
request /health/live
↓
allow up to 2 seconds
↓
3 consecutive failures
↓
container considered unhealthy
↓
restart behavior triggered
```

---

# 30. HTTP Readiness Example

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2
  successThreshold: 1
```

Meaning:

```text
check readiness repeatedly
↓
failure makes Pod NotReady
↓
success can restore readiness
```

---

# 31. HTTP Startup Example

```yaml
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  periodSeconds: 5
  failureThreshold: 30
```

The application has a generous startup window before restart behavior is triggered.

---

# 32. Named Ports

HTTP probes can use named ports.

Container:

```yaml
ports:
  - name: http
    containerPort: 8080
```

Probe:

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: http
```

This can improve readability and reduce duplicated numeric port references.

---

# 33. TCP Probe

A TCP probe checks whether Kubernetes can establish a TCP connection to a specified port.

Example:

```yaml
livenessProbe:
  tcpSocket:
    port: 8080
```

Conceptually:

```text
kubelet
↓
connect to Pod IP:8080
↓
connection succeeds?
```

---

# 34. What TCP Probes Prove

A successful TCP probe proves roughly:

```text
something is accepting TCP connections
on that port.
```

It does not necessarily prove:

```text
application logic works

database queries work

HTTP responses are correct

business transactions work
```

---

# 35. When TCP Probes Are Useful

TCP probes can be useful when:

```text
application does not expose HTTP health endpoints

service is TCP-based

opening the listening socket is a meaningful health signal
```

---

# 36. TCP Probe Limitation

Suppose:

```text
port 8080 accepts connections
```

but the application returns:

```text
500 Internal Server Error
```

for every HTTP request.

TCP probe may still succeed.

An HTTP probe can provide deeper application-level evidence.

---

# 37. Exec Probe

An exec probe runs a command inside the container.

Example:

```yaml
livenessProbe:
  exec:
    command:
      - /bin/sh
      - -c
      - test -f /tmp/healthy
```

Success:

```text
exit code 0
```

Failure:

```text
non-zero exit code.
```

---

# 38. Exec Probe Example

Suppose the application creates:

```text
/tmp/ready
```

after initialization.

You could test:

```yaml
readinessProbe:
  exec:
    command:
      - /bin/sh
      - -c
      - test -f /tmp/ready
```

If file exists:

```text
exit 0
→ Ready
```

If missing:

```text
non-zero
→ NotReady
```

---

# 39. Exec Probe Considerations

Exec probes require:

```text
executing a process inside the container.
```

Frequent exec probes across many high-density Pods can add overhead.

Also, minimal/distroless images may not contain:

```text
/bin/sh

curl

cat

test
```

Design probes based on what the container actually contains.

---

# 40. Do Not Assume `curl` Exists

This may fail:

```yaml
exec:
  command:
    - curl
    - http://localhost:8080/health
```

because the image may not contain:

```text
curl.
```

If HTTP health is available, prefer:

```text
httpGet
```

instead of launching curl repeatedly.

---

# 41. gRPC Probe Concept

Kubernetes also supports native gRPC probes for applications implementing the gRPC Health Checking Protocol.

Conceptually:

```text
kubelet
↓
gRPC health request
↓
application health service
↓
SERVING
```

This is useful for native gRPC applications.

The same fundamental probe purposes still apply:

```text
startup

readiness

liveness
```

---

# 42. Probe Timing

Probe behavior is controlled by several timing fields:

```text
initialDelaySeconds

periodSeconds

timeoutSeconds

failureThreshold

successThreshold
```

Understanding these is more important than copying arbitrary values from examples.

---

# 43. `initialDelaySeconds`

Example:

```yaml
initialDelaySeconds: 20
```

Meaning:

```text
wait before beginning this probe.
```

Default:

```text
0
```

if not specified.

---

# 44. `initialDelaySeconds` Is Not Startup Detection

A large initial delay can prevent premature checks.

But it is a fixed delay.

Example:

```text
initialDelaySeconds: 120
```

means Kubernetes waits roughly that startup delay even if the application becomes healthy much earlier before that probe begins.

A startup probe is often a better model for applications with variable startup time.

---

# 45. `periodSeconds`

Example:

```yaml
periodSeconds: 10
```

means:

```text
perform the probe approximately every 10 seconds
```

subject to Kubernetes probe behavior.

Default:

```text
10 seconds.
```

Minimum:

```text
1 second.
```

---

# 46. Readiness Timing Nuance

While a container is not Ready, Kubernetes may execute readiness checks more frequently than the configured `periodSeconds` in order to make the Pod ready sooner.

Therefore do not build application correctness around an assumption that readiness executes at perfectly exact intervals.

---

# 47. `timeoutSeconds`

Example:

```yaml
timeoutSeconds: 2
```

means:

```text
allow the probe up to 2 seconds
before considering it timed out.
```

Default:

```text
1 second.
```

---

# 48. One-Second Timeout Trap

If you omit:

```yaml
timeoutSeconds:
```

the default is short.

Applications whose health endpoint occasionally needs slightly longer may experience false failures.

But simply setting:

```text
timeoutSeconds: 60
```

is not automatically better.

Health endpoints should generally be:

```text
fast

cheap

predictable.
```

---

# 49. `failureThreshold`

Example:

```yaml
failureThreshold: 3
```

means Kubernetes requires:

```text
3 consecutive failures
```

before treating the overall probe as failed for its probe purpose.

Default:

```text
3.
```

---

# 50. Liveness Failure Threshold

Example:

```text
periodSeconds = 10

failureThreshold = 3
```

Simplified mental model:

```text
failure
↓
10 sec
failure
↓
10 sec
failure
↓
restart action
```

This is approximately a 30-second failure tolerance after probing reaches the failure sequence, although exact wall-clock timing also depends on probe execution and other timing details.

---

# 51. Startup Failure Window

Example:

```yaml
startupProbe:
  httpGet:
    path: /startup
    port: 8080
  periodSeconds: 10
  failureThreshold: 30
```

Approximate startup tolerance:

```text
10 × 30
=
300 seconds
=
5 minutes
```

This is a useful design calculation.

---

# 52. `successThreshold`

`successThreshold` means:

```text
minimum consecutive successful probes
needed after failure before the probe is considered successful again.
```

Default:

```text
1.
```

---

# 53. Important `successThreshold` Rule

For:

```text
liveness probes

startup probes
```

`successThreshold` must be:

```text
1.
```

Readiness can use values greater than 1.

---

# 54. Why Readiness May Use Multiple Successes

Suppose an unstable application alternates:

```text
healthy
unhealthy
healthy
unhealthy
```

A readiness configuration such as:

```yaml
successThreshold: 2
```

can require multiple consecutive successful checks before traffic returns.

This can reduce rapid ready/unready oscillation in some designs.

---

# 55. Probe Timing Example

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080

  initialDelaySeconds: 5
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2
  successThreshold: 2
```

Interpretation:

```text
wait before normal readiness checks begin

probe repeatedly

allow limited response time

multiple failures can remove readiness

multiple successes can restore readiness
```

---

# 56. Never Copy Probe Numbers Blindly

Values depend on:

```text
application startup behavior

normal response latency

load characteristics

failure mode

recovery time

dependency behavior

traffic patterns
```

Probe timing is application engineering.

It is not merely Kubernetes syntax.

---

# 57. Readiness and Service Traffic

Suppose Service selects:

```text
app=web
```

and there are three Pods:

```text
Pod A → Ready

Pod B → Ready

Pod C → NotReady
```

Normal Service traffic should target:

```text
Pod A

Pod B
```

not:

```text
Pod C.
```

---

# 58. Readiness Architecture

```text
Readiness Probe
↓
kubelet evaluates readiness
↓
Pod readiness condition
↓
EndpointSlice endpoint readiness
↓
Service traffic behavior
```

This connects application health directly to Kubernetes networking.

From Part 8:

```text
Service
↓
EndpointSlice
↓

```

Readiness affects whether a Pod endpoint is considered ready for normal Service traffic.

This is why readiness is not merely cosmetic status information.

# 63. Liveness and Restarts

When liveness fails enough times:

```text
kubelet
↓
terminates unhealthy container
↓
restartPolicy applies
```

For containers in Deployments:

```text
restartPolicy
```

is effectively:

```text
Always.
```

The container normally restarts inside the same Pod.

---

# 64. Liveness Restart Does Not Necessarily Replace the Pod

Important distinction:

```text
liveness failure
↓
container restart
```

usually does not mean:

```text
Deployment immediately creates an entirely new Pod.
```

The same Pod can remain while its container restart count increases.

---

# 65. Observe Restart Count

Run:

```bash
kubectl get pods \
  -n <NAMESPACE>
```

Example:

```text
NAME      READY   STATUS    RESTARTS
web       1/1     Running   4
```

This tells you:

```text
container has restarted.
```

---

# 66. Previous Container Logs

After a restart:

```bash
kubectl logs <POD> \
  -n <NAMESPACE> \
  --previous
```

This is extremely important.

It retrieves logs from the previous container instance when available.

For probe-related restart loops, this may contain the most useful application evidence.

---

# 67. Startup Protection

Without startup probe:

```text
slow application
↓
liveness begins
↓
liveness fails
↓
container restarts
↓
slow application starts again
↓
liveness fails again
```

With startup probe:

```text
slow application
↓
startup probe owns startup period
↓
liveness/readiness suppressed
↓
application initializes
↓
startup succeeds
↓
normal probes begin
```

---

# 68. Startup Probe Design

A useful startup probe should test:

```text
whether initialization has completed enough
for normal health checking to begin.
```

It should not simply be:

```text
sleep for a huge arbitrary time.
```

Use application behavior when possible.

# 70. LAB 1: Basic Readiness Probe

Create:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: readiness-web
  namespace: probe-lab

spec:
  replicas: 3

  selector:
    matchLabels:
      app: readiness-web

  template:
    metadata:
      labels:
        app: readiness-web

    spec:
      containers:
        - name: nginx
          image: nginx:1.27

          ports:
            - name: http
              containerPort: 80

          readinessProbe:
            httpGet:
              path: /
              port: http

            initialDelaySeconds: 2
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
            successThreshold: 1

          resources:
            requests:
              cpu: "25m"
              memory: "32Mi"
            limits:
              memory: "64Mi"
```

# 75. Expected Readiness Failure

The container may remain:


# 94. Choosing the Right Probe

For an HTTP API:

```text

```

is often appropriate.

For a non-HTTP TCP service:

```text
TCP probe
```

may be appropriate.

For application-specific local state:

```text
exec probe
```

may be appropriate.

For native gRPC health checking:

```text
gRPC probe
```

may be appropriate.

---

# 95. Bad Probe Design: `/`

Suppose liveness checks:

```text

```

The homepage performs:

```text
database query

cache query

authentication lookup

remote API call

template rendering
```

Now every liveness check depends on many systems.

A remote dependency outage can make Kubernetes restart perfectly healthy application processes.

That is dangerous.

---

# 96. Better Liveness Endpoint

A liveness endpoint should generally answer:

```text
Is this application process capable of continuing useful operation?
```

It should be:

```text
cheap

local

fast

reliable

unlikely to fail because of unrelated dependencies
```

---

# 97. Readiness Can Be Dependency-Aware

Readiness can sometimes include critical dependencies.

Example:

```text
Application process healthy
↓
Database unavailable
↓
Application cannot serve requests
↓
Readiness = false
```

That may be reasonable.

But dependency checks still require careful design.

---

# 98. Dependency Amplification Problem

Imagine:

```text
100 application Pods
```

Each readiness probe checks:

```text
database every second.
```

Now probes themselves generate:

```text
100 database requests per second
```

even before user traffic.

During database degradation, health checks can worsen the problem.

---

# 99. Better Dependency Health Design

Possible patterns include:

```text
cached dependency state

local health state maintained by application

lightweight checks

reasonable probe frequency

failure thresholds

timeouts

circuit breakers
```

Health checking should not become a denial-of-service mechanism against dependencies.

---

# 100. Cascading Failure Example

Suppose 20 replicas serve traffic.

Traffic spike occurs.

Each Pod becomes slow.

Liveness timeout:

```text
1 second.
```

Application health endpoint takes:

```text
1.5 seconds.
```

Result:

```text
liveness fails
↓
containers restart
↓
capacity decreases
↓
traffic shifts to remaining Pods
↓
remaining Pods slow further
↓
their probes fail
↓
more restarts
↓
service collapse
```

The liveness probe amplified the incident.

---

# 101. Safer Response

Maybe the correct behavior under temporary overload is:

```text
readiness false
```

rather than:

```text
restart container.
```

Or perhaps the application should remain ready and rely on:

```text
load shedding

autoscaling

backpressure

rate limiting
```

depending on architecture.

Probe behavior must match application failure semantics.

---

# 102. Never Use Liveness as a Generic Dependency Monitor

Bad:

```text
Database unavailable
↓
Liveness false
↓
Restart application
↓
Database still unavailable
↓
Restart application
↓
repeat forever
```

Restarting cannot repair the database.

This wastes resources and can create additional load.

---

# 103. Readiness Dependency Caution

Even readiness dependency checks can cause systemic problems.

Suppose all application Pods depend on one database.

Database experiences a brief slowdown.

Every Pod becomes NotReady simultaneously.

Result:

```text
Service has no ready endpoints.
```

Sometimes degraded service is preferable to:

```text
zero service.
```

Design readiness semantics carefully.

---

# 104. Health Endpoints Are Application APIs

Treat:

```text
/live

/ready

/startup
```

as production application interfaces.

They should have:

```text
clear semantics

tests

documentation

performance expectations

stable behavior
```

Do not add them as an afterthought.

---

# 105. Bad Probe Design: Expensive Query

Bad liveness:

```text
SELECT COUNT(*)
FROM huge_table;
```

This can:

```text
load database

time out

restart applications

increase database load further
```

Health checks should not perform expensive business operations.

---

# 106. Bad Probe Design: External Internet Dependency

Suppose liveness checks:

```text
Can I reach example-external-api.com?
```

External provider outage:

```text
provider fails
↓
all your Pods restart
↓
your own service becomes unavailable
```

You converted:

```text
dependency outage
```

into:

```text
application outage.
```

---

# 107. Bad Probe Design: Too Aggressive Timing

Example:

```yaml
periodSeconds: 1
timeoutSeconds: 1
failureThreshold: 1
```

One brief scheduling delay or application pause can cause immediate failure action.

For liveness this can be especially dangerous.

---

# 108. Bad Probe Design: Too Relaxed

Opposite extreme:

```yaml
periodSeconds: 60
failureThreshold: 10
```

could allow a genuinely stuck application to remain unhealthy for a long period before recovery.

Probe design balances:

```text
false positives
```

against:

```text
slow detection.
```

---

# 109. Bad Probe Design: Same Semantics Everywhere

You can technically use the same endpoint for multiple probes.

But ask whether:

```text
alive
```

really means the same thing as:

```text
ready.
```

Often it does not.

---

# 110. Better Separation

Example:

```text
/startup
→ initialization complete
```

```text
/live
→ process can make progress
```

```text
/ready
→ application can serve requests now
```

This creates clearer failure semantics.

---

# 111. LAB 7: Design Safer Probes

Given application behavior:

```text
startup takes 20–90 seconds

database may temporarily disconnect

process occasionally deadlocks

cache is optional
```

Design:

```text
startup probe
↓
allow up to approximately 120 seconds
```

```text
liveness
↓
detect internal deadlock
without requiring database/cache
```

```text
readiness
↓
check ability to serve critical requests
```

Do not make optional cache availability a reason to restart the application.

Application worst-case startup:




---

# 127. Do You Always Need Liveness?

No.

If the application reliably:

```text
exits when unrecoverably unhealthy
```

the container runtime/kubelet restart behavior may already provide appropriate recovery.

A liveness probe is useful when:

```text
process can remain running
while application becomes unrecoverably stuck.
```

---

# 128. Do You Always Need Readiness?

Not necessarily.

But readiness becomes particularly valuable when:

```text
startup requires initialization

application can temporarily lose ability to serve

traffic must not arrive before warm-up

application requires controlled traffic admission
```

---

# 129. Do You Always Need Startup Probe?

No.

Applications that start almost instantly and predictably may not need one.

Startup probes are especially useful for:

```text
slow startup

variable startup

large cache loading

initial data processing

complex initialization

legacy applications
```

---

# 130. Probe-Level `terminationGracePeriodSeconds`

Modern Kubernetes supports probe-level:

```text
terminationGracePeriodSeconds
```

for liveness and startup probe failure handling.

This can override the Pod-level termination grace period for termination triggered by that probe.

Use this carefully.

---

# 131. Why Probe-Level Grace Can Matter

Suppose normal Pod deletion needs:

```text
60 seconds
```

for graceful traffic draining.

But a deadlocked process should receive only:

```text
5 seconds
```

before forced termination.

A probe-specific termination grace can distinguish these scenarios.

Do not shorten it below what the application genuinely needs to terminate safely.

---

# 132. Graceful Shutdown

Reliability is not only:

```text
starting correctly.
```

It is also:

```text
stopping correctly.
```

Applications should handle termination gracefully.

---

# 133. Kubernetes Termination Concept

Simplified lifecycle:

```text
Pod termination requested
↓
Endpoint begins transitioning away from normal traffic
↓
preStop hook may run
↓
termination signal sent to container process
↓
application shuts down
↓
grace period expires if necessary
↓
forced termination
```

The exact termination sequence contains important implementation details, but this is the operational mental model.

---

# 134. SIGTERM

Containers normally receive a termination signal when Kubernetes asks them to stop.

For many Linux applications this is:

```text
SIGTERM.
```

Application should use that opportunity to:

```text
stop accepting new work

finish in-flight requests

flush buffers

close connections

commit safe state

release resources
```

---

# 135. SIGKILL

If the application does not exit before the grace period expires:

```text
forced termination
```

can occur.

For Linux processes this is commonly associated with:

```text
SIGKILL.
```

Unlike SIGTERM:

```text
SIGKILL cannot be handled by the application.
```

---

# 136. `terminationGracePeriodSeconds`

Example:

```yaml
spec:
  terminationGracePeriodSeconds: 30
```

This provides a termination grace period for the Pod.

Default Pod termination grace is commonly:

```text
30 seconds
```

unless configured otherwise.

---

# 137. Grace Period Must Match Application Behavior

Suppose an application needs:

```text
45 seconds
```

to safely finish long-running requests.

Setting:

```yaml
terminationGracePeriodSeconds: 5
```

may cause:

```text
requests terminated

partial work

connection resets

data inconsistency
```

Graceful shutdown is application-specific.

---

# 138. `preStop`

A container lifecycle hook can define:

```yaml
lifecycle:
  preStop:
    exec:
      command:
        - /bin/sh
        - -c
        - /app/prepare-shutdown.sh
```

This can perform application-specific shutdown preparation.

---

# 139. Important `preStop` Rule

The termination grace period includes the time spent executing the `preStop` hook.

Do not assume:

```text
preStop time
+
terminationGracePeriodSeconds
```

are completely separate unlimited periods.

Design shutdown within the available termination window.

---

# 140. Do Not Use Arbitrary Sleep as Your Entire Shutdown Strategy

A pattern such as:

```text
preStop:
sleep 20
```

is sometimes used to allow routing changes to propagate.

But arbitrary sleeps are not a substitute for:

```text
correct application shutdown

traffic draining

connection handling

termination semantics.
```

Understand why the delay exists before adding it.

---

# 141. Graceful Shutdown and Readiness

Applications may deliberately become:

```text
NotReady
```

during shutdown so that new traffic stops arriving.

However, Kubernetes Pod termination itself also updates endpoint readiness behavior.

Do not build a shutdown design solely around manually failing readiness without understanding Kubernetes termination and endpoint handling.

---

# 142. Graceful Shutdown Architecture

```text
Termination Requested
↓
Stop New Traffic
↓
Allow In-Flight Requests to Finish
↓
Application Receives Termination Signal
↓
Close Resources
↓
Exit
```

Goal:

```text
zero or minimal user-visible disruption.
```

---

# 145. Disruptions

A disruption is an event that causes one or more Pods to become unavailable or disappear.

Kubernetes distinguishes broadly between:

```text
voluntary disruptions
```

and:

```text
involuntary disruptions.
```

---

# 146. Involuntary Disruption

Examples include:

```text
physical hardware failure

VM failure

kernel panic

node network partition

certain node resource-pressure evictions

unexpected infrastructure failure
```

These are not orderly planned maintenance events.

---

# 147. Voluntary Disruption

Examples include:

```text
node drain for maintenance

node drain during upgrade

some cluster scale-down operations

administrator-initiated eviction

application owner changes
```

But different voluntary actions interact differently with PodDisruptionBudgets.

---

# 148. Important PDB Limitation

PodDisruptionBudgets do not protect against every way a Pod can disappear.

For example:

```text
directly deleting a Pod
```

or:

```text
deleting its Deployment
```

is not the same as requesting eviction through the Eviction API.

A PDB is not a universal "never let my Pods go down" switch.

---

# 149. PodDisruptionBudget

A:

```text
PodDisruptionBudget
```

or:

```text
PDB
```

limits how many Pods in a replicated application can be unavailable because of voluntary disruptions that respect the Eviction API.

---

# 150. PDB Mental Model

Suppose:

```text
5 replicas
```

and application requires at least:

```text
4 available.
```

PDB:

```yaml
minAvailable: 4
```

Then voluntary eviction generally cannot reduce healthy availability below that budget.

---

# 151. PDB Does Not Create Replicas

A PDB does not mean:

```text
create enough Pods to satisfy minAvailable.
```

Replica count comes from:

```text
Deployment

StatefulSet

other workload controller.
```

PDB controls disruption allowance.

---

# 152. PDB Does Not Fix Broken Pods

If Pods are already unhealthy:

```text
PDB does not repair them.
```

Health and replica controllers still matter.

---

# 153. PDB Does Not Prevent Node Failure

If hardware suddenly dies:

```text
PDB cannot stop the hardware failure.
```

Involuntary disruptions can happen regardless of the budget.

They do, however, affect the remaining disruption budget state.

---

# 154. PDB and Eviction API

Tools such as:

```text
kubectl drain
```

normally request Pod eviction through Kubernetes' eviction mechanism.

The Eviction API evaluates applicable PDBs.

Conceptually:

```text
Drain Node
↓
Eviction Request
↓
Check PDB
↓
Would eviction violate budget?
↓
Yes
↓
Eviction temporarily rejected
```

---

# 155. `minAvailable`

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
  namespace: probe-lab

spec:
  minAvailable: 2

  selector:
    matchLabels:
      app: reliable-web
```

Meaning:

```text
voluntary evictions respecting this PDB
should preserve at least 2 available Pods
for the selected application.
```

---

# 156. Percentage `minAvailable`

Example:

```yaml
minAvailable: 75%
```

This expresses availability relative to the intended replica count.

Use percentages carefully, especially with small replica counts, because rounding behavior matters.

---

# 157. `maxUnavailable`

Instead of minimum available, you can specify:

```yaml
maxUnavailable: 1
```

Meaning:

```text
allow at most one Pod
to be unavailable from relevant voluntary disruption
at a time.
```

---

# 158. Do Not Specify Both

A PDB should use:

```text
minAvailable
```

or:

```text
maxUnavailable
```

not both simultaneously.

Choose the expression that best communicates your application's availability requirement.

---

# 159. PDB Example

Deployment:

```text
replicas = 3
```

PDB:

```yaml
minAvailable: 2
```

Conceptually:

```text
3 healthy
↓
one voluntary eviction can proceed
↓
2 remain available
```

Another eviction may need to wait until sufficient availability is restored.

---

# 160. PDB Selector

The PDB selector determines which Pods belong to the protected application.

Example:

```yaml
selector:
  matchLabels:
    app: reliable-web
```

If labels do not match:

```text
PDB may protect the wrong Pods
or no intended Pods.
```

Selector correctness is critical.

---

# 161. PDB and Deployment Rollouts

A subtle but important point:

```text
Deployment rolling updates
```

are controlled by the Deployment rollout strategy.

A PDB does not directly constrain the Deployment controller's own rolling update behavior in the same way it constrains voluntary evictions through the Eviction API.

For Deployment rollouts, review:

```text
maxUnavailable

maxSurge
```

from Part 7.

---

# 162. Two Different `maxUnavailable` Fields

Do not confuse:

```text
Deployment:
strategy.rollingUpdate.maxUnavailable
```

with:

```text
PodDisruptionBudget:
spec.maxUnavailable
```

They belong to different resources and solve different problems.

---

# 163. Deployment Availability Control

```text
Deployment maxUnavailable
↓
controls rolling update behavior
```

PDB:

```text
PDB maxUnavailable
↓
controls permitted voluntary disruptions
through mechanisms that respect the PDB
```

# 164. PDB and Node Drain

Imagine:

```text
3 application replicas

Node A → replica 1

Node B → replica 2

Node C → replica 3
```

PDB:

```text
minAvailable: 2
```

Drain Node A:

```text
eviction can proceed
```

assuming the budget permits it.

If another replica is already unavailable:

```text
drain may wait
```

until application availability recovers.

# 165. PDB Can Block Maintenance

This is intentional.

But a badly configured PDB can make operations difficult.

Example:

```text
replicas: 1

minAvailable: 1
```

Now voluntary eviction of that sole healthy replica would violate the budget.

Node drain can be blocked.

---

# 166. Single Replica Reality

If application has:

```text
1 replica
```

you cannot simultaneously guarantee:

```text
zero downtime
```

and:

```text
freely evict that only replica.
```

PDB cannot manufacture high availability from a single Pod.

---

# 167. PDB Design Requires Replication

A highly available workload usually combines:

```text
multiple replicas

failure-domain spreading

readiness probes

graceful termination

PDB

sufficient spare capacity
```

Each solves a different problem.

---

# 168. PDB and Unhealthy Pods

PDB behavior around unhealthy running Pods includes:

```text
unhealthyPodEvictionPolicy.
```

Current Kubernetes supports policies including:

```text
IfHealthyBudget

AlwaysAllow
```

This affects whether unhealthy running Pods can be evicted during operations such as node drain.

---

# 169. `AlwaysAllow`

Conceptually:

```text
unhealthyPodEvictionPolicy: AlwaysAllow
```

allows unhealthy running Pods to be evicted regardless of whether the PDB's normal healthy-budget condition would otherwise block that unhealthy Pod's eviction.

This can help prevent node drains from becoming stuck behind misbehaving Pods.

Use current Kubernetes documentation when setting this in production.

# 170. PDB Example with Unhealthy Pod Policy

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget

  name: reliable-web
  namespace: probe-lab

spec:
  minAvailable: 2

  unhealthyPodEvictionPolicy: AlwaysAllow

  selector:
    matchLabels:
      app: reliable-web
```

Understand your cluster version and application requirements before using advanced PDB behavior.

# 182. PDB and Anti-Affinity

Suppose:

```text
3 replicas

3 nodes

hard one-per-node anti-affinity
```

```text

```

The PDB does not override scheduling constraints.

Good:

```text

```

or minimal structured state:

```json
{

}
```

Avoid exposing:

```text

internal topology

customer data

sensitive configuration
```

# 188. Health Endpoints and Authentication

Kubelet probes must be able to reach the configured health endpoint.

If your application requires complex interactive authentication for every health request, probe design becomes harder.

A common design is:

```text

```

that reveals no sensitive information and is appropriately protected by network/application architecture.

# 190. Probe Network Path

HTTP and TCP probes are performed by the kubelet against the Pod.

Conceptually:

```text

↓

↓

```

This is not the same path as:

```text

↓
Load Balancer
↓
Ingress/Gateway
↓
Service
↓

```

A successful Pod probe does not prove the complete external request path works.

# 197. Probe and Stateful Applications

Stateful workloads require extra care.

A database process may be:

```text
alive
```

while:

```text
not ready to accept client traffic.
```

Examples:

```text
replica still synchronizing

recovery in progress

leader election incomplete

database starting crash recovery
```

Separate liveness from readiness carefully.

---

# 198. Never Restart a Database Merely Because a Replica Is Synchronizing

If:

```text
database replica still catching up
```

then:

```text
readiness false
```

may be appropriate.

But:

```text
liveness false
```

may repeatedly restart the database and prevent recovery.

This is exactly why probe semantics matter.

# 199. Job Probe Considerations

Jobs are run-to-completion workloads.

A readiness probe is often irrelevant if:

```text
Job does not receive Service traffic.
```

Liveness may still be useful in some designs if a worker can become permanently stuck.

But probe configuration should match workload purpose.

# 200. DaemonSet Probe Considerations

Node-level agents may use:

```text

liveness
```

but understand what readiness means for that agent.

If it is not behind a Service, readiness may still be useful as status, but its traffic-routing effect may be irrelevant.

# 222. Reliability Anti-Pattern: Health Endpoint Always Returns 200

Some teams create:

```text
/health
```

that always returns:

```text
200 OK
```

even when the application cannot function.

This satisfies Kubernetes but provides no useful health signal.

A health endpoint should represent meaningful application state.

# 223. Reliability Anti-Pattern: Everything in Liveness

Bad:

```text
database

Redis

Kafka

external payment API

DNS

object storage

third-party identity provider
```

all checked by liveness.

One external outage can restart the entire fleet.

Do not make liveness a global dependency dashboard.

---

# 224. Reliability Anti-Pattern: No Startup Protection

Slow application:

```text
needs 3 minutes.
```

Liveness begins after:

```text
10 seconds.
```

Container repeatedly restarts.

Use:

```text
startupProbe
```

instead of inflating liveness timing solely to survive startup.

---

# 225. Reliability Anti-Pattern: Readiness Too Sensitive

If readiness fails after one tiny latency spike:

```text
Pods leave Service rapidly
↓
remaining Pods receive more traffic
↓
remaining Pods become overloaded
↓
they become NotReady
↓
capacity collapses
```

Readiness can also participate in cascading failures.

---

# 226. Reliability Anti-Pattern: PDB with One Replica

```text
replicas: 1
minAvailable: 1
```

may block voluntary eviction.

This does not create availability.

If downtime is unacceptable:

```text
design actual redundancy.
```

---

# 227. Reliability Anti-Pattern: No Spare Capacity

Three replicas exactly fill three nodes.

PDB protects disruption.

One node drains.

Replacement cannot schedule anywhere.

Reliability requires:

```text
capacity to recover.
```

---

# 228. Reliability Anti-Pattern: Replicas in One Failure Domain

Five replicas:

```text
all on one node.
```

PDB:

```text
minAvailable: 4.
```

Node fails involuntarily.

All five disappear.

PDB cannot protect against that.

Combine with Part 15:

```text
anti-affinity

topology spread

multi-zone capacity
```

where appropriate.

# 230. Example Production Pod Template

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: production

spec:
  replicas: 3

  selector:
    matchLabels:
      app: api

  strategy:
    type: RollingUpdate

    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1

  template:
    metadata:
      labels:
        app: api

    spec:
      terminationGracePeriodSeconds: 30

      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway

          labelSelector:
            matchLabels:
              app: api

      containers:
        - name: api
          image: example.invalid/api:1.0.0

          ports:
            - name: http
              containerPort: 8080

          startupProbe:
            httpGet:
              path: /health/startup
              port: http
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 24

          readinessProbe:
            httpGet:
              path: /health/ready
              port: http
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
            successThreshold: 1

          livenessProbe:
            httpGet:
              path: /health/live
              port: http
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3

          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"

            limits:
              memory: "512Mi"
```

This is an architectural example.

Production values must come from actual application behavior and testing.

```text
timeoutSeconds

```

```text
failureThreshold
```

```text
Application starts
↓
Startup Probe protects initialization

↓
```
