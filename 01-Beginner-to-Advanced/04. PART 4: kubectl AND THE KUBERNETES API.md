# 3. kubectl Is an API Client

`kubectl` is primarily a command-line client for interacting with Kubernetes through its API.

It does not normally:

```text
SSH into every node

Read etcd directly

Talk directly to containerd

Edit Kubernetes database files

Manually contact every Pod
```

Instead:

```text
kubectl
↓
Kubernetes API Server
↓
Kubernetes API
```

The API server is the front door to Kubernetes.

# 5. Kubernetes Objects

A Kubernetes object represents persistent intent or state in the Kubernetes system.

For example, a Deployment object can express:

```text
Run this application.

Use this container image.

Maintain this many replicas.

Apply these labels.

Use this update strategy.
```

Kubernetes then works continuously toward the declared state.

Mental model:

```text
Object
↓
Desired State
↓
Stored Through Kubernetes API
↓
Controllers Observe
↓
Actual State
↓
Reconciliation
```

---

# 6. spec and status

Many Kubernetes objects contain two important concepts:

```text
spec
```

and:

```text
status
```

Think:

```text
spec
↓
What you want

status
↓
What Kubernetes currently observes
```

Example:

```text
spec.replicas = 3
```

means:

```text
I want three replicas.
```

The status may indicate how many replicas actually exist or are available.

---

# 7. Desired State vs Observed State

Suppose:

```text
Desired replicas
=
3
```

but:

```text
Running replicas
=
2
```

Kubernetes does not simply record the difference.

Controllers work to reconcile it.

```text
Desired State
3 replicas
↓
Controller Observes
2 replicas
↓
Difference Detected
↓
Create Replacement
↓
Actual State Moves Toward Desired State
```

This is why understanding API objects is more important than memorizing commands.

# 8. The kubectl Request Journey

Suppose you run:

```bash
kubectl get pods
```

Conceptually:

```text
1. Shell finds kubectl

2. kubectl starts

3. kubectl loads kubeconfig

4. kubectl determines context

5. kubectl determines cluster endpoint

12. kubectl formats the result

```

One command crosses several layers.

---

# 9. kubectl Does Not Bypass Kubernetes Security

A user may have:

```text
kubectl installed
```

and:

```text
working kubeconfig
```

but still be unable to perform certain actions.

For example:

```bash
kubectl get pods
```

might work while:

```bash
kubectl delete pods ...
```

is forbidden.

Why?

Because Kubernetes authorization can allow:

```text
read
```

while denying:

```text
delete.
```

kubectl does not grant permissions.

The API server enforces authorization.

# 12. Important Syntax Correction

You may sometimes see kubectl described conceptually as:

```text
kubectl RESOURCE ACTION NAME FLAGS
```

But actual kubectl command syntax normally places the command/action first:

```text
kubectl ACTION RESOURCE NAME FLAGS
```

Example:

```bash
kubectl describe pod web
```

not:

```bash
kubectl pod describe web
```

Use the actual CLI syntax when operating the cluster.

# 51. UID

Every Kubernetes object has a UID assigned by Kubernetes.

A name may be reused after an object is deleted.

A UID identifies a particular object instance.

Conceptually:

```text
Pod named web
UID A
↓
Deleted

New Pod named web
UID B
```

Same name.

Different object instance.

---

# 52. resourceVersion

`resourceVersion` participates in Kubernetes concurrency and change-tracking semantics.

Do not treat it as:

```text
Application version
```

or:

```text
Git version.
```

It belongs to Kubernetes API resource versioning/concurrency behavior.

You will study these internals more deeply later.


Choose tools for clarity, not cleverness.

# 65. Label Mental Model

Labels answer questions such as:

```text

Which environment?

Which component?

Which tier?

Which release track?
```

Example:

```yaml
metadata:
  labels:
```

Labels are not merely decoration.

---

# 66. Labels vs Names

Names identify specific objects.

Labels identify characteristics and groups.

Example:

```text
Pod:
payments-api-abc123

Pod:
payments-api-def456
```

Different names.

Same label:

```text
app=payments-api
```

Now automation can select both.

---


```text

```

Only matching objects are returned.

# 68. Add Another Pod

```bash
kubectl run worker \
```


# 70. Multiple Label Requirements

You can use:

```bash
kubectl get pods \
  -n kubectl-lab \
  -l 'environment=lab,app=web'
```

The comma means both requirements must match.

Conceptually:

```text
environment=lab
AND
app=web
```

---

# 71. Set-Based Selectors

Kubernetes label selectors also support set-based forms.

Example:

```bash
kubectl get pods \
  -n kubectl-lab \
  -l 'app in (web,worker)'
```

This selects Pods whose `app` label has either listed value.

---

# 72. notin

Example:

```bash
kubectl get pods \
  -n kubectl-lab \
  -l 'app notin (worker)'
```

This can be useful for filtering resource sets.

Be careful with negative selectors.

Always verify the selected objects before applying destructive commands.

# 73. Production Safety With Selectors

This can be powerful:

```bash

```

It can also delete many objects.

Safe workflow:

```text
Write selector
↓
GET matching objects
↓
Inspect
↓
Confirm scope
↓
Perform change
↓
Verify
```

For example:

```bash

```

before:

```bash

```

# 74. Field Selectors

Labels are user-defined metadata.

Field selectors filter using supported resource fields.

Example:

```bash
kubectl get pods \
  -n kubectl-lab \
  --field-selector status.phase=Running
```

This selects Pods whose phase is `Running`.

---

# 75. Label Selector vs Field Selector

Think:

```text
Label selector
↓
metadata.labels
```

Example:

```text
app=web
```

Field selector:

```text
Supported object field
```

Example:

```text
status.phase=Running
```

Different mechanisms.

---

# 76. Supported Field Selectors Vary

Do not assume every object field can be used as a field selector.

Supported fields depend on the resource type.

For example, common Pod selectors include fields such as:

```text
spec.nodeName

status.phase
```

Unsupported field selectors result in an API error.

Automation should not rely blindly on:

```text

```

because:

```text
Maybe workload ready in 5 seconds.

Maybe workload needs 50 seconds.

Maybe workload never becomes ready.
```

A condition-based wait is more meaningful.

Conceptually:

```text

↓
Wait for condition
↓
Continue if satisfied
↓

```

# 125. wait Is Not Universal Health Verification

A Pod being:

```text
Ready
```

does not automatically prove:

```text
Every business function works.

Database queries work.

External dependencies work.

Customers can complete transactions.
```

Readiness is one layer of verification.

Production verification must be layered.

# 171. REST Resource Path Mental Model

A namespaced core resource can conceptually use paths such as:

```text
/api/v1/namespaces/<NAMESPACE>/pods
```

A named API group resource may use:

```text
/apis/<GROUP>/<VERSION>/namespaces/<NAMESPACE>/<RESOURCE>
```

Cluster-scoped resources omit the namespace portion.

You do not need to manually build these URLs for daily kubectl work.

But understanding them makes Kubernetes much less mysterious.

# 175. API Versions Are Not Kubernetes Release Versions

Do not confuse:

```text

```

with:

```text

```

The first describes Kubernetes software release versioning.

The second describes an API group/version.

They are related through compatibility and lifecycle rules, but they are not the same thing.

style version names.

Alpha and beta APIs have different stability expectations.

Production engineers must watch API deprecations during Kubernetes upgrades.

# 237. Knowledge Check

### 1. What is kubectl?

A command-line client for interacting with Kubernetes through the Kubernetes API.

### 2. Does kubectl normally read etcd directly?

No.

### 3. What component receives Kubernetes API requests?

The API server.

### 4. What does kubeconfig provide?

Cluster, authentication and context information used by Kubernetes clients.

### 5. What does `kubectl get` do?

Retrieves resource information.

---

# 238. Knowledge Check: Objects

### 6. What is a Kubernetes object?

A persistent API entity representing cluster state or desired intent.

### 7. What does `spec` generally represent?

Desired configuration.

### 8. What does `status` generally represent?

Observed/current state reported by Kubernetes.

### 9. What is metadata used for?

Identity and descriptive information such as names, namespaces, labels and annotations.

### 10. Is YAML itself the Kubernetes API?

No.

YAML is one representation commonly used to describe Kubernetes objects.

---

# 239. Knowledge Check: Commands

### 11. Difference between `get` and `describe`?

`get` is suited to listing/quick retrieval.

`describe` provides human-oriented operational detail.

### 12. Difference between `create` and `apply`?

`create` creates a new resource and normally fails if it already exists.

`apply` manages declared configuration and can create or update according to apply semantics.

### 13. What does `logs` do?

Retrieves container logs through Kubernetes.

### 14. What does `exec` do?

Requests command execution inside a container.

### 15. Is `exec` SSH?

No.

---

# 240. Knowledge Check: Output

### 16. Show YAML.

```bash
kubectl get pod <NAME> -o yaml
```

### 17. Show JSON.

```bash
kubectl get pod <NAME> -o json
```

### 18. Show additional table columns.

```bash
kubectl get pods -o wide
```

### 19. Extract one structured field.

Use an output mechanism such as JSONPath.

### 20. Create your own columns.

Use:

```text

```

---

# 241. Knowledge Check: Selectors

### 21. What are labels?

Key/value metadata used to identify and organize objects.

### 22. What is a label selector?

A query selecting objects based on labels.

### 23. What is a field selector?

A filter based on supported resource fields.

### 24. Can every YAML field automatically be used as a field selector?

No.

### 25. Why preview a selector before delete?

Because selectors can match multiple objects and therefore increase blast radius.

---

# 242. Knowledge Check: Namespaces

### 26. Name the four initial Kubernetes namespaces.

```text
default

kube-system

kube-public

kube-node-lease
```

### 27. Are Pods namespaced?

Yes.

### 28. Are Nodes namespaced?

No.

### 29. Can two Pods have the same name in different namespaces?

Yes.

### 30. Can namespaces be nested?

No.

---

# 243. Knowledge Check: API Discovery

### 31. Discover resources.

```bash
kubectl api-resources
```

### 32. Discover API versions.

```bash
kubectl api-versions
```

### 33. Inspect a resource schema.

```bash
kubectl explain <RESOURCE>
```

### 34. Why is API discovery important?

Because clusters may expose different built-in, extension and custom APIs.

### 35. What does `NAMESPACED` in `api-resources` tell you?

Whether objects of that resource type are namespace-scoped.

---

# 244. Knowledge Check: Operations

### 36. What does port-forward do?

Creates temporary local forwarding to a Kubernetes resource.

### 37. Is it normal production public exposure?

No.

### 38. What does kubectl wait do?

Waits for a specified resource condition or related criterion.

### 39. What does kubectl diff do?

Shows differences associated with applying configuration before you make the change.

### 40. What does kubectl cp depend on in the container?

Its normal implementation requires `tar`.
