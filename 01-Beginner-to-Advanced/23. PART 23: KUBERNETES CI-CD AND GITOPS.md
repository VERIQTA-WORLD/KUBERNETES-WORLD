# PART 23: KUBERNETES CI/CD AND GITOPS

## From Git Commit to Controlled Production Deployment

---

# 1. Goal

The goal of this part is to move Kubernetes deployments away from an engineer's laptop and into controlled, repeatable, reviewable delivery systems.

Until now, you have frequently deployed applications using commands such as:

```bash
kubectl apply -f deployment.yaml
```

That is useful for learning.

It is not a sufficient production delivery strategy.

A production system needs to answer:

```text
Who changed the application?

What changed?

Which commit produced the container?

Which image was deployed?

Who reviewed the change?

Which tests passed?

Which security checks passed?

Who approved production?

When was the deployment performed?

What exactly is running now?

Can we reproduce it?

Can we roll it back?

Has somebody changed the cluster manually?

Does production still match the approved desired state?
```

CI/CD and GitOps provide mechanisms for answering those questions.

# 3. The Problem With Laptop Deployments

Imagine production deployment depends on:

```bash
kubectl apply -f production/
```

from one engineer's laptop.

Immediately ask:

```text
Which files were on that laptop?

Were they committed?

Was the correct Git branch checked out?

Was the correct kubeconfig active?

Was the correct cluster selected?

Were local files modified?

Who reviewed the manifests?

Were security checks executed?

Was the image scanned?

Which image was deployed?

Was production approval obtained?

Is there an audit trail?
```

The command itself is not the problem.

The uncontrolled process is the problem.

Conceptually:

```text

↓

↓

↓

↓
```

# 8. Continuous Deployment

```text
Commit
↓
CI
↓
All Required Checks Pass
↓
Automatic Production Deployment
```

There may be no human approval immediately before deployment.

```text

```

For example:

```text
Developers
↓

```

```text

↓
```

# 15. Monorepository Model

Another valid model is:

```text

├── src/
├── tests/
├── Dockerfile
├── kubernetes/
└── .github/
```

Advantages can include:

```text

```

Tradeoffs can include:

```text

```

Choose intentionally.

# 30. YAML Syntax Validation

A file can fail before Kubernetes semantics are considered.

Bad:

```yaml

 name: web
   namespace: production
```

CI should catch this before deployment.

---

# 31. Kubernetes Client Dry Run

For suitable manifests:

```bash
kubectl apply \
  --dry-run=client \
  -f kubernetes/
```

Purpose:

```text
perform client-side processing without creating resources.
```

This is useful but is not equivalent to API-server validation.

---

# 32. Server Dry Run

Where CI has safe access to an appropriate validation cluster/API server:

```bash
kubectl apply \
  --dry-run=server \
  -f kubernetes/
```

This can provide server-side validation and admission behavior without persisting the requested objects.

Do not give an untrusted Pull Request broad production access merely to perform server dry-run validation.

---

# 33. `kubectl diff`

Before applying a change:

```bash
kubectl diff -f kubernetes/
```

can show how declared configuration differs from live state.

In GitOps, the controller provides its own desired-state comparison model, but understanding diffs remains essential.

---

# 34. Helm Validation

For Helm charts:

```bash

```

Then render:

```bash

```

Pipeline:

```text

↓

↓

↓
```

# 42. A Container Image Is an Artifact

Treat the image as a release artifact.

The goal is:

```text

```

then:

```text

```

through environments.

Avoid rebuilding supposedly identical releases independently for:

```text
development

staging

production
```

because different builds may produce different artifacts.

# 46. Image Tags

Example:

```text
registry.example.com/api:v1.4.2
```

Here:

```text
v1.4.2
```

is the tag.

Tags are human-friendly identifiers.

---

# 47. Mutable Tags

A tag can potentially point to different image content over time unless registry controls prevent that behavior.

Example:

```text
api:latest
```

today may represent one image.

Tomorrow it may represent another.

This weakens reproducibility.

---

# 48. Why `latest` Is Weak for Production

Imagine:

```text
Deployment
↓
api:latest
```

Question:

```text
Which exact image is production running?
```

The answer is not obvious from the manifest.

Avoid relying on mutable tags for precise production identity.

---

# 49. Commit-Based Tags

A CI pipeline may create:

```text
api:8f31a1c
```

where:

```text
8f31a1c
```

comes from the Git commit.

This improves traceability.

But a tag is still conceptually a registry reference that may be mutable unless protected.

---

# 50. Image Digest

OCI images can be referenced by digest.

Conceptually:

```text
registry.example.com/api@sha256:<DIGEST>
```

A digest identifies immutable image content.

This is stronger for exact artifact identity.

---

# 51. Tag vs Digest

Tag:

```text
api:v1.4.2
```

Human-friendly.

Digest:

```text
api@sha256:...
```

Content-specific.

A mature release system may use:

```text
human-friendly version metadata
+
immutable digest identity.
```

---

# 52. Immutable Deployment Reference

Conceptually:

```yaml
containers:
  - name: api
    image: registry.example.com/api@sha256:<DIGEST>
```

Now the desired state specifies exact image content.

# 55. Image Scan

After building:

```text
Image
↓
Vulnerability Scanner
↓
Findings
```

Policies may consider:

```text

exploitability

fix availability

runtime exposure

```

A simplistic:


A simplistic:

```text

```

# 56. Publish Only Approved Artifacts

Conceptually:

```text
Build
↓
Scan
↓
Policy
│
├── Pass → Push/Promote
│
└── Fail → Stop
```

# 73. Trust Policy Matters

```text

```

# 81. GitOps Architecture

```text

↓

↓

↓
```

---

# 82. GitOps Core Idea

Suppose Git says:

```text
replicas: 3
```

but somebody manually changes production:

```bash
kubectl scale deployment api --replicas=7
```

Now:

```text
Git desired state = 3

Cluster actual state = 7
```

This is drift.

A configured GitOps controller can detect the difference and, depending on policy, reconcile the cluster back to the approved state.

---

# 83. Reconciliation

Reconciliation means:

```text
Observe
↓
Compare
↓
Detect Difference
↓
Act
↓
Verify
↓
Repeat
```

This is familiar.

Kubernetes controllers already work this way.

GitOps extends that controller pattern to deployment configuration.

---

# 84. GitOps Is Not "Git Runs kubectl"

The important difference is continuous reconciliation.

Weak interpretation:

```text
Git webhook
↓
run kubectl apply once
```

GitOps model:

```text
Desired State
↓
Controller
↓
Continuous Reconciliation
```

If drift occurs later, the controller notices.

# 112. Drift

Drift means actual state differs from intended state.

Example:

Git:

```yaml
replicas: 3
```

Cluster:

```yaml
replicas: 5
```

That is drift if no authorized controller is expected to modify the field.

---

# 113. Not Every Difference Is Bad Drift

Remember HPA.

Git might intentionally omit or coexist carefully with fields modified by another controller.

For example:

```text
HPA
↓
modifies Deployment replica count
```

If GitOps continuously forces:

```text
replicas: 3
```

while HPA wants:

```text
replicas: 8
```

you have controller conflict.

Desired-state ownership must be designed carefully.

---

# 114. Controller Ownership

For every field ask:

```text
Who owns this field?
```

Example:

```text
image
→ GitOps

replicas
→ HPA

AWS node count
→ node autoscaler

Pod readiness
→ kubelet/application health

Service endpoints
→ Kubernetes controllers
```

Multiple controllers fighting over one field is an architecture problem.

# 117. Rollback

Rollback means restoring a known good application/configuration state.

In a GitOps system, one clean method is:

```text
Bad Commit
↓
Git Revert
↓
Desired State Returns to Known Good Version
↓
Controller Reconciles
↓
Cluster Rolls Back
```

---

# 118. Git Revert

Suppose:

```text
commit A = good

commit B = bad
```

Instead of rewriting shared history, you can create:

```text
commit C
```

that reverses B.

Then:

```text
GitOps Controller
↓
sees commit C
↓
reconciles old desired state.
```

---

# 119. Kubernetes Rollback vs GitOps Rollback

Traditional Kubernetes:

```bash
kubectl rollout undo deployment/api
```

can restore a previous Deployment revision.

But if Git still declares the broken version:

```text
GitOps Controller
↓
may restore broken desired state again.
```

Therefore GitOps environments usually require fixing the source of truth.

---

# 120. Source-of-Truth Rule

If Git is authoritative:

```text

```

Do not permanently fight the controller from the cluster.

# 133. Example PR Validation Workflow

Illustrative GitHub Actions structure:

```yaml
name: PR Validation

on:
  pull_request:

permissions:
  contents: read

jobs:
  validate:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@<PINNED_VERSION_OR_SHA>

      - name: Validate YAML
        run: |
          kubectl apply \
            --dry-run=client \
            -f kubernetes/base/

      - name: Lint Helm
        run: |
          helm lint ./helm/application

      - name: Render Helm
        run: |
          helm template application ./helm/application > rendered.yaml
```

In production, pin third-party actions according to your supply-chain policy and add your approved scanners/validators.

---

# 134. Never Blindly Copy CI Actions

A line such as:

```yaml
uses: vendor/action@main
```

allows future changes to the referenced branch to affect your workflow.

For security-sensitive workflows, organizations commonly pin actions according to a controlled versioning policy, often to reviewed versions or immutable commit references.

Your CI dependencies are supply-chain dependencies.

# 256. Practical Assessment 1

What is the primary goal of CI?

Answer:

```text
integrate and validate changes through automated checks
before they become trusted release artifacts.
```

---

# 257. Practical Assessment 2

What is the difference between building and deploying?

```text
Build
=
create artifact.
```

```text
Deploy
=
make an approved artifact part of an environment's desired/running state.
```

---

# 258. Practical Assessment 3

Why build once?

Because promotion should move the same tested artifact through environments rather than creating potentially different artifacts for each environment.

---

# 259. Practical Assessment 4

Why are immutable image references useful?

They identify exact image content and improve:

```text
reproducibility

traceability

rollback confidence.
```

---

# 260. Practical Assessment 5

Why should CI avoid long-lived cloud credentials?

Because credential theft can create long-lived access.

Short-lived federated credentials reduce persistence and can be narrowly scoped.

---

# 261. Practical Assessment 6

What is GitOps?

A declarative operational model in which desired system state is version-controlled and automated controllers reconcile running systems toward that desired state.

---

# 262. Practical Assessment 7

What is reconciliation?

```text
Observe actual state
↓
compare with desired state
↓
correct differences
↓
repeat.
```

---

# 263. Practical Assessment 8

What is drift?

A difference between intended desired state and actual managed state that is not an expected result of another authorized controller.

---

# 264. Practical Assessment 9

Why can manual `kubectl` changes disappear in GitOps?

Because the GitOps controller detects that live state differs from authoritative desired state and reconciles it.

---

# 265. Practical Assessment 10

What is the difference between push and pull deployment?

Push:

```text
external deployment system
↓
cluster.
```

Pull/GitOps:

```text
cluster-side reconciliation controller
↓
desired-state source
↓
cluster reconciliation.
```

---

# 266. Practical Assessment 11

Does GitOps replace CI?

No.

CI still performs:

```text
testing

validation

build

security scanning

artifact publication.
```

GitOps primarily addresses controlled desired-state delivery and reconciliation.

---

# 267. Practical Assessment 12

Why is `latest` weak for production?

Because it does not reliably communicate exact immutable artifact identity.

---

# 268. Practical Assessment 13

What should happen after an image is built?

At minimum:

```text
scan

publish

record identity/digest

update desired deployment state

review/promote

deploy

verify.
```

---

# 269. Practical Assessment 14

Why is Git security critical in GitOps?

Because authorization to change authoritative production configuration can become authorization to change production.

---

# 270. Practical Assessment 15

What is wrong with storing production AWS access keys permanently in CI?

It creates long-lived credential exposure.

Prefer supported federation and short-lived credentials where practical.

---

# 271. Practical Assessment 16

What happens if GitOps manages replicas while HPA also manages replicas?

The controllers may conflict.

Field ownership must be designed so HPA can control replica count.

---

# 272. Practical Assessment 17

What is the correct GitOps rollback concept?

```text
restore known-good desired state in Git
↓
controller reconciles cluster
↓
verify recovery.
```

---

# 273. Practical Assessment 18

What is progressive delivery?

Controlled gradual exposure of a new release while observing health and deciding whether to continue or roll back.

---

# 274. Practical Assessment 19

What is a canary deployment?

A release technique where a new version initially receives only a limited portion of workload/traffic before wider promotion.

---

# 275. Practical Assessment 20

Why is post-deployment verification required?

Because:

```text
configuration accepted
```

does not prove:

```text
application works correctly.
```

# 293. Final Learner Test

You are given this incident:

```text
A developer merged a release.

CI passed.

The image exists in the registry.

Production still runs the old image.
```

You should investigate:

```text
Was deployment configuration updated?

Was deployment PR merged?

Is the GitOps controller watching the correct repository?

Correct branch?

Correct path?

Did it fetch the latest revision?

Did rendering succeed?

Did reconciliation succeed?

Was admission denied?

Did the Deployment update?

Did rollout stall?

Did the image pull?

Did readiness succeed?
```

That is CI/CD troubleshooting.

# 294. Second Final Learner Test

```text
Production was manually fixed at 02:00.

At 02:05 the problem returned.
```

Ask:

```text
Is GitOps managing the resource?

What does Git declare?

Did the manual fix create drift?

Did reconciliation restore the old desired state?
```

Do not blame Kubernetes before understanding the control loop.

# 295. Third Final Learner Test

```text
CI Run

Image
↓
Digest
↓
SBOM / Provenance
↓
Deployment Commit
↓
Environment
```

Every production artifact should be traceable.

# 296. Fourth Final Learner Test

Incident:

```text
CI credentials were compromised.
```

Ask:

```text
Were credentials long-lived?

Which environments could they access?

Could they push images?

Could they modify Git?

Could they access Kubernetes?

Could they modify AWS infrastructure?

How quickly do credentials expire?

Can they be revoked?

What audit evidence exists?
```

This is why identity architecture belongs inside CI/CD design.

```text
another controller owns replica count.
```
