# PART 6: PODS AND THE CONTAINER LIFECYCLE

## Understand Kubernetes' Fundamental Workload Unit

---

# 1. Goal

In Part 5, you learned how to describe Kubernetes objects using manifests.

You learned:

```text
Requirement
↓
YAML Manifest
↓
Kubernetes API
↓
Object
↓
Desired State
↓
Reconciliation
```

Now we move to the object at the center of Kubernetes workload execution:

```text
Pod
```

A Pod is the smallest deployable compute unit Kubernetes manages.

But understanding a Pod requires more than knowing how to write:

```yaml
kind: Pod
```

You need to understand:

```text
Why Pods exist

Why Kubernetes does not normally manage application containers directly

How containers inside a Pod relate to each other

How Pod networking works

How containers share storage

How containers start

How containers stop

How Kubernetes records container state

How restart policies work

How commands and arguments affect startup

How init containers prepare workloads

How sidecars support applications

How lifecycle hooks interact with startup and shutdown

How graceful termination works

Why CrashLoopBackOff happens

How to investigate failed Pods
```

By the end of this part, you should be able to look at a Pod and answer:

```text
What is supposed to run?

What is currently running?

What already terminated?

What is waiting?

Why did it restart?

What command is actually executing?

Which containers share this Pod?

Which initialization steps occurred?

Is the Pod Ready?

What happened during termination?

Where should I investigate next?
```

---

# 2. The Pod Mental Model

Start with:

```text
Kubernetes Cluster
↓
Node
↓
Pod
↓
Container
↓
Application Process
```

A common beginner mistake is to think:

```text
Kubernetes
↓
Container
```

The more accurate model is:

```text
Kubernetes
↓
Pod
↓
One or More Containers
```

Kubernetes normally schedules and manages Pods as workload units.

---

# 3. What Is a Pod?

A Pod is the smallest deployable unit of computing that you can create and manage in Kubernetes.

A Pod can contain:

```text
One application container
```

or:

```text
Multiple tightly coupled containers
```

A Pod provides a shared execution context around those containers.

Conceptually:

```text
Pod
│
├── Network Context
├── Pod IP
├── Volumes
├── Configuration
├── Security Context
│
├── Container A
│
└── Container B
```

Containers inside the same Pod are:

```text
Co-located
+
Co-scheduled
```

They run together on the same node.

---

# 4. Pod as a Logical Host

A useful mental model is:

```text
Pod
≈
Small logical host for tightly related containers
```

Historically, applications running on the same server could communicate using:

```text
localhost
```

and share files on that machine.

A Pod provides similar application-level co-location for containers.

For example:

```text
Pod
│
├── Web Application
│
└── Supporting Sidecar
```

Both can cooperate as one workload unit.

---

# 5. Why Kubernetes Manages Pods Instead of Individual Containers

Suppose Kubernetes only managed individual containers.

You might need:

```text
Application Container
+
Logging Helper
+
Proxy
+
Configuration Helper
```

But Kubernetes would need a way to express:

```text
These containers belong together.

Place them on the same machine.

Give them closely related lifecycle behavior.

Allow them to communicate locally.

Allow them to share selected storage.
```

The Pod provides that boundary.

---

# 6. Pod as the Scheduling Unit

Kubernetes schedules Pods.

Not individual application containers inside the same Pod independently.

Think:

```text
Scheduler
↓
Pod
↓
Node
```

Once a Pod is assigned to:

```text
Node A
```

the containers belonging to that Pod run within that Pod's context on:

```text
Node A
```

Kubernetes does not normally place:

```text
Container A from Pod X
```

on Node A and:

```text
Container B from Pod X
```

on Node B.

They belong to the same Pod.

---

# 7. Co-Scheduling

Imagine:

```text
Pod: payments
│
├── payments-api
└── supporting-proxy
```

If Kubernetes schedules the Pod onto:

```text
worker-node-2
```

both containers belong there.

Conceptually:

```text
worker-node-2
└── Pod/payments
    ├── payments-api
    └── supporting-proxy
```

That is co-scheduling.

---

# 8. A Pod Is Not a Virtual Machine

Do not think:

```text
Pod = VM
```

A Pod does not normally provide a complete operating system machine abstraction.

Instead, it provides a Kubernetes workload boundary around one or more containers.

Containers still run using the node's container runtime and underlying operating-system mechanisms.

---

# 9. Pods Are Relatively Ephemeral

Pods should not be treated as permanent servers.

Think:

```text
Pod created
↓
Pod scheduled
↓
Containers started
↓
Pod runs
↓
Pod terminates / is deleted / fails
```

Another Pod may later replace it.

This becomes especially important when you learn:

```text
Deployments

ReplicaSets

StatefulSets

Jobs
```

These higher-level workload resources manage Pods for you.

---

# 10. Do Not Treat Pod Names Like Permanent Server Names

Traditional infrastructure thinking:

```text
server-prod-01
↓
Protect forever
```

Kubernetes workload thinking:

```text
Pod
↓
Replaceable workload instance
```

The application architecture should not depend unnecessarily on one particular Pod surviving forever.

---

# 11. Direct Pods vs Controller-Managed Pods

You can create a Pod directly:

```yaml
apiVersion: v1
kind: Pod
```

This is useful for:

```text
learning

experiments

debugging

certain specialized cases
```

But production application Pods are usually created through workload controllers.

For example:

```text
Deployment
↓
ReplicaSet
↓
Pods
```

Why?

Because if you directly create:

```text
Pod/web
```

and delete it:

```bash
kubectl delete pod web
```

nothing automatically guarantees that a replacement Pod will be created.

A Deployment changes that model.

You will study this in Part 7.

---

# 12. Single-Container Pods

The most common Pod model is:

```text
Pod
└── One Application Container
```

Example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
    - name: nginx
      image: nginx:alpine
```

Conceptually:

```text
Pod/web
└── Container/nginx
    └── nginx process
```

---

# 13. Why One Container Per Pod Is Common

Applications are easier to reason about when each Pod has one primary responsibility.

For example:

```text
Frontend Pod
↓
Frontend Container
```

```text
API Pod
↓
API Container
```

```text
Worker Pod
↓
Worker Container
```

You should not put unrelated applications into the same Pod merely because Kubernetes allows multiple containers.

---

# 14. Bad Multi-Container Design

Avoid:

```text
Pod
├── Frontend
├── Database
├── Redis
├── Background Worker
└── Random Monitoring Tool
```

simply because:

```text
"They are all part of my application."
```

These components usually have different:

```text
scaling requirements

failure domains

deployment schedules

resource needs

storage needs

security boundaries
```

They often belong in separate Pods.

---

# 15. Multi-Container Pods

A Pod can contain multiple application containers.

Example:

```text
Pod
│
├── Main Application
└── Supporting Container
```

This is appropriate when the containers are:

```text
tightly coupled

must be co-located

benefit from shared network context

benefit from shared storage

belong to the same workload lifecycle
```

---

# 16. Multi-Container Mental Model

Think:

```text
Pod
│
├── Shared Network Context
├── Shared Pod IP
├── Shared Volumes when configured
│
├── Container A
│   └── Process A
│
└── Container B
    └── Process B
```

The containers remain separate containers.

They do not magically become one process.

---

# 17. What Containers in a Pod Share

Containers in the same Pod share important context.

Most importantly:

```text
Network namespace/context
↓
Same Pod IP
```

They can also share:

```text
Volumes
```

when the Pod configuration mounts the same volume into multiple containers.

---

# 18. What They Do Not Automatically Share

Do not assume every resource is automatically shared.

Each container still has its own container filesystem view.

For example:

```text
Container A
/usr/share/data
```

does not automatically contain the same files as:

```text
Container B
/usr/share/data
```

unless shared storage is configured appropriately.

---

# 19. Pod Networking

Each Pod receives its own network identity.

Conceptually:

```text
Node
│
├── Pod A
│   └── Pod IP: 10.x.x.10
│
└── Pod B
    └── Pod IP: 10.x.x.11
```

All application containers within one Pod share the Pod's network context.

---

# 20. Shared Network Namespace Concept

Suppose:

```text
Pod
│
├── Container A
│   └── listens on port 8080
│
└── Container B
```

Container B can communicate with Container A using:

```text
localhost:8080
```

because they share the Pod's network context.

---

# 21. localhost Inside a Pod

Imagine:

```text
Pod IP: 10.244.1.20

Container A
Web server listening on:
0.0.0.0:8080

Container B
Client
```

Container B can potentially connect to:

```text
http://localhost:8080
```

The communication stays within the Pod's shared network context.

---

# 22. Port Conflicts Inside a Pod

Because containers share the Pod's network namespace, they cannot independently bind the same IP/port combination.

For example:

```text
Container A
↓
Port 8080

Container B
↓
Port 8080
```

If both attempt to listen on the same Pod address and port in conflicting ways, one can fail.

Think:

```text
Same Pod
↓
Shared network namespace
↓
Coordinate ports
```

---

# 23. Pod IP

Inspect a Pod:

```bash
kubectl get pod web -o wide
```

You may see:

```text
NAME   READY   STATUS    IP            NODE
web    1/1     Running   10.244.1.15   worker-1
```

The:

```text
10.244.1.15
```

is the Pod IP in this example.

---

# 24. Pod IPs Are Not Permanent Application Endpoints

Do not design applications around manually storing Pod IP addresses.

Pods can be replaced.

Replacement Pods may receive different IPs.

Later you will learn:

```text
Service
↓
Stable service abstraction
↓
Changing Pod endpoints
```

Therefore:

```text
Pod IP
≠
stable application identity
```

---

# 25. Shared Storage

Containers in a Pod can mount the same volume.

Example:

```text
Pod
│
├── Shared Volume: data
│
├── Container A
│   └── /shared
│
└── Container B
    └── /shared
```

Container A can write:

```text
/shared/message.txt
```

and Container B can read it if both mount the same volume appropriately.

---

# 26. Pod Volume vs Container Filesystem

Without shared volume:

```text
Container A filesystem
≠
Container B filesystem
```

With a shared Pod volume:

```text
Volume
├── mounted into Container A
└── mounted into Container B
```

selected data can be shared.

---

# 27. emptyDir Preview

A common Pod-scoped volume is:

```yaml
volumes:
  - name: shared-data
    emptyDir: {}
```

It begins empty for the Pod and can be mounted into multiple containers.

Example:

```yaml
volumeMounts:
  - name: shared-data
    mountPath: /shared
```

You will study Kubernetes storage comprehensively later.

For now, understand:

```text
Pod
↓
Volume
↓
Multiple Containers
↓
Shared Files
```

# 33. Pod Lifecycle

A Pod has a lifecycle.

Conceptually:

```text
Manifest Submitted
↓
Pod Accepted
↓
Scheduling
↓
Pod Bound to Node
↓
Pod Sandbox / Networking Prepared
↓
Volumes Prepared
↓
Images Pulled
↓
Init Containers
↓
Application Containers
↓
Running
↓
Termination
↓
Succeeded / Failed
```

Not every Pod follows every step in exactly the same visible way, but this is a useful operational model.

---

# 34. Pods Are Scheduled Once

A critical concept:

```text
Pod
↓
Scheduled to Node A
```

Kubernetes does not normally move that same Pod object to:

```text
Node B
```

if Node A fails.

Instead, higher-level controllers can create replacement Pods.

Think:

```text
Pod identity
↓
Bound to node
↓
Eventually terminates
```

not:

```text
Pod behaves like a VM that migrates everywhere
```

---

# 35. Pod Phase

A Pod's:

```text
.status.phase
```

provides a high-level summary of where it is in its lifecycle.

Common phases are:

```text
Pending

Running

Succeeded

Failed

Unknown
```

Do not treat Pod phase as a complete diagnostic state machine.

It is deliberately high-level.

---

# 36. Pending

`Pending` means Kubernetes accepted the Pod, but one or more containers have not yet been set up and made ready to run.

Pending can include time spent:

```text
waiting for scheduling

pulling images

preparing startup
```

Therefore:

```text
Pending
```

does not automatically mean:

```text
Scheduler problem
```

You need evidence.

---

# 37. Investigating Pending

Start:

```bash
kubectl get pod <POD> \
  -n <NAMESPACE>
```

Then:

```bash
kubectl describe pod <POD> \
  -n <NAMESPACE>
```

Pay special attention to:

```text
Node

Conditions

Container States

Events
```

A Pending Pod could be waiting because of:

```text
scheduling constraints

resource shortages

volume problems

image operations

initialization
```

among other causes.

---

# 38. Running

A Pod phase of:

```text
Running
```

means the Pod has been bound to a node, all containers have been created, and at least one container is still running or is starting/restarting.

Important:

```text
Running
≠
Application healthy
```

A Pod can be:

```text
Running
```

while:

```text
not Ready
```

or while one of its containers is repeatedly restarting.

---

# 39. Succeeded

A Pod enters:

```text
Succeeded
```

when all containers have terminated successfully and will not restart.

This is common for run-to-completion workloads such as Jobs.

Example:

```text
Task starts
↓
Task finishes successfully
↓
Exit code 0
↓
No restart required
↓
Pod phase Succeeded
```

---

# 40. Failed

A Pod can enter:

```text
Failed
```

when its containers have terminated and at least one terminated in failure in a way that will not be restarted.

Example:

```text
Container exits non-zero
↓
restartPolicy: Never
↓
Pod fails
```

---

# 41. Unknown

`Unknown` generally means Kubernetes cannot reliably obtain the Pod's state, often because communication with the node is unavailable.

Do not diagnose:

```text
Unknown
```

as an application bug without checking node and control-plane communication.

---

# 42. Pod STATUS Column vs Pod Phase

This distinction matters.

When:

```bash
kubectl get pods
```

shows:

```text
CrashLoopBackOff
```

that is not one of the documented Pod phases.

Likewise:

```text
ImagePullBackOff
```

is not a Pod phase.

The `STATUS` column from kubectl can show useful human-oriented status information based on more than simply `.status.phase`.

---

# 43. Verify the Actual Pod Phase

Run:

```bash
kubectl get pod web \
  -n pod-lab \
  -o jsonpath='{.status.phase}{"\n"}'
```

Expected for the working web Pod:

```text
Running
```

Do not confuse:

```text
kubectl STATUS display
```

with:

```text
Pod .status.phase
```

---

# 44. Container States

Kubernetes tracks each container separately.

A container can be:

```text
Waiting

Running

Terminated
```

These are container states.

They are different from Pod phases.

---

# 45. Pod vs Container State

Think:

```text
Pod
↓
Phase
```

and:

```text
Container
↓
State
```

For a multi-container Pod:

```text
Pod Phase: Running

Container A: Running
Container B: Waiting
```

That is possible.

---

# 46. Waiting Container State

A container is:

```text
Waiting
```

when it is not currently Running or Terminated and Kubernetes is performing or waiting on startup-related work.

Examples include:

```text
image pulling

startup preparation

restart backoff

configuration dependencies
```

The state usually includes a:

```text
reason
```

that is extremely useful during troubleshooting.

---

# 47. Inspect Waiting State

Run:

```bash
kubectl describe pod <POD> \
  -n <NAMESPACE>
```

You may find:

```text
State:
  Waiting
    Reason: ...
```

Do not stop at:

```text
Waiting
```

Read:

```text
Reason

Message

Events
```

---

# 48. Running Container State

`Running` means the container is currently executing.

Kubernetes can also report when the container entered the Running state.

Inspect:

```bash
kubectl describe pod web \
  -n pod-lab
```

Find:

```text
State:
  Running
```

---

# 49. Terminated Container State

`Terminated` means a container started and then finished execution.

It may have:

```text
succeeded
```

or:

```text
failed
```

Important fields include:

```text
Reason

Exit Code

Started

Finished
```

---

# 50. Exit Codes Matter

A common convention:

```text
Exit Code 0
↓
Successful process completion
```

Non-zero:

```text
Potential failure
```

But the meaning of specific non-zero exit codes depends on the process/application.

Do not memorize every exit code as universal truth.

Investigate the application's behavior.

---

# 51. Current State and Last State

For restarting containers, `kubectl describe` can show:

```text
State
```

and:

```text
Last State
```

Example conceptually:

```text
State:
  Waiting
  Reason: CrashLoopBackOff

Last State:
  Terminated
  Exit Code: 1
```

This is extremely useful.

Current state says:

```text
What is happening now?
```

Last state says:

```text
What happened during the previous attempt?
```

---

# 53. Container Lifecycle

Conceptually:

```text
Container Defined
↓
Waiting
↓
Running
↓
Terminated
```

Depending on restart policy:

```text
Terminated
↓
Restart
↓
Waiting
↓
Running
```

may occur again.

---

# 54. Restart Policy

At the Pod level, Kubernetes supports:

```text
Always

OnFailure

Never
```

Example:

```yaml
spec:
  restartPolicy: Always
```

The default Pod restart policy is:

```text
Always
```

when it is omitted.

---

# 55. restartPolicy: Always

Example:

```yaml
spec:
  restartPolicy: Always
```

Conceptually:

```text
Container terminates
↓
Successful or unsuccessful exit
↓
kubelet restarts it
```

This is common for long-running application Pods.

---

# 56. restartPolicy: OnFailure

Example:

```yaml
spec:
  restartPolicy: OnFailure
```

Conceptually:

```text
Container exits 0
↓
Do not restart because of that completion
```

but:

```text
Container exits non-zero
↓
Restart
```

This is useful for workloads where successful completion should remain completed.

---

# 57. restartPolicy: Never

Example:

```yaml
spec:
  restartPolicy: Never
```

Conceptually:

```text
Container terminates
↓
Do not automatically restart it
```

This is extremely useful for learning and debugging one-shot container failures because the failed state remains easy to inspect.

---

# 58. Restart Policy Does Not Move the Pod

Important:

```text
restartPolicy
```

describes container restart behavior by the kubelet within the Pod on its node.

It does not mean:

```text
Create a completely new Pod on another node.
```

Higher-level controllers handle replacement Pod creation.

---

# 59. Container Restart Backoff

When a container repeatedly fails and restart policy requires restarting it, Kubernetes does not necessarily restart it continuously with zero delay.

The kubelet uses backoff between restart attempts.

Conceptually:

```text
Start
↓
Fail
↓
Wait
↓
Restart
↓
Fail
↓
Wait Longer
↓
Restart
↓
Fail
↓
Backoff
```

This protects the node from extremely aggressive failure loops.

---

# 60. CrashLoopBackOff

`CrashLoopBackOff` generally means:

```text
Container starts
↓
Container fails
↓
Restart policy says restart
↓
Container starts again
↓
Fails again
↓
Kubernetes backs off before next restart
```

`CrashLoopBackOff` is not the root cause.

It is a symptom of repeated container failure/restart behavior.

---

# 61. Never Diagnose Only "CrashLoopBackOff"

Bad diagnosis:

```text
Root cause:
CrashLoopBackOff
```

Better:

```text
Symptom:
CrashLoopBackOff

Last termination:
Exit code 1

Logs:
Application cannot find configuration file

Root cause:
Missing required configuration

Fix:
Provide correct configuration

Verification:
Container remains running and restart count stabilizes
```

# 67. Kubernetes command

In Kubernetes:

```yaml

```

corresponds conceptually to overriding the image's command/ENTRYPOINT behavior.

Example:

```yaml

  - sleep
```

---

# 68. Kubernetes args

`args` provides arguments to the command.

Example:

```yaml

  - sleep
args:
  - "3600"
```

Conceptually:

```text
sleep 3600
```

---

# 69. Docker and Kubernetes Terminology

This is a common source of confusion.

A useful mapping is:

```text
Container image ENTRYPOINT
↔
Kubernetes command
```

and:

```text
Container image CMD
↔
Kubernetes args
```

But always remember the exact final process depends on which image defaults you override.

---

# 70. Four Important Cases

### Case 1

No `command`.

No `args`.

```text
Use image defaults.
```

### Case 2

`command` supplied.

No `args`.

```text
Override image command while argument behavior follows the applicable image/Kubernetes semantics.
```

### Case 3

No `command`.

`args` supplied.

```text
Use image command and replace its default arguments.
```

### Case 4

Both supplied.

```text
Use Kubernetes command + Kubernetes args.
```

---

# 71. Prefer Array Form

Example:

```yaml
command:
  - sh
  - -c
  - echo "Hello"; sleep 3600
```

or:

```yaml
command:
  - sleep
args:
  - "3600"
```

The structure clearly shows the process arguments.

---

# 72. Why `sh -c` Is Different

This:

```yaml
command:
  - sh
  - -c
  - 'echo "starting"; sleep 3600'
```

starts a shell.

The shell interprets:

```text
;

environment expansion

pipes

redirection

shell syntax
```

This:

```yaml
command:
  - sleep
args:
  - "3600"
```

runs the executable directly.

Use a shell when you actually need shell behavior.

---

# 73. PID 1 Matters

The main container process normally becomes:

```text
PID 1
```

inside the container's process namespace.

This matters because the process must handle:

```text
signals

termination

child processes
```

correctly.

A poorly designed wrapper script can interfere with graceful shutdown if it does not forward or receive signals as intended.

---

# 74. Shell Wrapper Problem

Suppose your container runs:

```text
sh -c "my-application"
```

Depending on shell behavior and how the process is launched, the shell can become the signal recipient instead of the application behaving as expected.

Production container entrypoints should be designed carefully.

A common shell-script pattern is to eventually use:

```text
exec
```

to replace the shell with the intended application process where appropriate.

# 99. Init Containers

Init containers are specialized containers that run during Pod initialization.

Regular init containers:

```text
run before application containers

run sequentially

must complete successfully

normally run to completion
```

Conceptually:

```text
Pod Created
↓
Init Container 1
↓
Success
↓
Init Container 2
↓
Success
↓
Application Containers Start
```

---

# 100. Why Init Containers Exist

Applications often require setup before startup.

Examples:

```text
generate configuration

wait for prerequisite

prepare files

set permissions

download startup data

perform initialization checks
```

Instead of placing all setup logic inside the application image, Kubernetes lets you separate initialization responsibilities.

---

# 101. Init Container Architecture

Example:

```text
Pod
│
├── Init Container
│   └── Prepare configuration
│
└── Application Container
    └── Start application
```

Sequence:

```text
Init starts
↓
Init completes successfully
↓
Application starts
```

---

# 102. Multiple Init Containers

Example:

```text
Init A
↓
Success
↓
Init B
↓
Success
↓
Init C
↓
Success
↓
Application Containers
```

Regular init containers execute in the order they are listed.

This is different from ordinary application containers, which do not provide that same sequential startup guarantee.

---

# 103. Failed Init Container

Suppose:

```text
Init A
↓
Success

Init B
↓
Failure
```

The main application containers do not proceed normally past the failed initialization.

The kubelet handles retries according to applicable restart behavior.

This can leave a Pod appearing stuck in initialization.

---

# 104. Init Containers and Shared Volumes

A powerful pattern:

```text
Init Container
↓
Writes Configuration
↓
Shared Volume
↓
Application Container
↓
Reads Configuration
```

This lets initialization prepare data without adding setup utilities to the application image.

---

# 105. LAB: Init Container

Create:

```text
init-container.yaml
```

with:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: init-demo
  namespace: pod-lab
spec:
  initContainers:
    - name: prepare-content
      image: busybox:1.36
      command:
        - sh
        - -c
        - 'echo "Prepared by init container" > /work/index.html'
      volumeMounts:
        - name: content
          mountPath: /work

  containers:
    - name: web
      image: nginx:alpine
      volumeMounts:
        - name: content
          mountPath: /usr/share/nginx/html

  volumes:
    - name: content
      emptyDir: {}
```

# 106. Understand the Init Manifest

Flow:

```text

↓

↓
Init Container Starts
↓
Writes /work/index.html
↓
Init Container Exits Successfully
↓
nginx Container Starts
↓
Same Volume Mounted at /usr/share/nginx/html
↓
nginx Serves Generated File
```

The mount paths can differ.

The underlying volume is the same.

```text

↓
```

```text

↓
Destroy everything
```

This property is called:

```text
idempotence
```

# 118. Sidecar Concept

A sidecar is a supporting container that runs alongside the primary application container.

Examples include:

```text
logging helper

proxy

data synchronization helper

security helper

supporting monitoring functionality
```

Conceptually:

```text
Pod
│
├── Main Application
│
└── Sidecar
    └── Supporting Function
```

---

# 119. Sidecar Is an Architectural Role

Historically, engineers often used the word:

```text
sidecar
```

to describe an ordinary second long-running application container.

Modern Kubernetes also has native sidecar container semantics.

Therefore distinguish:

```text
sidecar pattern
```

from:

```text
Kubernetes-native sidecar container behavior
```

---

# 120. Kubernetes-Native Sidecars

Modern Kubernetes supports native sidecar containers using an entry under:

```yaml
initContainers:
```

with:

```yaml
restartPolicy: Always
```

Conceptually:

```yaml
initContainers:
  - name: helper
    restartPolicy: Always
```

This makes the container restartable and allows it to continue running alongside the application containers.

---

# 121. Native Sidecar Mental Model

Conceptually:

```text
Pod Startup
↓
Sidecar Starts
↓
Sidecar Becomes Started
↓
Remaining Initialization Continues
↓
Main Application Starts
↓
Sidecar Continues Running
↓
Main Application Terminates
↓
Sidecar Terminates During Ordered Shutdown
```

Native sidecars provide lifecycle semantics that ordinary app-container sidecar patterns did not express as explicitly.

---

# 122. Do Not Turn Every Helper Into a Sidecar

Ask:

```text
Does this helper need the same Pod?

Must it share localhost?

Must it share Pod-local storage?

Must it follow the application's lifecycle closely?
```

If not, it may belong in a separate workload.

Sidecars increase:

```text
resource usage

startup complexity

failure interactions

observability complexity

Pod debugging complexity
```

Use them intentionally.

---

# 123. Init Container vs Sidecar

Regular init container:

```text
Start
↓
Perform setup
↓
Complete
↓
Application starts
```

Sidecar:

```text
Start
↓
Remain running
↓
Application runs alongside it
```

Different responsibilities.

# 124. Lifecycle Hooks

Kubernetes provides container lifecycle hooks.

The two important hooks are:

```text
postStart

preStop
```

They allow container-specific actions around lifecycle events.

---

# 125. postStart

A `postStart` hook is triggered immediately after the container is created.

Important:

```text
postStart
```

does not mean:

```text
Run strictly after the application has completely initialized.
```

The hook and the container's main process can begin around the same startup period.

Do not depend on `postStart` as proof that the application is already healthy.

---

# 126. postStart Example

Example:

```yaml
lifecycle:
  postStart:
    exec:
      command:
        - sh
        - -c
        - 'echo "postStart executed" > /tmp/poststart.txt'
```

The hook executes inside the container context.

---

# 127. postStart Failure

A failing `postStart` hook can cause container lifecycle problems.

When investigating:

```text
Container unexpectedly terminates
```

inspect:

```bash
kubectl describe pod <POD> \
  -n <NAMESPACE>
```

and look for lifecycle hook-related events.

Do not assume all startup failures originate in the application's main process.

---

# 128. preStop

`preStop` is called during graceful container termination before the container is terminated.

Common uses:

```text
stop accepting new work

notify another component

perform short shutdown preparation

allow controlled drain behavior
```

But the hook must fit inside the Pod's termination grace period.

---

# 129. preStop Is Not Unlimited Cleanup Time

Do not write a:

```text
20-minute preStop hook
```

when the Pod's termination grace period cannot accommodate it.

The termination grace period applies to the shutdown process.

When the grace period expires, forced termination can occur.

---

# 130. Lifecycle Hook Example

Create:

```text
lifecycle.yaml
```

with:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: lifecycle-demo
  namespace: pod-lab
spec:
  terminationGracePeriodSeconds: 30
  containers:
    - name: app
      image: busybox:1.36
      command:
        - sh
        - -c
        - 'trap "echo TERM-received >> /tmp/lifecycle.log; exit 0" TERM; touch /tmp/lifecycle.log; while true; do sleep 1; done'
      lifecycle:
        postStart:
          exec:
            command:
              - sh
              - -c
              - 'echo postStart >> /tmp/lifecycle.log'
        preStop:
          exec:
            command:
              - sh
              - -c
              - 'echo preStop >> /tmp/lifecycle.log; sleep 5'
```

If you simply delete the Pod:


```text
↓

↓
```

```text

```

# 133. Graceful Termination

When a Pod is deleted normally, Kubernetes attempts graceful termination.

A simplified mental model:

```text
Delete Requested
↓
Pod Marked Terminating
↓
Grace Period Begins
↓
preStop Hook if configured
↓
Termination Signal
↓
Application Shuts Down
↓
Containers Exit
↓
Pod Removed
```

There are additional details involving endpoints, sidecars and kubelet behavior, but this is the foundation.

---

# 134. Default Grace Period

Pods commonly use a default graceful termination period of:

```text
30 seconds
```

unless configured otherwise.

You can configure:

```yaml
spec:
  terminationGracePeriodSeconds: 60
```

for workloads that legitimately need more shutdown time.

---

# 135. SIGTERM

During normal container termination, the container runtime is instructed to send the relevant termination signal to the container process.

For typical Linux container behavior, this is commonly:

```text
SIGTERM
```

The application should respond appropriately.

Conceptually:

```text
SIGTERM
↓
Stop accepting new work
↓
Finish in-flight work if possible
↓
Flush state/logs as appropriate
↓
Close connections
↓
Exit
```

---

# 136. Why SIGTERM Handling Matters

Imagine:

```text
Payment API
↓
Receives termination
↓
Immediately disappears
```

while requests are being processed.

Possible result:

```text
failed requests

partially completed work

poor user experience
```

Applications should implement appropriate graceful shutdown behavior.

---

# 137. Grace Period

The grace period provides time for shutdown.

Conceptually:

```text
Termination starts
↓
Grace Period Countdown
↓
Application expected to exit
```

If it exits:

```text
Graceful shutdown complete
```

If it does not:

```text
Grace period expires
↓
Forced termination may follow
```

---

# 138. SIGKILL Concept

If a process does not terminate before the allowed graceful shutdown period completes, Kubernetes/container-runtime termination can escalate to forced process termination.

On Linux this involves:

```text
SIGKILL
```

Unlike SIGTERM:

```text
SIGKILL
```

cannot be handled by the application to perform graceful cleanup.

Therefore:

```text
SIGTERM
↓
Opportunity to shut down

SIGKILL
↓
Immediate forced termination
```

---

# 139. Graceful Shutdown Design

A production application should answer:

```text
How long does shutdown require?

How does it stop receiving traffic?

What happens to in-flight requests?

What happens to background jobs?

Are database transactions completed?

Are messages acknowledged safely?

Are connections closed?

What happens if forced termination occurs?
```

Kubernetes cannot magically make an application gracefully terminable if the application ignores shutdown semantics.

---

# 140. preStop and Grace Period

The `preStop` hook consumes part of the termination grace period.

Conceptually:

```text
Grace period begins
↓
preStop
↓
Application termination
↓
Remaining grace time
```

Therefore:

```text
Long preStop
+
Slow application shutdown
=
Risk of forced termination
```

---

# 141. Do Not Use Arbitrary preStop Sleeps as Your Entire Strategy

You may encounter:

```yaml
preStop:
  exec:
    command:
      - sleep
      - "10"
```

This can sometimes be used deliberately for timing behavior, but do not blindly copy it.

Understand:

```text
Why is the delay needed?

What traffic behavior are we solving?

How does readiness interact?

How long does the load balancer take?

What happens during rollout?
```

Production termination design requires evidence.

# 201. Restart Policies Cheat Sheet

```text

↓
Restart after termination
```

```text

↓

```

```text

↓

```

# 202. Native Sidecar Restart Behavior

Kubernetes-native sidecars are special.

They are specified as restartable init containers with:

```yaml
restartPolicy: Always
```

Their container-level behavior differs from ordinary app containers following the Pod-level restart policy.

Do not confuse:

```text
Pod restartPolicy
```

with:

```text
native sidecar restartPolicy
```

Modern Kubernetes also has evolving support for more granular per-container restart behavior, so always check the documentation for the Kubernetes version you operate before depending on newer restart-rule features.

```text
Pod conditions
```

```text
Stable Kubernetes concept
```

from:

```text
Version-specific feature behavior

```

# 204. Container Lifecycle Hooks Cheat Sheet

```text
postStart
↓
Triggered around container startup after creation
```

```text
preStop
↓
Triggered during graceful termination before container termination
```

They are not replacements for:

```text

startup probes
```

Those are separate health mechanisms covered later.

---

# 205. Hook Delivery Consideration

Lifecycle hook handlers should be designed carefully because lifecycle events can have delivery semantics where duplicate execution is possible in exceptional situations.

Therefore:

```text
Hook
↓
Prefer safe/idempotent behavior
```

Do not design a hook where accidentally executing twice causes catastrophic state corruption.

---

# 206. Hook Resource Usage

An `exec` lifecycle hook runs in the container context.

The resources consumed by that command count against the container.

Therefore a lifecycle hook is not:

```text
free external compute.
```

A heavy hook can affect container behavior.

---

# 207. postStart Is Not Readiness

Suppose:

```text
postStart succeeded
```

This does not automatically mean:

```text
Application is ready for customer traffic.
```

Readiness is a separate concept.

Later:

```text
readinessProbe
↓
Determines traffic readiness
```

Do not overload lifecycle hooks with responsibilities that belong to health checks.

---

# 208. preStop Is Not a Backup System

Do not depend on:

```text
preStop
```

as your only method for protecting critical durable data.

Unexpected failures can happen.

Nodes can fail.

Processes can crash.

Infrastructure can disappear.

Durability requires proper storage and application architecture.

---

# 209. Pod Storage Warning

An `emptyDir` volume belongs to the Pod's lifetime.

It can survive individual container restarts within the same Pod.

But when the Pod itself is removed, that `emptyDir` data is removed with it.

Therefore:

```text
emptyDir
≠
durable database storage
```

You will study persistent storage later.

# 210. Container Restart vs Pod Replacement

This distinction must become automatic.

Container restart:

```text
Same Pod UID
↓
Same Pod
↓
Container process restarted
```

Pod replacement:

```text
Old Pod removed
↓
New Pod created
↓
New UID
↓
Potentially new Pod IP
↓
Potentially different node
```

These are fundamentally different events.

# 211. Verify Restart vs Replacement

For a restarting container:

```bash
kubectl get pod <POD> \
  -n <NAMESPACE> \
  -o jsonpath='{.metadata.uid}{"\n"}'
```

UID remains the same while the container restarts within that Pod.

For Pod replacement:

```text

```

This is a powerful troubleshooting distinction.

A Pod.

No.

No. They are co-located and co-scheduled.

Yes.

No.

### 10. Should a Pod IP normally be treated as a permanent application endpoint?

No.

No.

By mounting a shared volume.

Pod-scoped temporary/shared storage.

No.

### 15. Can init and application containers share a volume?

Yes.

No.

No.

Higher-level workload controllers.

`Always`.

### 28. Which restarts after failure?

`OnFailure`.

`Never`.

No.

# 261. Knowledge Check: Commands

### 31. What does Kubernetes `command` generally correspond to?

The container image's ENTRYPOINT-style command override.

Arguments / CMD-style defaults.

Before application containers.

### 37. Do regular init containers normally run in parallel?

No. They run sequentially.

### 38. Must each regular init container succeed before normal application startup continues?

Yes.

### 39. Why should init logic be idempotent?

Because initialization can be retried or re-executed.

### 40. Can init containers use a different image from the application?

Yes.

A supporting container running alongside the primary application workload.

No.

A restartable init container with:

### 44. Can sidecars share network and volumes with the application?

Yes.

### 45. Why should sidecars be used intentionally?

They increase lifecycle, resource and operational complexity.

Forced termination can occur.

No.

```text

├── Can contain init containers
├── Can contain sidecars
├── Can expose shared volumes to containers
├── Has lifecycle
├── Has phase
├── Has conditions
└── Contains containers with independent states
```

# 272. The Most Important Lesson

A Pod is not merely a wrapper around a Docker container.

It is Kubernetes' execution boundary for a workload instance.

It combines:

```text
Scheduling
+
Container execution
+
Networking
+
Storage attachment
+
Configuration
+
Lifecycle
+
Status
+
Restart behavior
+
Initialization
+
Termination
```

into one Kubernetes workload abstraction.

Once you understand the Pod, higher-level Kubernetes resources become much easier to understand.

They are largely mechanisms for:

```text
Creating

Replacing

Scaling

Updating

and Managing

Pods
```

reliably.
