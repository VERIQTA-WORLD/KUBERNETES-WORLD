# PART 20: KUBERNETES TROUBLESHOOTING AND FAILURE INVESTIGATION

## From Symptoms to Root Cause Without Guessing

---

# 1. Goal

The goal of this part is to develop systematic Kubernetes troubleshooting skills.

By the end, you should be able to investigate failures using evidence instead of randomly:

```text
restarting Pods

deleting resources

changing YAML

increasing memory

recreating Services

disabling security

blaming the network
```

You will learn to move systematically from:

```text
Symptom
↓
Evidence
↓
Hypothesis
↓
Root Cause
↓
Fix
↓
Verification
```

The production standard is:

```text
Do not ask:

"What command should I try?"

Ask:

"Which layer is failing, and what evidence proves it?"
```

# 3. The First Rule of Troubleshooting

Before changing anything:

```text
observe.
```

Collect evidence first.

A change can destroy useful evidence.

For example:

```bash
kubectl delete pod <POD>
```

may remove the exact failed Pod you needed to inspect.

Before modifying a failing workload, capture:

```text
status

Events

container state

termination reason

exit code

restart count

current logs

previous logs

configuration

Node

timestamps
```

---

# 4. Troubleshooting Is a Scientific Process

A strong investigation follows:

```text
Observe
↓
Form hypothesis
↓
Test hypothesis
↓
Collect evidence
↓
Accept or reject hypothesis
↓
Identify root cause
↓
Apply controlled fix
↓
Verify
```

Example:

```text
Symptom:
Pod is Pending

Hypothesis:
Insufficient CPU

Evidence:
FailedScheduling:
Insufficient cpu

Conclusion:
CPU request cannot currently be satisfied

Fix:
Adjust capacity or workload request

Verification:
Pod schedules and becomes Ready
```

---

# 5. Symptom Is Not Root Cause

Suppose:

```text
CrashLoopBackOff
```

appears.

That is not necessarily the root cause.

It means Kubernetes is repeatedly restarting a container that fails to remain running.

Possible underlying causes include:

```text
bad command

missing configuration

invalid Secret

application crash

dependency failure

permissions

bad liveness probe

memory failure
```

Likewise:

```text
Pending
```

is a symptom.

Possible causes include:

```text
insufficient CPU

insufficient memory

nodeSelector mismatch

required affinity mismatch

untolerated taint

PVC binding failure

topology restriction
```

---

# 6. Define the Symptom Precisely

Weak incident description:

```text
Kubernetes is broken.
```

Better:

```text
checkout Deployment has 3 desired replicas,
but only 1 is Ready.
```

Better:

```text
Two checkout Pods entered CrashLoopBackOff
immediately after version v2.4.1 was deployed.
```

Precision narrows the investigation.

# 10. Production Safety Rule

Before destructive commands verify:

```text
cluster

context

namespace

resource name
```

A correct troubleshooting command against the wrong production cluster is still a dangerous command.

---

# 11. Determine the Workload Owner

A failing Pod may belong to:

```text
Deployment

ReplicaSet

StatefulSet

DaemonSet

Job

CronJob
```

Inspect:

```bash
kubectl get pod <POD> \
  -n <NAMESPACE> \
  -o jsonpath='{.metadata.ownerReferences}'
```

Why?

Because fixing the Pod directly may be pointless.

If a Deployment created it:

```text
Deployment
↓
ReplicaSet
↓
Pod
```

the desired configuration usually belongs higher in the ownership chain.

# 21. Current vs Previous Logs

Think:

```text
Current container
↓
kubectl logs
```

```text
Previous terminated container instance
↓
kubectl logs --previous
```

A common mistake is repeatedly inspecting only current logs after the evidence-producing process has already died.

# 25. `kubectl debug`

Modern Kubernetes supports debugging sessions using:





# 37. Pod Phase vs Displayed Status

The official Pod phases are broadly:

```text
Pending

Running

Succeeded

Failed

Unknown
```

But:

```bash
kubectl get pods
```

can display more descriptive values such as:

```text
CrashLoopBackOff

ImagePullBackOff

Terminating
```

Do not assume every value in the `STATUS` column is a Pod phase.

# 38. Pending

A Pod in:

```text
Pending
```

has been accepted by Kubernetes but one or more required steps before normal execution are incomplete.

Possible causes include:

```text
cannot schedule

image still downloading

volume not available

init/setup work
```

Therefore:

```text
Pending
```

does not automatically mean:

```text
scheduler failure.
```

# 43. CrashLoopBackOff

Conceptually:

```text
Container starts
↓
Container exits
↓
Kubernetes restarts it
↓
Container exits again
↓
Restart delay increases
↓
CrashLoopBackOff
```

This does not mean:

```text
Kubernetes itself crashed.
```

It means Kubernetes is backing off repeated restart attempts.

---

# 47. ImagePullBackOff

After repeated pull failures Kubernetes backs off further pull attempts.

Conceptually:

```text
Pull
↓
Failure
↓
Retry
↓
Failure
↓
Backoff
```

Investigate:

```bash
kubectl describe pod <POD> \
  -n <NAMESPACE>
```

Read Events.

---

# 48. OOMKilled

`OOMKilled` indicates a container was killed because of an out-of-memory condition.

Inspect:

```bash
kubectl describe pod <POD> \
  -n <NAMESPACE>
```

Look for:

```text
Last State:
  Terminated:
    Reason: OOMKilled
```

Then investigate:

```text
memory limit

actual/historical memory use

application behavior

traffic

memory leaks

working set

recent changes
```

---

# 49. OOMKilled vs Node Eviction

These are not the same failure.

Container OOM:

```text
container exceeds available/allowed memory conditions
↓
container can be killed
↓
restartPolicy may restart it
```

Node-pressure eviction:

```text
Node experiences resource pressure
↓
kubelet may evict Pods
↓
Pod can become Failed
```

Do not confuse them.

---

# 50. Evicted

A Pod can be evicted because the Node is under resource pressure.

Examples:

```text
MemoryPressure

DiskPressure

PIDPressure
```

Inspect:

```bash
kubectl describe pod <POD> \
  -n <NAMESPACE>
```

and:

```bash
kubectl describe node <NODE>
```

---

# 51. Eviction Is a Node-Level Clue

If multiple unrelated Pods on the same Node are being evicted:

```text
do not troubleshoot each application independently first.
```

Investigate the shared Node.

---

# 52. Terminating

A Pod can remain in:

```text
Terminating
```

while Kubernetes attempts graceful deletion.

Possible reasons for prolonged termination include:

```text
long application shutdown

preStop hook

volume detach/unmount

finalizers

kubelet/node communication problem

API object cleanup
```

Do not immediately use:

```text
--force
```

without understanding why normal deletion is blocked.

---

# 53. Finalizers

A finalizer can prevent object deletion until cleanup logic completes.

Inspect:

```bash
kubectl get pod <POD> \
  -n <NAMESPACE> \
  -o yaml
```

Look for:

```yaml
metadata:
  finalizers:
```

Never remove finalizers casually in production.

Doing so can bypass required cleanup.

# 62. Failure Area: Probes

Broken:

```text
readiness probe
```

can remove a Pod from Service traffic.

Broken:

```text
liveness probe
```

can repeatedly restart a healthy application.

Broken:

```text
startup probe
```

can prevent a slow-starting application from ever completing startup.

---

Use:

```bash

```

```text
Unhealthy
```

Then inspect:

```text

```

# 64. Readiness Failure Pattern

```text
Container Running
↓
Readiness probe fails
↓
Pod Ready=False
↓
Endpoint not considered ready for normal Service traffic
↓
Traffic can be removed
```

A readiness failure does not necessarily restart the container.

---

# 65. Liveness Failure Pattern

```text
Container Running
↓
Liveness probe repeatedly fails
↓
kubelet restarts container
↓
restart count increases
```

This can look like an application crash even when the application process itself did not voluntarily exit.

Events are critical evidence.

| ------------------- | ------------------------------- | --------------------------------------- |

| FailedScheduling    | scheduler Event                 | CPU, memory, affinity, taints, topology |

| Terminating         | YAML + Node + finalizers        | shutdown, finalizer, node, storage      |

| Service unreachable | Service + EndpointSlice         | selector, ports, readiness, network     |
| DNS failure         | DNS test + resolv.conf          | name, DNS, policy                       |
| Forbidden           | auth can-i + RBAC               | identity, Role, binding                 |

```text
control-plane behavior
```

well enough to locate the failing layer.

The workflow becomes:

```text
I do not know the root cause yet.

But I know exactly where to start.

I know what evidence to collect.

I know how to narrow the scope.

I know how to test a hypothesis.

I know how to avoid destroying evidence.

I know how to apply the smallest safe fix.

And I know how to prove the system recovered.
```

That is the real objective of Kubernetes troubleshooting.
