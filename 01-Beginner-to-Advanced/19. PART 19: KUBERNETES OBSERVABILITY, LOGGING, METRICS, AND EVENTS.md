# PART 19: KUBERNETES OBSERVABILITY, LOGGING, METRICS, AND EVENTS

## Seeing What Kubernetes and Your Applications Are Actually Doing

---

# 1. Goal

The goal of this part is to learn how to observe a Kubernetes system instead of guessing what is happening inside it.

By the end, you should understand how to use:

```text
Metrics
Logs
Traces
Kubernetes Events
kubectl logs
kubectl logs --previous
kubectl get events
kubectl events
kubectl top
Metrics Server
Prometheus concepts
Application metrics
Centralized logging
OpenTelemetry concepts
Dashboards
Alerts
SLIs
SLOs
```

to answer questions such as:

```text
Is the application healthy?

Why did the Pod restart?

Why is the application slow?

Why is the Pod Pending?

Why did Kubernetes kill the container?

Did CPU usage increase?

Did memory usage increase?

What happened immediately before the failure?

Is the problem inside Kubernetes?

Is the problem inside the application?

Is the problem inside a dependency?

Which request is slow?

Which service caused the latency?

Are users actually being affected?
```

The central production idea is:

```text
Something happens
↓
Kubernetes changes state
↓
Applications produce behavior
↓
Telemetry is generated
↓
Metrics + Logs + Traces + Events
↓
Engineer investigates
↓
Evidence is correlated
↓
Root cause is identified
↓
Fix is applied
↓
Telemetry verifies recovery
```

---

# 2. Observability

Observability is the ability to understand the internal state and behavior of a system from the signals that system produces.

A simple mental model is:

```text
System
↓
Telemetry
↓
Observation
↓
Understanding
↓
Decision
```

In Kubernetes, the system includes much more than your application.

You may need visibility into:

```text
Application
Containers
Pods
Deployments
Services
Nodes
Scheduler
kubelet
API server
Controllers
Storage
Networking
Ingress/Gateway
DNS
Cloud infrastructure
External dependencies
```

---

# 3. Monitoring vs Observability

These terms overlap, but a useful distinction is:

Monitoring often asks known questions:

```text
Is CPU above 80%?

How many Pods are Ready?

Is the API returning errors?

Is disk space low?
```

Observability helps investigate questions you may not have predicted:

```text
Why did checkout latency suddenly increase?

Why are only Pods on one Node failing?

Why did requests become slow after deployment?

Why does one service fail only in one zone?

Why are users receiving errors while all Pods are Running?
```

Monitoring is part of observability.

Observability is the broader capability.

---

# 4. Why Kubernetes Needs Observability

Kubernetes is dynamic.

Pods:

```text
start

stop

restart

move between Nodes

scale up

scale down

receive new IP addresses

become Ready

become NotReady
```

Deployments change.

Nodes appear and disappear.

Traffic moves between replicas.

Autoscalers change capacity.

A static view is therefore insufficient.

---

# 5. `Running` Does Not Mean Healthy

Suppose:

```bash
kubectl get pods
```

returns:

```text
NAME        READY   STATUS    RESTARTS
api-abc     1/1     Running   0
```

You still do not know:

```text
Is the application returning HTTP 500?

Is latency 10 seconds?

Is the database unreachable?

Is the application dropping requests?

Is memory increasing continuously?

Is one endpoint failing?

Are users experiencing errors?
```

Kubernetes object state is only one layer of evidence.

---

# 6. The Three Major Observability Signals

The three major signals are:

```text
Metrics
Logs
Traces
```

Each answers different questions.

---

# 7. Metrics

Metrics are numerical measurements collected over time.

Examples:

```text
CPU usage

memory usage

request count

request rate

error rate

latency

queue depth

active connections

Pod count

restart count

disk usage
```

Metrics are excellent for answering:

```text
What is happening?

How much?

How often?

When did it start?

Is it getting worse?

Is it affecting many instances?
```

---

# 8. Logs

Logs are records describing individual events or application activity.

Examples:

```text
application started

database connection failed

authentication rejected

request returned 500

configuration loaded

payment request failed

container shutting down
```

Logs are especially useful for:

```text
What exactly happened?

What error occurred?

Which request failed?

What did the application report?

What happened immediately before the crash?
```

---

# 9. Traces

Traces follow work as it moves through a distributed system.

Example:

```text
User Request
↓
Gateway
↓
Frontend
↓
API
↓
Payment Service
↓
Database
```

A trace can reveal:

```text
which services participated

how long each operation took

where latency occurred

where an error originated

how services depend on one another
```

---

# 10. The Three Signals Together

Imagine checkout latency suddenly rises.

Metrics show:

```text
p95 latency:
200 ms
↓
4.8 seconds
```

Logs show:

```text
payment-service:
timeout waiting for database
```

Trace shows:

```text
checkout-api       4.9 s
└── payment        4.7 s
    └── database   4.6 s
```

Now the evidence points toward:

```text
database path
```

rather than:

```text
frontend

Ingress

scheduler

DNS
```

This is why signal correlation matters.

---

# 11. Kubernetes Events

Kubernetes provides another extremely useful diagnostic source:

```text
Events
```

Events report notable activity or state changes associated with Kubernetes resources.

Examples include:

```text
Pod scheduled

image pulling

image pulled

container started

container failed

probe failed

volume mount failed

Pod could not schedule

node became unavailable

back-off restarting container
```

Events are not a replacement for logs.

They provide Kubernetes-side evidence.

---

# 12. Events Are Best-Effort Diagnostic Evidence

Events should be treated as:

```text
temporary

informational

best-effort

supplemental
```

Do not design long-term auditing around the assumption that Kubernetes Events will remain forever.

For durable historical analysis, telemetry should be exported to systems designed for long-term retention.

---

# 13. Events vs Application Logs

Suppose a container fails.

Kubernetes Event:

```text
Back-off restarting failed container
```

Application log:

```text
FATAL: database password rejected
```

The Event tells you:

```text
what Kubernetes observed.
```

The application log may tell you:

```text
why the process failed.
```

Together:

```text
Event
+
Log
=
much stronger diagnosis.
```

# 14. Inspect Events

A traditional command is:

```bash
kubectl get events
```

Purpose:

```text
display Kubernetes Events
in the current namespace.
```

---

# 15. Events in a Namespace

Run:

```bash
kubectl get events \
  -n <NAMESPACE>
```

Example:

```bash
kubectl get events \
  -n observability-lab
```

---

# 16. Events Across Namespaces

Run:

```bash
kubectl get events \
  --all-namespaces
```

Short form:

```bash
kubectl get events -A
```

Be careful in large clusters.

The output may be extensive.

---

# 17. Sort Events

A useful troubleshooting command is:

```bash
kubectl get events \
  -n <NAMESPACE> \
  --sort-by=.metadata.creationTimestamp
```

This helps create a chronological view.

Another commonly used field is:

```text
.lastTimestamp
```

but Event API behavior and fields have evolved.

For portable modern workflows, inspect the Event structure rather than assuming every cluster exposes exactly the same timestamp fields.

# 18. `kubectl events`

Modern kubectl also provides:

```bash
kubectl events
```

Example:

```bash
kubectl events \
  -n observability-lab
```

# 19. Events for One Resource


# 20. Watch Events

Run:

```bash
kubectl events \
```

# 21. Warning Events

You can focus on warning events:

This can quickly surface:


# 22. Events Are Namespace Scoped

Many Events belong to namespaced objects.

A common mistake is:

```bash
kubectl get events
```

while investigating a Pod in:

```text
production
```

but your current namespace is:

```text
default.
```

You may see nothing useful.

Always verify:

```text
namespace.
```

# 23. `kubectl describe`

`kubectl describe` often includes Events related to the object.



This is one of the fastest first steps in Pod troubleshooting.

# 25. Container Logs

Applications commonly write logs to:

```text

```

# 26. Logging Architecture

A basic Kubernetes logging path is:

```text
Application
↓
stdout / stderr
↓
Container Runtime
↓
Node Log Files
↓
kubelet
↓
kubectl logs
```

For production centralized logging:

```text
Container
↓
stdout / stderr
↓
Container Runtime
↓
Node
↓
Log Collector
↓
Central Log Platform
↓
Search / Dashboard / Alert
```

---

# 27. Why stdout and stderr?

Containers are ephemeral.

Writing important application logs only to:

```text
/application/logs/app.log
```

inside a container can create operational problems.

If the container disappears:

```text
the file may disappear with it.
```

A common container practice is:

```text
application logs
↓
stdout / stderr
↓
runtime captures output
↓
logging infrastructure collects it
```

---

# 28. stdout

Standard output commonly carries ordinary application output.

Example:

```text
INFO server started
INFO request completed
INFO cache initialized
```

---

# 29. stderr

Standard error commonly carries error-oriented output.

Example:

```text
ERROR database unavailable
FATAL configuration invalid
```

Applications are not required to use these streams perfectly.

Log severity should therefore come from structured application logging rather than assuming:

```text
stderr always means critical error.
```

---

# 30. Read Pod Logs

Basic command:

```bash
kubectl logs <POD>
```

Example:

```bash
kubectl logs web \
  -n observability-lab
```

Purpose:

```text
retrieve logs from the Pod's container.
```

If there is only one container, specifying the container is normally unnecessary.

---

# 31. Multi-Container Pods

Suppose:

```text
Pod
├── application
└── sidecar
```

Specify the container:

```bash
kubectl logs <POD> \
  -c application \
  -n <NAMESPACE>
```

Example:

```bash
kubectl logs web \
  -c application \
  -n observability-lab
```

---

# 32. List Container Names

Run:

```bash
kubectl get pod web \
  -n observability-lab \
  -o jsonpath='{.spec.containers[*].name}'
```

Example output:

```text
application sidecar
```

Now you know which value to pass to:

```text
-c
```

---

# 33. Follow Logs

Use:

```bash
kubectl logs -f <POD>
```

Example:

```bash
kubectl logs -f web \
  -n observability-lab
```

`-f` means:

```text
follow.
```

The command continues displaying new log entries.

---

# 34. Add Timestamps

Run:

```bash
kubectl logs web \
  -n observability-lab \
  --timestamps
```

Timestamps are extremely useful when correlating:

```text
Events

```

---

# 35. Tail Recent Logs

Run:

```bash
kubectl logs web \
  -n observability-lab \
  --tail=50
```

Purpose:

```text
show only the most recent 50 lines.
```

This avoids dumping enormous logs into your terminal.

---

# 36. Logs From a Time Window

Example:

```bash
kubectl logs web \
  -n observability-lab \
  --since=10m
```

Purpose:

```text
show logs generated during approximately
the last ten minutes.
```

Useful when:

```text
alert occurred five minutes ago.
```

---

# 37. Logs Since a Specific Time

You can also use:

```bash
kubectl logs web \
  -n observability-lab \
  --since-time=<RFC3339-TIMESTAMP>
```

This is useful when you know exactly when an incident began.

---

# 38. Logs Across Matching Pods

For workloads with multiple replicas:

```bash
kubectl logs \
  -n observability-lab \
  -l app=web \
  --all-containers=true \
  --prefix
```

This can retrieve logs from matching Pods.

The prefix helps identify:

```text
which Pod

which container
```

produced each line.

For large workloads, use filters and time windows carefully.

---

# 39. Deployment Logs

kubectl can also retrieve logs through supported resource references.

Example:

```bash
kubectl logs deployment/web \
  -n observability-lab
```

For multi-Pod production investigation, however, explicitly understanding:

```text
which Pod failed
```

is often valuable.

---

# 40. Previous Container Logs

One of the most important troubleshooting commands is:

```bash
kubectl logs <POD> --previous
```

Short form:

```bash
kubectl logs <POD> -p
```

Purpose:

```text
retrieve logs from the previous instance
of a restarted container when available.
```

---

# 41. Why `--previous` Matters

Suppose:

```text
container starts
↓
application crashes
↓
container restarts
↓
new process starts
```

Normal:

```bash
kubectl logs web
```

may show logs from:

```text
the current container instance.
```

But the evidence explaining the previous crash may be in:

```bash
kubectl logs web --previous
```

---

# 42. Crash Investigation Pattern

When you see:

```text
CrashLoopBackOff
```

do not repeatedly run only:

```bash
kubectl logs <POD>
```

Use:

```bash
kubectl logs <POD> \
  --previous
```

Then:

```bash
kubectl describe pod <POD>
```

Then inspect:

```text
Last State

Reason

Exit Code

Events
```

---

# 43. Previous Logs Have Limits

`--previous` is not a historical logging database.

Node-level container log retention is limited.

If:

```text
Pod is deleted

Node disappears

logs rotate

container history is unavailable
```

the old evidence may no longer be accessible through `kubectl logs`.

That is why production environments need:

```text
centralized logging.
```

---

# 44. Kubernetes Is Not a Log Database

Kubernetes does not provide a complete native cluster-level log storage backend.

Production logging generally requires external or additional infrastructure for:

```text
collection

storage

indexing

search

retention

dashboards

alerting
```

---

# 45. Node-Level Logging

Conceptually:

```text
Pod
↓
Container
↓
stdout/stderr
↓
Container Runtime
↓
Node Log Files
```

The kubelet manages container log files and rotation behavior according to its configuration.

---

# 46. Node Logging Problem

Suppose:

```text
Pod runs on Node A
↓
logs remain on Node A
↓
Node A dies
```

Without external collection:

```text
important incident evidence may disappear.
```

Therefore production logging should have a lifecycle independent of:

```text
Pods

containers

individual Nodes.
```

---

# 47. Node-Level Log Collector

A common architecture is:

```text
Node A
├── Pod logs
└── Log Agent

Node B
├── Pod logs
└── Log Agent

Node C
├── Pod logs
└── Log Agent

        ↓

Central Log Platform
```

The agent commonly runs as:

```text
DaemonSet
```

because each Node needs log collection.

---

# 51. Structured Logging

Instead of:

```text
Something went wrong
```

prefer structured information.

Example concept:

```json
{
  "timestamp": "2026-09-21T12:00:00Z",
  "level": "ERROR",
  "service": "checkout-api",
  "request_id": "req-84291",
  "message": "database query failed",
  "duration_ms": 2400
}
```

Structured logs are easier to:

```text
search

filter

aggregate

correlate

alert on
```

# 52. Useful Log Fields

Production application logs may include:


---

# 53. Logging Security

Never casually log:

```text
passwords

API keys

access tokens

refresh tokens

private keys

session secrets

authorization headers

full sensitive request bodies

personal data that is not operationally required
```

Logs often have:

```text
broad operational access

long retention

external storage
```

A secret written to a log should generally be treated as:

```text
exposed.
```

---

# 54. Log Volume

Excessive logging creates:

```text
storage cost

network cost

CPU overhead

indexing cost

signal-to-noise problems
```

Do not solve every problem with:

```text
log everything forever.
```

Design:

```text
log levels

sampling where appropriate

retention

structured fields

redaction
```

# 58. Metrics

Metrics represent numeric observations over time.

Examples:

```text
CPU = 430m

memory = 512Mi

requests_total = 1,340,223

request_rate = 400 requests/second

error_rate = 2.4%

p95_latency = 320 ms
```

Metrics are usually stored as:

```text
time series.
```

---

# 59. Time Series

A time series is conceptually:

```text
metric name
+
labels/dimensions
+
timestamp
+
value
```

Example:

```text
http_requests_total
service="checkout"
method="GET"
status="500"
```

Values are recorded over time.

# 60. Metrics Server

Metrics Server provides resource metrics through Kubernetes' resource metrics API.

It is commonly used for:

```text
kubectl top

Horizontal Pod Autoscaler resource metrics
```

It is not intended to be:

```text
a full historical monitoring platform.
```

---

# 61. Metrics Server Architecture

Conceptually:

```text
kubelets
↓
resource metrics
↓
Metrics Server
↓
Resource Metrics API
↓
kubectl top
       +
HPA
```

---

# 62. Metrics Server Is Not Prometheus

This distinction is essential.

Metrics Server:

```text
lightweight resource metrics

supports kubectl top

supports resource-based autoscaling
```

Prometheus-style monitoring:

```text
collects many time series

stores historical measurements

supports queries

supports dashboards

supports alerts
```

They solve different problems.

# 66. `kubectl top` Is a Snapshot

`kubectl top` is excellent for:

```text
quick current resource inspection.
```

But it does not answer:

```text
What was memory usage at 02:17 yesterday?

When did CPU begin increasing?

What was p95 CPU for the last seven days?

Did memory grow continuously for six hours?
```

For those questions you need:

```text
historical metrics.
```

# 75. Infrastructure Healthy, Application Broken

Imagine:

```text
CPU = 20%

Memory = 40%

Nodes = Ready

Pods = Running
```

But:

```text
checkout failure rate = 35%
```

Infrastructure metrics alone would suggest:

```text
everything looks fine.
```

Application metrics reveal:

```text
users are failing.
```

---

# 76. RED Method

A useful service-monitoring model is RED:

```text
Rate

Errors

Duration
```

Rate:

```text
How many requests are occurring?
```

Errors:

```text
How many are failing?
```

Duration:

```text
How long are requests taking?
```

---

# 77. Example RED Metrics

For an HTTP API:

```text
Rate:
requests per second

Errors:
HTTP 5xx rate

Duration:
p50 / p95 / p99 request latency
```

This gives a much stronger view of user-facing service health than CPU alone.

---

# 78. USE Method

For infrastructure resources, another useful model is USE:


# 83. Cardinality


# 123. SLI

SLI means:

```text

```

```text

```

---

# 124. SLO

SLO means:

```text
Service Level Objective.
```

An SLO defines a target for an SLI.

Example:

```text

successful HTTP request ratio

SLO:
99.9% successful requests
over 30 days
```

---

# 125. SLI vs SLO

```text
SLI
=
what you measure
```

```text
SLO
=
the target you want that measurement to meet.
```

---

# 126. Example Availability SLI

Suppose:

```text
good requests = successful requests

valid requests = all eligible requests
```

Conceptually:

```text
Availability SLI
=
Good Requests
÷
Valid Requests
```

If:

```text
999,500 good requests

1,000,000 valid requests
```

then:

```text
SLI = 99.95%
```

---

# 127. Example SLO

You might define:

```text
99.9% of eligible requests
must succeed
over a rolling 30-day window.
```

Whether that is the correct target is a business and reliability decision.

Do not blindly copy:

```text
99.9%
```

because it looks professional.

---

# 128. Error Budget Concept

If an SLO allows less than perfect reliability, the difference between:

```text
100%
```

and:

```text
SLO target
```

creates an error-budget concept.

For a:

```text
99.9%
```

availability target, the allowed unsuccessful fraction is:

```text
0.1%
```

over the measurement window, according to the SLI definition.

---

# 129. Why SLOs Matter to Observability

Without service objectives, teams can monitor thousands of metrics without knowing:

```text
what actually matters.
```

SLOs help connect telemetry to:

```text
user expectations

reliability goals

operational decisions.
```

---

# 130. Infrastructure Metric vs SLI

CPU:

```text
85%
```

is usually not itself a user-facing SLI.

But:

```text
99.95% successful requests
```

can directly represent service reliability.

Infrastructure metrics help explain service behavior.

They do not automatically define service success.

```text
alert condition
```

with:

```text
root cause.
```

# 239. Build Evidence Before Restarting

One of the most damaging troubleshooting habits is:

```text
problem
↓
restart immediately
```

Restarting can destroy useful evidence.

Before restarting, where possible capture:

```text
Pod state

Events

current logs

previous logs

metrics

configuration

Node

timestamps
```

Then decide whether restart is appropriate.

---

# 240. Restart Is Not Root-Cause Analysis

If:

```text
restart fixes it
```

you have learned:

```text
restart changed the condition.
```

You have not necessarily learned:

```text
why the failure occurred.
```

Production engineering requires both:

```text
restore service
+
understand cause.
```

# 273. Production Observability Standard

A production Kubernetes engineer should not respond to:

```text
"The application is broken."
```

with:

```text
"Let me restart the Pods."
```

The stronger response is:

```text
What is the user impact?

When did it start?

What changed?

Which service is affected?

What do the metrics show?

What do Kubernetes Events show?

What do current and previous logs show?

What do traces show?

Which Pods, Nodes, zones, or versions are affected?

Which dependency is failing?

What evidence supports the root cause?

What change will fix it?

How will we verify recovery?
```

That is the transition from:

```text
operating Kubernetes by commands
```

to:

```text
operating Kubernetes by evidence.
```
