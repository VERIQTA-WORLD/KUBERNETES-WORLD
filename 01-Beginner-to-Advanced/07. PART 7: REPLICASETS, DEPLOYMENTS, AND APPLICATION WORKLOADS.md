# 2. The Problem With Directly Managed Pods

Suppose you create:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
    - name: web
      image: nginx:alpine
```

You now have:

```text
Pod/web
↓
nginx
```

That works.

But what happens when you run:

```bash
kubectl delete pod web
```

The Pod disappears.

If no controller owns it:

```text
Desired Pods = ?
```

There is no higher-level workload controller saying:

```text
I require one copy of this application.
```

Therefore nothing necessarily recreates it.

---

# 3. Direct Pod Mental Model

Direct Pod:

```text
User
↓
Pod
↓
Container
```

Delete Pod:

```text
User
↓
Delete Pod
↓
Pod Gone
```

There is no application-level reconciliation.

---

# 4. Managed Workload Mental Model

With a controller:

```text
Desired State
↓
Controller
↓
Pods
```

Suppose:

```text
Desired replicas = 3
```

Actual:

```text
Pod A
Pod B
Pod C
```

Everything matches.

Then:

```text
Pod B disappears
```

Actual becomes:

```text
2
```

Desired remains:

```text
3
```

Controller sees:

```text
Desired = 3
Actual = 2
```

and acts:

```text
Create replacement Pod
```

Eventually:

```text
Desired = 3
Actual = 3
```

This is Kubernetes reconciliation applied to workloads.

---

# 5. Why Pods Should Rarely Be Managed Directly

Direct Pods lack higher-level application management features such as:

```text
automatic replacement

replica management

controlled scaling

rolling updates

deployment revisions

rollout status

rollback
```

For most stateless application workloads, Kubernetes recommends using a Deployment rather than manually managing individual Pods.

---

For a typical stateless application:

```text

└── ReplicaSet
    │
    ├── Pod
    │   └── Container
    │
    ├── Pod
    │   └── Container
    │
    └── Pod

```

Each layer has a responsibility.


ReplicaSet:

```text

```

# 8. Control Loop Thinking

Suppose your Deployment declares:

```yaml
replicas: 3
```

Kubernetes continuously compares:

```text
Desired State
vs
Actual State
```

If:

```text
Desired = 3
Actual = 3
```

no corrective scaling action is required.

If:

```text
Desired = 3
Actual = 2
```

Kubernetes works toward:

```text
Create 1
```

If:

```text
Desired = 3
Actual = 4
```

Kubernetes works toward:

```text
Remove 1
```

This is not a one-time script.

It is reconciliation.

---

# 9. ReplicaSet

A ReplicaSet maintains a stable set of replica Pods.

Its basic job is:

```text
Keep N matching Pods running
```

For example:

```text
ReplicaSet
Desired replicas: 3
```

means:

```text
Keep approximately this desired population:

Pod
Pod
Pod
```

---

# 10. ReplicaSet Architecture

```text
ReplicaSet
│
├── Desired Replica Count
├── Selector
├── Pod Template
│
├── Pod
├── Pod
└── Pod
```

The ReplicaSet needs to know:

```text
How many Pods should exist?

Which Pods belong to me?

What should newly created Pods look like?
```

These correspond primarily to:

```text
replicas

selector

template
```

---

# 11. ReplicaSet Manifest

Example:

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
  namespace: workload-lab
spec:
  replicas: 3

  selector:
    matchLabels:
      app: web

  template:
    metadata:
      labels:
        app: web

    spec:
      containers:
        - name: web
          image: nginx:alpine
          ports:
            - name: http
              containerPort: 80
```

---

# 12. ReplicaSet Desired Replicas

This:

```yaml
replicas: 3
```

means:

```text
Desired Pod count = 3
```

The ReplicaSet controller works to maintain that count.

---

# 13. ReplicaSet Selector

This:

```yaml
selector:
  matchLabels:
    app: web
```

means the ReplicaSet identifies Pods using:

```text
app=web
```

The selector is fundamental to ownership and reconciliation behavior.

---

# 14. Pod Template

This:

```yaml
template:
  metadata:
    labels:
      app: web

  spec:
    containers:
      - name: web
        image: nginx:alpine
```

defines what newly created Pods should look like.

Think:

```text
ReplicaSet needs another Pod
↓
Read Pod template
↓
Create Pod based on template
```

---

# 15. Selector and Template Labels Must Match

If the ReplicaSet selector is:

```yaml
selector:
  matchLabels:
    app: web
```

but the Pod template says:

```yaml
labels:
  app: api
```

the controller definition is inconsistent.

The selector must appropriately match the labels of the Pods the controller creates.

---

# 16. Why Selectors Matter So Much

Controllers identify workloads using labels and selectors.

Think:

```text
Pod
labels:
  app=web
```

ReplicaSet:

```text
selector:
  app=web
```

Result:

```text
ReplicaSet recognizes matching Pod
```

Incorrect or overlapping selectors can create dangerous controller behavior.

---

# 17. Avoid Overlapping Controller Selectors

Do not create:

```text
ReplicaSet A
selector:
app=web
```

and:

```text
ReplicaSet B
selector:
app=web
```

for unrelated workloads.

Controllers can interfere with one another when selectors overlap incorrectly.

Production label design matters.

---

Conceptually:


# 19. ReplicaSet Reconciliation

Suppose:

```text
Desired = 3
```

Current:

```text
Pod A
Pod B
Pod C
```

Delete:

```text
Pod B
```

Now:

```text
Actual = 2
```

ReplicaSet controller observes:

```text
Desired 3
Actual 2
```

and creates:

```text
Pod D
```

Now:

```text
Actual = 3
```

The old Pod is not resurrected.

A new Pod is created.

# 20. Replacement Pod Identity

Suppose deleted Pod:

```text
web-rs-abc12
UID: AAA
IP: 10.244.1.15
```

Replacement might be:

```text
web-rs-xzy91
UID: BBB
IP: 10.244.2.17
```

The application replica was restored.

The individual Pod was not.

This reinforces:

```text
Desired application state
>
individual Pod identity
```

for interchangeable stateless replicas.

---

# 21. ReplicaSets Are Usually Not Managed Directly

You should understand ReplicaSets deeply.

But for ordinary stateless applications, you normally create:

```text
Deployment
```

and let the Deployment manage:

```text
ReplicaSets
```

for you.

Why?

Because a ReplicaSet handles replica maintenance well, but Deployment adds application update management.

---

# 22. ReplicaSet vs Deployment

ReplicaSet:

```text
Keep N Pods running
```

Deployment:

```text
Manage application revisions
+
Manage ReplicaSets
+
Perform controlled updates
+
Provide rollback
```

Therefore:

```text
Deployment
↓
ReplicaSet
↓
Pods
```

is the standard model.

---

# 23. What Is a Deployment?

A Deployment is a Kubernetes workload resource used to declaratively manage a set of Pods, usually for stateless application workloads.

You declare:

```text
Desired replicas

Pod template

Selector

Update strategy
```

The Deployment controller manages the underlying ReplicaSets needed to achieve that state.

---

# 24. Deployment Architecture

```text
Deployment
│
└── ReplicaSet
    │
    ├── Pod
    ├── Pod
    └── Pod
```

During an update:

```text
Deployment
│
├── Old ReplicaSet
│   ├── Old Pod
│   └── Old Pod
│
└── New ReplicaSet
    ├── New Pod
    └── New Pod
```

The Deployment coordinates the transition.

---

# 25. Deployment Manifest

Create:

```text
deployment.yaml
```

with:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: workload-lab
  labels:
    app: web

spec:
  replicas: 3

  selector:
    matchLabels:
      app: web

  template:
    metadata:
      labels:
        app: web

    spec:
      containers:
        - name: web
          image: nginx:1.27-alpine
          ports:
            - name: http
              containerPort: 80
```

# 27. replicas

# 28. selector


# 29. template

```yaml

```

```yaml

  metadata:
```

```yaml

```

---

# 30. Deployment Selector Immutability

For `apps/v1` Deployments, the selector is immutable after creation.

Therefore treat selector design as an important architectural decision.

Do not casually change:

```yaml
spec:
  selector:
```

on an existing Deployment.

Changing application classification often requires a different migration approach or replacement workload.

---

# 31. Deployment Pod Restart Policy

Deployment Pod templates use:

```text
restartPolicy: Always
```

Only `Always` is allowed for the Pod template in a Deployment.

You normally omit it because it is the default.

Remember the layers:

```text
Container crashes
↓
kubelet restart behavior

Pod disappears
↓
ReplicaSet restores desired replica count

Pod template changes
↓
Deployment manages rollout through ReplicaSets
```

These are different recovery mechanisms.

# 47. Scaling

Applications experience changing load.

You may need:

```text
3 Pods
↓
5 Pods
```

or:

```text
10 Pods
↓
4 Pods
```

A Deployment can be manually scaled.

---

# 48. Scale Command

Syntax:

```bash
kubectl scale deployment <DEPLOYMENT> \
  --replicas=<NUMBER> \
  -n <NAMESPACE>
```

Example:

```bash
kubectl scale deployment web \
  --replicas=5 \
  -n workload-lab
```

---

# 49. What Scaling Actually Changes

Conceptually:

```text
Deployment replicas: 3
↓
kubectl scale --replicas=5
↓
Deployment desired replicas: 5
↓
ReplicaSet desired replicas: 5
↓
2 additional Pods created
```

---

# 51. Scale Down

Run:

```bash
kubectl scale deployment web \
  --replicas=2 \
  -n workload-lab
```

```bash
kubectl get pods \
  -n workload-lab \
  --watch
```

---

# 52. Scaling Does Not Mean Resizing a Pod

Scaling from:

```text
2 → 5
```

does not mean:

```text
Make two Pods larger.
```

It means:

```text
Increase replica count.
```

This is horizontal scaling.

Later you will learn resource sizing and autoscaling.

---

# 53. Declarative Scaling

Instead of:

```bash
kubectl scale
```

you can change:

```yaml
spec:
  replicas: 5
```

in the manifest.

Then:

```bash
kubectl apply -f deployment.yaml
```

This keeps Git/manifests aligned with the desired state.

---

# 54. Important Scaling Warning

Suppose:

```text
deployment.yaml
replicas: 3
```

Then you manually run:

```bash
kubectl scale deployment web \
  --replicas=8 \
  -n workload-lab
```

The live object now wants:

```text
8
```

Later you apply the manifest again:

```bash
kubectl apply -f deployment.yaml
```

The manifest still declares:

```text
3
```

Your manual scale can therefore be overwritten back toward the declarative value.

Understand which system owns replica count.

---

# 55. Autoscaling Preview

Later, a HorizontalPodAutoscaler can manage replica count dynamically.

When autoscaling owns replicas, you should avoid competing manual/declarative replica management patterns.

The principle is:

```text
One field
↓
Clear owner
```

Avoid multiple automation systems fighting over the same desired state.

# 57. Pod Template Changes Trigger Rollouts

A Deployment rollout occurs when its:

```text
Pod template
```

changes.

For example:

```yaml
image: nginx:1.27-alpine
```

becomes:

```yaml
image: nginx:1.28-alpine
```

This changes:

```text
spec.template
```

and triggers a rollout.

---

# 58. Not Every Deployment Change Creates a Rollout

Changes outside the Pod template do not necessarily create a new rollout revision.

For example, simply scaling replicas does not represent a new application Pod-template revision.

Think:

```text
Pod Template Changed?
↓
Potential new rollout
```

versus:

```text
Replica Count Changed?
↓
Scaling
```

# 62. Rolling Update Architecture

Before:

```text
Deployment
│
└── ReplicaSet A
    ├── v1
    ├── v1
    └── v1
```

During rollout:

```text
Deployment
│
├── ReplicaSet A
│   ├── v1
│   └── v1
│
└── ReplicaSet B
    ├── v2
    └── v2
```

After:

```text
Deployment
│
├── ReplicaSet A
│   └── replicas: 0
│
└── ReplicaSet B
    ├── v2
    ├── v2
    └── v2
```

Old ReplicaSets can remain for revision history and rollback.

---

# 63. Deployment Strategies

Kubernetes Deployment supports two primary strategies:

```text
RollingUpdate

Recreate
```

`RollingUpdate` is the default.

---

# 64. RollingUpdate

RollingUpdate gradually transitions from the old ReplicaSet to the new ReplicaSet.

Conceptually:

```text
v1 v1 v1 v1
↓
v1 v1 v1 v2
↓
v1 v1 v2 v2
↓
v1 v2 v2 v2
↓
v2 v2 v2 v2
```

The exact numbers depend on:

```text
replicas

maxSurge

maxUnavailable

readiness

termination timing
```

---

# 65. Why RollingUpdate Exists

Without controlled rollout:

```text
Delete all old Pods
↓
Create all new Pods
```

could create complete application downtime.

RollingUpdate lets Kubernetes control:

```text
how quickly new Pods appear

how quickly old Pods disappear

how much temporary extra capacity exists

how much temporary unavailability is allowed
```

---

# 66. Recreate Strategy

Configure:

```yaml
strategy:
  type: Recreate
```

For an update:

```text
Old Pods
↓
Terminate
↓
New Pods
↓
Create
```

This can create downtime.

---

# 67. When Recreate Might Be Needed

Examples could include workloads where:

```text
old and new application versions cannot safely run simultaneously
```

or:

```text
the application architecture requires complete replacement
```

But do not choose Recreate casually.

For typical highly available stateless web applications:

```text
RollingUpdate
```

is usually more appropriate.

---

# 68. Recreate Does Not Mean "Never Two Pods Exist"

Be precise.

The Recreate strategy governs Deployment upgrades.

It does not provide a universal guarantee that old and replacement Pods can never overlap under every possible operational action.

For example, manually deleting a Pod interacts with ReplicaSet reconciliation separately.

Do not treat Recreate as a general-purpose strict singleton guarantee.

---

# 69. Configure RollingUpdate

Example:

```yaml
spec:
  replicas: 4

  strategy:
    type: RollingUpdate

    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
```

These two settings control rollout capacity.

---

# 70. maxSurge

`maxSurge` controls how many extra Pods can be created above the desired replica count during a rolling update.

Example:

```text
Desired replicas = 4
maxSurge = 1
```

Kubernetes can temporarily create up to approximately:

```text
5 non-terminating rollout Pods
```

subject to rollout behavior and readiness.

---

# 71. maxSurge as Percentage

You can also use:

```yaml
maxSurge: 25%
```

The percentage is calculated against desired replicas and rounded up for maxSurge.

Example conceptually:

```text
replicas = 10
maxSurge = 20%
```

allows additional rollout capacity based on that percentage.

---

# 72. maxUnavailable

`maxUnavailable` controls how many desired replicas can be unavailable during the rollout.

Example:

```text
Desired replicas = 4
maxUnavailable = 1
```

Kubernetes aims to keep at least:

```text
3
```

available during the rollout.

---

# 73. maxUnavailable as Percentage

Example:

```yaml
maxUnavailable: 25%
```

For this field, percentage conversion is rounded down.

The setting defines how much temporary unavailability the rollout is allowed to tolerate.

---

# 74. maxSurge and maxUnavailable Together

Suppose:

```text
replicas = 4

maxSurge = 1

maxUnavailable = 1
```

Conceptually Kubernetes has room to:

```text
temporarily add one extra Pod
```

and:

```text
allow one desired Pod to be unavailable
```

while transitioning versions.

---

# 75. Availability-Oriented Configuration

Example:

```yaml
rollingUpdate:
  maxSurge: 1
  maxUnavailable: 0
```

Conceptually:

```text
Do not intentionally reduce available capacity below desired count
+
Allow temporary extra Pod
```

This can be useful for availability-sensitive applications.

But it requires sufficient cluster capacity for surge Pods.

---

# 76. Capacity Matters

Suppose:

```text
Desired Pods = 100

maxSurge = 25%
```

The cluster may need capacity for significant temporary additional workload.

Therefore rollout configuration is not merely application configuration.

It affects:

```text
CPU capacity

memory capacity

node capacity

scheduling

cost
```

---

# 77. Terminating Pods and Surge Accounting

During rollouts, terminating Pods may remain present while their grace periods expire.

Therefore you can temporarily observe more Pod objects or resource consumption than a simplistic:

```text
replicas + maxSurge
```

calculation might suggest.

Always inspect:

```text
Running

Ready

Available

Terminating
```

rather than assuming every visible Pod is equivalent.

---

# 78. Default RollingUpdate Values

If not specified, Kubernetes Deployment RollingUpdate defaults are:

```text
maxUnavailable: 25%

maxSurge: 25%
```

Do not rely blindly on defaults for production.

Choose rollout behavior based on:

```text
replica count

traffic requirements

startup time

cluster capacity

failure tolerance

application readiness behavior
```

---

# 79. Critical maxSurge/maxUnavailable Rule

They cannot both effectively be zero.

Kubernetes must be allowed to make progress.

If:

```text
maxSurge = 0
```

then some unavailability must be permitted.

If:

```text
maxUnavailable = 0
```

then surge capacity must be permitted.

# 86. Revision History

A Deployment's revision history is represented through old ReplicaSets retained by the Deployment.

Think:

```text
Revision 1
↓
ReplicaSet A

Revision 2
↓
ReplicaSet B

Revision 3
↓
ReplicaSet C
```

Old ReplicaSets can remain scaled to zero.

Their templates allow rollback.

---

# 87. revisionHistoryLimit

Configure:

```yaml
spec:
  revisionHistoryLimit: 5
```

This tells Kubernetes how many old ReplicaSets to retain for rollback history.

The default is:

```text
10
```

old ReplicaSets.

---

# 88. Why Revision History Consumes State

Old ReplicaSets:

```text
consume API/etcd object state

appear in ReplicaSet listings

retain previous Pod-template configuration
```

You do not necessarily need hundreds of old revisions.

But deleting all history removes rollback capability.

---

# 89. revisionHistoryLimit: 0

If:

```yaml
revisionHistoryLimit: 0
```

old ReplicaSets with zero replicas are cleaned up.

That means previous Deployment revisions are not retained for rollback.

Do not set this casually.

---

# 90. Revision History Is Not Source Control

Kubernetes rollout history does not replace:

```text
Git
```

Git should still answer:

```text
Who changed this?

Why?

What was reviewed?

Which ticket approved it?

What source produced the deployment?
```

Kubernetes revision history helps operational rollback.

Git provides durable change history and governance.

# 96. Rollout Restart

Sometimes you need Pods recreated even though the application Pod template does not otherwise need a meaningful business configuration change.

# 97. Why Rollout Restart Is Useful

Examples include:

```text
restarting Pods after an external dependency/configuration change

controlled process restart

operational recovery when restarting instances is appropriate
```

It is safer than manually deleting all Pods simultaneously.

---

# 98. What Rollout Restart Actually Does

It updates the Pod template with a restart-related annotation.

Because the Pod template changes:

```text
New ReplicaSet
↓
New Pods
↓
Rolling replacement
```

This means:

```text
rollout restart
```

is still a rollout.

# 100. Do Not Use Restart as a Substitute for Root-Cause Analysis

Bad incident response:

```text

↓
Restart
↓
Works
↓
Close incident
```

Better:

```text

↓

↓

↓

↓
Verify recovery
↓
Determine root cause
↓
Prevent recurrence
```

Restarting can destroy useful evidence.

# 106. Deployment Progress

A Deployment is considered progressing while operations such as these occur:


# 107. Completed Rollout

A rollout is complete when the Deployment reaches its expected updated and available state and old replicas are no longer running as active old-version workload replicas.

Use:

```bash
kubectl rollout status deployment/web \
  -n workload-lab
```

rather than manually guessing from one Pod.

---

# 108. progressDeadlineSeconds

A Deployment can configure:

```yaml
progressDeadlineSeconds: 600
```

This tells Kubernetes how long to wait for Deployment progress before reporting that the rollout has failed to progress.

It does not automatically perform rollback.

That distinction is important.

---

# 109. Progress Deadline Is Not Automatic Rollback

Think:

```text
Deployment fails to progress
↓
Condition reports failure
```

not:

```text
Deployment fails
↓
Kubernetes automatically restores old version
```

Rollback remains an operational or automation decision.

---

# 110. minReadySeconds

You can configure:

```yaml
minReadySeconds: 10
```

This requires a new Pod to remain Ready without crashing for the specified period before being considered available.

This can help avoid considering extremely unstable Pods immediately available.

---

# 111. Readiness Determines Safe Rollout Behavior

RollingUpdate depends heavily on:

```text
Pod readiness
```

If your application becomes:

```text
Running
```

before it is actually capable of serving traffic, poor readiness configuration can cause Kubernetes to progress a rollout too aggressively.

This is why later you will study:

```text
readinessProbe

startupProbe

livenessProbe
```

in depth.

---

# 112. Running Is Still Not Ready

Part 6 rule:

```text
Running
≠
Ready
```

Part 7 consequence:

```text
Incorrect readiness
↓
Incorrect rollout decisions
↓
Possible user-facing failures
```

Health checks are not decorative YAML.

They influence workload availability.

# 162. Deployment Rollout vs Container Restart

```text

```



# 163. Deployment Rollout vs Scaling





is rollout.

# 164. Deployment Rollout vs Pod Deletion


This does not mean you created a new Deployment revision.

The Pod template did not change.



ReplicaSets can adopt certain matching Pods that are not already controlled appropriately.

# 201. ReplicaSet Scaling Logic

ReplicaSet control loop:

```text
Read desired replicas
↓
Find matching owned/adoptable Pods
↓
Count actual replicas
↓
Compare
```

If:

```text
Actual < Desired
```

create Pods.

If:

```text
Actual > Desired
```

remove excess Pods.

Then repeat over time as cluster state changes.

---

# 202. Deployment Scaling Logic

Deployment desired replica count eventually influences the active ReplicaSet.

Stable state:

```text
Deployment replicas = 5
↓
Current ReplicaSet replicas = 5
↓
5 Pods
```

During rollout, the Deployment distributes replica counts across old/new ReplicaSets according to rollout strategy.

---

# 203. Deployment Update Logic

Simplified:

```text
Pod template changes
↓
Deployment detects new template
↓
Create/find ReplicaSet for new template
↓
Scale new ReplicaSet up
↓
Scale old ReplicaSet down
↓
Observe availability
↓
Continue
↓
New ReplicaSet reaches desired state
↓
Old ReplicaSet reaches zero
```

This is the core RollingUpdate mechanism.

---

# 204. Rollover

Suppose revision 2 is still rolling out.

Before it completes, you update to revision 3.

Kubernetes can begin transitioning toward the newest desired Pod template rather than requiring revision 2 to finish first.

This behavior is called:

```text
rollover
```

Conceptually:

```text
v1
↓
v2 rollout begins
↓
v3 requested before v2 completes
↓
Deployment transitions toward v3
```

Production pipelines should avoid uncontrolled overlapping releases unless deliberately designed for them.

---

# 205. Deployment Race Prevention

A mature release process should prevent:

```text
Pipeline A deploying revision A
```

while:

```text
Pipeline B unexpectedly deploys revision B
```

without coordination.

Possible controls include:

```text
deployment concurrency controls

environment locks

GitOps reconciliation

approval gates

release queues
```

Kubernetes can reconcile desired state, but your delivery process must define who is allowed to change that state.

# 262. Knowledge Check: ReplicaSets

### 1. What is the main purpose of a ReplicaSet?

Maintain a specified number of matching Pod replicas.

### 2. What are its three key concepts?

```text
replicas
selector
Pod template
```

### 3. What happens if one ReplicaSet-managed Pod is deleted?

The ReplicaSet creates a replacement to restore desired replica count.

### 4. Is the replacement the same Pod?

No.

It has a new identity.

### 5. Should ordinary applications usually create ReplicaSets directly?

Usually no.

Use a Deployment.

---

# 263. Knowledge Check: Deployment

### 6. What does a Deployment manage?

ReplicaSets and application rollout state.

### 7. What manages Pods underneath a Deployment?

ReplicaSets.

### 8. What is the hierarchy?

```text
Deployment
↓
ReplicaSet
↓
Pod
↓
Container
```

### 9. What type of workload is Deployment usually best suited for?

Stateless applications with interchangeable replicas.

### 10. Why not edit Deployment-managed Pods directly?

The change is not durable desired state and can disappear when Pods are replaced.

---

# 264. Knowledge Check: Scaling

### 11. What does `kubectl scale` change?

Desired replica count.

### 12. Does scaling create a new application Pod-template revision?

No.

### 13. Is 3 → 10 replicas vertical scaling?

No.

It is horizontal scaling.

### 14. Can applying a manifest overwrite a manual replica count?

Yes, if the manifest declares a different `.spec.replicas`.

### 15. Why should field ownership be clear?

To prevent humans and automation from fighting over desired state.

---

# 265. Knowledge Check: Strategies

### 16. What are the two Deployment strategies?

```text
RollingUpdate
Recreate
```

### 17. Which is default?

RollingUpdate.

### 18. What does RollingUpdate do?

Gradually transitions from old Pods to new Pods using ReplicaSets.

### 19. What does Recreate do during an update?

Terminates old revision Pods before creating the new revision Pods.

### 20. Can Recreate cause downtime?

Yes.

---

# 266. Knowledge Check: maxSurge

### 21. What does maxSurge control?

How many additional Pods can be created above desired replicas during a rolling update.

### 22. Can it be a percentage?

Yes.

### 23. How is percentage-based maxSurge rounded?

Up.

### 24. What operational resource does surge require?

Additional cluster capacity.

### 25. Is higher surge always better?

No.

It trades additional resource consumption for rollout capacity/speed.

---

# 267. Knowledge Check: maxUnavailable

### 26. What does maxUnavailable control?

How many desired replicas can be unavailable during rollout.

### 27. Can it be zero?

Yes, if maxSurge permits rollout progress.

### 28. How is percentage-based maxUnavailable rounded?

Down.

### 29. Does higher maxUnavailable improve availability?

No.

It permits greater temporary unavailability.

### 30. Can maxSurge and maxUnavailable both be zero?

No.

---

```bash
kubectl rollout status deployment/<NAME>
```

### 32. How do you view history?


### 34. How do you restart Pods through the Deployment?

# 269. Knowledge Check: Revisions

### 36. What typically creates a new Deployment revision?

A Pod-template change.

### 37. Where is Deployment revision history represented?

In retained ReplicaSets.

### 38. What controls retained old ReplicaSets?

```text
revisionHistoryLimit
```

### 39. What is its default?

10.

### 40. What happens if it is zero?

Old zero-replica ReplicaSets are cleaned up, removing rollback history.

---

# 270. Knowledge Check: Failures

### 41. What does ImagePullBackOff usually indicate?

The requested image cannot currently be successfully pulled.

### 42. What does CrashLoopBackOff indicate?

A container starts, repeatedly terminates, and restart attempts enter backoff.

### 43. What can keep a Running Pod from progressing a rollout?

Failure to become Ready.

### 44. Does progressDeadlineSeconds automatically roll back a failed Deployment?

No.

### 45. Why inspect old and new ReplicaSets?

To understand which revision is healthy, which is being introduced, and how rollout is progressing.

```text
What was the last healthy revision?

Should we fix forward or roll back?

How will we verify recovery?
```

That is production Kubernetes thinking.

# 279. The Most Important Lesson

Pods run application instances.

ReplicaSets maintain replica count.

Deployments manage application evolution.

Remember:

```text
Pod
↓
Runs one workload instance
```

```text
ReplicaSet
↓
Maintains N interchangeable Pods
```

```text
Deployment
↓
Manages ReplicaSets
+
Scaling
+
Rolling Updates
+
Revisions
+
Rollback
```

Together:

```text
Deployment
↓
ReplicaSet
↓
Pods
↓
Containers
↓
Application
```

This hierarchy is one of the foundations of Kubernetes.

# 281. What Comes Next

You can now run:

```text
3 Pods
```

and Kubernetes can keep:

```text
3 Pods
```

running.

You can scale them.

You can replace them.

You can update them.

You can roll them back.

But another problem appears.

Suppose your application currently has:

```text
Pod A
10.244.1.10

Pod B
10.244.2.14

Pod C
10.244.3.21
```

A rollout occurs.

Those Pods disappear.

New Pods receive:

```text
different names
different UIDs
different IP addresses
```

How does another application reliably find them?

How do users connect to a changing group of Pods?

How do you load balance across replicas?

How do you provide one stable endpoint in front of replaceable Pods?

That leads directly to:

```text
PART 8
↓
Kubernetes Services
↓
Stable Networking
↓
Service Discovery
↓
ClusterIP
↓
NodePort
↓
LoadBalancer
↓
EndpointSlices
↓
DNS
↓
Traffic to Pods
```

Deployments solve:

```text
How do I reliably maintain and update application instances?
```

Services solve the next problem:

```text
How do I reliably reach those changing application instances?
```
