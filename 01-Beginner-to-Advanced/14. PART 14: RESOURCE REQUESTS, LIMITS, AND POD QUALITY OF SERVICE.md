# 2. Why Resource Management Matters

A Kubernetes cluster has finite resources.

Every node has some amount of:

```text
CPU
Memory
Storage
Network capacity
```

Consider a worker node with:

```text
4 CPUs

8 GiB RAM
```

Now imagine deploying:

```text
20 applications
```

without declaring how much CPU or memory they need.

Each application could potentially compete for the same resources.

This creates:

```text
resource contention
```

---

# 3. Resource Contention

Imagine:

```text
Pod A
Pod B
Pod C
Pod D
```

all running on the same node.

During normal traffic:

```text
CPU usage low
Memory usage low
```

Everything appears healthy.

Then traffic increases.

Suddenly:

```text
Pod A → high CPU

Pod B → high memory

Pod C → high CPU

Pod D → high memory
```

The node has not magically gained additional resources.

The workloads now compete.

---

# 4. The Resource Management Problem

Kubernetes needs answers to two different questions.

First:

```text
Where can this Pod safely be scheduled?
```

Second:

```text
How much resource may this container consume while running?
```

These questions lead to:

```text
Requests
```

and:

```text
Limits
```

---

# 5. The Most Important Distinction

Memorize:

```text
REQUEST
=
resource amount used primarily for scheduling and resource allocation decisions
```

```text
LIMIT
=
runtime ceiling or enforcement boundary
```

Simplified:

```text
Request
↓
"Please reserve/plan for this much."

Limit
↓
"Do not let me exceed this runtime boundary."
```

But CPU and memory limits behave differently.

We will examine that carefully.

---

# 6. Compute Resources

The two most important Kubernetes compute resources are:

```text
CPU
Memory
```

Kubernetes can manage other resources, but CPU and memory form the foundation of resource management.

---

# 7. CPU

CPU represents computational processing time.

Kubernetes expresses CPU as:

```text
CPU units
```

One CPU unit roughly corresponds to:

```text
1 physical CPU core
```

on a physical machine, or:

```text
1 virtual CPU
```

on a virtual machine.

---

# 8. CPU Units

Examples:

```text
1
```

means:

```text
1 CPU
```

```text
0.5
```

means:

```text
half a CPU
```

Kubernetes also supports:

```text
millicpu
```

commonly called:

```text
millicores
```

---

# 9. Millicpu

```text
1000m
=
1 CPU
```

Therefore:

```text
500m
=
0.5 CPU
```

```text
250m
=
0.25 CPU
```

```text
100m
=
0.1 CPU
```

---

# 10. CPU Conversion

Memorize:

```text
1 CPU = 1000m
```

Therefore:

```text
100m = 10% of one CPU

250m = 25% of one CPU

500m = 50% of one CPU

750m = 75% of one CPU

1000m = 1 CPU

2000m = 2 CPUs
```

---

# 11. CPU Is Absolute

A request of:

```text
500m
```

means approximately half of one CPU worth of processing capacity.

It does not mean:

```text
50% of whatever node happens to run the Pod.
```

It represents an absolute CPU quantity.

---

# 12. CPU Example

Suppose a node has:

```text
8 CPUs
```

A container requests:

```text
500m
```

That request represents:

```text
0.5 CPU
```

not:

```text
50% of the 8-CPU node.
```

---

# 13. Memory

Memory represents RAM consumed by processes.

Kubernetes supports several quantity suffixes.

Common examples:

```text
Ki

Mi

Gi
```

---

# 14. Binary Memory Units

Common binary units:

```text
1 Ki = 1024 bytes

1 Mi = 1024 Ki

1 Gi = 1024 Mi
```

Examples:

```text
128Mi

256Mi

512Mi

1Gi

2Gi
```

---

# 15. Decimal and Binary Units

Kubernetes quantity notation can use decimal units such as:

```text
M
G
```

and binary units such as:

```text
Mi
Gi
```

These are not identical.

For example:

```text
1Gi
```

is not exactly the same quantity as:

```text
1G
```

Be deliberate with resource units.

---

# 16. Dangerous Memory Typo

This is especially important:

```yaml
memory: 400m
```

does NOT mean:

```text
400 megabytes.
```

The suffix:

```text
m
```

means milli.

For memory, use values such as:

```yaml
memory: 400Mi
```

when you mean approximately 400 mebibytes.

A tiny typo can completely change the intended resource quantity.

---

# 17. Resource Configuration Location

Traditional container-level requests and limits are defined under:

```yaml
resources:
```

inside a container specification.

Example:

```yaml
containers:
  - name: web
    image: nginx:1.27

    resources:
      requests:
        cpu: "250m"
        memory: "128Mi"

      limits:
        cpu: "500m"
        memory: "256Mi"
```

---

# 18. Read This Manifest

The container requests:

```text
250m CPU
128Mi memory
```

and has limits of:

```text
500m CPU
256Mi memory
```

This gives Kubernetes information for both:

```text
scheduling
```

and:

```text
runtime enforcement.
```

---

# 19. Resource Requests

A request tells Kubernetes the amount of a resource the workload expects to need for scheduling purposes.

Example:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "128Mi"
```

The scheduler considers these values when deciding where the Pod can run.

---

# 20. Requests Are Not Usage

This distinction is critical.

Suppose:

```text
CPU request = 500m
```

Actual CPU usage might currently be:

```text
50m
```

or:

```text
400m
```

or, if no lower limit prevents it and spare CPU is available:

```text
more than 500m.
```

Request is not a real-time usage measurement.

---

# 21. Requests Are Scheduling Commitments

Think:

```text
Request
↓
Scheduler planning value
```

not:

```text
Request
=
exact resource consumption
```

---

# 22. Scheduler Relationship

Suppose a node has:

```text
4 CPUs allocatable
```

and already hosts Pods whose CPU requests total:

```text
3.5 CPUs
```

A new Pod requests:

```text
1 CPU
```

The scheduler sees:

```text
available by requests:
0.5 CPU
```

The Pod requires:

```text
1 CPU
```

Result:

```text
Pod cannot fit.
```

---

# 23. Actual CPU Usage May Be Low

Suppose the existing Pods are actually using only:

```text
0.5 CPU
```

The scheduler may still refuse the new Pod.

Why?

Because scheduling is based on resource requests and available allocatable capacity, not simply a snapshot of current usage.

---

# 24. Why Kubernetes Works This Way

Imagine scheduling based only on current usage.

At 03:00:

```text
all applications idle
```

Scheduler packs many workloads onto one node.

At 12:00:

```text
all applications reach peak traffic
```

Now they all need the capacity they originally expected.

The node becomes overloaded.

Requests provide planning information.

---

# 25. Scheduler Mental Model

Conceptually:

```text
New Pod
↓
Read Pod requests
↓
Inspect candidate nodes
↓
Compare existing requested resources
against node allocatable resources
↓
Filter nodes that cannot satisfy request
↓
Score feasible nodes
↓
Select node
↓
Bind Pod
```

---

# 26. Requests Across Multiple Containers

Suppose a Pod contains:

```text
Container A
CPU request: 200m
Memory request: 128Mi

Container B
CPU request: 300m
Memory request: 256Mi
```

Conceptually, the Pod requires:

```text
CPU:
200m + 300m = 500m

Memory:
128Mi + 256Mi = 384Mi
```

The scheduler must account for the Pod's overall resource requirements.

---

# 27. Init Container Nuance

Pods can contain init containers.

Scheduling calculations involving init containers are more nuanced than simply adding every init container request to every application container request because init containers normally run sequentially.

You do not need to memorize every formula yet.

The important lesson is:

```text
scheduler evaluates the Pod's effective resource requirement,
not merely one container in isolation.
```

---

# 28. Resource Limits

Limits specify runtime resource boundaries.

Example:

```yaml
resources:
  limits:
    cpu: "500m"
    memory: "256Mi"
```

But:

```text
CPU limit behavior
≠
Memory limit behavior
```

This distinction is essential.

---

# 29. CPU Limit

A CPU limit controls how much CPU time a container can consume.

Example:

```yaml
limits:
  cpu: "500m"
```

means the container is constrained to approximately:

```text
0.5 CPU
```

worth of CPU time.

---

# 30. CPU Limit Does Not Kill the Container

If the application wants:

```text
1 CPU
```

but the limit is:

```text
500m
```

Kubernetes does not normally respond by:

```text
killing the container.
```

Instead CPU access is restricted.

This is:

```text
CPU throttling.
```

---

# 31. CPU Throttling

Conceptually:

```text
Application wants more CPU
↓
CPU limit reached
↓
Linux cgroup enforcement
↓
process receives less CPU time
↓
application continues running
↓
performance may degrade
```

---

# 32. CPU Throttling Symptoms

Possible symptoms include:

```text
higher latency

slower request processing

longer batch jobs

reduced throughput

timeouts

queue growth
```

Yet:

```text
Pod may remain Running.
```

This can make CPU-limit problems less obvious than crashes.

---

# 33. CPU Request vs CPU Limit

Example:

```yaml
requests:
  cpu: "250m"

limits:
  cpu: "500m"
```

Interpretation:

```text
Scheduler plans around:
250m

Container may use:
up to roughly 500m before CPU throttling enforcement
```

when CPU demand exists.

---

# 34. CPU Bursting Concept

Suppose:

```text
request = 250m

limit = 1000m
```

The workload can potentially use more CPU than its request when capacity is available.

This allows bursts.

But it cannot continuously consume beyond the configured CPU limit.

---

# 35. No CPU Limit

If a container has:

```text
CPU request
```

but:

```text
no CPU limit
```

it can potentially consume spare CPU beyond its request when available.

This may be useful for some workloads.

It also means noisy-neighbor behavior must be considered carefully.

---

# 36. Are CPU Limits Always Good?

Not necessarily.

CPU limits can protect shared environments.

But overly restrictive CPU limits can cause:

```text
throttling

latency

poor application performance
```

even when the node has otherwise unused CPU capacity.

Production resource policy should be based on workload behavior rather than blindly applying the same numbers everywhere.

---

# 37. Memory Request

Example:

```yaml
requests:
  memory: "256Mi"
```

The scheduler uses this value when deciding whether a node has sufficient allocatable memory.

---

# 38. Memory Usage Can Exceed Request

Suppose:

```text
memory request = 256Mi

memory limit = 1Gi
```

The container may use:

```text
300Mi

500Mi

800Mi
```

assuming runtime conditions allow it.

The request is not the maximum.

---

# 39. Memory Limit

Example:

```yaml
limits:
  memory: "512Mi"
```

Memory behaves differently from CPU.

There is no simple equivalent of:

```text
"just slow the process down"
```

for ordinary memory-limit enforcement.

When memory pressure crosses the relevant enforced boundary, the kernel may terminate processes.

---

# 40. Memory Enforcement

Conceptually:

```text
Container allocates memory
↓
memory usage grows
↓
cgroup memory limit reached/exceeded
↓
kernel OOM handling
↓
process terminated
↓
container terminates
```

This often appears in Kubernetes as:

```text
OOMKilled
```

---

# 41. OOM

OOM means:

```text
Out Of Memory
```

An:

```text
OOM kill
```

means the kernel terminated a process because of memory constraints.

---

# 42. `OOMKilled`

A Kubernetes container may show:

```text
Reason: OOMKilled
```

This is strong evidence that memory exhaustion or a memory limit was involved.

---

# 43. OOMKilled Does Not Mean CPU Problem

Do not troubleshoot:

```text
OOMKilled
```

by increasing:

```text
CPU.
```

OOM is fundamentally a memory problem.

Investigate:

```text
memory limit

application memory usage

memory leak

working set

traffic pattern

cache behavior

heap settings

concurrency
```

---

# 44. Container Restart After OOM

Suppose a Deployment Pod uses:

```yaml
restartPolicy: Always
```

which is standard for Deployment-managed Pods.

Container exceeds memory limit.

Flow:

```text
Container
↓
OOMKilled
↓
Container terminates
↓
kubelet restarts container
↓
same Pod may continue
```

Repeated memory failure can eventually appear operationally as:

```text
CrashLoopBackOff
```

depending on repeated restart behavior.

---

# 45. OOMKilled vs Evicted

These are not the same thing.

`OOMKilled` usually refers to a process/container being terminated by memory OOM handling.

`Evicted` can refer to the kubelet terminating a Pod to reclaim node resources under node pressure.

Conceptually:

```text
Container memory limit problem
→ possible OOMKilled

Node-wide memory pressure
→ possible Pod eviction
```

They can be related but should not be treated as identical.

---

# 46. Runtime Enforcement

After scheduling:

```text
kubelet
↓
container runtime
↓
Linux kernel mechanisms
```

apply resource controls.

On Linux, this is typically implemented through:

```text
cgroups
```

or:

```text
control groups.
```

---

# 47. cgroups Concept

Linux control groups allow processes to be grouped and controlled for resources such as:

```text
CPU

memory
```

Kubernetes does not invent an entirely separate CPU scheduler or memory manager.

It relies on operating-system primitives.

---

# 48. Kubernetes Resource Stack

Think:

```text
Kubernetes API
↓
Pod resource specification
↓
Scheduler
↓
Node
↓
kubelet
↓
Container runtime
↓
Linux cgroups
↓
Kernel
↓
Application processes
```

# 49. Important Request/Limit Rule

If you specify a resource limit but do not specify a request for that same resource, Kubernetes can copy the limit into the request when no admission-time mechanism has already provided a request.

Example:

```yaml
limits:
  memory: "512Mi"
```

may effectively result in:

```text
memory request = 512Mi

memory limit = 512Mi
```

depending on admission/defaulting context.

Do not assume:

```text
"no request written"
=
"request always zero."
```

---

# 50. Requests Without Limits

You can configure:

```yaml
requests:
  cpu: "250m"
  memory: "256Mi"
```

without limits.

This gives the scheduler placement information while allowing runtime usage above the request when resources are available.

Whether that is appropriate depends on workload and cluster policy.

---

# 51. Limits Without Thoughtful Requests

A common beginner configuration is:

```yaml
limits:
  cpu: "2"
  memory: "2Gi"
```

without understanding the resulting request behavior or namespace defaults.

This can accidentally make workloads request far more resources than expected.

Result:

```text
Pods Pending
```

even when observed node usage appears low.

---

# 52. Quality of Service

Kubernetes assigns each Pod a:

```text
Quality of Service class
```

abbreviated:

```text
QoS
```

The three main classes are:

```text
Guaranteed

Burstable

BestEffort
```

---

# 53. Why QoS Exists

When a node experiences resource pressure, Kubernetes needs information that helps determine how workloads should be treated.

QoS classification reflects how requests and limits are configured.

It influences resource-pressure behavior.

---

# 54. QoS Classes

Hierarchy conceptually:

```text
Guaranteed

Burstable

BestEffort
```

But do not interpret this as:

```text
Guaranteed Pods can never fail.
```

They can.

QoS is one part of Kubernetes resource management and eviction behavior.

---

# 55. Guaranteed QoS

For a Pod to receive:

```text
Guaranteed
```

QoS under the traditional container-level model, every container in the Pod must have:

```text
CPU request

CPU limit

memory request

memory limit
```

and for each container:

```text
CPU request = CPU limit

memory request = memory limit
```

---

# 56. Guaranteed Example

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "256Mi"

  limits:
    cpu: "500m"
    memory: "256Mi"
```

For every container in the Pod, the required CPU and memory request/limit relationships must satisfy Guaranteed criteria.

---

# 57. Guaranteed Mental Model

```text
CPU request = CPU limit

AND

Memory request = Memory limit

for all relevant containers
↓
Guaranteed
```

---

# 58. Why It Is Called Guaranteed

The term does not mean:

```text
application will never crash.
```

It means the Pod has the strongest QoS resource specification relationship.

It can still fail because of:

```text
application bugs

node failure

storage failure

network failure

administrative action

extreme node conditions
```

---

# 59. Burstable QoS

A Pod is typically:

```text
Burstable
```

when it has some CPU or memory request/limit configuration but does not meet all requirements for:

```text
Guaranteed.
```

---

# 60. Burstable Example

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "128Mi"

  limits:
    cpu: "1000m"
    memory: "512Mi"
```

Requests and limits differ.

Therefore this is not Guaranteed.

It is typically:

```text
Burstable.
```

---

# 61. Another Burstable Example

```yaml
resources:
  requests:
    memory: "256Mi"
```

This Pod has a resource request but does not satisfy Guaranteed criteria.

Result:

```text
Burstable.
```

---

# 62. BestEffort QoS

A Pod is:

```text
BestEffort
```

when containers do not have CPU or memory requests or limits configured in the way that would move the Pod into another QoS class.

Example:

```yaml
containers:
  - name: app
    image: nginx:1.27
```

with no CPU or memory requests/limits.

---

# 63. BestEffort Mental Model

```text
No CPU request
No CPU limit
No memory request
No memory limit
↓
BestEffort
```

under the traditional model.

---

# 64. Why BestEffort Can Be Risky

BestEffort tells Kubernetes very little about resource needs.

Under node resource pressure, these workloads can be especially vulnerable.

This does not mean:

```text
BestEffort always fails.
```

It means:

```text
resource guarantees are weakest.
```

# 75. Node Capacity

Every node reports its total resource capacity.

Inspect:

```bash
kubectl describe node <NODE>
```

Look for:

```text
Capacity:
```

You may see values for:

```text
cpu

memory

ephemeral-storage

pods
```

---

# 76. Capacity Means Physical or Virtual Capacity

Conceptually:

```text
Node Capacity
=
resources available on the machine
before Kubernetes reservations and other considerations
```

But Pods generally cannot consume the entire raw node capacity.

---

# 77. Allocatable Resources

Nodes also report:

```text
Allocatable
```

This represents the resources available for Pods after Kubernetes accounts for resources that should not be available to ordinary workloads.

Conceptually:

```text
Capacity
-
system reservations
-
Kubernetes reservations
-
other relevant reservations
=
Allocatable
```

---

# 78. Capacity vs Allocatable

Example:

```text
Node Capacity:
CPU = 4
Memory = 8Gi
```

Allocatable might be:

```text
CPU = 3.8
Memory = 7.2Gi
```

The exact values depend on node configuration.

The scheduler works with allocatable resources rather than pretending the entire machine belongs to application Pods.

---

# 79. Why Reservations Exist

The node itself requires resources for:

```text
Linux kernel

kubelet

container runtime

system daemons

networking components

logging agents

other node services
```

If workloads consume every last byte of RAM, the node itself can become unstable.

---

# 83. Requests Can Exceed Current Usage

Imagine:

```text
Node allocatable CPU:
4 CPUs

Total requests:
3.8 CPUs

Actual current usage:
0.4 CPUs
```

A Pod requesting:

```text
500m
```

may remain Pending because:

```text
3.8 + 0.5 = 4.3
```

which exceeds:

```text
4 CPUs allocatable.
```

---

# 84. Limits Can Be Overcommitted

Depending on policy, total limits on a node can exceed physical capacity.

Example:

```text
Node:
4 CPUs

Pod A CPU limit:
2 CPUs

Pod B CPU limit:
2 CPUs

Pod C CPU limit:
2 CPUs
```

Total limits:

```text
6 CPUs
```

This can exist because not every workload necessarily reaches its limit simultaneously.

But overcommit creates contention risk.

---

# 85. Memory Overcommit Is More Dangerous

CPU contention often results in:

```text
slower execution
```

Memory exhaustion can result in:

```text
process termination

OOM kills

Pod eviction

node instability
```

Therefore memory sizing requires particular care.



# 89. Node Pressure

The kubelet monitors node resources.

Important node conditions can include:

```text
MemoryPressure

DiskPressure

PIDPressure
```

When resource pressure reaches configured thresholds, the kubelet can reclaim resources and may evict Pods.

---

# 90. MemoryPressure

Inspect:

```bash
kubectl describe node <NODE>
```

Look under:

```text
Conditions:
```

for:

```text

```

If:

```text
MemoryPressure=True
```

the node is experiencing memory pressure according to its configured thresholds.

---

# 91. Node-Pressure Eviction

When a node becomes resource-starved, kubelet can terminate Pods to reclaim resources.

This is:

```text
node-pressure eviction.
```

Flow:

```text
Node resource decreases
↓
Eviction threshold crossed
↓
kubelet attempts resource reclamation
↓
insufficient recovery
↓
Pod selection
↓
Pod eviction
```

---

# 92. QoS and Eviction Nuance

A common oversimplification is:

```text
BestEffort always evicted first,
then Burstable,
then Guaranteed.
```

Reality is more nuanced.

For memory pressure, Kubernetes considers factors including:

```text
whether usage exceeds requests

Pod Priority

usage relative to requests
```

QoS is useful for understanding likely behavior, but the actual eviction decision is not simply a three-item QoS sort.

---

# 93. Important Production Lesson

A:

```text
Guaranteed
```

Pod is not:

```text
immune from eviction.
```

Under sufficiently severe conditions Kubernetes may still have to terminate workloads to preserve node stability.

# 120. ResourceQuota

A ResourceQuota applies aggregate restrictions to a namespace.

It can control quantities such as:

```text

PVC counts
```

```text
↓
```

```text
many Pods
↓
sudden CPU and memory demand
```

This is sometimes called a workload spike or scheduling burst.

Spread schedules where appropriate.

---

# 161. Resource Starvation and Noisy Neighbors

A noisy neighbor is a workload that consumes excessive shared resources and negatively affects other workloads.

Example:

```text
Pod A
↓
consumes large CPU share

Pod B
↓
latency increases
```

Resource controls help reduce this risk.

---

# 162. Requests Are Not Hard CPU Isolation

A CPU request does not mean:

```text

```

If additional CPU is available and no limit prevents it, the workload can potentially use more.

Request and limit solve different problems.

---

# 163. Memory Requests Are Not Memory Reservations in the Simplest Physical Sense

Do not imagine Kubernetes carving physical RAM into permanently isolated chunks immediately when a Pod is scheduled.

Requests primarily provide scheduling/resource management information.

Actual memory consumption depends on the workload.

# 173. Resource Fragmentation

Imagine two nodes:

```text
Node A:
500m CPU available
4Gi memory available

Node B:
4 CPU available
500Mi memory available
```

New Pod requires:

```text
1 CPU
1Gi memory
```

Cluster totals appear to have enough:

```text
CPU > 1

Memory > 1Gi
```

But no single node satisfies both simultaneously.

Pod remains Pending.

This is:

```text
resource fragmentation.
```

---

# 174. Scheduler Thinks Per Node

Resources are not magically pooled into one giant virtual machine.

The scheduler must find:

```text
one node
```

that satisfies the Pod's scheduling requirements.

This is why cluster-wide totals alone can be misleading.

# 175. Overcommit

Overcommit means promising or allowing workloads access to more potential resource capacity than physically exists under the assumption that not all workloads peak simultaneously.

CPU is commonly overcommitted.

Memory overcommit requires greater caution because:

```text
CPU shortage
→ slower

memory shortage
→ potentially killed.
```

# 198. Never Fix Pending by Randomly Lowering Requests


# 234. Scheduler vs Runtime

This is one of the most important exam and production concepts.

Scheduler:

```text
uses requests
to decide placement.
```

Runtime/kernel:

```text
enforces limits
during execution.
```

Simplified:

```text
REQUEST
→ placement

LIMIT
→ runtime enforcement
```

# 235. CPU vs Memory Enforcement

Memorize:

