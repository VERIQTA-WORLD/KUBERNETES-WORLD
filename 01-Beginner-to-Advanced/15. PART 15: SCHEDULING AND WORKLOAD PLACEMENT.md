# 2. Why Scheduling Matters

Imagine a Kubernetes cluster containing:

```text
10 worker nodes
```

A new Pod is created.

Where should it run?

Perhaps:

```text
Node 1
```

or:

```text
Node 7
```

or:

```text
Node 10
```

The answer is not random.

Kubernetes evaluates the Pod's requirements against the cluster.

---

# 3. Scheduling Is Placement

Scheduling means:

```text
matching an unscheduled Pod
to a suitable Node.
```

The component responsible for normal Kubernetes scheduling is:

```text
kube-scheduler
```

---

# 4. Scheduler Review

From Part 2:

```text
Developer
↓
kubectl
↓
API Server
↓
Pod object stored
↓
Scheduler observes unscheduled Pod
↓
Scheduler selects Node
↓
Binding recorded
↓
kubelet on selected Node observes Pod
↓
Container Runtime
↓
Containers start
```

The scheduler does not normally start containers.

Its primary responsibility is:

```text
placement.
```

---

# 5. What Is an Unscheduled Pod?

A newly created Pod normally does not initially have a node assigned.

Conceptually:

```text
Pod
↓
spec.nodeName = not yet assigned
```

The scheduler watches for Pods that need placement.

---

# 6. Scheduling Architecture

The simplified scheduling architecture is:

```text
Pending Pod
↓
Scheduler
↓
Filtering
↓
Constraints
↓
Scoring
↓
Selected Node
↓
Binding
```

This is the mental model for this entire part.

---

# 7. Filtering

Filtering asks:

```text
Can this Pod run on this Node?
```

Nodes that fail mandatory requirements are eliminated.

Examples:

```text
insufficient CPU

insufficient memory

nodeSelector mismatch

required node affinity mismatch

untolerated NoSchedule taint

required Pod anti-affinity violation

topology spread requirement violation
```

---

# 8. Feasible Nodes

Nodes that survive filtering are:

```text
feasible nodes.
```

Example:

```text
Cluster:
Node A
Node B
Node C
Node D
Node E
```

After filtering:

```text
Node A → rejected

Node B → feasible

Node C → rejected

Node D → feasible

Node E → feasible
```

The scheduler now has:

```text
3 feasible nodes.
```

---

# 9. Scoring

If multiple feasible nodes remain, Kubernetes scores them.

Conceptually:

```text
Node B → score 63

Node D → score 81

Node E → score 72
```

The scheduler can then select the highest-scoring suitable node.

The exact scheduler scoring process uses multiple scheduling plugins and should not be reduced to one simple formula.

---

# 10. Filtering vs Scoring

This distinction is essential.

```text
Filtering
=
Can the Pod run here?
```

```text
Scoring
=
Among nodes where it can run,
which placement is preferred?
```

This helps explain:

```text
required
```

versus:

```text
preferred
```

placement rules.

---

# 11. Binding

After selecting a node, the scheduler binds the Pod to that node.

Conceptually:

```text
Pod
↓
Selected Node
↓
Binding
↓
API Server records assignment
```

Afterward:

```text
spec.nodeName
```

reflects the selected node.

# 14. Scheduling Is More Than Resources

Part 14 covered:


But Kubernetes can also evaluate:

```text

affinity

anti-affinity

taints

topology

policy constraints
```

A node can therefore have enough CPU and memory and still be unsuitable.




# 25. `nodeSelector`

`nodeSelector` is the simplest recommended node-selection constraint.

Example:

```yaml
spec:
  nodeSelector:
    disk: ssd
```

This means:

```text
schedule this Pod only onto nodes
with:

disk=ssd
```

---

# 26. `nodeSelector` Is Mandatory

If the Pod says:

```yaml
nodeSelector:
  disk: ssd
```

and no node has:

```text
disk=ssd
```

the scheduler cannot ignore the requirement.

The Pod remains unscheduled.

---

# 27. Multiple `nodeSelector` Labels

Example:

```yaml
nodeSelector:
  disk: ssd
  environment: production
```

The node must satisfy:

```text
disk=ssd

AND

environment=production
```

# 35. `nodeSelector` Limitation

`nodeSelector` is useful but simple.

Suppose you want:

```text
disk is either ssd OR nvme
```

or:

```text
prefer zone A,
but zone B is acceptable
```

or:

```text
avoid nodes with a certain label
```

For richer expressions use:

```text
node affinity.
```

---

# 36. Node Affinity

Node affinity allows Pods to express more flexible rules about node labels.

Two important forms are:

```text
requiredDuringSchedulingIgnoredDuringExecution
```

and:

```text
preferredDuringSchedulingIgnoredDuringExecution
```

---

# 37. Required Node Affinity

```text
requiredDuringSchedulingIgnoredDuringExecution
```

means:

```text
the node MUST satisfy this rule
when the Pod is scheduled.
```

If no node satisfies it:

```text
Pod remains Pending.
```

---

# 38. Preferred Node Affinity

```text
preferredDuringSchedulingIgnoredDuringExecution
```

means:

```text
the scheduler SHOULD prefer matching nodes.
```

But if those preferred nodes are unavailable:

```text
the Pod can still be scheduled elsewhere
if another node satisfies all mandatory requirements.
```

---

# 39. Hard vs Soft Placement

Think:

```text
Required
=
hard requirement
```

```text
Preferred
=
soft preference
```

This distinction appears repeatedly throughout Kubernetes scheduling.

---

# 40. `IgnoredDuringExecution`

Both common node affinity forms include:

```text
IgnoredDuringExecution
```

This means the rule is evaluated for scheduling, but a later node-label change does not automatically cause Kubernetes to evict an already running Pod solely because the node no longer satisfies that affinity rule.

---

# 41. Important Example

Pod requires:

```text
disk=ssd
```

Pod schedules to:

```text
worker-1
```

Later administrator removes:

```text
disk=ssd
```

from worker-1.

The existing Pod is not automatically evicted merely because the required node affinity is no longer satisfied.

Future scheduling decisions evaluate the current labels.

---

# 42. Node Affinity Structure

Example:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: disk
              operator: In
              values:
                - ssd
                - nvme
```

Interpretation:

```text
Node must have:

disk=ssd

OR

disk=nvme
```

---

# 43. Node Affinity Operators

Common operators include:

```text
In

NotIn

Exists

DoesNotExist

Gt

Lt
```

These make affinity more expressive than basic `nodeSelector`.

---

# 44. `In`

Example:

```yaml
- key: disk
  operator: In
  values:
    - ssd
    - nvme
```

Meaning:

```text
disk must equal one of:

ssd
nvme
```

---

# 45. `NotIn`

Example:

```yaml
- key: environment
  operator: NotIn
  values:
    - development
```

Meaning:

```text
environment must not have
the value development
```

within the selector semantics.

---

# 46. `Exists`

Example:

```yaml
- key: accelerator
  operator: Exists
```

Meaning:

```text
the node must have
the accelerator label key.
```

No specific value is required.

---

# 47. `DoesNotExist`

Example:

```yaml
- key: legacy
  operator: DoesNotExist
```

Meaning:

```text
node must not have
the legacy label key.
```

# 48. LAB 5: Required Node Affinity

Label nodes:

```bash
kubectl label node <NODE-1> storage-tier=ssd
```

```bash
kubectl label node <NODE-2> storage-tier=nvme
```

```yaml

  namespace: scheduling-lab

        nodeSelectorTerms:
          - matchExpressions:
              - key: storage-tier
                operator: In
                values:
                  - ssd
                  - nvme

  containers:
    - name: web
      image: nginx:1.27

      resources:
        requests:
          cpu: "50m"
          memory: "32Mi"
```

# 50. Multiple Node Selector Terms

An important logical rule:

```text
multiple nodeSelectorTerms
=
OR
```

Expressions within one term are generally:

```text
AND
```

Conceptually:

```text
Term 1:
A AND B

OR

Term 2:
C AND D
```

Understanding this prevents subtle scheduling mistakes.

---

# 51. Combining `nodeSelector` and Node Affinity

If a Pod defines both:

```text
nodeSelector
```

and:

```text
nodeAffinity
```

the node must satisfy both sets of mandatory requirements.

Think:

```text
nodeSelector
AND
required node affinity
```

---

# 52. Preferred Node Affinity Structure

Example:

```yaml
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
            - key: storage-tier
              operator: In
              values:
                - nvme
```

This tells the scheduler:

```text
prefer nodes with:

storage-tier=nvme
```

---

# 53. Preferred Affinity Weight

A preferred rule has:

```text
weight
```

between:

```text
1 and 100
```

Higher weight gives that preference more influence within node-affinity scoring.

But it does not override hard constraints.

---

# 54. Preference Cannot Make an Invalid Node Valid

Suppose:

```text
Node A
matches preferred affinity
BUT
does not have enough memory.
```

Node A is not magically allowed.

Hard scheduling requirements still apply.

Preferred rules influence selection among nodes that remain eligible.

---

# 55. LAB 6: Preferred Node Affinity

Label one node:

```bash
kubectl label node <NODE> performance=high
```

```yaml
apiVersion: v1

metadata:
  name: preferred-node

            matchExpressions:
              - key: performance

        requests:
          cpu: "50m"
          memory: "32Mi"
```

Remember:

```text
preferred
≠
guaranteed.
```

---

# 56. Node Affinity vs Pod Affinity

Do not confuse them.

Node affinity asks:

```text
Which NODE characteristics
should this Pod run on?
```

Pod affinity asks:

```text
Which OTHER PODS
should this Pod run near?
```

---

# 57. Pod Affinity

Pod affinity places Pods relative to other Pods.

Example requirement:

```text
Run my API Pods
in the same zone
as cache Pods.
```

The scheduler evaluates labels on existing Pods and the topology of their nodes.

---

# 58. Pod Anti-Affinity

Pod anti-affinity does the opposite.

Example:

```text
Do not place two replicas
of this application
on the same node.
```

This is commonly used for availability.

---

# 59. Why Anti-Affinity Matters

Suppose:

```text
web replica 1
web replica 2
web replica 3
```

all run on:

```text
worker-1.
```

If worker-1 fails:

```text
all three replicas disappear simultaneously.
```

Replica count alone does not guarantee failure isolation.

Placement matters.

---

# 60. Failure Domain

A failure domain is a group of infrastructure that can fail together.

Examples:

```text
node

rack

availability zone

region
```

If all replicas occupy one failure domain, one failure can affect all replicas.

---

# 61. Topology

Kubernetes commonly represents failure domains through node labels.

Examples:

```text
kubernetes.io/hostname

topology.kubernetes.io/zone

topology.kubernetes.io/region
```

A topology key tells scheduling logic:

```text
which infrastructure boundary matters?
```

---

# 62. Hostname as Topology

Using:

```text
kubernetes.io/hostname
```

means:

```text
treat each distinct hostname value
as a topology domain.
```

This is commonly used to spread Pods across nodes.

---

# 63. Zone as Topology

Using:

```text
topology.kubernetes.io/zone
```

means:

```text
treat each zone
as a topology domain.
```

This is useful in multi-zone clusters.

---

# 64. Region as Topology

Using:

```text
topology.kubernetes.io/region
```

groups nodes by region when those labels are provided by the environment.

Do not manually assume every local or self-managed cluster automatically contains meaningful region/zone labels.

Verify first.

---

---

# 67. Pod Anti-Affinity Example

Suppose Deployment Pods have:

```yaml
labels:
  app: web
```

You can tell Kubernetes:

```text
avoid putting app=web Pods
in the same node topology domain.
```

---

# 68. Required Pod Anti-Affinity

Example:

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: web

        topologyKey: kubernetes.io/hostname
```

Meaning:

```text
do not schedule this Pod
into a hostname topology domain
already containing a matching app=web Pod.
```

---

# 69. Required Anti-Affinity Can Block Scheduling

Suppose:

```text
2 eligible nodes
```

and:

```text
3 replicas
```

with hard anti-affinity:

```text
maximum one matching Pod per hostname.
```

Then:

```text
Replica 1 → Node A

Replica 2 → Node B

Replica 3 → Pending
```

The scheduler obeys the hard rule.

---

# 70. High Availability vs Schedulability

This illustrates a production tradeoff:

```text
strict anti-affinity
↓
strong failure separation
```

but:

```text
insufficient topology domains
↓
unschedulable replicas
```

Placement policies must reflect actual infrastructure capacity.

---

# 71. Preferred Pod Anti-Affinity

You can instead use:

```text
preferredDuringSchedulingIgnoredDuringExecution
```

Meaning:

```text
try to separate replicas,
but allow co-location if necessary.
```

This improves schedulability but weakens strict separation.

---

# 72. LAB 8: Anti-Affinity Deployment

Create:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: anti-affinity-web
  namespace: scheduling-lab

spec:
  replicas: 2

  selector:
    matchLabels:
      app: anti-affinity-web

  template:
    metadata:
      labels:
        app: anti-affinity-web

    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: anti-affinity-web

              topologyKey: kubernetes.io/hostname

      containers:
        - name: web
          image: nginx:1.27

          resources:
            requests:
              cpu: "50m"
              memory: "32Mi"
```

# 77. Pod Affinity Manifest

Conceptually:

```yaml
affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: cache

        topologyKey: topology.kubernetes.io/zone
```

Meaning:

```text
place this Pod in a zone
where matching app=cache Pods exist.
```

---

# 78. Why Co-Locate Workloads?

Possible reasons:

```text
reduce network latency

reduce cross-zone traffic

improve locality

co-locate tightly coupled workloads
```

But excessive co-location can increase:

```text
shared failure risk.
```

Performance and resilience sometimes pull placement in opposite directions.

---

# 79. Pod Affinity Performance Consideration

Inter-Pod affinity and anti-affinity require the scheduler to reason about other Pods and topology.

In large clusters, complex affinity rules can increase scheduling work.

Do not use elaborate placement rules merely because Kubernetes supports them.

Use them when there is a real requirement.

---

# 80. Namespace Behavior in Pod Affinity

Pod affinity and anti-affinity selectors can also have namespace-scoping behavior.

This matters because:

```text
app=web
```

might exist in multiple namespaces.

Production rules should deliberately define the intended scope instead of assuming label uniqueness across the entire cluster.

---

# 81. Taints

Node labels plus affinity usually describe:

```text
where a Pod wants to run.
```

Taints solve a different problem.

A taint tells Kubernetes:

```text
repel Pods that do not tolerate this condition.
```

---

# 82. Taint Mental Model

```text
Node
↓
Taint
↓
"Do not place ordinary Pods here."
```

A Pod can declare:

```text
Toleration
↓
"I am allowed to tolerate that taint."
```

---

# 83. Toleration Does Not Mean Attraction

This distinction is critical.

A toleration means:

```text
this taint does not prohibit me.
```

It does NOT mean:

```text
schedule me onto that node.
```

A Pod with a toleration can still run elsewhere unless other placement rules attract or require it.

---

# 84. Taint Syntax

Example:

```bash
kubectl taint nodes <NODE> dedicated=database:NoSchedule
```

Components:

```text
key:
dedicated

value:
database

effect:
NoSchedule
```

---

# 85. Taint Effects

Three important effects are:

```text
NoSchedule

PreferNoSchedule

NoExecute
```

---

# 86. `NoSchedule`

```text
NoSchedule
```

means:

```text
do not schedule new Pods
onto this node
unless they tolerate the taint.
```

Existing Pods are not automatically evicted solely because you add this taint.

---

# 87. `PreferNoSchedule`

```text
PreferNoSchedule
```

is a softer rule.

Meaning:

```text
try not to schedule non-tolerating Pods here,
but scheduling there is still possible.
```

---

# 88. `NoExecute`

`NoExecute` affects both:

```text
new placement
```

and:

```text
Pods already running.
```

Pods without a matching toleration can be evicted.

Pods with matching tolerations can remain according to their toleration configuration.

---

# 89. `tolerationSeconds`

For certain `NoExecute` tolerations, a Pod can specify:

```yaml
tolerationSeconds: 300
```

Conceptually:

```text
tolerate the condition temporarily
for 300 seconds.
```

After that period, the Pod can be evicted if the taint remains applicable.

---

# 98. Dedicated Nodes

A common production pattern is:

```text
Label
+
Taint
+
Toleration
+
Affinity / Selector
```

Why combine them?

Because:

```text
Taint
↓
keeps unrelated workloads away
```

while:

```text
Affinity / Selector
↓
directs intended workloads toward the dedicated nodes.
```

---

# 99. Dedicated Database Nodes

Example:

```text
Node:
dedicated=database label

Node:
dedicated=database:NoSchedule taint
```

Database workload:

```text
required node affinity:
dedicated=database

AND

toleration:
dedicated=database:NoSchedule
```

This creates stronger placement intent.

---

# 100. Toleration Alone Is Insufficient for Dedication

Suppose database Pod only has:

```text
toleration
```

It is allowed onto the database node.

But it can also potentially schedule onto:

```text
general nodes.
```

If you require dedicated placement, combine toleration with:

```text
nodeSelector
```

or:

```text
node affinity.
```

---

# 101. Remove Taint

Syntax:

```bash
kubectl taint nodes <NODE> dedicated=database:NoSchedule-
```

The trailing:

```text
-
```

removes that specific taint.

Verify:

```bash
kubectl describe node <NODE>
```

---

# 102. Multiple Taints

A node can have multiple taints.

Example:

```text
dedicated=database:NoSchedule

hardware=gpu:NoSchedule
```

The scheduler considers all applicable taints.

A Pod must tolerate every relevant taint that would otherwise block it.

---

# 103. Automatic Node Taints

Kubernetes can also use taints to represent node conditions.

Examples can include conditions associated with:

```text
memory pressure

disk pressure

unreachable nodes

not-ready nodes
```

Do not assume every taint was manually created by an administrator.

---

# 104. Taints Are Not Security Boundaries

A taint is:

```text
scheduling control.
```

It is not:

```text
authentication

authorization

network isolation

container sandboxing
```

A user with permission to create Pods containing tolerations might bypass a placement convention.

Use RBAC and other security mechanisms separately.

---

# 105. Node Labels and Security

Node labels can influence sensitive placement.

Example:

```text
compliance=pci
```

If compromised nodes are allowed to self-apply sensitive labels, placement guarantees become weak.

For security-sensitive node isolation, use label namespaces and cluster controls designed to prevent kubelets from modifying trusted isolation labels.

---

# 106. NodeRestriction Concept

Kubernetes provides mechanisms such as:

```text
Node authorizer
```

and:

```text
NodeRestriction admission plugin
```

to restrict what kubelets can modify.

For sensitive placement, label trust matters as much as label syntax.

---

# 107. Topology Spread Constraints

Anti-affinity can say:

```text
do not co-locate matching Pods.
```

But sometimes you want more precise balancing.

Example:

```text
Spread 6 replicas approximately evenly
across 3 zones.
```

Kubernetes provides:

```text
topologySpreadConstraints.
```

---

# 108. Why Topology Spread Exists

Suppose:

```text
6 replicas

3 zones
```

Desired:

```text
Zone A → 2

Zone B → 2

Zone C → 2
```

Without explicit placement controls, scheduling outcomes may not provide the failure-domain balance you need.

---

# 109. Topology Spread Structure

Example:

```yaml
topologySpreadConstraints:
  - maxSkew: 1

    topologyKey: topology.kubernetes.io/zone

    whenUnsatisfiable: DoNotSchedule

    labelSelector:
      matchLabels:
        app: web
```

---

# 110. `topologyKey`

This defines the topology domain.

Example:

```yaml
topologyKey: topology.kubernetes.io/zone
```

means:

```text
balance matching Pods
across zone label values.
```

---

# 111. Node-Level Spread

Use:

```yaml
topologyKey: kubernetes.io/hostname
```

to spread across nodes.

Conceptually:

```text
Node A

Node B

Node C
```

are separate topology domains.

---

# 112. Zone-Level Spread

Use:

```yaml
topologyKey: topology.kubernetes.io/zone
```

to spread across zones.

Conceptually:

```text
Zone A

Zone B

Zone C
```

are topology domains.

---

# 113. `labelSelector`

The spread constraint needs to know:

```text
which Pods should be counted?
```

Example:

```yaml
labelSelector:
  matchLabels:
    app: web
```

The scheduler considers matching Pods when evaluating distribution.

---

# 114. `maxSkew`

`maxSkew` controls how uneven the distribution may become according to topology-spread semantics.

Example:

```yaml
maxSkew: 1
```

aims to keep eligible-domain counts within the allowed skew rules.

Do not interpret it simply as:

```text
exactly one Pod per node.
```

It describes allowed distribution imbalance.

---

# 115. `whenUnsatisfiable`

Important values include:

```text
DoNotSchedule
```

and:

```text
ScheduleAnyway
```

---

# 116. `DoNotSchedule`

Meaning:

```text
if placing the Pod would violate
the hard topology-spread constraint,
do not schedule it there.
```

This can cause:

```text
Pending Pods.
```

---

# 117. `ScheduleAnyway`

Meaning:

```text
prefer placements that reduce skew,
but allow scheduling even if ideal distribution cannot be achieved.
```

This behaves as a softer spread policy.

---

# 118. Hard vs Soft Spread

Think:

```text
DoNotSchedule
=
hard spread requirement
```

```text
ScheduleAnyway
=
soft spread preference
```

# 119. LAB 11: Spread Replicas Across Nodes

Create:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: spread-web
  namespace: scheduling-lab

spec:
  replicas: 3

  selector:
    matchLabels:
      app: spread-web

```

# 124. Multiple Spread Constraints

A workload can have multiple topology spread constraints.

For example:

```text
spread across zones

AND

spread across hosts
```

The scheduler must evaluate the combined constraints.

This can produce strong resilience, but overly strict combinations can make Pods impossible to schedule.

---

# 125. Example Production Strategy

For a three-zone application:

```text
Spread across:
topology.kubernetes.io/zone
```

and:

```text
Spread across:
kubernetes.io/hostname
```

This can reduce the chance that:

```text
one node failure
```

or:

```text
one zone failure
```

affects too many replicas.

---

# 126. Topology Spread vs Anti-Affinity

Pod anti-affinity asks:

```text
Should these Pods avoid sharing a topology domain?
```

Topology spread asks:

```text
How evenly should these Pods be distributed
across topology domains?
```

They overlap in purpose but are not identical mechanisms.

---

# 127. Anti-Affinity Example

Required anti-affinity across hostname:

```text
matching Pod already on Node A
↓
another matching Pod cannot use Node A.
```

This can effectively limit matching Pods to one per topology domain.

---

# 128. Spread Example

Topology spread:

```text
Node A → 2 Pods

Node B → 2 Pods

Node C → 1 Pod
```

may be perfectly acceptable depending on:

```text
maxSkew.
```

Spread constraints provide more nuanced balancing.

High availability is not simply:

```text
replicas > 1.
```

Ask:

```text
Where are those replicas?
```

Three replicas on one node:

```text
one node failure
↓
three replicas lost.
```

To improve resilience against zone failure:

Typical topology key:


when correctly populated.

# 132. Region Failure Domain

```text
multiple clusters
```

# 135. Scheduling Failure

```text
Pending
```

as the final root cause.

# 169. Required vs Preferred

Across scheduling:

```text

↓
must satisfy
↓
```

```text

↓
```

# 170. Production Decision: Hard or Soft?

Use a hard rule when violating it would be unacceptable.

Examples might include:

```text
required hardware

required compliance node group

storage topology requirement
```

Use a soft preference when:

```text
ideal placement is desirable,
but running the application is more important.
```

# 171. Overusing Hard Constraints

Suppose application requires:

```text

AND
ssd
AND
special=true
AND
dedicated=payments
AND
hard anti-affinity
```

Only one node satisfies most conditions.

Result:

```text
fragile scheduling

Pending Pods

difficult rollouts

poor autoscaling
```

Hard constraints should represent real requirements.

# 172. Scheduling and Rolling Updates
