# PART 11: CONFIGMAPS, SECRETS, AND APPLICATION CONFIGURATION

## Separating Application Configuration from Container Images

---

# 1. Goal

The goal of this part is to learn how Kubernetes separates application configuration and sensitive information from container images.

By the end of this part, you should understand:

* why configuration should normally be separated from application images
* what ConfigMaps are
* what Secrets are
* when to use a ConfigMap
* when to use a Secret
* how to create configuration from literal values
* how to create configuration from files
* how Pods consume configuration
* environment-variable injection
* configuration volume mounts
* Secret volume mounts
* `data`
* `stringData`
* Base64 encoding
* why Base64 is not encryption
* configuration reload behavior
* immutable ConfigMaps and Secrets
* configuration failure modes
* Secret exposure risks
* RBAC considerations
* etcd encryption at rest
* external secret systems
* cloud secret managers
* secret rotation
* Git security
* production configuration patterns

Most importantly, you should understand this architecture:

```text
Container Image
=
Application + Runtime Dependencies

ConfigMap
=
Non-Confidential Configuration

Secret
=
Confidential Configuration
```

Instead of:

```text
Container Image
=
Application
+
Database Host
+
Environment Name
+
API Endpoint
+
Password
+
API Key
+
Private Credentials
```

---

# 2. The Configuration Problem

Imagine you build an application.

It needs:

```text
DATABASE_HOST

DATABASE_PORT

LOG_LEVEL

ENVIRONMENT

FEATURE_FLAG

API_URL

DATABASE_USERNAME

DATABASE_PASSWORD

API_TOKEN
```

Some values are ordinary configuration.

Others are sensitive.

For example:

```text
LOG_LEVEL=info
```

is normally not secret.

But:

```text
DATABASE_PASSWORD=SuperSecretPassword
```

is confidential.

We need different ways to manage them.

---

# 3. The Bad Approach

Imagine putting everything directly inside your application source code:

```python
DATABASE_HOST = "production-db.example.internal"
DATABASE_USERNAME = "admin"
DATABASE_PASSWORD = "SuperSecretPassword"
```

Then building that into a container image.

Now the image contains:

```text
application
+
environment-specific configuration
+
credentials
```

This creates serious operational and security problems.

---

# 4. Problem: Different Environments

You may have:

```text
development

testing

staging

production
```

Each environment might use a different:

```text
database host

API endpoint

log level

feature configuration

credential
```

If configuration is baked into the image, you may need different images for different environments.

That weakens the idea of promoting the same tested artifact through environments.

---

# 5. Better Model

A better model is:

```text
Same Application Image
        +
Different Configuration
        ↓
Different Environment
```

For example:

```text
myapp:v1.4.2
+
development configuration
```

and:

```text
myapp:v1.4.2
+
production configuration
```

use the same application artifact.

---

# 6. Why This Matters in DevOps

A common delivery pattern is:

```text
Source Code
↓
Build
↓
Container Image
↓
Test
↓
Registry
↓
Deploy same image
↓
Environment-specific configuration
```

You want to avoid:

```text
Build development image

Build staging image

Build production image
```

merely because configuration values changed.

---

# 7. Kubernetes Configuration Objects

Kubernetes provides two important API objects:

```text
ConfigMap

Secret
```

Their high-level purposes are:

```text
ConfigMap
↓
Non-confidential configuration
```

```text
Secret
↓
Confidential information
```

---

# 8. Critical Distinction

Memorize:

```text
ConfigMap
≠
Secret
```

A ConfigMap does not provide secrecy.

Do not place:

```text
passwords

API keys

private keys

access tokens

database credentials
```

inside a ConfigMap simply because it is convenient.

---

# 9. Configuration Architecture

A Pod might receive:

```text
                    ┌── ConfigMap
                    │
Container Image ────┤
                    │
                    └── Secret
```

The application image remains independent of environment-specific configuration.

---

# 10. Example Production Architecture

```text
Container Registry
↓
myapp:v3.7.1
↓
Deployment
↓
Pod
├── ConfigMap
│   ├── APP_ENV=production
│   ├── LOG_LEVEL=info
│   └── API_URL=https://api.example.com

└── Secret
    ├── DB_USERNAME
    ├── DB_PASSWORD
    └── API_TOKEN
```

# 11. ConfigMap

A ConfigMap is a Kubernetes API object used to store non-confidential configuration data.

ConfigMaps commonly contain:

```text
application settings

hostnames

ports

feature flags

log levels

configuration files

non-sensitive URLs

environment names
```

---

# 12. ConfigMap Is Namespaced

A ConfigMap belongs to a namespace.

Example:

```text
Namespace:
production

ConfigMap:
application-config
```

A Pod normally references a ConfigMap from its own namespace.

---

# 13. ConfigMap Object Structure

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: application-config
  namespace: config-lab
data:
  APP_ENV: "production"
  LOG_LEVEL: "info"
  API_URL: "https://api.example.test"
```

Notice something important.

Unlike many workload objects, ConfigMap does not normally have:

```yaml
spec:
```

Its configuration is primarily stored under:

```yaml
data:
```

and optionally:

```yaml
binaryData:
```

```text

```

```yaml

  name: application-config
```

```text

```

# 15. ConfigMap Data

This:

```yaml
data:
  APP_ENV: "production"
  LOG_LEVEL: "info"
```

stores two key-value pairs:

```text
APP_ENV
↓
production

LOG_LEVEL
↓
info
```

Applications can consume those values in several ways.

---

# 16. ConfigMap Size

ConfigMaps are intended for configuration, not large datasets.

A ConfigMap is limited to approximately:

```text
1 MiB
```

of data.

Do not use ConfigMaps as:

```text
databases

artifact stores

large document repositories

large binary stores
```

Use an appropriate storage system instead.

---

# 17. Ways Pods Can Consume ConfigMaps

Common methods include:

```text
environment variables

individual environment-variable references

environment-variable collections

volume-mounted files

container command/argument references
```

Applications can also access configuration through the Kubernetes API if deliberately designed to do so.


# 29. Environment Variables

Applications frequently read configuration from environment variables.

For example:

```text
APP_ENV=production

LOG_LEVEL=info
```

Inside Linux:

```bash
printenv APP_ENV
```

might return:

```text
production
```

Kubernetes can populate container environment variables from ConfigMaps.

---

# 30. Individual ConfigMap Environment Variable

Example Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: env-demo
  namespace: config-lab
spec:
  containers:
    - name: app
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          echo "APP_ENV=$APP_ENV"
          echo "LOG_LEVEL=$LOG_LEVEL"
          sleep 3600
      env:
        - name: APP_ENV
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: APP_ENV

        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: LOG_LEVEL
```

---

```yaml
env:

```

```text

```

```yaml

```

means:

```text
Do not hard-code the value here.
Retrieve it from another source.
```

# 35. Importing Multiple ConfigMap Values

Instead of referencing every key individually, you can use:

```yaml
envFrom:
  - configMapRef:
      name: app-config
```

Example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: envfrom-demo
  namespace: config-lab
spec:
  containers:
    - name: app
      image: busybox:1.36
      command:
        - sh
        - -c
        - env && sleep 3600
      envFrom:
        - configMapRef:
            name: app-config
```

---

# 36. `env` vs `envFrom`

`env` gives you precise control:

```text
specific key
↓
specific environment variable
```

`envFrom` imports many keys.

Use `env` when you want:

```text
explicit mapping

renamed variables

clear dependencies

limited exposure
```

Use `envFrom` when importing the complete set is deliberate and appropriate.

# 37. Configuration as Files

Applications may expect files such as:

```text

```

Kubernetes can mount ConfigMap data as files.

```text
ConfigMap
│
├── application.yaml
```

# 39. ConfigMap Volume Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: config-file-demo
  namespace: config-lab
spec:
  containers:
    - name: app
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          cat /etc/app/application.conf
          sleep 3600
      volumeMounts:
        - name: app-config-volume
          mountPath: /etc/app

  volumes:
    - name: app-config-volume
      configMap:
        name: application-files
```


```yaml

  - name: app-config-volume
    configMap:
      name: application-files
```

means:

```text
The volume's source is:

```



# 47. Secrets

A Kubernetes Secret is an API object intended to hold confidential data.

Examples:

```text
passwords

tokens

API keys

SSH keys

TLS material

registry credentials
```

Secrets separate confidential values from Pod definitions and container images.

---

# 48. Secret Does Not Mean Perfectly Secure

This is one of the most important lessons in Kubernetes.

A Secret is:

```text
a Kubernetes API object designed for confidential data.
```

It is not:

```text
a magical encrypted vault under every configuration.
```

Its security depends on:

```text
RBAC

API security

etcd encryption

node security

workload security

secret delivery method

application behavior

logging practices

Git practices

operational controls
```

---

# 49. Secret Object Structure

Example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: database-credentials
  namespace: config-lab
type: Opaque
data:
  username: YXBwdXNlcg==
  password: U3VwZXJTZWNyZXQ=
```

---

# 50. Secret `type`

This:

```yaml
type: Opaque
```

means the Secret contains arbitrary user-defined secret data.

Kubernetes also defines specialized Secret types for particular purposes.

Examples include:

```text
TLS secrets

Docker registry credentials

bootstrap token secrets
```

For ordinary application credentials, `Opaque` is common.

---

# 51. Secret `data`

Values under:

```yaml
data:
```

must be Base64-encoded strings.

Example:

```text
appuser
```

might become:

```text
YXBwdXNlcg==
```

after Base64 encoding.

---

# 52. Base64 Encoding

On Linux/macOS:

```bash
printf '%s' 'appuser' | base64
```

Example result:

```text
YXBwdXNlcg==
```

Decode:

```bash
printf '%s' 'YXBwdXNlcg==' | base64 --decode
```

Result:

```text
appuser
```

Exact decode flags can vary between operating systems.

---

# 53. Why Use `printf` Instead of Casual `echo`

This:

```bash
echo 'password' | base64
```

can include a newline depending on shell behavior.

That newline becomes part of the encoded input.

Using:

```bash
printf '%s' 'password' | base64
```

avoids accidentally encoding a trailing newline.

This matters for credentials.

---

# 54. Critical Security Lesson

Memorize:

```text
Base64
≠
Encryption
```

Again:

```text
Base64
≠
Encryption
```

And again:

```text
Base64
≠
Security
```

Anyone who obtains the Base64 value can trivially decode it.

---

# 55. Why Kubernetes Uses Base64

Base64 provides a text representation for arbitrary byte data.

It helps safely serialize values through formats such as JSON/YAML.

It does not provide confidentiality.

---

# 56. Demonstration

Encode:

```bash
printf '%s' 'SuperSecretPassword' | base64
```

Suppose output is:

```text
U3VwZXJTZWNyZXRQYXNzd29yZA==
```

Decode:

```bash
printf '%s' \
  'U3VwZXJTZWNyZXRQYXNzd29yZA==' \
  | base64 --decode
```

You immediately recover:

```text
SuperSecretPassword
```

Therefore:

```text
Base64 is encoding.
```

Not encryption.

---

# 57. `stringData`

Kubernetes provides another field:

```yaml
stringData:
```

This lets you specify ordinary strings without manually Base64-encoding them.

Example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: database-credentials
  namespace: config-lab
type: Opaque
stringData:
  username: appuser
  password: SuperSecretPassword
```

---

# 58. What Happens to `stringData`

When Kubernetes processes the Secret:

```text
stringData
↓
API processing
↓
merged into data
↓
stored as Secret data representation
```

When you retrieve the Secret:

```bash
kubectl get secret database-credentials \
  -n config-lab \
  -o yaml
```

you normally see:

```yaml
data:
  username: ...
  password: ...
```

not the original `stringData` field.

---

# 59. `data` vs `stringData`

Use:

```yaml
data:
```

when values are already Base64 encoded.

Use:

```yaml
stringData:
```

for convenient plaintext input.

But remember:

```text
Putting plaintext secrets in a YAML file
creates a sensitive file.
```

`stringData` improves convenience.

It does not make Git storage safe.

---

# 60. Important `stringData` Caveat

`stringData` is a write-only convenience field and does not work especially well with server-side apply workflows.

Do not build a production secret-management strategy around repeatedly storing plaintext credentials in ordinary Git-tracked YAML merely because `stringData` is convenient.

# 69. Restrict Secrets to Containers That Need Them

Imagine a Pod with:

```text
application container

metrics sidecar

logging sidecar
```

Only the application needs database credentials.

Do not automatically inject the Secret into all containers.

Prefer:

```text
application
↓
Secret access

metrics sidecar
↓
no Secret

logging sidecar
↓
no Secret
```

---

# 70. Secret as Mounted Files

Secrets can also be mounted as files.

Architecture:

```text
Secret
├── username
└── password
      ↓
Secret Volume
      ↓
Container
├── /etc/secrets/username
└── /etc/secrets/password
```

---

# 71. Secret Volume Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secret-volume-demo
  namespace: config-lab
spec:
  containers:
    - name: app
      image: busybox:1.36
      command:
        - sh
        - -c
        - sleep 3600
      volumeMounts:
        - name: credentials
          mountPath: /etc/secrets
          readOnly: true

  volumes:
    - name: credentials
      secret:
        secretName: database-credentials
```

# 72. LAB 7: Mount a Secret

Apply:

```bash
kubectl apply -f secret-volume-demo.yaml
```

Verify:

```bash
kubectl get pod secret-volume-demo \
  -n config-lab
```

List files:

```bash
kubectl exec \
  -n config-lab \
  secret-volume-demo \
  -- ls -l /etc/secrets
```

Expected keys become files:

```text
username

password
```

---

# 73. Secret Files Are Decoded for the Application

Inside the container, the mounted file contains the actual value.

The application does not normally need to manually Base64-decode the mounted Secret.

Conceptually:

```text
Secret API representation
↓
Kubernetes
↓
Secret volume
↓
actual secret bytes
↓
application
```

---

# 74. Environment Variables vs Mounted Files

Two common delivery patterns are:

```text
Secret
↓
Environment Variable
```

and:

```text
Secret
↓
Mounted File
```

Both can be valid.

But they behave differently.

---

# 75. Environment Variable Advantages

Environment variables are:

```text
simple

widely supported

easy for applications to consume

common in twelve-factor-style applications
```

Example:

```text
DB_PASSWORD
```

---

# 76. Environment Variable Risks

Environment variables can leak through:

```text
debug output

application diagnostics

crash reports

process inspection depending on environment

careless logging

support tooling
```

Applications must never log all environment variables blindly in production.

---

# 77. Mounted File Advantages

Mounted files can provide:

```text
filesystem permissions

clear secret file locations

compatibility with certificate/key-based applications

potential update propagation
```

They can also avoid some environment-variable exposure patterns.

---

# 78. Mounted File Risks

Mounted files can still be exposed through:

```text
compromised container

overly broad filesystem permissions

debugging commands

application logs

privileged containers

node compromise
```

A file is not automatically secure merely because it came from a Secret.

---

# 79. Production Preference Is Context Dependent

Do not memorize:

```text
environment variables are always bad
```

or:

```text
mounted files are always perfect.
```

Instead evaluate:

```text
application support

reload requirements

exposure risk

file permissions

rotation behavior

platform architecture

external secret integration
```

---

# 80. Configuration Update Behavior

This is one of the most important operational differences.

Suppose:

```text
ConfigMap
LOG_LEVEL=info
```

is injected as an environment variable.

You update it to:

```text
LOG_LEVEL=debug
```

Does the existing process automatically receive:

```text
LOG_LEVEL=debug?
```

No.

---

# 81. Environment Variables Are Established at Container Start

A container's environment is established when the container starts.

Changing the referenced ConfigMap or Secret does not rewrite the environment of an already-running process.

Therefore:

```text
ConfigMap changes
↓
existing environment variable
↓
does not automatically change
```

The workload usually needs new Pods to consume the new environment value.

---

# 82. Common Environment-Variable Reload Pattern

```text
Update ConfigMap
↓
Restart / roll out Pods
↓
New containers start
↓
New environment values loaded
```

For a Deployment, a common explicit restart is:

```bash
kubectl rollout restart deployment/<DEPLOYMENT> \
  -n <NAMESPACE>
```

---

# 83. Mounted ConfigMap Updates

ConfigMaps mounted as volumes behave differently.

Kubernetes can eventually project updated ConfigMap content into the mounted volume.

However:

```text
file changed
```

does not necessarily mean:

```text
application reloaded configuration.
```

The application must notice or reload the changed file.

---

# 84. Update Propagation Is Not Instantaneous

Do not expect:

```text
kubectl apply
↓
every mounted file changes instantly
```

Kubelet synchronization and caching behavior can introduce delay.

Design applications and operational procedures accordingly.

---

# 85. Critical `subPath` Caveat

A ConfigMap or Secret mounted using:

```yaml
subPath:
```

does not receive automatic projected updates in the same way as a normal ConfigMap or Secret volume mount.

This surprises many engineers.

If runtime configuration reload matters, understand the exact mount method.

---

# 86. Secret Volume Updates

Mounted Secret volumes can also receive updates eventually when the Secret changes.

Again:

```text
Secret file changed
```

does not automatically guarantee:

```text
application started using new credential.
```

The application may need:

```text
reload

reconnect

restart

credential refresh logic
```

---

# 87. Configuration Reload Patterns

Common patterns include:

```text
Pod restart

Deployment rollout

application watches file

application periodically rereads file

application receives reload signal

sidecar triggers reload

external secret integration refreshes mounted material
```

The correct design depends on the application.

---

# 88. Pattern 1: Restart on Configuration Change

Simple architecture:

```text
Config changes
↓
Deployment restarted
↓
New Pods
↓
New configuration loaded
```

Advantages:

```text
simple

predictable
```

Tradeoff:

```text
requires Pod replacement.
```

---

# 89. Pattern 2: Application Watches Configuration

Architecture:

```text
Mounted ConfigMap
↓
file changes
↓
application detects change
↓
application reloads configuration
```

This requires application support.

Kubernetes cannot force arbitrary applications to reread their configuration.

---

# 90. Pattern 3: Immutable Versioned Configuration

Instead of modifying:

```text
app-config
```

you create:

```text
app-config-v1

app-config-v2

app-config-v3
```

Then update the workload reference:

```text
Deployment
↓
app-config-v3
```

This naturally causes a workload-template change when used in the Pod template and provides clearer history.

---

# 91. Immutable ConfigMaps

Kubernetes allows:

```yaml
immutable: true
```

on ConfigMaps.

Example:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: immutable-config
  namespace: config-lab
immutable: true
data:
  APP_ENV: "production"
```

---

# 92. Why Immutability Helps

Immutable ConfigMaps can:

```text
prevent accidental changes

prevent unwanted runtime configuration mutation

improve control-plane performance in very large clusters
```

because kubelets do not need to maintain watches for immutable objects in the same way.

---

# 93. Important Immutable Behavior

Once a ConfigMap or Secret is marked:

```yaml
immutable: true
```

you cannot later make it mutable again or modify its data.

To change the data:

```text
delete/recreate
```

or preferably use:

```text
a new versioned object
```

depending on your deployment model.

---

# 94. Immutable Secrets

Secrets can also use:

```yaml
immutable: true
```

Example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: application-secret-v1
  namespace: config-lab
type: Opaque
immutable: true
stringData:
  token: test-token
```

Use test values only.

---

# 95. Immutability Is Not Encryption

Do not confuse:

```text
immutable
```

with:

```text
encrypted.
```

Immutable means:

```text
data cannot be changed through normal object updates.
```

It does not mean:

```text
data cannot be read.
```

# 104. Secret Exposure Risks

Secrets can leak through many paths.

Examples:

```text
Git repositories

shell history

terminal output

CI/CD logs

application logs

debug dumps

screenshots

ticketing systems

chat systems

container environment inspection

misconfigured RBAC

etcd backups

node compromise

privileged containers
```

Secret security requires thinking beyond the Secret object itself.

---

# 105. Git Exposure

This is dangerous:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: production-db
stringData:
  username: admin
  password: RealProductionPassword
```

and then:

```bash
git add secret.yaml
git commit
git push
```

The credential is now in Git history.

Deleting the current file does not necessarily remove it from repository history.

---

# 106. Base64 Does Not Make Git Safe

This is still unsafe:

```yaml
data:
  password: U3VwZXJTZWNyZXQ=
```

Anyone with repository access can decode it.

Never think:

```text
"It looks unreadable, so it is protected."
```

It is not.

---

# 107. `.gitignore` Helps but Is Not Secret Management

You might exclude local secret files:

```gitignore
*.secret.yaml
.env
.env.*
secrets/
```

But `.gitignore` only helps prevent accidental addition of matching untracked files.

It does not:

```text
encrypt secrets

remove already committed secrets

protect copied secrets

rotate compromised credentials
```

---

# 108. If a Secret Is Committed

Do not merely:

```text
delete the file
```

and assume the incident is resolved.

Treat the credential as potentially compromised.

Typical response:

```text
identify exposure
↓
revoke/rotate credential
↓
remove inappropriate repository content
↓
investigate history and downstream copies
↓
review access
↓
verify new credential
↓
prevent recurrence
```

Rotation is more important than cosmetic deletion.

---

# 109. RBAC and Secrets

Kubernetes RBAC determines who can perform actions such as:

```text
get Secrets

list Secrets

watch Secrets

create Secrets

update Secrets

delete Secrets
```

Secret permissions should follow:

```text
least privilege.
```

---

# 110. Dangerous Secret Permissions

Be cautious with:

```text
get

list

watch
```

on Secrets.

`list` and `watch` can expose Secret data broadly within the authorized scope.

Do not grant them simply because a workload needs one credential.

---

# 111. Pod Creation Can Also Imply Secret Exposure

This is a subtle but critical security lesson.

Suppose a user cannot directly:

```text
get Secret
```

but can create Pods in a namespace.

They may create a Pod that mounts a Secret from that namespace and then read it through the Pod.

Therefore:

```text
"cannot kubectl get secret"
```

does not automatically mean:

```text
"cannot access secret data."
```

Authorization must be evaluated as a complete capability model.

---

# 112. Secret RBAC Example

A narrowly scoped Role might allow access to one named Secret:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app-secret-reader
  namespace: config-lab
rules:
  - apiGroups:
      - ""
    resources:
      - secrets
    resourceNames:
      - database-credentials
    verbs:
      - get
```

This is an educational example.

Do not automatically grant API access to Secrets when a volume mount can meet the application's needs.

---

# 113. Why Workloads Often Do Not Need Secret API Permissions

If Kubernetes injects a Secret as:

```text
environment variable
```

or:

```text
mounted volume
```

the application itself does not necessarily need permission to call:

```text
GET /api/v1/.../secrets
```

That reduces application API privileges.

---

# 114. Better Security Question

Instead of asking:

```text
"Can I give this application access to Secrets?"
```

ask:

```text
"What is the minimum capability this application needs?"
```

If it only needs:

```text
one password
```

do not automatically grant:

```text
list all Secrets in namespace.
```

---

# 115. Secret Storage in etcd

Kubernetes API objects are persisted in the control plane's backing store.

For Secrets, this commonly means:

```text
Secret
↓
API Server
↓
etcd
```

This creates an important security concern.

---

# 116. Default Storage Warning

Kubernetes Secrets are not automatically equivalent to encrypted vault entries.

By default, Secret data can be stored unencrypted in etcd unless API data encryption at rest is configured.

Therefore production cluster administrators should deliberately configure encryption at rest for sensitive Kubernetes API data.

---

# 117. Encryption at Rest

Conceptually:

```text
Secret
↓
API Server
↓
Encryption Provider
↓
Encrypted Representation
↓
etcd
```

Without appropriate encryption:

```text
Secret
↓
API Server
↓
etcd
```

can leave sensitive values readable to someone who gains appropriate access to the backing data.

---

# 118. Encryption at Rest Protects a Specific Boundary

It helps protect data stored in:

```text
etcd
```

or backups containing that API data.

It does not mean the Secret is encrypted everywhere.

The application still needs usable plaintext eventually.

---

# 119. Secret Lifecycle

Conceptually:

```text
External source / administrator
↓
Kubernetes API
↓
Secret
↓
encrypted storage at rest when configured
↓
kubelet
↓
authorized Pod
↓
mounted file / environment
↓
application
```

Each stage has a security boundary.

---

# 120. Encryption at Rest Is Not Enough

Even with encrypted etcd:

```text
compromised application
```

may read its own Secret.

Likewise:

```text
overprivileged user

privileged container

compromised node

unsafe logs
```

can create exposure.

Security requires defense in depth.

---

# 121. etcd Security

etcd contains highly sensitive cluster state.

Protect:

```text
network access

TLS

authentication

authorization

host access

backup files

encryption keys

administrative access
```

Direct etcd access should be highly restricted.

---

# 122. Backups Matter

Suppose the live cluster encrypts Secret data appropriately but:

```text
etcd backup
```

is copied to insecure storage.

Your security architecture may still fail.

Protect backups using appropriate:

```text
encryption

access control

retention

audit

secure deletion
```

policies.

Instead:

# 130. Workload Identity

A strong production pattern is:

```text

↓

```

```text
↓

```

---

# 131. Secret Rotation

Credentials should not necessarily live forever.

Rotation means replacing:

```text
old credential
```

with:

```text
new credential.
```

Examples:

```text
database password

API token

TLS certificate

signing key

cloud credential
```

---

# 132. Rotation Is a Workflow

A safe rotation may require:

```text
create new credential
↓
make new credential valid
↓
update secret source
↓
update/reload workloads
↓
verify new credential works
↓
revoke old credential
↓
monitor
```

The exact order depends on the external system.

---

# 133. Bad Rotation

Bad pattern:

```text
change database password
↓
application still uses old password
↓
production outage
```

Secret rotation must consider both:

```text
credential issuer
```

and:

```text
credential consumer.
```

---

# 134. Better Rotation

Where supported:

```text
New Credential Created
↓
Both Old and New Temporarily Valid
↓
Application Receives New Credential
↓
Application Reloaded
↓
Verification
↓
Old Credential Revoked
```

This can reduce outage risk.

Not every system supports overlapping credentials, so design according to the target system.

```text
↓

↓
```

```text
↓
```

# 177. Secret Rollback Is Different

Be careful.


```text

```

but:

```text

```

Simply reverting YAML makes the outage worse.

# 218. Knowledge Check

### Is Base64 encryption?

No.

### Does Base64 provide confidentiality?

No.

### Can Base64 be trivially decoded?

Yes.

---

# 219. Knowledge Check

### What is `stringData`?

A convenience input field that lets Secret values be provided as strings rather than manually Base64-encoding them.

### Does `stringData` make plaintext Secret manifests safe for Git?

No.

---

# 220. Knowledge Check

### What happens when a ConfigMap-backed environment variable changes?

An already-running process does not automatically receive the new environment value.

A new container must normally start to consume the updated environment value.

---

# 221. Knowledge Check

### What happens when a normally mounted ConfigMap changes?

Kubernetes can eventually update the projected files.

But the application must support rereading or reloading the configuration.

---

# 222. Knowledge Check

### Does a `subPath` ConfigMap mount receive normal automatic projected updates?

No.

This is an important operational caveat.

---

# 223. Knowledge Check

### What does `immutable: true` do?

It prevents modification of the ConfigMap or Secret data after the object becomes immutable.

### Does immutable mean encrypted?

No.

---

# 224. Knowledge Check

### Are Kubernetes Secrets encrypted in etcd automatically in every cluster?

Do not assume so.

Production administrators should explicitly configure and verify encryption at rest according to their Kubernetes environment.

---

# 225. Knowledge Check

### Why is RBAC important for Secrets?

Because API permissions determine which identities can read, list, watch, create, update, or delete Secret resources.

---

# 226. Knowledge Check

### Why can Pod creation permission be security-sensitive?

Because someone able to create a Pod in a namespace may be able to create a workload that consumes Secrets available in that namespace.

Security analysis must consider indirect capabilities.

---

# 227. Knowledge Check

### Why use an external secret manager?

Potential benefits include:

```text
centralized ownership

rotation

audit

cloud integration

policy

reduced plaintext Git exposure

dynamic credential patterns
```

It does not remove the need for workload security.

---

# 228. Knowledge Check

### What is secret rotation?

Replacing an existing credential with a new credential and safely transitioning consumers to the new value.

### Why can rotation cause outages?

Because the external system and application can temporarily disagree about which credential is valid.

# 242. Production Engineer Mental Model

When someone says:

```text
"The application cannot connect to the database."
```

do not immediately blame Kubernetes networking.

Ask:

```text
Is the Pod running?

What do application logs say?

Does the Secret exist?

Is it in the correct namespace?

Does the expected key exist?

How is the Secret delivered?

Did the Pod start before or after rotation?

Is the application using the new value?

Did the database credential also rotate?

Is the username correct?

Is the password current?

Can the network reach the database?

Does TLS work?

Does the database authorize this identity?

What changed?
```

That is configuration troubleshooting.

# 243. Production Failure Example

Symptom:

```text
Deployment rollout completed.

Pods are Running.

Application returns 500 errors.
```

Investigation:

```text
Pods:
Running

Service:
Healthy

Network:
Healthy

Application logs:
Database authentication failed

Secret:
Updated

Pod environment:
Old password

Database:
Only new password valid
```

Root cause:

```text
Secret was rotated,
but existing containers were using
the old environment variable.
```

Fix:

```text
restart workload safely
↓
new Pods receive new Secret
↓
verify database authentication
↓
verify application
```

This is why understanding configuration delivery behavior matters.

# 244. Another Production Failure Example

Investigation:

