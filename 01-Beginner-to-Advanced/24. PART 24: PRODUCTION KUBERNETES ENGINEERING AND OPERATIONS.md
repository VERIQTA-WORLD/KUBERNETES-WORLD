# PART 24: PRODUCTION KUBERNETES ENGINEERING AND OPERATIONS

## From “It Runs” to “We Can Operate It Reliably”

---

# 1. Goal

The goal of this part is to bridge the gap between:

```text
I know Kubernetes
```

and:

```text
I can operate Kubernetes workloads safely in production.
```

Those are not the same skill.

A tutorial asks:

```text
Can you create a Deployment?
```

Production asks:

```text
Should this Deployment exist?

Who owns it?

Which environment does it belong to?

What happens if a node disappears?

What happens during maintenance?

What happens when traffic doubles?

What happens if the new release is broken?

How is access controlled?

How are secrets protected?

How do we know the application is healthy?

How do we upgrade the cluster?

How do we recover from disaster?

How much capacity remains?

How much does this workload cost?

Who gets paged when it fails?

Where is the runbook?
```

Production Kubernetes engineering is the discipline of answering those questions before they become incidents.

# 4. Production Standardization

Production environments need standards because hundreds or thousands of independent decisions eventually become operational complexity.

Without standards:

```text
Team A calls namespace "prod"

Team B calls it "production"

Team C deploys into default

Team D has no resource requests

Team E uses cluster-admin

Team F stores plaintext credentials

Team G has no probes

Team H has one replica

Team I uses :latest

Team J has no owner metadata
```

Everything may initially work.

Operations eventually becomes chaos.

# 33. Resource Requests

Requests describe the resources Kubernetes should consider when scheduling the workload.

Example:

```yaml
resources:
  requests:
    cpu: 250m
    memory: 256Mi
```

The scheduler uses requests when determining where the Pod can fit.

---

# 34. Resource Limits

Example:

```yaml
resources:
  limits:
    cpu: "1"
    memory: 512Mi
```

Limits constrain runtime resource consumption according to resource semantics.

Remember:

```text
CPU limit
→ may lead to throttling

Memory limit
→ may lead to OOM termination
```

---

# 35. Resource Standard

Do not blindly copy:

```yaml
requests:
  cpu: 100m
  memory: 128Mi
```

into every workload.

Use:

```text
observed usage

load testing

application behavior

capacity goals

reliability requirements
```

to right-size resources.

---

# 36. ResourceQuota

ResourceQuota can restrict aggregate resource consumption in a namespace.

Conceptual example:

```yaml
apiVersion: v1
kind: ResourceQuota

metadata:
  name: production-quota
  namespace: payments-production

spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    pods: "100"
```

---

# 37. Why Quotas Matter

Without quota:

```text
one namespace
↓
creates excessive workloads
↓
consumes shared cluster capacity
```

Quota creates a resource governance boundary.

---

# 38. LimitRange

LimitRange can establish namespace-level constraints/defaults for individual resources.

Conceptually:

```yaml
apiVersion: v1
kind: LimitRange

metadata:
  name: workload-limits

spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      default:
        cpu: 500m
        memory: 512Mi
```

Use defaults carefully.

A default that hides poor resource engineering is not a substitute for proper sizing.

# 40. Scheduling Standards


---

# 41. nodeSelector

Simple requirement:

```yaml
nodeSelector:
  workload-type: application
```

This says:

```text
schedule only onto nodes with this label.
```

Useful for simple placement.

---

# 42. Node Affinity

Node affinity allows richer placement rules.

Conceptually:

```text
required
=
must satisfy

preferred
=
scheduler should prefer
```

Use required rules only when they are truly required.

Over-constraining scheduling can make workloads Pending.

---

# 43. Pod Anti-Affinity

For high availability, replicas may need to avoid the same failure domain.

Concept:

```text
Replica A → Node 1

Replica B → Node 2

Replica C → Node 3
```

instead of:

```text
A
B
C
↓
Node 1
```

---

# 44. Anti-Affinity Is Not Enough

Large clusters may need more flexible distribution than strict anti-affinity provides.

Topology spread constraints can express desired distribution across:

```text
nodes

zones

other topology domains
```

---

# 45. Topology Spread

Example goal:

```text
Zone A → 2 replicas

Zone B → 2 replicas

Zone C → 2 replicas
```

instead of:

```text
Zone A → 6 replicas

Zone B → 0

Zone C → 0
```

This improves resilience to zone failure.

---

# 46. Taints

Taints repel workloads.

Concept:

```text
Node
↓
Taint
↓
Most Pods cannot schedule here.
```

Useful for:

```text
dedicated workloads

special hardware

sensitive workloads

system nodes
```

---

# 47. Tolerations

A toleration allows a Pod to tolerate a matching taint.

It does not necessarily guarantee placement onto that node.

Combine taints/tolerations with affinity when dedicated placement is required.

---

# 48. Dedicated Nodes

```text

↓
Tainted
↓
Only GPU Workloads Tolerate
```


Dedicated capacity can improve isolation and predictability.

# 50. Replicas


```text

```

```text

```

---

# 51. Replica Placement

Three replicas on one node do not provide strong node-failure resilience.

Think:

```text
Replica Count
+
Replica Distribution
=

```

---

# 52. Probes

Production applications commonly need deliberate:

```text
startupProbe

readinessProbe

livenessProbe
```

when their behavior warrants them.

Remember:

```text
startup
→ Has startup completed?

readiness
→ Should this Pod receive traffic?

liveness
→ Should Kubernetes restart this container?
```

---

# 53. Probe Standard

A probe should test the property it claims to test.

Bad liveness endpoint:

```text
checks every downstream dependency
```

because a database outage may cause Kubernetes to restart every application Pod.

That can transform:

```text
dependency outage
```

into:

```text
application restart storm.
```

---

# 54. PodDisruptionBudget

PDBs help limit voluntary disruption.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget

metadata:
  name: payments-api

spec:
  minAvailable: 2

  selector:
    matchLabels:
      app: payments-api
```

This can help protect availability during operations such as node draining.

---

# 55. PDB Limitation

PDBs do not prevent every failure.

They do not stop:

```text
node crash

hardware failure

zone outage

application bug

container crash
```

They primarily govern voluntary disruptions using the eviction mechanism.

---

# 56. Graceful Shutdown

When Kubernetes terminates a Pod, the application should have a shutdown strategy.

Conceptually:

```text
Termination begins
↓
Application stops accepting new work
↓
Existing work drains
↓
SIGTERM handled
↓
Application exits
```

If it does not exit within the configured grace period, termination can become forced.

---

# 57. `terminationGracePeriodSeconds`

Example:

```yaml
spec:
  terminationGracePeriodSeconds: 30
```

Do not choose the number randomly.

Ask:

```text
How long do requests run?

How long do jobs run?

How long does connection draining take?

Can the application safely stop?
```

---

# 58. Rolling Deployment

Production Deployment strategy commonly uses RollingUpdate.

Example:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1
    maxSurge: 1
```

This controls how many old/new Pods can exist during rollout.

---

# 59. Rolling Update Capacity

Rolling updates may temporarily require additional resources.

Example:

```text
10 old Pods
+
2 surge Pods
=
12 Pods temporarily.
```

If the cluster only has capacity for 10, rollout can stall.

Capacity planning must include deployment behavior.

# 63. RBAC

Apply least privilege.

Ask:

```text
Who needs access?

To what resource?

Which namespace?

Which verbs?

For how long?
```

Avoid broad permissions such as:

```text
*
```

---

# 64. Verify Permissions

Use:

```bash
kubectl auth can-i get pods \
  -n production
```

Test another identity where authorized:

```bash
kubectl auth can-i get secrets \
  -n production \
  --as=<IDENTITY>
```

Use impersonation only if your own permissions permit it.

---

# 65. ServiceAccounts

Each workload that needs a Kubernetes identity should use an intentionally selected ServiceAccount.

Example:

```yaml
apiVersion: v1
kind: ServiceAccount

metadata:
  name: payments-api
  namespace: payments-production
```

Deployment:

```yaml
spec:
  template:
    spec:
      serviceAccountName: payments-api
```

Do not give every workload the same powerful ServiceAccount.

---

# 66. Disable Unneeded API Credentials

If a Pod does not need Kubernetes API credentials:

```yaml
automountServiceAccountToken: false
```

can reduce unnecessary credential exposure.

Verify application requirements before applying it.


# 71. NetworkPolicy


# 72. Default-Deny Concept


```text

↓

```

This is stronger than trying to blacklist every unwanted path.

# 76. Admission Control

Admission is the policy checkpoint between authenticated/authorized requests and persisted resources.

Concept:

```text

↓
Authentication
↓
Authorization
↓
Admission
↓
Validation
↓

```

Admission can reject unsafe resources before they run.

---

# 77. Admission Policies


Implement rules carefully.

# 104. Node Maintenance

Nodes require maintenance for:

```text

```

Do not simply shut down a busy node.

---

# 105. Cordon

Run:

```bash
kubectl cordon <NODE>
```

Purpose:

```text
mark node unschedulable for normal scheduler placement.
```

Existing Pods continue running.

Verify:

```bash
kubectl get nodes
```

You should see scheduling disabled for the node.

---

# 106. What Cordon Does Not Do

Cordon does not automatically remove existing Pods.

Think:

```text
CORDON
=
No new normal scheduling
```

not:

```text
CORDON
=
empty node.
```

---

# 107. Drain

Run:

```bash
kubectl drain <NODE> \
  --ignore-daemonsets
```

Purpose:

```text
prepare the node for maintenance by safely evicting applicable workloads.
```

Drain uses eviction behavior and can respect PodDisruptionBudgets.

---

# 108. Drain Flow

```text
Node
↓
Unschedulable
↓
Evict Workloads
↓
Respect Disruption Constraints
↓
Pods Recreated Elsewhere
↓
Node Ready for Maintenance
```

---

# 109. DaemonSets During Drain

DaemonSet Pods require special treatment because the DaemonSet controller expects them on matching nodes.

This is why:

```bash
--ignore-daemonsets
```

is commonly required during drain.

Understand what each DaemonSet does before maintenance.

---

# 110. PDB Blocking Drain

Suppose:

```text
3 replicas

PDB minAvailable = 3
```

A voluntary eviction could violate the budget.

Drain may wait/fail rather than break the disruption requirement.

That is not Kubernetes malfunctioning.

The PDB is protecting the availability policy you requested.

---

# 111. Do Not Immediately Use `--force`

When drain is blocked:

```text

↓

↓

↓

↓

```

Do not mechanically add destructive flags.

# 143. RPO

Recovery Point Objective asks:

```text
How much data can we afford to lose?
```

Example:

```text
RPO = 15 minutes
```

means the recovery strategy should target no more than roughly that amount of data loss under the defined scenario.

---

# 144. RTO

Recovery Time Objective asks:

```text
How long can recovery take?
```

Example:

```text
RTO = 1 hour
```

means the recovery process should be designed to restore required service within that target under defined conditions.

---

# 145. RPO vs RTO

```text

=
acceptable data-loss window.
```

```text
RTO
=
acceptable recovery-time window.
```

They drive different architecture decisions.

# 192. LAB 5: Deploy Production-Style Workload

Create a Deployment containing:

```text
multiple replicas

resource requests

resource limits

readiness probe

liveness probe

securityContext

ServiceAccount

graceful termination

labels
```

Example skeleton:

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: web
  namespace: veriqta-production

  labels:
    app.kubernetes.io/name: web
    app.kubernetes.io/part-of: veriqta-lab

spec:
  replicas: 3

  selector:
    matchLabels:
      app: web

  template:
    metadata:
      labels:
        app: web

    spec:
      serviceAccountName: web
      automountServiceAccountToken: false
      terminationGracePeriodSeconds: 30

      securityContext:
        seccompProfile:
          type: RuntimeDefault

      containers:
        - name: web
          image: nginx:1.27

          ports:
            - containerPort: 80

          resources:
            requests:
              cpu: 100m
              memory: 64Mi

            limits:
              cpu: 500m
              memory: 256Mi

          readinessProbe:
            httpGet:
              path: /
              port: 80

            periodSeconds: 5

          livenessProbe:
            httpGet:
              path: /
              port: 80

            periodSeconds: 10

          securityContext:
            allowPrivilegeEscalation: false
            capabilities:
              drop:
                - ALL
```

For a real production image, use an approved immutable image reference and test compatibility with stronger hardening such as non-root and read-only filesystem settings.

# 223. Production Anti-Pattern: Snowflake Cluster

A snowflake cluster is one nobody can reproduce.

Characteristics:

```text
manual configuration

unknown changes

undocumented add-ons

one engineer understands it

no Infrastructure as Code
```

Avoid this.

---

# 224. Production Anti-Pattern: No Requests

Without meaningful requests:

```text
scheduler lacks useful workload demand information
```

which weakens placement and capacity planning.

---

# 225. Production Anti-Pattern: One Replica

For a critical service:

```text
one replica
```

creates a single-Pod availability dependency.

Use it only where business/reliability requirements justify it.

---

# 226. Production Anti-Pattern: All Replicas Same Node

```text
3 replicas
↓
1 node
```

can still become:

```text
0 replicas
```

after that node fails.

Distribution matters.

---

# 227. Production Anti-Pattern: No PDB

During node maintenance:

```text
drain
↓
too many replicas disrupted
```

because voluntary disruption requirements were never defined.

---

# 228. Production Anti-Pattern: Broken PDB

The opposite also happens.

An impossible PDB can block legitimate maintenance.

Availability controls must be designed with replica count and operational procedures together.

---

# 229. Production Anti-Pattern: Bad Liveness Probe

```text
Dependency fails
↓
liveness fails
↓
containers restart
↓
dependency receives more reconnect traffic
↓
incident worsens
```

Probe design is production engineering.

---

# 230. Production Anti-Pattern: No Graceful Shutdown

During rollout:

```text
Pod terminated
↓
active requests interrupted
↓
users receive errors
```

Applications must participate in their own lifecycle.

---

# 231. Production Anti-Pattern: Cluster-Admin Everywhere

Broad access increases:

```text
accidental deletion risk

credential blast radius

security impact
```

Use least privilege.

---

# 232. Production Anti-Pattern: Secrets in Git

Plaintext production secrets should not be committed to normal repositories.

Use an appropriate secret-management architecture.

---

# 233. Production Anti-Pattern: No Network Boundaries

If every workload can communicate with every other workload:

```text
compromised Pod
↓
large lateral movement opportunity.
```

Use NetworkPolicy where appropriate and supported.

---

# 234. Production Anti-Pattern: Untested Backup

```text
Backup job succeeded
```

does not equal:

```text
recovery works.
```

Test restores.

---

# 235. Production Anti-Pattern: Unsupported Kubernetes

Running unsupported releases increases:

```text
security risk

upgrade difficulty

ecosystem incompatibility

operational debt
```

Maintain a deliberate upgrade cadence.

---

# 236. Production Anti-Pattern: Ignored Deprecations

A warning today can become an outage during tomorrow's upgrade.

Track deprecated APIs before removal.

---

# 237. Production Anti-Pattern: Infinite Logs

Collecting everything forever creates:

```text
high cost

poor searchability

privacy risk

security risk
```

Define retention.

---

# 238. Production Anti-Pattern: No Owner

When incident occurs:

```text
Who owns payments-api?
```

Answer:

```text
I don't know.
```

That is an operational failure before the technical investigation begins.

---

# 239. Production Anti-Pattern: No Runbook

If every incident begins from zero knowledge:

```text
recovery is slower

mistakes increase

knowledge remains tribal.
```

Document repeatable procedures.

---

# 240. Production Anti-Pattern: Maintenance Without Capacity Check

```text
Drain node
↓
Pods Pending
↓
Service capacity drops
```

because remaining nodes cannot accommodate requests.

Always inspect capacity first.
