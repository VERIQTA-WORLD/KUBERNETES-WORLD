# 25. Phase 2: Build the Application

Create:

```text
app/src/app.py
```

Use:

```python
import os
import time
from flask import Flask, jsonify, Response

app = Flask(__name__)

APP_NAME = os.getenv("APP_NAME", "veriqta-api")
APP_VERSION = os.getenv("APP_VERSION", "development")
ENVIRONMENT = os.getenv("ENVIRONMENT", "local")

REQUEST_COUNT = 0
START_TIME = time.time()


@app.get("/")
def index():
    global REQUEST_COUNT
    REQUEST_COUNT += 1

    return jsonify(
        application=APP_NAME,
        version=APP_VERSION,
        environment=ENVIRONMENT,
        status="running"
    )


@app.get("/health/live")
def liveness():
    return jsonify(status="alive"), 200


@app.get("/health/ready")
def readiness():
    return jsonify(status="ready"), 200


@app.get("/version")
def version():
    return jsonify(
        application=APP_NAME,
        version=APP_VERSION
    )


@app.get("/metrics")
def metrics():
    uptime = time.time() - START_TIME

    body = (
        f"veriqta_requests_total {REQUEST_COUNT}\n"
        f"veriqta_uptime_seconds {uptime:.2f}\n"
    )

    return Response(body, mimetype="text/plain")


if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8080)
```

# 44. EKS Access Model

Modern Amazon EKS supports access entries for IAM principals.

Concept:

```text
IAM Principal
↓
EKS Access Entry
↓
EKS Access Policy and/or Kubernetes Group
↓
Kubernetes Authorization
```

Organizations may also have older clusters using legacy `aws-auth` configuration.

Do not randomly edit cluster authentication while troubleshooting.

Determine the cluster's actual access model first.

# 57. Kubernetes Identity vs AWS Identity

Do not confuse:

```text
Kubernetes ServiceAccount
```

with:

```text
AWS IAM Role
```

A ServiceAccount represents workload identity inside Kubernetes.

If the application needs AWS APIs:

```text
Pod
↓
ServiceAccount
↓
EKS Pod Identity association
↓
IAM Role
↓
AWS Permissions
```

can provide temporary AWS credentials.

---

# 58. EKS Pod Identity

Current EKS Pod Identity architecture uses:

```text
Kubernetes ServiceAccount
↓
Pod Identity Association
↓
IAM Role
↓
EKS Pod Identity Agent
↓
Temporary AWS Credentials
```

This avoids putting long-lived AWS access keys inside application containers.

# 59. Least Privilege

If this demonstration API does not require AWS API access:

```text

```

Least privilege means:

```text
No requirement
=
No permission
```

Do not create cloud permissions simply because the application runs in AWS.

# 73. Why Three Replicas?

Three replicas provide room to demonstrate:

```text
self-healing

rolling deployment

HPA

PDB

node distribution

Pod failure

node failure
```

Three replicas alone do not guarantee high availability.

Placement matters.

---

# 74. Why `maxUnavailable: 0`?

During a normal rollout, this strategy asks Kubernetes not to intentionally reduce available replicas below the desired number while replacing Pods, subject to actual health and capacity conditions.

With:

```yaml
maxSurge: 1
```

Kubernetes may temporarily create an additional Pod.

Therefore:

```text
rolling deployment
requires
temporary capacity.
```

---

# 75. Why Startup Probe?

The startup probe protects slow-starting applications from premature liveness failures.

Flow:

```text
Container Starts
↓
Startup Probe
↓
Startup Succeeds
↓
Readiness + Liveness Become Relevant
```

---

# 76. Why Readiness?

Readiness answers:

```text
Should this Pod receive Service traffic?
```

Failure:

```text
Pod still exists
↓
container may still run
↓
Pod becomes NotReady
↓
endpoint readiness changes
↓
normal Service traffic stops reaching it
```

---

# 77. Why Liveness?

Liveness answers:

```text
Is this container unhealthy enough that kubelet should restart it?
```

Do not make liveness depend unnecessarily on every external dependency.

A database outage should not automatically cause a restart storm.
