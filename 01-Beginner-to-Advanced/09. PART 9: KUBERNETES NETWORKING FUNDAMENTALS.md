# PART 9: KUBERNETES NETWORKING FUNDAMENTALS

## From Pod IPs to CNI, Services, DNS, Nodes, and Real Connectivity Troubleshooting

---

# 1. Goal

The goal of this part is to build a real mental model of Kubernetes networking.

You already understand:

```text
Deployment
↓
ReplicaSet
↓
Pods
```

and:

```text
Client
↓
Service DNS
↓
Service
↓
EndpointSlice
↓
Pod
```

Now we go underneath those abstractions.

You need to understand what happens after Kubernetes decides:

```text
Send this connection to Pod 10.244.2.15
```

How does the packet actually reach that Pod?

What if the Pod is on another node?

Who gave the Pod its IP address?

What is CNI?

What is the difference between:

```text
Pod IP
Node IP
Service IP
```

Where does kube-proxy fit?

What do:

```text
iptables
IPVS
nftables
```

have to do with Kubernetes?

How does DNS fit into the path?

What happens when:

```text
DNS works
Service exists
EndpointSlice exists
Pod is Running
```

but the application still cannot connect?

That is the purpose of Part 9.

# 2. The Core Networking Mental Model

Start with this:

```text

↓
Service DNS
↓
Service

↓
Pod IP

Pod Network
```

# 3. The Four Main Kubernetes Networking Problems

A useful way to study Kubernetes networking is to separate it into:

```text
1. Container-to-container communication inside a Pod

2. Pod-to-Pod communication

3. Pod-to-Service communication

4. External-to-Service communication
```

We will also add:

```text
5. Pod-to-external communication

6. Node-to-Pod communication

7. DNS-based service discovery
```

These paths are related, but they are not identical.

A production engineer does not troubleshoot:



---

# 5. The Most Important Troubleshooting Question

Ask:

```text
At which layer does connectivity stop working?
```

For example:

```text
Application
↓
localhost
↓
Pod IP
↓
Service ClusterIP
↓
Service DNS
↓
External Load Balancer
```

If:

```text
localhost works
Pod IP works
Service IP fails
```

then the application itself is probably not your first suspect.

If:

```text
Pod IP fails
```

then debugging external DNS first makes little sense.

This layered thinking will guide the entire chapter.

# 6. Kubernetes Network Model

Kubernetes expects each Pod to receive its own network identity.

Conceptually:

```text
Pod A
10.244.1.10

Pod B
10.244.2.20

Pod C
10.244.3.30
```

Each Pod behaves much more like:

```text
a small network host
```

than like a traditional Docker container that must always be accessed through host port mappings.

---

# 7. Fundamental Pod Networking Principle

In the normal Kubernetes network model, Pods should be able to communicate with other Pods across the cluster without requiring application-visible NAT between Pod addresses.

Conceptually:

```text
Pod A
10.244.1.10
↓
10.244.2.20
↓
Pod B
```

Pod A sees Pod B as:

```text
10.244.2.20
```

and Pod B sees Pod A using Pod A's Pod-network identity.

NetworkPolicy or other intentional restrictions can limit this communication.

---

# 8. Why This Model Matters

Without this model, applications would constantly need to know:

```text
Which node hosts the destination?

Which host port was assigned?

Which NAT mapping exists?

Which proxy should I use?
```

Kubernetes instead aims for:

```text
Pod
↓
Pod IP
↓
Network
↓
Other Pod IP
```

This simplifies the application networking model.

# 9. Every Pod Gets Network Identity

Inspect your Pods:

```bash
kubectl get pods -A -o wide
```

You will see columns such as:

```text
NAME
READY
STATUS
IP
NODE
```

The:

```text
IP
```

column contains the Pod IP.

The:

```text
NODE
```

column tells you where that Pod currently runs.

# 10. Pod IP

A Pod IP is the network address assigned to a Pod.

Example:

```text
10.244.2.17
```

Conceptually:

```text
Pod
↓
Network interface
↓
Pod IP
```

Applications running inside the Pod can send and receive traffic through this networking environment.

---

# 11. Pod IP Is Not Service IP

Do not confuse:

```text
Pod IP:
10.244.2.17
```

with:

```text
Service ClusterIP:
10.96.42.10
```

They solve different problems.

---

# 12. Pod IP Purpose

Pod IP represents:

```text
a particular Pod network identity.
```

Service IP represents:

```text
a stable virtual identity for a logical group of backends.
```

---

# 13. Pod IP Lifecycle

Suppose:

```text
web-abc
10.244.2.17
```

is deleted.

Deployment creates:

```text
web-def
10.244.3.25
```

The application replica was replaced.

The new Pod can have a different IP.

Therefore:

```text
Pod IP
=
important network identity

but

not normally stable application discovery identity
```

---

# 14. Node IP

Every Kubernetes node also has network addresses.

Inspect:

```bash
kubectl get nodes -o wide
```

You may see:

```text
INTERNAL-IP
EXTERNAL-IP
```

depending on your environment.

Example:

```text
Node 1
192.168.10.11

Node 2
192.168.10.12

Node 3
192.168.10.13
```

---

# 15. Node IP Purpose

Node IP represents:

```text
the network identity of the Kubernetes node
```

rather than:

```text
the network identity of a Pod.
```

A node can host many Pods.

---

# 16. Node vs Pod

Example:

```text
Node
192.168.10.12
│
├── Pod A
│   10.244.2.10
│
├── Pod B
│   10.244.2.11
│
└── Pod C
    10.244.2.12
```

One node address.

Multiple Pod addresses.

---

# 17. Service Virtual IP

Now add:

```text
Service
10.96.50.20
```

The architecture becomes:

```text
Node
192.168.10.12

Pods
10.244.2.10
10.244.2.11
10.244.2.12

Service
10.96.50.20
```

These three address types have different responsibilities.

---

# 18. Three Critical IP Types

Memorize this distinction.

```text
Node IP
↓
Identifies a Kubernetes node
```

```text
Pod IP
↓
Identifies a Pod on the Pod network
```

```text
Service ClusterIP
↓
Virtual stable identity for a Service
```

# 19. They May Come From Different Address Ranges

Example only:

```text
Node network:
192.168.10.0/24

Pod network:
10.244.0.0/16

Service network:
10.96.0.0/12
```

Actual values depend on your cluster configuration.

Never assume these exact ranges.

# 20. Non-Overlapping Addressing

Cluster network design normally requires the relevant:

```text
Node ranges

Pod ranges

Service ranges
```

to be planned so that address spaces do not conflict.

Overlapping address ranges can create extremely confusing routing failures.

# 21. Pod Network

The Pod network is the network that provides connectivity between Pods.

You may also hear:

```text
cluster network
```

in this context.

Its responsibilities include:

```text
assigning Pod addresses

connecting Pods

routing Pod traffic

handling cross-node Pod communication
```

depending on implementation.

---

# 22. Kubernetes Does Not Implement Every Networking Detail Itself

This is fundamental.

Kubernetes defines:

```text
networking expectations
```

and:

```text
networking APIs
```

but much of the actual networking is implemented by other components.

Examples include:

```text
CNI-based network implementations

Linux networking

cloud networking

service proxies

DNS components
```

---

# 23. What Is CNI?

CNI stands for:

```text
Container Network Interface
```

CNI is a specification and libraries for configuring networking for Linux containers.

In Kubernetes environments, container runtimes commonly interact with CNI-based networking components to configure Pod networking.

---

# 24. CNI Is Not Kubernetes Networking Itself

Do not say:

```text
CNI = Kubernetes network
```

More accurately:

```text
Kubernetes requires Pod networking behavior
↓
Container runtime / node networking integration
↓
CNI specification commonly provides integration mechanism
↓
Network implementation configures Pod networking
```

---

# 25. CNI Plugin Concept

A CNI-compatible network implementation can participate in operations such as:

```text
creating/configuring network interfaces

assigning Pod IP addresses

connecting Pod namespaces

configuring routes

configuring network rules

cleaning up networking when Pods disappear
```

Exact responsibilities vary by implementation.

---

# 26. CNI Does Not Mean One Product

CNI is not:

```text
one Kubernetes networking product.
```

There are many network implementations.

Examples you may encounter include:

```text
Calico

Cilium

Flannel

Antrea

cloud-provider networking implementations
```

These differ significantly in architecture and capabilities.

Do not assume all clusters behave identically internally.

---

# 27. Networking Implementation Differences

One implementation may use:

```text
Linux routes
```

another may use:

```text
VXLAN
```

another may integrate with:

```text
cloud VPC networking
```

another may use:

```text
eBPF
```

and implementations may combine several techniques.

Kubernetes focuses on the required network behavior rather than forcing one internal design.

---

# 28. Pod Network Namespace

On Linux, Pods use network namespaces.

Conceptually:

```text
Linux Host
│
├── Host Network Namespace
│
├── Pod A Network Namespace
│
├── Pod B Network Namespace
│
└── Pod C Network Namespace
```

A network namespace provides an isolated networking environment.

It can contain its own:

```text
interfaces

IP addresses

routing table

ports

network state
```

---

# 29. Containers in the Same Pod

Containers in the same Pod share the Pod's network namespace.

Example:

```text
Pod
10.244.2.10
│
├── application container
└── sidecar container
```

Both containers share:

```text
Pod IP
```

and can communicate using:

```text
localhost
```

---

# 30. Same-Pod Communication

Suppose:

```text
Container A
listens on 8080
```

Container B in the same Pod can access:

```text
localhost:8080
```

because both containers share the same Pod networking environment.

---

# 31. Port Collision Inside a Pod

Because containers share the Pod network namespace:

```text
Container A
```

and:

```text
Container B
```

cannot both bind the same address and port combination independently.

For example, if both attempt:

```text
0.0.0.0:8080
```

one will normally fail.

They share the same networking namespace.

# 32. Pod-to-Pod Communication

Now consider two Pods:

```text
Pod A
10.244.1.10

Pod B
10.244.1.11
```

If they are on the same node:

```text
Node 1
├── Pod A
└── Pod B
```

traffic can stay within the node's networking environment.

# 33. Same-Node Pod Communication

Conceptually:

```text
Pod A
↓
Pod network interface
↓
Node networking
↓
Pod B network interface
↓
Pod B
```

Exact implementation depends on the network plugin.

You might encounter:

```text

```

```text
Node 1

    10.244.1.10

└── Pod B
    10.244.2.20
```

Pod A needs to reach:


# 35. Cross-Node Mental Model

```text
Pod A
10.244.1.10
↓
Node 1 networking
↓
Cluster / infrastructure network
↓
Node 2 networking
↓
Pod B
10.244.2.20
```

# 36. Two Broad Networking Approaches

Two useful conceptual categories are:

```text
Overlay networking
```

and:

```text
Routed networking
```

These are learning models.

Real implementations can combine techniques.

---

# 37. Overlay Networking

An overlay network creates a logical network on top of another network.

Imagine:

```text
Underlying Node Network
192.168.x.x
```

while Pods use:

```text
10.244.x.x
```

The Pod packet may be encapsulated inside another packet to travel between nodes.

---

# 38. Overlay Mental Model

Original Pod packet:

```text
Source:
10.244.1.10

Destination:
10.244.2.20
```

The network implementation may encapsulate it for transport:

```text
Outer packet
Node 1 → Node 2

Inside:
Pod A → Pod B
```

Node 2 receives it, removes the encapsulation, and forwards the original Pod packet toward Pod B.

---

# 39. Common Overlay Technology Concept

A technology you may encounter is:

```text
VXLAN
```

VXLAN can encapsulate Layer 2-style network traffic over an IP network.

You do not need to master VXLAN internals yet.

Understand:

```text
Pod network traffic
↓
encapsulation
↓
node network
↓
decapsulation
↓
destination Pod
```

---

# 40. Overlay Advantages

Overlay networks can make it easier to create a Pod network independent of the underlying infrastructure routing design.

Potential benefits include:

```text
portability

simplified logical network design

less dependency on physical routing
```

---

# 41. Overlay Costs

Encapsulation can introduce:

```text
packet overhead

MTU considerations

additional processing

more troubleshooting layers
```

For example:

```text
Application packet
↓
Pod network packet
↓
encapsulation
↓
node network packet
```

Packet size becomes important.

---

# 42. MTU Preview

MTU means:

```text
Maximum Transmission Unit
```

It represents the largest packet size that can be transmitted over a network interface without requiring fragmentation or other handling.

Overlay encapsulation adds headers.

If MTU configuration is wrong, you can encounter strange symptoms such as:

```text
small requests work

large requests fail

TLS connections hang

file transfers stall
```

MTU problems are classic production networking failures.

---

# 43. Routed Networking

In a routed design, the infrastructure knows how to route traffic to Pod address ranges.

Conceptually:

```text
10.244.1.0/24
↓
Node 1

10.244.2.0/24
↓
Node 2
```

The network can route Pod packets toward the node responsible for the destination Pod network.

---

# 44. Routed Mental Model

```text
Pod A
10.244.1.10
↓
Node 1
↓
Route says:
10.244.2.0/24 → Node 2
↓
Node 2
↓
Pod B
10.244.2.20
```

No overlay encapsulation is required in a pure routed model.

---

# 45. Overlay vs Routed

Overlay:

```text
Pod traffic
↓
encapsulated across underlying network
```

Routed:

```text
underlying routing understands how to reach Pod networks
```

Neither statement means:

```text
overlay always bad
```

or:

```text
routed always better.
```

Architecture depends on:

```text
infrastructure

scale

cloud environment

performance requirements

operational requirements

network policy requirements
```

---

# 46. Cloud-Native Networking

Some cloud Kubernetes networking implementations assign Pod addresses from networks closely integrated with the cloud VPC or virtual network.

Conceptually:

```text
Cloud VPC
↓
Node
↓
Pod network interfaces / addresses
```

This can make Pod addressing more directly integrated with the infrastructure network.

---

# 47. Pod-to-Pod Traffic Does Not Require a Service

This is important.

Pod A can potentially communicate directly with:

```text
Pod B IP
```

without a Service.

Example:

```text
Pod A
↓
10.244.2.20:8080
↓
Pod B
```

The Service solves:

```text
stable discovery and access
```

not the basic existence of Pod-to-Pod networking.

---

# 48. Why Services Are Still Necessary

Direct Pod communication is technically possible.

But:

```text
Pods are replaceable.
```

Therefore:

```text
Pod A
↓
10.244.2.20
```

is fragile as an application dependency.

Better:

```text
Pod A
↓
payments
↓
Service
↓
current payments Pod
```

---

# 49. Pod-to-Service Communication

Suppose:

```text
Client Pod
10.244.1.15
```

calls:

```text
payments:80
```

DNS resolves:

```text
payments
↓
10.96.20.50
```

where:

```text
10.96.20.50
```

is the Service ClusterIP.

---

# 50. Pod-to-Service Flow

Conceptually:

```text
Client Application
↓
DNS
↓
Service ClusterIP:80
↓
Service Dataplane
↓
EndpointSlice
↓
Backend PodIP:targetPort
↓
Application
```

Example:

```text
10.244.1.15
↓
10.96.20.50:80
↓
10.244.2.31:8080
```

---

# 51. Service IP Is Usually Virtual

A ClusterIP is generally not an ordinary interface address attached to a process.

It is a:

```text
virtual service address.
```

The Service networking implementation recognizes traffic for that Service and directs it toward a backend.

---

# 52. Why `ping` Is a Poor Service Test

A beginner might run:

```bash
ping <CLUSTER-IP>
```

and expect a Service to answer.

But Kubernetes Services are defined around supported transport protocols and ports.

An HTTP Service should be tested with something appropriate such as:

```bash
curl http://service:port
```

not merely ICMP ping.

A failed ping does not prove the Service is broken.

---

# 53. EndpointSlice Role

Suppose:

```text
payments Service
10.96.20.50
```

has:

```text
Pod A
10.244.1.20:8080

Pod B
10.244.2.30:8080

Pod C
10.244.3.40:8080
```

EndpointSlices represent those backend destinations.

---

# 54. Service Dataplane

Something must translate:

```text
Service virtual address
```

into:

```text
actual backend endpoint.
```

Kubernetes provides:

```text
kube-proxy
```

as a standard Service proxy implementation.

But kube-proxy is not mandatory in every cluster architecture.

Some network implementations provide their own Service dataplane.

---

# 55. kube-proxy Concept

kube-proxy watches Kubernetes API information related to:

```text
Services

EndpointSlices
```

and programs node networking so Service traffic can reach backend endpoints.

Conceptually:

```text
Kubernetes API
↓
Service + EndpointSlice
↓
kube-proxy
↓
Node network rules
↓
Service traffic reaches Pod
```

---

# 56. kube-proxy Does Not Usually Proxy Every Packet in User Space

The name:

```text
kube-proxy
```

can be misleading.

You might imagine:

```text
Application
↓
kube-proxy process
↓
Pod
```

for every connection.

That is not the correct general mental model.

kube-proxy commonly programs operating-system networking rules so the kernel dataplane handles packet forwarding.

---

# 57. kube-proxy Is Optional

Modern Kubernetes clusters can use networking implementations that replace kube-proxy's Service proxy role.

Therefore:

```text
No kube-proxy Pods
```

does not automatically mean:

```text
Services cannot work.
```

You must understand your cluster's networking architecture.

---

# 58. Service Proxy Implementation Concepts

Historically and currently, you may encounter implementations involving:

```text
iptables

IPVS

nftables
```

You may also encounter network implementations that use:

```text
eBPF
```

for Service handling.

Do not assume one implementation.

---

# 59. iptables Concept

iptables is a Linux packet filtering and network rule framework.

In a Service implementation, rules can match traffic such as:

```text
Destination:
10.96.20.50:80
```

and redirect it toward a backend such as:

```text
10.244.2.31:8080
```

This is a simplified conceptual model.

---

# 60. iptables Mental Model

```text
Packet enters node
↓
Linux packet-processing rules
↓
Service destination recognized
↓
Backend selected
↓
Destination translated / redirected
↓
Packet sent toward Pod
```

The actual generated rule chains are more complicated.

---

# 61. nftables Concept

nftables is a newer Linux packet filtering framework.

Modern Kubernetes versions can use kube-proxy's:

```text
nftables
```

mode where supported.

Conceptually it serves the same high-level purpose:

```text
Service state
↓
network rules
↓
backend forwarding
```

but implementation details differ from iptables.

---

# 62. IPVS Concept

IPVS stands for:

```text
IP Virtual Server
```

It is Linux kernel load-balancing technology.

Kubernetes kube-proxy deployments have historically supported an IPVS mode.

Conceptually:

```text
Virtual Service IP
↓
IPVS virtual service
↓
backend destinations
```

---

# 63. Important Current Operational Lesson

Do not troubleshoot every cluster with:

```bash
iptables -L
```

and assume that tells you everything.

The cluster might use:

```text
nftables

another service proxy

eBPF

provider-specific networking
```

First identify the architecture.


Then:

```bash
kubectl logs \
  -n kube-system \
```


# 66. Do Not Modify kube-proxy Casually

kube-proxy is cluster infrastructure.

Do not:

```text
delete configuration

change modes

flush packet rules

restart every node component
```

just because a Service is unreachable.

First prove the problem is actually at the Service dataplane layer.

# 68. Pod Egress

Traffic leaving the cluster is often called:

```text
egress.
```

Example:

```text
Application Pod
↓
https://api.example.com
```

The Pod needs:

```text
DNS

possibly NAT

firewall permission

external destination availability
```

---

# 69. Source NAT Concept

Pod IP addresses may not be routable on external networks.

A network implementation may therefore translate:

```text
Source:
Pod IP
```

into:

```text
Source:
Node IP
```

or another egress address.

This is:

```text
Source Network Address Translation
```

or:

```text
SNAT.
```

---

# 70. SNAT Mental Model

Original:

```text
Source:
10.244.2.15

Destination:
203.0.113.50
```

After egress translation:

```text
Source:
192.168.10.12

Destination:
203.0.113.50
```

or another infrastructure-controlled egress address.

Exact behavior depends on the network implementation.

---

# 71. Why Egress Source IP Matters

External systems may allow traffic only from approved source addresses.

Example:

```text
External Database Firewall

Allow:
203.0.113.25
```

If Kubernetes egress suddenly comes from:

```text
203.0.113.26
```

connections may fail.

Production engineers need to understand:

```text
What source IP does the destination actually see?
```

---

# 72. Egress Failure Categories

If a Pod cannot reach the Internet or external service:

```text
DNS failure

No default route

CNI problem

Node routing

NAT problem

NetworkPolicy

Cloud firewall

Security group

Proxy configuration

External firewall

External service outage

TLS problem

Application configuration
```

Do not assume every timeout is a Kubernetes Service problem.

---

# 73. Test External DNS Separately

From a diagnostic Pod:

```bash
nslookup example.com
```

Then test:

```bash
curl -I https://example.com
```

These test different layers.

If DNS fails:

```text
name resolution problem
```

If DNS succeeds but connection fails:

```text
investigate routing/firewall/TLS/application layers.
```

# 75. External Traffic Has More Layers

# 92. DNS in Kubernetes

Kubernetes commonly uses:

```text

```

# 93. DNS Request Mental Model

Application asks:

```text

```

Flow:

```text

↓

↓

↓

↓

↓

```

# 94. DNS Is Itself Reached Through Networking

This creates an important troubleshooting insight.

To use DNS, the Pod needs to reach:

```text
the cluster DNS Service.
```

Therefore a DNS failure can actually originate from:

```text
Service networking

Pod networking

NetworkPolicy

CoreDNS itself

DNS configuration
```

not just the DNS software.

# 104. DNS Troubleshooting Order

Use:

```text

2. Query kubernetes.default

3. Query target Service

4. Check target namespace

5. Check kube-dns Service

7. Check CoreDNS Pods
```

# 105. Do Not Restart CoreDNS First

If:

```text
payments
```

does not resolve, do not immediately restart CoreDNS.

First ask:

```text
Does payments Service exist?

Is it in the correct namespace?

Is the query using the correct name?

Does kubernetes.default resolve?

Can the Pod reach the DNS Service?
```

Use evidence.

# 106. NetworkPolicy Preview

Kubernetes supports:

```text
NetworkPolicy
```

for controlling network communication involving Pods.

Examples:

```text
Allow frontend → API

Deny unrelated namespaces → database

Allow DNS egress

Restrict external egress
```

But enforcement depends on a network implementation that supports NetworkPolicy.

---

# 107. NetworkPolicy API Alone Is Not Enough

You can create a NetworkPolicy object even if the network implementation does not enforce it.

Therefore:

```text
NetworkPolicy exists
```

does not always prove:

```text
traffic is being filtered.
```

Understand your network plugin's capabilities.

---

# 108. Default Connectivity vs Intentional Isolation

The Kubernetes network model expects Pod connectivity unless communication is intentionally segmented.

NetworkPolicy can introduce:

```text
intentional restrictions.
```

Therefore:

```text
Pod A cannot reach Pod B
```

could mean:

```text
network failure
```

or:

```text
correct security policy.
```

Always inspect policy before declaring an outage.

# 154. Controlled DNS Failure Strategy

Create a test Pod whose DNS configuration intentionally points somewhere invalid using supported Pod DNS configuration.

Example concept:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: broken-dns-client
  namespace: network-lab
spec:
  dnsPolicy: None
  dnsConfig:
    nameservers:
      - 192.0.2.53
  containers:
    - name: client
      image: busybox:1.36
      command:
        - sleep
        - "3600"
```

`192.0.2.0/24` is documentation address space and should not be treated as a real DNS server.

# 207. NXDOMAIN

```text

```


# 208. DNS Timeout

A timeout can indicate:

```text

NetworkPolicy blocking DNS

CoreDNS unavailable

network path failure
```

This is different from NXDOMAIN.

# 209. SERVFAIL

SERVFAIL means the DNS server could not successfully answer the query.

Possible causes can include:

```text

upstream DNS problems
```

# 218. Packet Path Thinking

During advanced troubleshooting, mentally follow the packet.

```text

↓

↓

↓

↓
```

# 219. Return Path Matters

Request can reach the destination but response may not return correctly.

This can happen because of:

```text
asymmetric routing

firewall rules

NAT state

policy

misconfigured routes
```

Successful one-way packet delivery does not guarantee a working connection.

---

# 220. TCP Connection Concept

TCP requires a handshake.

Simplified:

```text
Client
SYN
↓

Server
SYN-ACK
↓

Client
ACK
```

If return traffic cannot reach the client:

```text
connection fails.
```

This is why return-path networking matters.

---

# 221. Service NAT Concept

Service implementations can rewrite packet destination information.

Conceptually:

```text
Original:
10.96.20.50:80
```

becomes:

```text
Backend:
10.244.2.31:8080
```

This is commonly associated with:

```text
DNAT
```

or destination translation concepts in applicable implementations.

---

# 222. Do Not Overgeneralize NAT

Not every modern Kubernetes dataplane implements Services using exactly the same NAT mechanisms.

Use:

```text
Service virtual destination
↓
backend forwarding
```

as your implementation-neutral mental model.

Then investigate implementation-specific details when needed.

---

# 223. Connection Tracking Concept

Linux networking can maintain connection state using:

```text
connection tracking
```

often called:

```text
conntrack.
```

This helps networking components handle stateful flows and NAT relationships.

At large scale, conntrack limits and pressure can become operational concerns.

This is advanced production knowledge.


# 283. Knowledge Check

### What is a Pod IP?

The network address assigned to a Pod.

### What is a Node IP?

A network address representing the Kubernetes node.

### What is a Service ClusterIP?

A virtual stable network identity for a Kubernetes Service.

---

# 284. Knowledge Check

### Does every Pod normally share the Node IP?

No.

Normal Pods receive their own Pod-network identity.

### Can multiple containers in one Pod have different Pod IPs?

Normally they share the Pod network namespace and Pod networking identity.

### Can they communicate using localhost?

Yes.

---

# 285. Knowledge Check

### Can Pods communicate directly without Services?

Yes, assuming networking and policy permit it.

### Why use Services then?

Because Pods are dynamic and Services provide stable discovery and access to logical backend sets.

---

# 286. Knowledge Check

### What is CNI?

Container Network Interface, a specification and associated ecosystem commonly used by runtimes to configure container/Pod networking.

### Is CNI one networking product?

No.

### Does Kubernetes require one specific network implementation?

No.

---

# 287. Knowledge Check

### What is an overlay network?

A logical network built over another network, commonly involving encapsulation between nodes.

### What is routed networking?

Networking where routes make Pod address ranges reachable through the underlying network.

### Can implementations combine approaches?

Yes.

---

# 288. Knowledge Check

### What is kube-proxy?

Kubernetes' standard Service proxy implementation that watches Service-related state and programs node networking for Service traffic.

### Must every cluster use kube-proxy?

No.

### Does every packet necessarily travel through the kube-proxy userspace process?

No.

---

# 289. Knowledge Check

### Name Service dataplane implementation concepts you may encounter.

```text
iptables

nftables

IPVS

eBPF-based implementations
```

### Should you assume one before inspecting the cluster?

No.

---

# 290. Knowledge Check

### What is CoreDNS?

The common/default Kubernetes cluster DNS implementation.

### What does Service DNS provide?

Name-based discovery for Services.

### Does DNS replace the Service dataplane?

No.

---

# 291. Knowledge Check

### What is Pod-to-external communication commonly called?

Egress.

### Why might SNAT occur?

Because Pod addresses may not be routable by external networks.

### Why does egress source IP matter?

External systems may filter traffic based on source addresses.

---

# 292. Knowledge Check

### If Pod IP works but ClusterIP fails, what should you investigate?

```text
Service configuration

selector

EndpointSlice

ports

Service dataplane
```

### If ClusterIP works but DNS fails?

```text
DNS.
```

### If same-node works but cross-node fails?

```text
cross-node networking.
```

---

# 293. Knowledge Check

### Does Running mean network healthy?

No.

### Does Ready prove all network paths work?

No.

### Does successful DNS resolution prove application connectivity?

No.

Each layer must be tested appropriately.
