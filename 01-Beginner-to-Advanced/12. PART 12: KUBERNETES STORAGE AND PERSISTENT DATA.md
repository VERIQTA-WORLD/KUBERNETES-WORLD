# PART 12: KUBERNETES STORAGE AND PERSISTENT DATA

## Understanding Persistent Application State

---

# 1. Goal

The goal of this part is to understand how Kubernetes applications store data that must survive container and Pod replacement.

By the end of this part, you should understand:

* the container filesystem
* why container files are ephemeral
* ephemeral storage
* Kubernetes volumes
* `emptyDir`
* persistent storage
* PersistentVolumes
* PersistentVolumeClaims
* StorageClasses
* static provisioning
* dynamic provisioning
* CSI
* access modes
* reclaim policies
* volume modes
* volume binding
* storage topology
* stateful application storage
* cloud storage concepts
* AWS EBS concepts
* other CSI-backed storage systems
* how Pods consume PVCs
* what happens when Pods are deleted
* what happens when PVCs are deleted
* why PVCs become `Pending`
* how to troubleshoot storage failures

Most importantly, you should understand this architecture:

```text
Pod
↓
PersistentVolumeClaim
↓
StorageClass
↓
CSI Driver
↓
Cloud / Storage System
↓
PersistentVolume
↓
Persistent Data
```

And you should understand why:

```text
Pod Lifecycle
≠
Data Lifecycle
```

---

# 2. The Storage Problem

Containers are designed to be replaceable.

A container can:

```text
start
stop
crash
restart
be recreated
be replaced
```

A Pod can:

```text
be deleted
be rescheduled
be recreated
move to another node
be replaced during a rollout
```

That is normal Kubernetes behavior.

But many applications produce data that cannot simply disappear.

Examples:

```text
database files
uploaded documents
application-generated files
message queue data
search indexes
user content
stateful application data
```

This creates a fundamental problem.

---

# 3. Stateless vs Stateful Data

Consider a web frontend.

It receives a request and returns HTML.

It may not need local persistent state.

Conceptually:

```text
Request
↓
Frontend Pod
↓
Response
```

If the Pod disappears:

```text
new Pod
↓
same application
```

No important local data was lost.

This is relatively stateless.

---

# 4. Stateful Application

Now imagine PostgreSQL.

It writes:

```text
customers
orders
payments
transactions
indexes
```

to disk.

If the database container disappears and all its files disappear with it:

```text
Database Pod deleted
↓
Database files disappear
↓
Business data lost
```

That is unacceptable.

The data lifecycle must be separated from the container lifecycle.

---

# 5. Fundamental Storage Principle

Memorize:

```text
Compute can be disposable.

Important data cannot.
```

Kubernetes is designed around replaceable workloads.

Persistent storage provides a way for data to outlive those replaceable workloads.

---

# 6. Container Filesystem

Every container has a writable filesystem layer.

For example:

```bash
echo "hello" > /tmp/example.txt
```

creates a file inside the container's writable filesystem.

You can inspect it:

```bash
cat /tmp/example.txt
```

Expected:

```text
hello
```

But this does not automatically make the data persistent.

---

# 7. Container Image vs Writable Layer

Conceptually:

```text
Container Image
Read-only layers
↓
Container
+
Writable container layer
```

The application can write files into its writable layer.

Example:

```text
Image
├── /usr/bin/application
├── /etc/application
└── libraries

Running Container
+
Writable Layer
├── /tmp/file
├── /var/log/application.log
└── /app/generated-data
```

---

# 8. The Problem with the Writable Layer

The writable container layer belongs to that particular container instance.

If Kubernetes replaces the container:

```text
Old Container
↓
removed
↓
New Container
↓
new writable layer
```

Data written only into the old writable layer is not a durable persistence strategy.

---

# 9. Container Restart Nuance

This requires an important distinction.

If the process inside a container crashes and kubelet restarts the container, Kubernetes creates a replacement container.

Files written only into the old container's writable layer should not be treated as durable application state.

By contrast, data stored in an appropriate Pod volume can survive container restarts according to that volume's lifecycle.

---

# 10. Why Production Applications Cannot Depend on Container Filesystems

Imagine:

```text
payments-api
```

writes uploaded receipts to:

```text
/app/uploads/
```

inside its container filesystem.

Everything works.

Then:

```text
container replaced
```

and the files disappear.

The application architecture was incorrect.

---

# 11. Storage Lifetimes

Think about storage by lifetime.

```text
Container filesystem
↓
tied closely to container instance

emptyDir
↓
tied to Pod lifetime

PersistentVolume-backed storage
↓
can outlive Pod lifetime

External storage system
↓
lifecycle controlled independently
```

Understanding lifetime is more important than memorizing YAML.

---

# 12. Kubernetes Volumes

A Kubernetes volume provides storage that containers in a Pod can access.

Volumes can serve many purposes.

Examples:

```text
temporary scratch storage

sharing files between containers

mounting configuration

mounting Secrets

persistent application data

accessing external storage
```

You already used volumes in Part 11 for:

```text
ConfigMaps

Secrets
```

Now we focus on application data.

---

# 13. Volume Mental Model

Conceptually:

```text
Pod
├── Container A
├── Container B
└── Volume
```

Containers mount the volume into their filesystems.

Example:

```text
Volume
↓
Container A:
/data

Container B:
/shared
```

The same underlying volume can sometimes be mounted into multiple containers depending on the volume type and configuration.

---

# 14. Volume Definition Has Two Parts

At the Pod level:

```yaml
volumes:
```

defines storage available to the Pod.

Inside a container:

```yaml
volumeMounts:
```

defines where that storage appears inside the container.

---

# 15. Example

```yaml
spec:
  containers:
    - name: app
      image: busybox:1.36
      volumeMounts:
        - name: application-data
          mountPath: /data

  volumes:
    - name: application-data
      emptyDir: {}
```

Read it as:

```text
Create volume:
application-data

Volume type:
emptyDir

Mount it into container:
app

Mount location:
/data
```

---

# 16. `volumeMounts`

This:

```yaml
volumeMounts:
  - name: application-data
    mountPath: /data
```

means:

```text
Take the Pod volume named:
application-data

and expose it inside this container at:
/data
```

---

# 17. `volumes`

This:

```yaml
volumes:
  - name: application-data
    emptyDir: {}
```

defines the actual volume source.

The names must match:

```text
volumeMounts.name
=
volumes.name
```

---

# 18. Ephemeral Storage

Ephemeral means:

```text
not intended to survive indefinitely.
```

Kubernetes has several forms of ephemeral storage.

Examples include:

```text
container writable layers

container logs

emptyDir

certain CSI ephemeral volumes

generic ephemeral volumes
```

The exact lifecycle depends on the storage mechanism.

---

# 19. Local Ephemeral Storage

Nodes provide local ephemeral storage.

Kubernetes can use local storage for things such as:

```text
container writable layers

container images

logs

emptyDir data
```

This storage is associated with the node rather than durable external storage.

---

# 20. Ephemeral Storage Is Still a Resource

Disk space is finite.

If workloads consume too much node-local ephemeral storage:

```text
node disk pressure
↓
eviction pressure
↓
Pods may be evicted
```

Storage problems are therefore also scheduling and reliability problems.

---

# 21. Ephemeral Storage Requests and Limits

Containers can request and limit local ephemeral storage.

Example:

```yaml
resources:
  requests:
    ephemeral-storage: "1Gi"
  limits:
    ephemeral-storage: "2Gi"
```

This is different from requesting a PersistentVolume.

---

# 22. Do Not Confuse the Two

```text
ephemeral-storage request
```

controls node-local ephemeral storage resources.

It is not:

```text
PersistentVolumeClaim.
```

A PVC requests persistent storage through the persistent volume subsystem.

---

# 23. `emptyDir`

One of the simplest Kubernetes volumes is:

```text
emptyDir
```

It is created when the Pod is assigned to a node.

Initially, it is empty.

---

# 24. `emptyDir` Lifetime

Conceptually:

```text
Pod created
↓
emptyDir created
↓
containers use it
↓
containers may restart
↓
emptyDir remains
↓
Pod removed from node
↓
emptyDir data deleted
```

This is critical.

---

# 25. `emptyDir` Survives Container Restart

Suppose:

```text
Pod
├── Container
└── emptyDir
```

The container crashes.

Kubernetes restarts the container.

The Pod still exists.

The `emptyDir` remains.

Therefore:

```text
container restart
≠
emptyDir deletion
```

---

# 26. `emptyDir` Does Not Survive Pod Removal

If the Pod is removed:

```text
Pod deleted
↓
emptyDir deleted
```

A replacement Pod gets a new `emptyDir`.

Therefore:

```text
emptyDir
≠
persistent storage
```

---

# 27. Good Uses for `emptyDir`

Examples:

```text
temporary processing files

scratch space

cache

sharing files between containers in a Pod

downloaded temporary artifacts

intermediate processing data
```

---

# 28. Bad Use for `emptyDir`

Do not use `emptyDir` for data that must survive Pod replacement.

Bad example:

```text
production database
↓
emptyDir
```

Pod disappears:

```text
database data disappears
```

---

# 33. LAB 2: Share `emptyDir` Between Containers

Create:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: shared-volume-demo
spec:
  containers:
    - name: writer
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          while true; do
            date >> /shared/time.log
            sleep 10
          done
      volumeMounts:
        - name: shared-data
          mountPath: /shared

    - name: reader
      image: busybox:1.36
      command:
        - sh
        - -c
        - sleep 3600
      volumeMounts:
        - name: shared-data
          mountPath: /shared

  volumes:
    - name: shared-data
      emptyDir: {}
```

---

# 34. Apply

```bash
kubectl apply -f shared-volume-demo.yaml
```

Verify:

```bash
kubectl get pod shared-volume-demo
```

---

# 35. Read From the Second Container

Run:

```bash
kubectl exec shared-volume-demo \
  -c reader \
  -- cat /shared/time.log
```

The reader sees data written by the writer.

Architecture:

```text
Writer Container
      ↓
   emptyDir
      ↑
Reader Container
```

---

# 36. Why This Works

Both containers belong to the same Pod.

Both mount:

```text
shared-data
```

The mount paths can even differ.

For example:

```text
Writer:
/output

Reader:
/input
```

can still refer to the same underlying volume.

# 37. Persistent Storage

Now we need storage whose lifecycle is independent of an individual Pod.

Kubernetes provides the PersistentVolume subsystem.

Two fundamental API objects are:

```text
PersistentVolume

PersistentVolumeClaim
```

Usually abbreviated:

```text
PV

PVC
```

---

# 38. PersistentVolume

A PersistentVolume is a cluster resource representing storage available to Kubernetes.

Think:

```text
PersistentVolume
=
Kubernetes representation of persistent storage capacity
```

The backing storage might be:

```text
cloud block storage

network filesystem

local persistent disk

enterprise storage array

distributed storage system
```

---

# 39. PV Lifecycle

A PV has a lifecycle independent of an individual Pod.

That is the major difference.

```text
Pod deleted
↓
PV can continue existing
↓
data can remain
```

depending on the storage and reclaim configuration.

---

# 40. PersistentVolumeClaim

A PersistentVolumeClaim is a user's request for storage.

Think:

```text
PVC
=
"I need storage with these characteristics."
```

For example:

```text
10 GiB

ReadWriteOnce

Filesystem

StorageClass: fast
```

---

# 41. PV vs PVC

Memorize:

```text
PV
=
storage resource
```

```text
PVC
=
request for storage
```

Analogy:

```text
Node
← consumed by → Pod

PersistentVolume
← claimed by → PersistentVolumeClaim
```

---

# 42. Why Pods Usually Reference PVCs

Applications should not normally need to know:

```text
disk ID

cloud volume ID

storage server

SAN details

storage implementation
```

Instead:

```text
Pod
↓
PVC
↓
storage abstraction
```

This separates application configuration from storage infrastructure.

---

# 43. Persistent Storage Architecture

Basic architecture:

```text
Pod
↓
PVC
↓
PV
↓
Physical / Cloud Storage
```

With dynamic provisioning:

```text
Pod
↓
PVC
↓
StorageClass
↓
CSI Provisioner
↓
Storage Backend
↓
PV
```

---

# 44. PersistentVolume Is Cluster-Scoped

A PV is:

```text
cluster-scoped.
```

It does not belong to a namespace.

Check:

```bash
kubectl get pv
```

There is no namespace column.

---

# 45. PVC Is Namespaced

A PVC is:

```text
namespaced.
```

Example:

```bash
kubectl get pvc -n production
```

A Pod normally references a PVC from the same namespace.

---

# 46. PVC Manifest

Example:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: application-data
  namespace: default
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
```

---

# 47. Read the PVC

```yaml
kind: PersistentVolumeClaim
```

means:

```text
Request persistent storage.
```

```yaml
accessModes:
  - ReadWriteOnce
```

requests a particular access capability.

```yaml
resources:
  requests:
    storage: 1Gi
```

requests:

```text
1 GiB
```

of storage.

---

# 48. PVC Status

After creation:

```bash
kubectl get pvc
```

you may see:

```text
NAME               STATUS    VOLUME
application-data   Pending
```

or:

```text
NAME               STATUS   VOLUME
application-data   Bound    pvc-...
```

---

# 49. `Pending`

`Pending` means the claim has not yet been successfully bound to usable persistent storage.

That may be normal temporarily.

Or it may indicate a storage problem.

---

# 50. `Bound`

`Bound` means:

```text
PVC
↓
matched/provisioned
↓
PV
```

The claim now has storage assigned.

---

# 51. Static Provisioning

Historically, administrators might manually create storage first.

Architecture:

```text
Storage Administrator
↓
Create storage asset
↓
Create PersistentVolume
↓
Developer creates PVC
↓
Kubernetes finds matching PV
↓
PVC binds to PV
```

This is static provisioning.

---

# 52. Static PV Example

Educational example:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: example-pv
spec:
  capacity:
    storage: 5Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
```

A real PV also requires an actual storage source.

A PV manifest does not magically create storage unless a provisioner is involved.

---

# 53. Matching PVC to PV

Kubernetes considers characteristics such as:

```text
storage class

requested capacity

access modes

volume mode

selectors where used
```

when matching a PVC with a PV.

A claim cannot simply bind to arbitrary incompatible storage.

---

# 54. Capacity Matching

Suppose:

```text
PVC requests:
5Gi
```

A:

```text
2Gi PV
```

cannot satisfy that request.

A sufficiently large compatible PV may.

---

# 55. PersistentVolumeClaim Is Not the Storage Itself

This is important.

```text
PVC
≠
disk
```

A PVC is an API object representing a claim.

The actual storage is provided by the backing storage system and represented through a PV.

---

# 56. StorageClass

A StorageClass describes a class of storage offered by the cluster.

Think:

```text
StorageClass
=
"How should this type of storage be provisioned?"
```

It can describe things such as:

```text
provisioner

storage backend parameters

reclaim policy

volume binding mode

volume expansion behavior
```

---

# 57. Why StorageClasses Exist

Different applications may need different storage.

Example:

```text
Database
↓
high-performance block storage

Backups
↓
different storage characteristics

Shared content
↓
network filesystem
```

Rather than exposing infrastructure details directly to every developer:

```text
StorageClass
↓
storage offering
```

---

# 58. Example Storage Classes

A cluster might offer:

```text
standard

fast

encrypted

database

shared
```

These names are chosen by cluster administrators.

They are not universal Kubernetes names.

Never assume every cluster has:

```text
standard
```

or:

```text
gp3
```

Check the actual cluster.


# 64. Dynamic Provisioning

Dynamic provisioning removes the need for administrators to manually pre-create a PV for every claim.

Architecture:

```text
Developer
↓
PVC
↓
StorageClass
↓
Provisioner
↓
Create Storage
↓
Create PV
↓
Bind PVC
```

This is one of Kubernetes storage's most important abstractions.

---

# 65. Static vs Dynamic Provisioning

Static:

```text
Storage created first
↓
PV created
↓
PVC created
↓
binding
```

Dynamic:

```text
PVC created
↓
StorageClass selected
↓
storage automatically provisioned
↓
PV created
↓
binding
```

---

# 66. Dynamic Provisioning Flow

Suppose you create:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: database-data
spec:
  storageClassName: fast
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

Conceptually:

```text
PVC database-data
↓
StorageClass fast
↓
Provisioner
↓
Storage backend creates volume
↓
Kubernetes creates PV representation
↓
PVC becomes Bound
```

# 73. Why PVC Might Stay Pending Until a Pod Exists

A StorageClass can use:

```text
volumeBindingMode:
WaitForFirstConsumer
```

This delays provisioning or binding until a Pod actually uses the claim.

Why?

Storage topology.

---

# 74. Storage Topology Problem

Imagine a cluster across:

```text
Zone A

Zone B

Zone C
```

The scheduler chooses a node in:

```text
Zone B
```

But the storage was already provisioned in:

```text
Zone A.
```

If the storage is zone-specific, the Pod may not be able to use it.

---

# 75. `WaitForFirstConsumer`

With:

```text
WaitForFirstConsumer
```

Kubernetes can coordinate:

```text
Pod scheduling requirements
+
storage topology
```

before provisioning or binding the volume.

This helps avoid topology conflicts.

---

# 76. `Immediate`

Another binding mode is:

```text
Immediate
```

The volume is provisioned/bound as soon as the PVC is created.

That can be appropriate for storage without the same topology concerns.

# 89. PersistentVolume Lifecycle

Typical lifecycle:

```text
Provisioning
↓
Binding
↓
Using
↓
Reclaiming
```

A PV can move through phases such as:

```text
Available

Bound

Released

Failed
```

depending on its lifecycle.

---

# 90. `Available`

Conceptually:

```text
PV exists
+
not currently bound
```

It may be available to satisfy a compatible claim.

---

# 91. `Bound`

```text
PV
↔
PVC
```

The volume is bound to a claim.

---

# 92. `Released`

The claim was deleted, but the PV has not necessarily been made available for reuse.

This is particularly relevant with:

```text
Retain
```

reclaim behavior.

---

# 93. `Failed`

The volume encountered a problem during automated reclamation or another storage lifecycle operation.

Investigate the storage backend and Kubernetes events/status.

---

# 94. Reclaim Policy

The reclaim policy determines what should happen to the underlying persistent storage after the claim is released.

Important policies are:

```text
Retain

Delete
```

There is also the legacy:

```text
Recycle
```

policy, which is deprecated and should not be used as the modern design.

---

# 95. `Retain`

With:

```text
Retain
```

when the PVC is deleted:

```text
PVC deleted
↓
PV becomes Released
↓
underlying storage retained
↓
manual administrative reclamation required
```

This can protect important data from automatic deletion.

---

# 96. Why `Retain` Can Be Useful

For critical storage:

```text
database
```

you may prefer:

```text
PVC accidentally deleted
↓
data still exists
```

rather than:

```text
PVC deleted
↓
disk automatically destroyed
```

But Retain requires lifecycle management.

---

# 97. `Delete`

With:

```text
Delete
```

deleting the PVC can eventually result in:

```text
PVC deleted
↓
PV removed
↓
backing storage asset deleted
```

when supported by the provisioner.

This is convenient but potentially destructive.

---

# 98. Dynamic Provisioning Default Reclaim Behavior

Dynamically provisioned PVs inherit the reclaim policy configured on their StorageClass.

If the StorageClass does not explicitly set one, the StorageClass reclaim policy defaults to:

```text
Delete
```

This is an extremely important production detail.

---

```text
What reclaim policy?

What data is on this volume?

Is there a backup?

Is deletion intended?

Will the cloud disk be deleted?

Can the data be restored?
```

Do not treat:

```bash
kubectl delete pvc ...
```

as a harmless cleanup command.

# 103. Access Modes

Persistent storage has access modes.

The major modes are:

```text
ReadWriteOnce

ReadOnlyMany

ReadWriteMany

ReadWriteOncePod
```

CLI abbreviations:

```text
RWO

ROX

RWX

RWOP
```

---

# 104. `ReadWriteOnce`

```text
ReadWriteOnce
```

means the volume can be mounted read-write by a single node.

Abbreviation:

```text
RWO
```

Critical nuance:

```text
RWO
≠
one Pod
```

Multiple Pods on the same node may potentially access an RWO volume.

---

# 105. `ReadWriteOncePod`

If you specifically require the volume to be mounted read-write by only one Pod across the cluster, Kubernetes provides:

```text
ReadWriteOncePod
```

Abbreviation:

```text
RWOP
```

This mode is supported for CSI volumes when the required driver capabilities are available.

---

# 106. `ReadOnlyMany`

```text
ReadOnlyMany
```

means:

```text
many nodes
↓
read-only access
```

Abbreviation:

```text
ROX
```

---

# 107. `ReadWriteMany`

```text
ReadWriteMany
```

means:

```text
many nodes
↓
read/write access
```

Abbreviation:

```text
RWX
```

Not every storage backend supports RWX.

---

# 108. Storage Backend Determines Capabilities

Do not assume:

```text
every CSI driver supports every access mode.
```

Actual support depends on:

```text
storage system

CSI driver

volume type

provider capabilities
```

---

# 109. Access Modes Are Not General Filesystem ACLs

Do not interpret:

```text
ReadWriteOnce
```

as a complete application-level permission system.

Access modes primarily participate in volume matching and mounting constraints.

They are not a substitute for:

```text
filesystem permissions

application authorization

securityContext

storage-side access controls
```

---

# 110. Access Mode Selection

Ask:

```text
Does one node need write access?

Do many nodes need read access?

Do many nodes need simultaneous write access?

Must exactly one Pod have write access?
```

Then select storage that actually supports that requirement.

```text

+

```

Shared web content:

```text

+
RWX
```

Shared read-only model data:

```text

```

Actual architecture depends on the application.

# 112. Volume Modes

Kubernetes persistent volumes support two primary volume modes:

```text
Filesystem

Block
```

---

# 113. `Filesystem`

This is the common mode.

```yaml
volumeMode: Filesystem
```

The storage appears as a mounted filesystem directory.

Example:

```text
/data
```

The application uses ordinary file operations:

```bash
ls
cat
mkdir
write
read
```

---

# 114. Default Volume Mode

If `volumeMode` is omitted, Kubernetes uses:

```text
Filesystem
```

for persistent volumes/claims.

---

# 115. Raw `Block`

You can request:

```yaml
volumeMode: Block
```

This exposes a raw block device rather than a mounted filesystem.

The application must know how to use a raw block device.

---

# 116. Filesystem vs Block

Filesystem:

```text
Storage Device
↓
Filesystem
↓
Directory
↓
Application files
```

Block:

```text
Storage Device
↓
Raw block device
↓
Application handles device directly
```

Most ordinary applications expect:

```text
Filesystem.
```

---

# 117. Raw Block Is Specialized

Do not choose:

```text
Block
```

because it sounds faster or more advanced.

The application must explicitly support raw block storage.

For most beginner labs:

```text
Filesystem
```

is correct.

### What is a PV?

A cluster resource representing persistent storage.

### What is a PVC?

A namespaced request for persistent storage.

# 234. Knowledge Check

### Why does a Pod normally reference a PVC rather than a specific cloud disk?

The PVC abstracts the storage request from the underlying infrastructure implementation.

# 235. Knowledge Check

### What is a StorageClass?

A cluster-level object describing a class of storage and how that storage should be provisioned.

---

# 236. Knowledge Check

### What is dynamic provisioning?

Automatic creation of persistent storage in response to a PVC using a StorageClass and provisioner.

---

# 237. Knowledge Check

### What is CSI?

Container Storage Interface.

It provides a standardized mechanism for Kubernetes to integrate with storage drivers.

---

# 238. Knowledge Check

### What does `ReadWriteOnce` mean?

The volume can be mounted read-write by a single node.

It does not necessarily mean only one Pod.

---

# 239. Knowledge Check

### Which access mode specifically constrains read-write mounting to one Pod?

```text
ReadWriteOncePod
```

when supported by the CSI storage implementation.

---

# 240. Knowledge Check

### What does `ReadWriteMany` mean?

The storage can support read-write mounting from many nodes according to the storage provider's capabilities.

# 241. Knowledge Check

### What is the default persistent volume mode if omitted?

```text
Filesystem.
```

---

# 242. Knowledge Check

### What does `volumeMode: Block` provide?

A raw block device rather than a filesystem mount.

---

# 243. Knowledge Check

### What does reclaim policy `Retain` mean?

The underlying storage is retained for manual reclamation after the claim is released.

---

# 244. Knowledge Check

### What does reclaim policy `Delete` mean?

For supported dynamically provisioned storage, deleting the claim can result in deletion of the PV and underlying storage asset.

# 245. Knowledge Check

### Why can `WaitForFirstConsumer` be useful?

It delays provisioning/binding so Kubernetes can consider Pod scheduling and storage topology together.

This is particularly useful for topology-constrained storage.

No.

No.

### Does persistent storage automatically provide high availability?

No.

```text
assuming every storage backend supports RWX

assuming Bound means mounted successfully

deleting PVCs without checking reclaim policy

assuming persistent storage equals backup

assuming storage automatically provides HA

ignoring Availability Zone topology

ignoring filesystem permissions

ignoring storage capacity

ignoring CSI health
```

# 266. Production Failure Example

```text
waiting for volume creation

authorization failure
```


```text
storage provisioning authorization.
```
