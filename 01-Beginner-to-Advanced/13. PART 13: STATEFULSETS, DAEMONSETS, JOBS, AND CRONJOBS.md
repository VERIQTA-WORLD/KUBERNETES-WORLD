# 2. Why Kubernetes Has Multiple Workload Controllers

You already know that applications ultimately run inside:

```text
Pods
```

But Pods can represent very different kinds of work.

Consider these workloads:

```text
Web API

PostgreSQL database

Node log collector

Database migration

Nightly backup
```

All can run inside containers.

But they do not have the same lifecycle requirements.

---

# 3. The Controller Must Match the Workload

A web application may require:

```text
3 interchangeable replicas
```

A database cluster may require:

```text
stable replica identity
+
stable storage
```

A logging agent may require:

```text
one instance on every worker node
```

A database migration may require:

```text
run once
+
finish successfully
+
stop
```

A backup process may require:

```text
run every night
```

These are different control problems.

Therefore Kubernetes provides different controllers.

---

# 4. The Wrong Controller Creates the Wrong Behavior

Imagine using a Deployment for a node monitoring agent.

You configure:

```yaml
replicas: 3
```

But your cluster has:

```text
5 nodes
```

Kubernetes might schedule:

```text
Node A
├── Agent Pod
└── Agent Pod

Node B
└── Agent Pod

Node C
└── none

Node D
└── none

Node E
└── none
```

The Deployment guarantees:

```text
3 replicas
```

It does not inherently guarantee:

```text
one replica per node.
```

A DaemonSet solves a different problem.

---

# 5. Controller Selection Mental Model

Ask:

```text
What relationship must exist between my Pods?
```

If:

```text
Pods are interchangeable
```

think:

```text
Deployment
```

If:

```text
Pods need stable identities
```

think:

```text
StatefulSet
```

If:

```text
Pod must follow nodes
```

think:

```text
DaemonSet
```

If:

```text
work must finish
```

think:

```text
Job
```

If:

```text
work must finish repeatedly on a schedule
```

think:

```text
CronJob
```

# 6. Workload Controller Overview

```text
Deployment
│
├── long-running
├── stateless
├── interchangeable Pods
└── replica-oriented

StatefulSet
│
├── long-running
├── stateful
├── stable identity
├── ordered behavior
└── persistent storage relationships

DaemonSet
│
├── long-running
├── node-oriented
└── one Pod on each eligible node

│
├── finite work
├── run-to-completion
└── success-oriented

CronJob
│
├── scheduled
├── creates Jobs

```

# 7. StatefulSet

A StatefulSet is a Kubernetes workload controller designed for applications whose Pods require persistent identities.

The key word is:

```text
identity
```

A StatefulSet manages Pods that are related but not necessarily interchangeable.

---

# 8. Deployment vs StatefulSet

Deployment:

```text
web-5d7f7b8d7c-ab123

web-5d7f7b8d7c-cd456

web-5d7f7b8d7c-ef789
```

These replicas are intended to be interchangeable.

Conceptually:

```text
Pod A
=
Pod B
=
Pod C
```

---

# 9. StatefulSet Identity

A StatefulSet named:

```text
database
```

with three replicas creates Pods such as:

```text
database-0

database-1

database-2
```

These names are predictable.

Their identities are stable.

---

# 10. Ordinals

The numbers:

```text
0

1

2
```

are called:

```text
ordinals
```

For a typical StatefulSet with three replicas:

```text
database-0
database-1
database-2
```

Each Pod has a unique ordinal identity.

---

# 11. Stable Identity

Suppose:

```text
database-1
```

fails.

The replacement is still logically:

```text
database-1
```

rather than becoming an unrelated random replica.

Conceptually:

```text
database-1
↓
fails
↓
replacement
↓
database-1
```

This matters for distributed systems.

---

# 12. Why Stable Identity Matters

Some systems need to know:

```text
who am I?
```

Examples include:

```text
database replicas

distributed databases

message brokers

cluster members

consensus systems
```

An application may have roles such as:

```text
member 0

member 1

member 2
```

Stable identity can be important to the application's own clustering model.

---

# 13. StatefulSet Identity Components

A StatefulSet Pod identity can include:

```text
stable ordinal

stable Pod name

stable hostname

stable DNS identity

stable persistent storage relationship
```

These survive Pod rescheduling in the logical workload sense.

---

# 14. StatefulSet Does Not Mean "Database"

Do not memorize:

```text
database
=
StatefulSet
```

Instead understand:

```text
stable identity requirements
→
StatefulSet may be appropriate
```

Some databases may be better operated through:

```text
managed database services

specialized Kubernetes operators

external database platforms
```

depending on the architecture.

---

# 15. StatefulSet Does Not Make Applications Stateful

Statefulness belongs to the application.

StatefulSet provides Kubernetes primitives that make certain stateful application patterns easier.

It does not automatically provide:

```text
database replication

leader election

data consistency

quorum

backup

disaster recovery

application-level failover
```

Those remain application or platform responsibilities.

---

# 16. StatefulSet and Persistent Storage

StatefulSets commonly combine:

```text
stable Pod identity
+
stable storage identity
```

Example:

```text
database-0
↓
PVC database-data-database-0

database-1
↓
PVC database-data-database-1

database-2
↓
PVC database-data-database-2
```

Each replica can receive its own persistent volume.

---

# 17. Why This Is Different From a Deployment

With a Deployment:

```text
Replica A
Replica B
Replica C
```

are normally interchangeable.

With a StatefulSet:

```text
database-0
database-1
database-2
```

have distinct identities.

That identity can be tied to:

```text
DNS

storage

application membership
```

---

# 18. `volumeClaimTemplates`

StatefulSets can define:

```yaml
volumeClaimTemplates:
```

This instructs Kubernetes to create PersistentVolumeClaims for StatefulSet Pods.

Example:

```yaml
volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes:
        - ReadWriteOnce
      resources:
        requests:
          storage: 1Gi
```

---

# 19. PVC Generation

Suppose StatefulSet:

```text
mysql
```

has:

```text
3 replicas
```

and a volume claim template named:

```text
data
```

Kubernetes creates claims with identities associated with each Pod.

Conceptually:

```text
mysql-0
↓
data-mysql-0

mysql-1
↓
data-mysql-1

mysql-2
↓
data-mysql-2
```

---

# 20. Storage Relationship

Architecture:

```text
StatefulSet
│
├── mysql-0
│   └── PVC-0
│       └── PV-0
│
├── mysql-1
│   └── PVC-1
│       └── PV-1
│
└── mysql-2
    └── PVC-2
        └── PV-2
```

This is a major StatefulSet pattern.

---

# 21. Pod Replacement

Suppose:

```text
mysql-1
```

fails.

Kubernetes creates replacement:

```text
mysql-1
```

and associates it with the storage intended for that identity.

Conceptually:

```text
Old mysql-1
↓
fails
↓
Replacement mysql-1
↓
same logical PVC identity
↓
persistent data
```

---

# 22. StatefulSet PVC Safety

A critical behavior:

Deleting or scaling down a StatefulSet does not automatically delete its associated persistent volumes simply because replicas disappeared.

This is intentionally conservative.

Why?

Because:

```text
automatic deletion
+
stateful data
=
dangerous
```

Storage cleanup must be deliberate.

---

# 23. Headless Services

StatefulSets commonly use a:

```text
Headless Service
```

You encountered headless Services conceptually in Part 8.

A normal Service usually provides:

```text
stable Service virtual IP
```

A headless Service uses:

```yaml
clusterIP: None
```

---

# 24. Headless Service Purpose

Instead of primarily giving clients one virtual Service IP, a headless Service allows DNS-based discovery of individual backend identities.

This is useful when applications need to discover specific StatefulSet members.

---

# 25. Example Headless Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: database
spec:
  clusterIP: None
  selector:
    app: database
  ports:
    - name: database
      port: 5432
```

The critical field is:

```yaml
clusterIP: None
```

---

# 26. StatefulSet Governing Service

A StatefulSet can specify:

```yaml
serviceName: database
```

This references the governing headless Service used for network identity.

---

# 27. Stable DNS

Suppose:

```text
StatefulSet:
database

Service:
database

Namespace:
stateful-lab
```

Pod names:

```text
database-0
database-1
database-2
```

DNS identities conceptually become:

```text
database-0.database.stateful-lab.svc.cluster.local

database-1.database.stateful-lab.svc.cluster.local

database-2.database.stateful-lab.svc.cluster.local
```

assuming the common default cluster domain:

```text
cluster.local
```

Cluster domains can be configured differently.

---

# 28. Why Individual DNS Matters

A distributed application may need to contact:

```text
database-0
```

specifically.

With ordinary interchangeable Deployment Pods, that identity is not normally part of the design.

StatefulSet makes it possible to build predictable network identities.

---

# 29. StatefulSet Ordering

By default, StatefulSets use:

```text
OrderedReady
```

Pod management.

When scaling up:

```text
database-0
↓
Ready
↓
database-1
↓
Ready
↓
database-2
```

The controller normally proceeds in ordinal order.

---

# 30. Ordered Scale Down

Scaling down generally proceeds in reverse ordinal order.

For example:

```text
database-2
↓
terminated

database-1
↓
terminated

database-0
↓
remains
```

The controller observes readiness and termination guarantees according to StatefulSet behavior.

---

# 31. Why Ordering Can Matter

Imagine a distributed system requiring:

```text
first member initializes cluster

second joins first

third joins existing cluster
```

Random parallel startup might violate application assumptions.

Ordered startup can help.

---

# 32. Ordering Is Not Application Initialization Logic

StatefulSet ordering does not automatically configure:

```text
database leader

replication

cluster membership

schema initialization
```

Your application still needs appropriate logic.

---

# 33. `Parallel` Pod Management

StatefulSets can use:

```yaml
podManagementPolicy: Parallel
```

This relaxes scaling ordering.

Pods can be created or terminated in parallel.

Use this only when the application does not require strict ordered scaling behavior.

---

# 34. StatefulSet Update Strategies

StatefulSets support update strategies such as:

```text
RollingUpdate

OnDelete
```

The default is generally:

```text
RollingUpdate
```

---

# 35. Rolling Updates

During a normal StatefulSet rolling update, Pods are replaced according to StatefulSet ordering behavior.

For example:

```text
database-2
↓
updated

database-1
↓
updated

database-0
↓
updated
```

The exact behavior depends on configuration and readiness.

---

# 36. Stateful Application Update Warning

Updating stateful systems can be more dangerous than updating stateless web servers.

You must consider:

```text
version compatibility

schema compatibility

replication compatibility

quorum

leader behavior

data format changes

rollback compatibility
```

Kubernetes cannot determine whether application versions are safe together.

# 40. Create the StatefulSet

For this first lab, we will focus on identity before adding persistent storage.

Create:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
  namespace: stateful-lab
spec:
  serviceName: web
  replicas: 3
  selector:
    matchLabels:
      app: stateful-web
  template:
    metadata:
      labels:
        app: stateful-web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - name: http
              containerPort: 80
```

Save:


# 50. StatefulSet Storage Manifest

Add:

```yaml
volumeMounts:
  - name: data
    mountPath: /usr/share/nginx/html
```

and:

```yaml
volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes:
        - ReadWriteOnce
      resources:
        requests:
          storage: 1Gi
```

A complete educational example:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: storage-web
  namespace: stateful-lab
spec:
  serviceName: web
  replicas: 2

  selector:
    matchLabels:
      app: storage-web

  template:
    metadata:
      labels:
        app: storage-web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27

          ports:
            - name: http
              containerPort: 80

          volumeMounts:
            - name: data
              mountPath: /usr/share/nginx/html

  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes:
          - ReadWriteOnce
        resources:
          requests:
            storage: 1Gi
```

# 51. Important Service Selector Note

Our existing headless Service selects:

```text
app=stateful-web
```


```yaml
  clusterIP: None
  selector:
    app: storage-web
  ports:
    - name: http
      port: 80
      targetPort: 80
```

Then change the StatefulSet:

```yaml
serviceName: storage-web
```

# 67. Ordered Behavior Can Block Progress

Suppose:

```text

```

never becomes Ready.

With default ordered behavior, creation of later replicas can be blocked.

Symptom:

```text

only database-0 exists
```

Do not immediately blame the StatefulSet controller.

Investigate:

```text
database-0
```

first.

# 69. DaemonSet

A DaemonSet ensures that a Pod runs on:

```text
all eligible nodes
```

or a selected subset of eligible nodes.

Its unit of thinking is not primarily:

```text
replica count
```

but:

```text
node coverage.
```

---

# 70. DaemonSet Mental Model

```text
Node A
↓
Daemon Pod

Node B
↓
Daemon Pod

Node C
↓
Daemon Pod
```

Add:

```text
Node D
```

and the DaemonSet creates:

```text
Daemon Pod
```

for Node D if it is eligible.

```text
Node C
```

```text

consume resources
```

# 134. Automatic Job Cleanup


Automatic cleanup is useful.

But ask:

```text

Do we need audit evidence?

Do we need debugging time?

```

If Jobs disappear before logs are collected, troubleshooting becomes harder.

# 136. Idempotency

Jobs should often be designed to tolerate retries.

Suppose a Job:

```text

↓

↓

↓
```

That is dangerous.

# 137. Idempotent Work

An idempotent operation can safely be repeated without producing an unintended additional effect.

For example, instead of:

```text

```

the task might:

```text

↓
detect already processed
↓

```

Retries are a distributed-systems concern, not just a Kubernetes setting.

Modern Kubernetes supports:

```yaml
spec:

```

```yaml

```

This makes schedule interpretation explicit.

For production, explicit timezone configuration can reduce ambiguity.

---

# 154. Timezone Example

```yaml
spec:
  schedule: "0 2 * * *"
  timeZone: "America/New_York"
```

means the schedule is interpreted using that IANA timezone.

Do not place:

```text
TZ=
```

or:

```text
CRON_TZ=
```

inside the cron expression.

Use:

```yaml
spec.timeZone
```

for supported Kubernetes CronJobs.

---

# 155. Daylight Saving Time

Named regional time zones may observe daylight-saving changes.

Therefore:

```text
02:00 local time
```

may not behave like:

```text
02:00 UTC
```

throughout the year.

For globally consistent operational schedules, teams often explicitly evaluate whether UTC is preferable.

# 156. Concurrency Problem

Imagine a backup runs every hour.

But one backup takes:

```text
90 minutes.
```

At the next scheduled time:

```text
old backup
=
still running

new schedule
=
arrives
```

What should happen?

CronJob has concurrency policies.

---

# 157. `concurrencyPolicy`

Possible values:

```text
Allow

Forbid

Replace
```

---

# 158. `Allow`

```yaml
concurrencyPolicy: Allow
```

means overlapping Jobs created by that CronJob are permitted.

This is the default.

Architecture:

```text
Job A still running
+
schedule arrives
↓
Job B starts
```

---

# 159. Risk of `Allow`

If the task modifies shared state:

```text
two backups

two database maintenance operations

two billing jobs

two cleanup processes
```

may conflict.

You must decide whether overlap is safe.

---

# 160. `Forbid`

```yaml
concurrencyPolicy: Forbid
```

means if the previous Job from the same CronJob is still running, a new overlapping execution is skipped rather than run concurrently.

Useful when:

```text
only one execution should run at a time.
```

---

# 161. `Replace`

```yaml
concurrencyPolicy: Replace
```

means a currently running Job created by the same CronJob can be replaced when the new scheduled execution arrives.

This can be useful for workloads where:

```text
latest execution
>
old execution
```

but can be dangerous for non-interruptible tasks.

---

# 162. Concurrency Policy Scope

The concurrency policy applies to Jobs created by:

```text
the same CronJob.
```

It does not prevent a completely different CronJob from running concurrently.

---

# 163. `startingDeadlineSeconds`

CronJobs can specify how late a missed execution is still allowed to start.

Example:

```yaml
startingDeadlineSeconds: 300
```

Conceptually:

```text
scheduled time missed
↓
controller notices later
↓
within allowed deadline?
├── yes → may start
└── no → considered missed
```

---

# 164. Why Schedules Can Be Missed

Possible reasons include:

```text
controller unavailable

cluster control-plane disruption

suspension

controller processing delay
```

Production CronJobs must account for scheduling imperfections.

---

# 165. CronJob Delivery Is Not an Exact-Once Guarantee

CronJobs should not be designed under the assumption:

```text
exactly one execution
at exactly one instant
guaranteed forever
```

Under some circumstances, Jobs can be missed or duplicate scheduling can occur.

Therefore scheduled workloads should generally be designed to be:

```text
idempotent
```

where possible.

It stops future scheduling while suspended.

# 173. LAB 7: Configure Job History

Modify:

```yaml
apiVersion: batch/v1

  name: time-reporter
```

# 185. Controller Selection: Deployment

Choose Deployment when:

```text
application is long-running

replicas are interchangeable

stable individual identity is unnecessary

replica count matters more than node identity
```

```text
web frontend

REST API

stateless backend

worker consuming from shared queue
```

# 186. Controller Selection: StatefulSet

Choose StatefulSet when the application needs one or more of:

```text
stable unique Pod identity

stable network identity

stable per-replica storage

ordered deployment

ordered scaling

ordered updates
```

Examples may include appropriately designed:

```text
databases

message brokers

distributed systems
```

# 187. Controller Selection: DaemonSet

Choose DaemonSet when the requirement is:

```text
run this workload on every eligible node
```

```text

```

Choose Job when:

```text
work should execute
↓
finish
↓
```

```text
migration

one-time maintenance
```

# 189. Controller Selection: CronJob

```text
Job-like work
```

# 194. Do Not Use Deployment for a One-Time Migration


For finite work:

```text

```

expresses the correct intent.

# 235. Workload Decision Tree

Use:

```text
Does the workload need to run continuously?
│
├── NO
│   │
│   ├── Does it run on a schedule?
│   │   ├── YES → CronJob
│   │   └── NO  → Job
│
└── YES
    │
    ├── Must one instance run on each eligible node?
    │   └── YES → DaemonSet
    │
    └── NO
        │
        ├── Does each replica require stable identity,
        │   ordered behavior, or stable per-replica storage?
        │
        ├── YES → StatefulSet
        │
        └── NO → Deployment
```

# 251. StatefulSet Knowledge Check

### What makes StatefulSet different from Deployment?

StatefulSet preserves distinct identities for its Pods and supports patterns requiring stable network identity, stable storage relationships, and ordered behavior.

Deployment assumes replicas are generally interchangeable.
