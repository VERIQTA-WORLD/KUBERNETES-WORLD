# PART 17: KUBERNETES SECURITY AND ACCESS CONTROL

## Identity, RBAC, Workload Hardening, Network Isolation, Secrets, Images, Admission, and Supply-Chain Security

---

# 1. Goal

The goal of this part is to build a production security foundation for Kubernetes.

By the end, you should understand how Kubernetes answers these questions:

```text
Who are you?

How did you prove who you are?

What are you allowed to do?

Should this request be accepted?

What privileges does this workload have?

Which other workloads can it communicate with?

Which Secrets can it access?

Which image is it allowed to run?

What happens if the image or configuration is malicious?

What prevents insecure workloads from entering the cluster?
```

The central security path is:

```text
Identity
↓
Authentication
↓
Authorization
↓
Admission
↓
Kubernetes API
↓
Resource
```

But production Kubernetes security extends beyond the API:

```text
Identity
↓
Authentication
↓
Authorization
↓
Admission
↓
API Resource
↓
Pod Security
↓
Runtime Security
↓
Network Security
↓
Secret Security
↓
Image Security
↓
Supply Chain Security
↓
Observability and Audit
```

---

# 2. Security Is a Layered System

There is no single Kubernetes security feature.

Security is composed of multiple controls:

```text
Authentication
Authorization
Admission
RBAC
ServiceAccounts
Security Contexts
Pod Security Standards
NetworkPolicy
Secrets
Encryption
Image Security
Supply Chain Controls
Runtime Controls
Audit
```

If one layer is weak, another layer may reduce impact.

This is called:

```text
defense in depth.
```

---

# 3. The Kubernetes Security Model

A simplified API request looks like:

```text
User / Workload
↓
Kubernetes API Request
↓
TLS
↓
Authentication
↓
Authorization
↓
Admission
↓
API Validation / Processing
↓
Resource Change
↓
Persistent Cluster State
```

Example:

```bash
kubectl delete pod payment-api-abc123
```

Kubernetes must answer several questions.

First:

```text
Who sent this request?
```

Then:

```text
Is that identity allowed to delete Pods
in this namespace?
```

Then, for applicable write operations:

```text
Does admission policy allow this request?
```

Only then can the requested API operation proceed.

---

# 4. Authentication vs Authorization

These concepts must never be confused.

Authentication:

```text
Who are you?
```

Authorization:

```text
What are you allowed to do?
```

Example:

```text
Identity:
ann@example.com
```

Authentication may prove:

```text
Yes, this really is Ann.
```

Authorization may still decide:

```text
Ann may list Pods
but may not delete Pods.
```

Authentication success does not imply administrator access.

---

# 5. Admission

Admission asks a different question:

```text
Even if this identity is allowed to request this operation,
should this particular object or request be accepted?
```

Example:

A developer may have permission to:

```text
create Pods
```

but organizational policy may reject a Pod that requests:

```yaml
securityContext:
  privileged: true
```

So:

```text
Authentication
=
Who are you?

Authorization
=
Can you request this operation?

Admission
=
Is this requested object acceptable?
```

# 7. Transport Security

Kubernetes API communication should be protected with TLS.

Conceptually:

```text
kubectl
↓
TLS
↓
kube-apiserver
```

TLS helps provide:

```text
encryption in transit

server authentication

protection against passive credential interception
```

A production Kubernetes API should never be treated like an ordinary unsecured HTTP endpoint.

# 8. Identity

An identity represents:

```text
who is making the request.
```

Common Kubernetes request identities include:

```text
human users

ServiceAccounts

nodes

control-plane components

automation systems

CI/CD systems
```

Different identities should receive different permissions.

---

# 9. Human Identity

Kubernetes itself does not provide a normal built-in API object representing every human user in the same way it provides ServiceAccount objects.

Production clusters commonly integrate with external identity mechanisms such as:

```text
OIDC identity providers

cloud IAM systems

client certificates

authentication proxies

managed Kubernetes identity integrations
```

The exact mechanism depends on the environment.

---

# 10. Groups

An authenticated user can belong to groups.

Example:

```text
alice@example.com

groups:
developers
platform-team
```

RBAC permissions can then be assigned to:

```text
users

groups

ServiceAccounts
```

Groups are particularly useful for human access management.

Instead of binding permissions individually to 100 developers:

```text
developer1
developer2
developer3
...
```

you can bind permissions to:

```text
developers
```

and manage membership through the identity system.

---

# 11. Authentication Does Not Define Permissions

Suppose Kubernetes authenticates:

```text
alice@example.com
```

That only proves identity.

Kubernetes still needs authorization.

```text
Authenticated
≠
Authorized for everything
```

---

# 12. ServiceAccounts

A ServiceAccount is a Kubernetes identity primarily designed for:

```text
workloads

automation

controllers

applications
```

It is a namespaced Kubernetes API object.

Example:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: payment-api
  namespace: production
```

---

# 13. ServiceAccount Identity

The ServiceAccount above is represented conceptually as:

```text
system:serviceaccount:production:payment-api
```

Pattern:

```text
system:serviceaccount:<namespace>:<serviceaccount-name>
```

---

# 14. Why ServiceAccounts Exist

Suppose an application needs to:

```text
list ConfigMaps
```

inside its namespace.

Do not give the application:

```text
your personal kubeconfig.
```

Instead:

```text
Pod
↓
ServiceAccount
↓
RBAC
↓
limited API permissions
```

This gives the workload its own identity.

---

# 15. Default ServiceAccount

Every namespace normally contains a ServiceAccount named:

```text
default
```

Check:

```bash
kubectl get serviceaccounts -n default
```

If a Pod does not specify:

```yaml
serviceAccountName:
```

Kubernetes normally assigns the namespace's:

```text
default
```

ServiceAccount.

---

# 16. Do Not Treat the Default ServiceAccount as a Shared Application Identity

Production workloads should generally use dedicated ServiceAccounts when workload identity matters.

Better:

```text
frontend
→ frontend-sa

payments
→ payments-sa

reporting
→ reporting-sa
```

Instead of:

```text
frontend
payments
reporting
↓
default
```

Dedicated identities make:

```text
RBAC

auditing

incident investigation

permission review
```

much clearer.

---

# 17. ServiceAccount Assignment

Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: api
  namespace: security-lab

spec:
  serviceAccountName: api-reader

  containers:
    - name: app
      image: nginx:1.27
```

Now the Pod is associated with:

```text
api-reader
```

rather than the namespace's default ServiceAccount.

---

# 18. ServiceAccount Credentials

Modern Kubernetes normally provides Pods with short-lived, automatically rotating ServiceAccount tokens through projected volumes.

These tokens can be used to authenticate to the Kubernetes API.

Conceptually:

```text
Pod
↓
Projected ServiceAccount Token
↓
Bearer Token
↓
API Server
↓
Authentication
↓
ServiceAccount Identity
```

Avoid designing new systems around permanent ServiceAccount token Secrets.

---

# 19. Disable Automatic Token Mounting When Unnecessary

Many applications never call the Kubernetes API.

For such applications:

```yaml
spec:
  automountServiceAccountToken: false
```

can prevent automatic ServiceAccount credential injection.

Example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: public-web
  namespace: production

spec:
  automountServiceAccountToken: false

  containers:
    - name: web
      image: nginx:1.27
```

This reduces credential exposure.


If:

```text
No
```

# 24. `get`

```text
get
```

means:

```text
retrieve a specific resource.
```

Example:

```bash
kubectl get pod web
```

---

# 25. `list`

```text
list
```

means:

```text

```

Example:

```bash
kubectl get pods
```

---

# 26. `watch`

```text
watch
```

means:

```text
observe resource changes over time.
```

Controllers frequently need:

```text
list

```

permissions.

# 27. Write Permissions

These include:

```text
create

update

patch

delete
```

They are more powerful because they change cluster state.

Production access should grant write permissions only where required.

---

# 28. RBAC

RBAC means:

```text
Role-Based Access Control
```

Kubernetes RBAC provides four core API objects:

```text
Role

ClusterRole

RoleBinding

ClusterRoleBinding
```

Understanding the relationship between these four objects is essential.

---

# 29. RBAC Mental Model

```text
Role / ClusterRole
=
WHAT actions are permitted
```

```text
RoleBinding / ClusterRoleBinding
=
WHO receives those permissions
```

That distinction eliminates much RBAC confusion.

---

# 30. Role

A:

```text
Role
```

defines permissions inside:

```text
one namespace.
```

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: security-lab

rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

This means:

```text
Permission:
read Pods

Scope:
security-lab namespace
```

But nobody receives the permission yet.

---

# 31. Role Does Not Assign Permissions

Creating:

```text
Role
```

alone does not grant that Role to anyone.

You still need:

```text
RoleBinding.
```

---

# 32. Role Rule Anatomy

Example:

```yaml
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

Break it down.

```text
apiGroups
=
which Kubernetes API group?
```

```text
resources
=
which resource types?
```

```text
verbs
=
which operations?
```

---

# 33. Core API Group

Resources such as:

```text
Pods

Services

ConfigMaps

Secrets

Namespaces
```

belong to the core API group.

RBAC represents the core group as:

```yaml
apiGroups: [""]
```

The empty string is intentional.

---

# 34. Apps API Group

Deployments belong to:

```text
apps
```

Example:

```yaml
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch"]
```

---

# 35. Discover API Groups

Run:

```bash
kubectl api-resources
```

Look at:

```text
APIVERSION
```

and:

```text
NAME
```

This helps build accurate RBAC rules.

---

# 36. ClusterRole

A:

```text
ClusterRole
```

is cluster-scoped as an RBAC object.

It can define permissions for:

```text
namespaced resources

cluster-scoped resources

non-resource API endpoints
```

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader

rules:
  - apiGroups: [""]
    resources: ["nodes"]
    verbs: ["get", "list", "watch"]
```

Nodes are cluster-scoped.

A normal namespaced Role cannot grant access to Nodes.

---

# 37. ClusterRole Does Not Automatically Mean Cluster-Wide Access

This is a critical distinction.

A ClusterRole defines reusable permissions.

Whether those permissions apply:

```text
inside one namespace
```

or:

```text
across the cluster
```

depends on how it is bound.

---

# 38. ClusterRole Bound with RoleBinding

A ClusterRole can be referenced by a RoleBinding.

Example:

```text
ClusterRole
↓
RoleBinding in namespace team-a
↓
permissions apply in team-a
```

This allows reusable namespaced permission templates.

---

# 39. ClusterRole Bound with ClusterRoleBinding

A ClusterRole can also be referenced by:

```text
ClusterRoleBinding
```

Then the permissions apply according to the ClusterRole across the cluster.

This is significantly broader.

---

# 40. RoleBinding

A RoleBinding connects:

```text
subject
```

to:

```text
Role or ClusterRole
```

within a namespace.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: api-reader-binding
  namespace: security-lab

subjects:
  - kind: ServiceAccount
    name: api-reader
    namespace: security-lab

roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-reader
```

---

# 41. RoleBinding Mental Model

```text
api-reader ServiceAccount
↓
RoleBinding
↓
pod-reader Role
↓
get/list/watch Pods
↓
security-lab only
```

---

# 42. `subjects`

A binding can refer to subjects such as:

```text
User

Group

ServiceAccount
```

Example:

```yaml
subjects:
  - kind: Group
    name: developers
    apiGroup: rbac.authorization.k8s.io
```

For ServiceAccounts, specify the namespace.

---

# 43. `roleRef`

Example:

```yaml
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-reader
```

This tells Kubernetes:

```text
which permission object
the binding grants.
```

---

# 44. ClusterRoleBinding

A ClusterRoleBinding grants a ClusterRole's permissions cluster-wide.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: node-readers

subjects:
  - kind: Group
    name: platform-node-readers
    apiGroup: rbac.authorization.k8s.io

roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: node-reader
```

Use ClusterRoleBindings carefully.

---

# 45. RBAC Scope Table

| Object             | Defines permissions? | Namespaced object? | Typical purpose                               |
| ------------------ | -------------------- | ------------------ | --------------------------------------------- |
| Role               | Yes                  | Yes                | Permissions in one namespace                  |
| ClusterRole        | Yes                  | No                 | Cluster resources or reusable permission sets |
| RoleBinding        | Assigns              | Yes                | Grant permissions within one namespace        |
| ClusterRoleBinding | Assigns              | No                 | Grant ClusterRole permissions cluster-wide    |

---

# 46. Least Privilege

Least privilege means:

```text
Give an identity only the permissions
required to perform its job.
```

Not:

```text
Give broad permissions now
because they are easier.
```

---

# 47. Bad Permission Design

Bad:

```yaml
apiGroups: ["*"]
resources: ["*"]
verbs: ["*"]
```

This is effectively:

```text
everything
on everything.
```

Avoid wildcard permissions unless the identity genuinely requires them and the risk is understood.

---

# 48. Better Permission Design

Suppose an application only needs to read one ConfigMap.

Better:

```yaml
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames:
      - app-settings
    verbs:
      - get
```

This is much narrower than:

```text
all ConfigMaps
all verbs
all namespaces.
```

---

# 49. `resourceNames`

RBAC can restrict some operations to named resources.

Example:

```yaml
resourceNames:
  - app-settings
```

This can be useful for specific:

```text
get

update

patch

delete
```

style access patterns.

However, understand verb semantics carefully.

For example, `list` and `watch` do not become ordinary "list only this named object" permissions simply because `resourceNames` exists.

Design and test the actual authorization behavior.

---

# 50. Least Privilege Questions

For every permission ask:

```text
Does it need get?

Does it need list?

Does it need watch?

Does it need create?

Does it need update?

Does it need patch?

Does it need delete?

Does it need every resource?

Does it need every namespace?

Does it need cluster scope?
```

---

# 51. Dangerous RBAC Permissions

Be especially cautious with permissions involving:

```text
Secrets

Roles

ClusterRoles

RoleBindings

ClusterRoleBindings

Pods

Deployments

DaemonSets

Jobs

ServiceAccounts

serviceaccounts/token

nodes

certificatesigningrequests

admission configuration
```

Some permissions can provide indirect privilege escalation.

---

# 52. Why Pod Creation Is Powerful

Suppose a user cannot directly:

```text
get secret production-password
```

but can create arbitrary Pods in the namespace.

If an existing Secret is available to workloads there, the user may be able to create a Pod that mounts or exposes that Secret.

Therefore:

```text
cannot directly read Secret
```

does not necessarily mean:

```text
cannot obtain Secret.
```

Security requires analyzing indirect capabilities.

---

# 53. Why RBAC Administration Is Sensitive

Suppose an identity can:

```text
create RoleBindings
```

and can bind powerful roles.

That identity may be able to increase its own privileges.

RBAC administration should therefore be tightly controlled.

---

# 54. `kubectl auth can-i`

One of the most useful RBAC troubleshooting commands is:

```bash
kubectl auth can-i
```

Example:

```bash
kubectl auth can-i get pods
```

Possible output:

```text
yes
```

or:

```text
no
```

---

# 55. Namespace-Specific Permission Check

```bash
kubectl auth can-i get pods \
  -n security-lab
```

This asks:

```text
Can my current identity get Pods
inside security-lab?
```

---

# 56. Test Another Verb

```bash
kubectl auth can-i delete pods \
  -n security-lab
```

This may return:

```text
no
```

That difference is exactly what least privilege should produce.

---

# 57. Test a ServiceAccount

Administrators with appropriate impersonation privileges can test:

```bash
kubectl auth can-i get pods \
  -n security-lab \
  --as=system:serviceaccount:security-lab:api-reader
```

Expected after correct RBAC:

```text
yes
```

Test delete:

```bash
kubectl auth can-i delete pods \
  -n security-lab \
  --as=system:serviceaccount:security-lab:api-reader
```

Expected:

```text
no
```

---

# 58. Important Impersonation Note

Using:

```text
--as
```

requires the caller to have appropriate impersonation privileges.

If your account cannot impersonate another identity, the command may be denied.

Do not mistake:

```text
cannot impersonate
```

for:

```text
tested identity lacks requested permission.
```

# 69. `Forbidden` Is Useful Evidence

Example:

```text
Error from server (Forbidden)
```

This usually tells you:

```text
authentication likely succeeded
```

but:

```text
authorization denied the requested operation.
```

Do not immediately assume network failure.

---

# 70. Authentication Failure Is Different

Authentication problems may produce messages indicating:

```text
unauthorized

credentials required

invalid token

certificate problem
```

Distinguish:

```text
401-style authentication failure
```

from:

```text
403-style authorization failure.
```

---

# 71. Workload Security

RBAC controls:

```text
what an identity can do through the Kubernetes API.
```

It does not fully control:

```text
what a process inside a container can do
on the Linux system.
```

For that we need workload security controls.

---

# 72. `securityContext`

A:

```text
securityContext
```

defines privilege and access-control settings for:

```text
a Pod

or

an individual container.
```

Examples include:

```text
user ID

group ID

run as non-root

Linux capabilities

privilege escalation

read-only root filesystem

seccomp profile
```

---

# 73. Pod-Level vs Container-Level Security Context

Pod level:

```yaml
spec:
  securityContext:
```

Container level:

```yaml
spec:
  containers:
    - name: app
      securityContext:
```

Some settings apply at Pod level.

Others apply to individual containers.

Container-specific settings can override applicable Pod-level settings.

---

# 74. Root Inside Containers

Containers provide isolation.

But:

```text
root inside a container
```

still has more power than a non-root process inside that container.

Container isolation is not a reason to run everything as root.

---

# 75. `runAsNonRoot`

Example:

```yaml
securityContext:
  runAsNonRoot: true
```

This tells Kubernetes:

```text
this container must not run as UID 0.
```

If the image attempts to run as root and Kubernetes cannot establish a valid non-root configuration, startup can fail.

---

# 76. `runAsUser`

Example:

```yaml
securityContext:
  runAsUser: 10001
```

This specifies:

```text
UID 10001.
```

You can also configure:

```yaml
runAsGroup: 10001
```

where appropriate.

---

# 77. Better Image Design

Do not rely solely on Kubernetes to transform a root-designed image into a non-root image.

Build the image correctly.

Dockerfile concept:

```dockerfile
RUN addgroup --system appgroup \
    && adduser --system --ingroup appgroup appuser

USER appuser
```

Exact syntax depends on the base image.

The important principle:

```text
build for non-root execution
+
enforce non-root execution
```

---

# 78. File Permission Problem

Changing:

```yaml
runAsUser: 10001
```

can break an image if the application expects to write to:

```text
/root

/etc

/usr/local

application directories owned only by root
```

Non-root security requires correct filesystem ownership and writable paths.

---

# 79. `allowPrivilegeEscalation`

Example:

```yaml
securityContext:
  allowPrivilegeEscalation: false
```

This controls whether a process can gain more privileges than its parent process.

For normal application containers:

```text
false
```

is a strong default.

---

# 80. Privileged Containers

A container can request:

```yaml
securityContext:
  privileged: true
```

Privileged containers bypass many normal isolation restrictions and receive extensive host-level capabilities.

Treat:

```text
privileged: true
```

as highly sensitive.

---

# 81. Privileged Is Not a Troubleshooting Shortcut

Bad pattern:

```text
application fails
↓
set privileged: true
↓
application works
↓
ship it
```

This may hide:

```text
permission problems

filesystem problems

capability requirements

device requirements

bad image design
```

Solve the actual requirement.

---

# 82. Linux Capabilities

Traditional Linux root privileges can be divided into smaller units called:

```text
capabilities.
```

Examples include:

```text
NET_ADMIN

NET_BIND_SERVICE

SYS_ADMIN

CHOWN

SETUID

SETGID
```

Capabilities allow more granular privilege control.

---

# 83. Drop Capabilities

A strong default for many application containers is:

```yaml
securityContext:
  capabilities:
    drop:
      - ALL
```

Then add back only what is truly required.

---

# 84. Add Back One Capability

Example:

```yaml
securityContext:
  capabilities:
    drop:
      - ALL

    add:
      - NET_BIND_SERVICE
```

Conceptually:

```text
remove everything
↓
restore only one explicitly required capability
```

This is better than keeping a large default capability set unnecessarily.

---

# 85. Avoid `SYS_ADMIN`

`SYS_ADMIN` is an extremely broad Linux capability.

If an application says:

```text
I need SYS_ADMIN
```

investigate carefully.

It can dramatically increase container power and attack surface.

---

# 86. `readOnlyRootFilesystem`

Example:

```yaml
securityContext:
  readOnlyRootFilesystem: true
```

This prevents normal writes to the container's root filesystem.

Why useful?

An attacker who compromises the application may have less ability to:

```text
modify application binaries

drop tools

change configuration

write persistent malicious files
```

inside the image filesystem.

---

# 87. Read-Only Root Filesystem Does Not Mean No Writes Anywhere

Applications often need writable paths such as:

```text
/tmp

cache

runtime files
```

Provide explicit writable volumes.

Example:

```yaml
volumes:
  - name: tmp
    emptyDir: {}
```

Mount:

```yaml
volumeMounts:
  - name: tmp
    mountPath: /tmp
```

Now:

```text
root filesystem
=
read-only
```

while:

```text
/tmp
=
writable ephemeral volume.
```

---

# 88. Seccomp

Seccomp is a Linux kernel mechanism for filtering system calls.

Containers ultimately interact with the host kernel using system calls.

Examples:

```text
open

read

write

clone

mount

socket
```

Seccomp can restrict which system calls are available.

---

# 89. `RuntimeDefault`

A common hardened configuration is:

```yaml
securityContext:
  seccompProfile:
    type: RuntimeDefault
```

This asks the container runtime to apply its default seccomp profile.

---

# 90. Why Seccomp Matters

If a compromised application attempts dangerous or unusual system calls:

```text
seccomp
```

may reduce the available attack surface.

Seccomp is not a complete sandbox.

It is one defense layer.

---

# 91. Hardened Container Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hardened-app
  namespace: security-lab

spec:
  automountServiceAccountToken: false

  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault

  containers:
    - name: app
      image: nginxinc/nginx-unprivileged:1.27-alpine

      securityContext:
        allowPrivilegeEscalation: false

        capabilities:
          drop:
            - ALL

        readOnlyRootFilesystem: true

      ports:
        - containerPort: 8080

      volumeMounts:
        - name: cache
          mountPath: /var/cache/nginx

        - name: run
          mountPath: /var/run

        - name: tmp
          mountPath: /tmp

  volumes:
    - name: cache
      emptyDir: {}

    - name: run
      emptyDir: {}

    - name: tmp
      emptyDir: {}
```

The exact writable paths depend on the application image.

Always test the image you actually deploy.

---

# 92. Defense Layers in the Hardened Pod

```text
automountServiceAccountToken: false
↓
No unnecessary API credential
```

```text
runAsNonRoot: true
↓
No root process
```

```text
allowPrivilegeEscalation: false
↓
No privilege escalation
```

```text
drop ALL capabilities
↓
Reduced kernel privilege
```

```text
readOnlyRootFilesystem: true
↓
Reduced filesystem modification
```

```text
RuntimeDefault seccomp
↓
System-call filtering
```

This is defense in depth.

# 97. Pod Security Standards

Kubernetes defines three Pod Security Standards:

```text
Privileged

Baseline

Restricted
```

They represent progressively stronger security constraints.

---

# 98. Privileged Profile

The:

```text
Privileged
```

profile is intentionally unrestricted.

It allows configurations that may bypass normal container isolation.

It is appropriate only for highly trusted workloads that genuinely require broad host-level access.

Examples may include certain:

```text
infrastructure agents

low-level networking components

storage components

system workloads
```

Do not use it as the default application profile.

---

# 99. Baseline Profile

The:

```text
Baseline
```

profile prevents known privilege-escalation patterns while maintaining compatibility with many common containerized applications.

It rejects or restricts risky features such as:

```text
privileged containers

host namespaces

dangerous hostPath use

certain capabilities

unsafe configurations
```

It provides a practical minimum security baseline.

---

# 100. Restricted Profile

The:

```text
Restricted
```

profile applies stronger current Pod hardening practices.

It includes requirements involving:

```text
non-root execution

privilege escalation prevention

seccomp

capability reduction

restricted volume types
```

and all applicable Baseline restrictions.

This is a stronger target for ordinary production application workloads when compatibility permits.

---

# 101. Restricted Capabilities Rule

Restricted policy requires containers to:

```text
drop ALL Linux capabilities
```

and only permits adding back:

```text
NET_BIND_SERVICE
```

under the applicable Linux policy.

That is much stricter than simply avoiding privileged mode.

---

# 102. Restricted Non-Root Rule

Restricted policy requires:

```yaml
runAsNonRoot: true
```

at an applicable Pod or container level.

It also prevents explicitly setting:

```text
runAsUser: 0
```

for Linux containers under the applicable policy.

---

# 103. Restricted Seccomp Rule

Restricted requires an allowed seccomp profile such as:

```text
RuntimeDefault
```

or:

```text
Localhost
```

rather than leaving the workload explicitly unconfined.

---

# 104. Pod Security Admission

Kubernetes includes a built-in:

```text
Pod Security Admission
```

controller.

It can enforce Pod Security Standards at namespace level.

Common modes are:

```text
enforce

audit

warn
```

---

# 105. `enforce`

```text
enforce
```

means:

```text
violating Pods are rejected.
```

---

# 106. `warn`

```text
warn
```

means:

```text
request can proceed
but client receives warning.
```

Useful during migration.

---

# 107. `audit`

```text
audit
```

means violations are recorded in audit-related metadata for applicable requests when API auditing is configured.

This helps evaluate policy impact before strict enforcement.

---

# 108. Namespace Pod Security Labels

Conceptually:

```bash
kubectl label namespace security-lab \
  pod-security.kubernetes.io/enforce=restricted
```

You can also use version labels.

For production, pinning a policy version can provide predictable behavior during cluster upgrades.

---

# 109. Do Not Enforce Restricted Blindly

Before switching a production namespace directly to:

```text
restricted enforcement
```

evaluate existing workloads.

A safer migration pattern can be:

```text
warn
↓
audit
↓
fix workloads
↓
test
↓
enforce
```

according to organizational policy.

---

# 110. LAB 11: Test Restricted Policy

Use a disposable namespace.

Label it appropriately for Restricted policy enforcement.

Then attempt to create:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: insecure
  namespace: security-lab

spec:
  containers:
    - name: app
      image: nginx:1.27

      securityContext:
        privileged: true
```

Expected in a correctly enforced Restricted namespace:

```text
rejected.
```

Read the error.

The error is security evidence.

---

# 111. Fix the Workload

Replace insecure settings with a hardened configuration appropriate for the image:

```yaml
securityContext:
  runAsNonRoot: true
  seccompProfile:
    type: RuntimeDefault
```

Container:

```yaml

  allowPrivilegeEscalation: false

  capabilities:
    drop:
      - ALL

  readOnlyRootFilesystem: true
```

Then retest.

Remember that the image itself must support non-root and read-only operation.

# 112. Network Security

RBAC answers:

```text
Can this identity use the Kubernetes API?
```

NetworkPolicy answers a different question:

```text
Which network connections are permitted
to or from selected Pods?
```

Do not confuse API authorization with network authorization.

---

# 113. Default Kubernetes Network Reality

Without NetworkPolicy enforcement, many clusters permit broad Pod-to-Pod communication.

Conceptually:

```text
frontend
↔
payments
↔
database
↔
monitoring
↔
other workloads
```

That may create excessive lateral movement opportunities.

---

# 114. NetworkPolicy

A NetworkPolicy controls network traffic involving selected Pods at:

```text
Layer 3 / Layer 4
```

using concepts such as:

```text
Pod selectors

namespace selectors

IP blocks

ports

protocols
```

---

# 115. Critical Requirement

Creating a NetworkPolicy object does not guarantee enforcement.

Your cluster network implementation must support:

```text
NetworkPolicy enforcement.
```

If the CNI/network implementation does not enforce NetworkPolicy:

```text
policy objects may exist
without producing the isolation you expect.
```

Always verify enforcement.

---

# 116. NetworkPolicy Is Additive

Network policies are additive.

When a Pod is selected for ingress or egress isolation, allowed traffic is the union of the rules that apply.

There is no simple:

```text
first rule wins
```

ordering model.

---

# 117. Default Deny Ingress

Example:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: security-lab

spec:
  podSelector: {}

  policyTypes:
    - Ingress
```

This selects:

```text
all Pods in security-lab
```

for ingress isolation and permits no ingress through this policy.

---

# 118. Default Deny Egress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: security-lab

spec:
  podSelector: {}

  policyTypes:
    - Egress
```

This establishes egress isolation for selected Pods without granting egress through this policy.

---

# 119. Default Deny Both

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: security-lab

spec:
  podSelector: {}

  policyTypes:
    - Ingress
    - Egress
```

This is a strong starting pattern when followed by explicit allow policies.

But beware:

```text
DNS may also be blocked.
```

---

# 120. Allow Frontend to API

Suppose:

```text
frontend
→
api
```

should be allowed.

API Pods:

```text
app=api
```

Frontend Pods:

```text
app=frontend
```

Policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-from-frontend
  namespace: security-lab

spec:
  podSelector:
    matchLabels:
      app: api

  policyTypes:
    - Ingress

  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend

      ports:
        - protocol: TCP
          port: 8080
```

Meaning:

```text
destination:
app=api

source:
app=frontend

port:
TCP/8080
```

---

# 121. Namespace Selector

You can allow traffic based on namespace labels.

Example:

```yaml
from:
  - namespaceSelector:
      matchLabels:
        access: approved
```

This selects namespaces carrying that label.

Namespace labeling therefore becomes security-sensitive.

---

# 122. Combining Namespace and Pod Selectors

Be careful with YAML structure.

This:

```yaml
from:
  - namespaceSelector:
      matchLabels:
        team: payments

    podSelector:
      matchLabels:
        app: gateway
```

conceptually means:

```text
gateway Pods
inside namespaces matching team=payments.
```

But separate list entries can mean a broader OR relationship.

YAML indentation and list structure materially affect policy.

---

# 123. Egress and DNS

If you create default-deny egress:

```text
DNS requests may stop working.
```

Application symptom:

```text
service-name
cannot resolve
```

while direct IP connectivity may behave differently.

This is a classic NetworkPolicy troubleshooting problem.

---

# 124. DNS Allow Policy Concept

In many clusters, applications need egress to the cluster DNS service.

The exact DNS labels, namespace, implementation, and networking behavior vary by cluster.

Commonly, DNS is provided by CoreDNS in:

```text
kube-system
```

but do not hard-code assumptions without inspecting your cluster.

Inspect:

```bash
kubectl get service \
  -n kube-system
```

and:

```bash
kubectl get pods \
  -n kube-system \
  --show-labels
```

before writing production DNS policies.

# 134. NetworkPolicy Is Not a Firewall for Everything

# 135. Secrets Security

Part 11 introduced Kubernetes Secrets.

Now view them through the security lens.

A Secret can hold:

```text
passwords

tokens

keys

certificates

credentials
```

But:

```text
Secret object
≠
automatically safe secret-management system.
```

---

# 136. Base64 Is Not Encryption

Secret manifest:

```yaml
data:
  password: cGFzc3dvcmQ=
```

does not mean:

```text
encrypted.
```

It means:

```text
base64 encoded.
```

Anyone who can read that value can decode it.

---

# 137. Secrets and etcd

Kubernetes API data is stored in:

```text
etcd.
```

By default, Secret data may be stored unencrypted at rest unless cluster encryption-at-rest is configured.

Production security should consider:

```text
API access controls

etcd access

encryption at rest

backup security

secret rotation
```

---

# 138. Secret RBAC

Be extremely careful with:

```text
get secrets

list secrets

watch secrets
```

`list` access is particularly powerful because Secret contents are included in returned objects.

Do not grant broad Secret access casually.

---

# 139. Secret Exposure Through Workloads

Remember:

```text
Can create arbitrary Pods
```

may indirectly provide access to Secrets that Pods can reference in that namespace.

Therefore security review must examine:

```text
direct permissions
+
indirect capabilities.
```

---

# 140. Restrict Secret Exposure

Good practices include:

```text
separate namespaces

dedicated ServiceAccounts

least-privilege RBAC

mount Secrets only into containers that need them

avoid logging Secret values

short-lived credentials where possible

rotation

encryption at rest

external secret systems where appropriate
```

---

# 141. Do Not Dump Secrets During Troubleshooting

Dangerous:

```bash
kubectl get secrets -A -o yaml
```

This can expose large quantities of credentials into:

```text
terminal history

screen recordings

support tickets

CI logs

chat messages

incident documents
```

Retrieve only what you need.

Redact sensitive values.

---

# 142. ServiceAccount Tokens Are Secrets Too

Treat ServiceAccount credentials as sensitive.

If stolen, they may allow an attacker to impersonate the workload.

Risk depends on:

```text
token lifetime

audience

RBAC permissions

network reachability

binding
```

This is another reason for least privilege.

---

# 143. Image Security

A Pod's security is limited by the software inside its image.

A perfectly configured Kubernetes manifest cannot make vulnerable application code magically secure.

Image security begins before deployment.

---

# 144. Image Attack Surface

Every package in an image can add:

```text
code

dependencies

vulnerabilities

tools useful to attackers
```

Production images should contain:

```text
only what the application needs.
```

---

# 145. Avoid Unnecessary Tools

Production images generally do not need:

```text
compilers

package managers

SSH servers

debugging suites

development dependencies
```

unless the application genuinely requires them.

Smaller images often reduce attack surface.

---

# 146. Run as Non-Root in the Image

Prefer an image that declares an unprivileged user.

Then reinforce this in Kubernetes with:

```yaml
runAsNonRoot: true
```

This provides defense in depth.

---

# 147. Image Tags Are Mutable References

Example:

```text
myapp:latest
```

can point to different image contents over time.

Even:

```text
myapp:1.0
```

can technically be moved unless registry policy prevents it.

This complicates:

```text
reproducibility

incident investigation

rollback

supply-chain verification
```

---

# 148. Image Digests

A digest identifies specific image content.

Concept:

```text
registry.example.com/myapp@sha256:<digest>
```

Using digests can provide stronger immutability than relying only on tags.

---

# 149. Tags Can Still Be Useful

Humans may prefer:

```text
v2.4.1
```

for readability.

A deployment process can resolve:

```text
v2.4.1
```

to an immutable digest.

Then Kubernetes deploys:

```text
specific content
```

rather than a mutable reference.

---

# 150. Image Pull Credentials

Private registries may require credentials.

Kubernetes can use:

```text
imagePullSecrets
```

but registry credentials must be protected like other Secrets.

Avoid sharing one highly privileged registry credential across unrelated workloads if narrower access is possible.

Image scanning looks for known security problems such as:

```text
vulnerable operating-system packages

known CVEs

misconfigurations
```

depending on the scanner.

Scanning is useful during:

```text
development

CI

registry workflows

deployment gates

continuous security review
```

Preferred pipeline:

```text

↓

↓

↓

↓
```

---

# 153. Scanning Is Not Proof of Safety

A clean vulnerability scan does not prove:

```text
application has no vulnerabilities.
```

# 184. LAB 14: Build a Hardened Deployment

Create:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hardened-web
  namespace: security-lab

spec:
  replicas: 2

  selector:
    matchLabels:
      app: hardened-web

  template:
    metadata:
      labels:
        app: hardened-web

    spec:
      serviceAccountName: api-reader

      securityContext:
        runAsNonRoot: true

        seccompProfile:
          type: RuntimeDefault

      containers:
        - name: web
          image: nginxinc/nginx-unprivileged:1.27-alpine

          ports:
            - name: http
              containerPort: 8080

          securityContext:
            allowPrivilegeEscalation: false

            capabilities:
              drop:
                - ALL

            readOnlyRootFilesystem: true

          resources:
            requests:
              cpu: "25m"
              memory: "32Mi"

            limits:
              memory: "64Mi"

          readinessProbe:
            httpGet:
              path: /
              port: http

            periodSeconds: 5

          livenessProbe:
            httpGet:
              path: /
              port: http

            periodSeconds: 10

          volumeMounts:
            - name: cache
              mountPath: /var/cache/nginx

            - name: run
              mountPath: /var/run

            - name: tmp
              mountPath: /tmp

      volumes:
        - name: cache
          emptyDir: {}

        - name: run
          emptyDir: {}

        - name: tmp
          emptyDir: {}
```

# 197. Defense-in-Depth Response

With proper controls:

```text
Application compromised
↓
non-root user
↓
no privilege escalation
↓
capabilities dropped
↓
read-only root filesystem
↓
limited ServiceAccount
↓
RBAC blocks Kubernetes API actions
↓
NetworkPolicy blocks lateral movement
↓
Secrets limited
↓

```

The initial vulnerability still matters.

But blast radius is reduced.

That is the purpose of defense in depth.

```text

```

```text

```

attacker has limited Kubernetes API access.

If it has:

```text

```

the incident may become catastrophic.

This is why:

```text

```

matters even when credentials are expected to remain secret.

# 256. Security Review Exercise 2

```yaml
  name: application

  - apiGroups: ["*"]
    resources: ["*"]
    verbs: ["*"]
```

Explain the risk.

```text
extremely broad permissions.
```

If cluster-wide bound to an application identity, compromise of that application could become cluster compromise.

Replace broad permissions with exact requirements.
